# Security

## Secret entry

The admin page is not exposed at the root path; access requires a randomly generated secret entry first:

```text
https://your-domain/<entry>/
```

- Entries are randomly generated by default with 20 upper- and lowercase letters and digits, and stored in the database.
- Pages and APIs accessed without the entry return `404`, including common probe paths such as bare `/` and `/api`.
- Visiting the correct entry sets a signed `HttpOnly` gate cookie valid for 24 hours (the server also validates expiry, so it cannot be replayed indefinitely) and then redirects to `/login`; the login page only opens with that cookie (or an existing login).
- Entry probing is rate-limited to prevent brute-force enumeration.
- The entry can be changed under "Settings → Secret entry" and takes effect immediately. Manual entries must be 8-32 characters; entries shorter than 8 characters are rejected to prevent fast enumeration by distributed scanners.
- On first initialization the full entry URL is printed to the startup log; after initialization it is never printed again, so log systems do not retain it long-term. If you forget the entry, override it with `LACTSSL_ENTRY` or look up `security.entry` in the database `settings` table.

The entry is an extra layer of protection; it does not replace HTTPS and strong passwords.

## Sessions and CSRF

- Login sessions are stored in `HttpOnly` cookies that frontend scripts cannot read; cookies use `SameSite=Strict`.
- On HTTPS deployments, session, CSRF, and entry cookies automatically use the `__Host-` prefix, preventing sibling subdomains under a shared parent domain from overwriting cookies with the same name.
- All requests that change server state (POST/PUT/DELETE, etc.) must carry an `X-LACTSSL-CSRF` request header that matches the `lactssl_csrf` cookie, otherwise they are rejected. Legacy sessions receive the cookie automatically on their first request; header-only fallback validation is no longer accepted.
- Unauthenticated endpoints such as login, setup, forgot password, and password reset additionally validate `Origin`/`Sec-Fetch-Site` to block cross-site state-changing requests.
- Changing the password bumps the token version and deletes all server-side session records, immediately invalidating every login including the current device; sign in again with the new password.
- Every service start clears all server-side session records and mixes a fresh random value into the JWT signing subkey. After a restart, every previous login (both cookie sessions and `Authorization: Bearer` tokens) is invalid and requires a new sign-in; short-lived entry-gate, CSRF, and secondary-verification signatures are unaffected.
- API calls that explicitly use `Authorization: Bearer <token>` are exempt from CSRF validation, which simplifies scripts and external integrations.
- Page responses use a random CSP nonce per request, and `script-src` no longer allows arbitrary inline scripts; inline styles are still allowed because component libraries need them.

## Password reset and public URL

Links in password reset emails must be generated from a fixed address:

```yaml
security:
  public_url: "https://ssl.example.com"
```

- When `security.public_url` is not configured, links are derived from the current Host only for loopback requests whose Host is `localhost`/a loopback IP; "forgot password" requests from other sources are rejected.
- Client-forgeable `X-Forwarded-Host` is no longer trusted. In reverse proxy setups, configure `public_url` instead of relying on request headers.
- This prevents attackers from forging the Host to point reset links (including the token and secret entry) at their own domain.

## Credential protection

- Administrator passwords are stored as bcrypt hashes and must be at least 8 characters.
- Sensitive fields such as DNS credentials, deployment credentials, SMTP passwords, notification tokens, TOTP secrets, private CA keys, and certificate private keys are encrypted with AES-256-GCM before being written to the database; legacy plaintext data is migrated automatically at startup.
- Target credentials only store authentication and connection details; deployment paths, sites, domains, and similar parameters live in task workflows and are outside the credential encryption scope.
- The encryption key comes from `security.salt` in `config.yaml`; JWTs are signed with `security.jwt_secret`.
- JWT signatures use an independent subkey derived from `jwt_secret` plus a per-start random value via HKDF, separate from the database AES-GCM key. Even when an older configuration reused the same value for both, the two key materials are no longer identical. Existing sessions are invalidated after every upgrade or restart and require a fresh sign-in.
- APIs mask secret fields when returning configuration; leaving them empty while editing keeps the existing value.
- SSH deployments record the target host fingerprint on first connection (TOFU) and reject connections when it later changes; you can also enter a `SHA256:...` fingerprint manually in the credential. After a server key change, clear the field so it can be recorded again.
- FTP deployments use explicit TLS by default to avoid sending certificate private keys and login passwords in plaintext; plain FTP is only used when `none` is explicitly selected.
- [Deployment plugins](deploy-plugins.md) receive the certificate private key and are effectively trusted code. They are disabled by default; only install trusted helpers. The plugin directory must be writable only by the service user, and helper files must not be group/world writable. The main program limits helper timeouts, resident memory and output size, and redacts credentials and private keys from error messages.

As a result, `config.yaml` and `data/` are equally important: back them up together and restrict access. Manual values for `security.jwt_secret` and `security.salt` must be at least 32 characters, or startup is refused.

An encryption password of at least 12 characters is mandatory when downloading backups; backup packages use PBKDF2-HMAC-SHA256 (600,000 iterations) + AES-256-GCM. Do not distribute unencrypted database or configuration copies.

Before a restore package is written to `data/restore-pending`, the configuration is fully validated (secret lengths, secret entry, listen address, TLS/mTLS combinations, and so on). Invalid configurations are rejected up front so the service cannot get stuck failing to start. A successful initial setup also clears any pending restore, preventing content staged before initialization from overwriting the new account on a later restart.

Email uses implicit TLS by default (`smtp.ssl=true`). When implicit TLS is disabled and the SMTP server does not support STARTTLS, the service refuses to send, preventing sensitive emails such as reset tokens from being transmitted in plaintext.

## Secondary verification for sensitive operations

Changing the secret entry, restoring a backup, downloading a backup, exporting a private CA key, exporting/viewing a certificate private key, changing system or notification settings, sending notification tests, changing DNS/deployment credentials, creating/modifying/deleting tasks, executing certificate deployments, deleting or cleaning up certificates, modifying site monitors, changing ACME service configuration and cleaning up diagnostics, and modifying private CAs, and uploading plugins all require an additional "secondary verification" beyond session authentication. Language switching and other purely presentational settings are exempt. You can switch between "None", "Password", "TOTP", "Password and TOTP", and "Passkey" under System Settings → Account security. Password is the default; TOTP modes are only available when two-factor authentication is enabled, and passkey verification requires at least one registered passkey. With "None", the operations above only rely on the login session, significantly reducing security; use it only when you fully understand the risk. Changing the verification method itself requires proving identity with the currently active method and cannot be changed with just a login session; "Password and TOTP" requires both the password and a one-time code. If TOTP is disabled, the last passkey is removed, the account password is reset by email, or the related data is unavailable after restoring an old backup, the method automatically falls back to password to avoid locking the account. A TOTP code can only be used once within its validity window, so an operation immediately after switching methods may need to wait for the next code.

In the Settings → Account security → Change verification method dialog, you can individually enable or disable secondary verification for deployments, task create/update/delete, DNS/deployment credentials, SMTP/notification settings, notification tests, ACME/private CA configuration, certificate private key export, certificate deletion/cleanup, and site monitor create/update/delete. Backup download/restore, secret entry changes, private CA key export, and plugin uploads are always verified and cannot be turned off.

Secondary verification uses short-lived tokens: the frontend first calls `/auth/secondary-verify`, the server validates the password/TOTP/passkey using the current method, and on success issues a token valid for 2 minutes bound to the current user, session, and specific operation; business APIs validate that token in the `X-LACTSSL-VERIFY` header and no longer accept account passwords directly. If the token expires or the operation does not match, secondary verification must be completed again.

This restriction reduces the impact of a stolen session: backups contain `jwt_secret` and `salt` from `config.yaml`, so anyone with a backup can decrypt all credentials and forge login tokens; therefore exporting must not rely on a cookie session alone. Account operations such as changing the password or email, enabling/disabling TOTP, and adding/removing passkeys still require the current password and are subject to independent failure rate limits.

## Outbound requests and SSRF

Deployment webhooks, notification channels, panel integrations, and site monitors make server-side outbound requests:

- Literal and resolved destinations reject cloud metadata, link-local, reserved, documentation, and NAT64 ranges (such as `169.254.169.254`, `100.100.100.200`, `fd00:ec2::254`, `0.0.0.0/8`, and `240.0.0.0/4`).
- Loopback and private addresses remain allowed so Gotify, self-hosted panels, and LAN webhooks keep working; restrict them at the network layer if not needed.
- Deployment webhooks carry certificate private keys, so public destinations must use `https://`; loopback, private, `.local`, and `.internal` destinations may use HTTP.
- DNS results are re-validated during dialing and the verified IP is dialed directly, preventing DNS-rebinding bypasses.
- URLs in third-party error messages are redacted before being written to logs, keeping Telegram bot tokens, Gotify tokens, ServerChan SendKeys, and similar secrets out of logs and backups.

## Passkeys and two-factor authentication

Passkey (WebAuthn) sign-in is supported. Adding a passkey requires the current password and an HTTPS domain or localhost; a bare IP address cannot be used as a WebAuthn origin. A passkey performs device fingerprint, face, or system PIN verification, so passkey sign-in does not ask for TOTP again, and that session does not need to repeat secondary verification for sensitive operations. A passkey is an additional sign-in and verification method and does not replace the account password.

TOTP is also supported (for example Google Authenticator or 1Password). Once enabled, password sign-in still requires a one-time code; TOTP verification has its own rate limit, and the same code cannot be reused within its validity window.

Enabling TOTP requires re-entering the current password, preventing a stolen session from binding an authenticator to the attacker's device. Resetting the password by email also disables TOTP and removes all passkeys as a recovery path for a lost authenticator or device; keep the email account itself secure. Verification operations such as changing the password, email, or secret entry, disabling TOTP, switching the secondary verification method, and restoring backups all have independent failure rate limits.

## Rate limiting

The following operations are rate-limited, counted by client IP or account:

- Administrator initialization
- Sign-in (IP and account are limited separately) and TOTP verification
- Forgot password / password reset
- Secret entry probing
- Changing the password, email, or secret entry; enabling/disabling TOTP; secondary verification; restoring backups
- Backup download, private CA key export, certificate private key export, notification tests, and private CA generation
- Sensitive changes to DNS/deployment credentials, tasks, ACME configuration, and private CAs
- ACME account creation, order creation, all ACME protocol requests (including new-nonce/directory), and CRL/OCSP requests

When a limit is triggered the service returns `429` with a `Retry-After` header.

## ACME server

The built-in ACME server is enabled by default, but it does not issue certificates until an endpoint is created and enabled. Once enabled it provides a separate protocol endpoint that does not use the admin secret entry, session cookies, or CSRF validation; set `acme.enabled` to `false` in `config.yaml` if you do not need it.

- For public deployments, use a dedicated port and restrict access at the firewall or reverse proxy layer.
- Every ACME endpoint must have a domain allowlist; enabling an endpoint with an empty allowlist is rejected.
- EAB can be enabled or disabled and is recommended on by default. With EAB disabled, anyone who can reach the port can create an account, so it must be combined with a domain allowlist, mTLS, or network ACLs.
- mTLS is a transport-layer gate and does not replace ACME JWS account authentication.
- Configure `acme.base_url` as a fixed public address to prevent Host header injection from pointing resource URLs at the wrong location.
- HTTP-01 validation rejects loopback, private, link-local, and CGNAT/reserved ranges by default (such as `100.64.0.0/10` and `192.0.0.0/24`); internal scenarios must explicitly allow them through endpoint-level CIDR allowlists.
- ACME protocol resources use random public IDs, not database auto-increment IDs.
- Single-instance deployments use in-memory nonces; after a restart, clients receive `badNonce` and retry automatically.
- CRL and OCSP endpoints live under `/pki/{ca}/...` and usually need to be publicly reachable; they are organized per CA and should remain available even when the ACME enrollment endpoint is disabled. When `acme.addr` is empty they are mounted on the main port together with `/acme/`; with a dedicated port they are served by that listener.
- When ACME is enabled, configure a fixed `acme.base_url` (or `security.public_url`); otherwise resource URLs are derived from the request Host, and public deployments should not rely on that fallback.
- CRL/OCSP endpoints are rate-limited by IP; CRLs cache results for the same revocation set and only increment the CRL Number when revocations change, preventing anonymous requests from amplifying signing and database write costs.
- ACME server rate limiting reads trusted proxies from `server.trusted_proxies` and counts by real client IP; configure trusted proxies correctly in reverse proxy setups, otherwise all clients share the proxy IP's quota.
- CRL/OCSP only affects clients that actively check revocation status; browsers behave inconsistently for private CAs. Existing certificates must be reissued to include CRL/OCSP URLs.

Endpoint certificate monitoring reads the target certificate and validates the domain against the system trust chain; an untrusted or incomplete chain, or a hostname mismatch, is marked abnormal, preventing a man-in-the-middle from using a self-signed certificate to hide real certificate problems.

## Reverse proxy

When a reverse proxy such as Nginx, Caddy, or Traefik terminates TLS:

1. Add the proxy address to `server.trusted_proxies` or `LACTSSL_TRUSTED_PROXIES`, for example `127.0.0.1,10.0.0.0/8`.
2. Make sure the proxy passes standard headers such as `X-Forwarded-For` and `X-Forwarded-Proto`.
3. Configure `security.public_url` as the fixed public address behind the proxy so email links such as password resets do not depend on the request Host.
4. Always access production over HTTPS so the secret entry, cookies, and passwords are not transmitted in plaintext.

Without trusted proxies configured, the service does not trust proxy headers and treats every request as coming from the proxy IP, which breaks IP-based rate limiting and `Secure` cookie detection.

Note: if TLS is terminated at the proxy while the backend is still accessed over HTTP, make sure the proxy passes `X-Forwarded-Proto` correctly, otherwise the `Secure` attribute on session cookies may behave unexpectedly.

## Deployment recommendations

- Run the service as a dedicated user, keep `config.yaml` at `0600`, and keep the data directory at `0700`.
- The Docker image uses an entrypoint script to fix volume ownership and then runs the main program as the non-root `lactssl` user; Compose drops all capabilities by default and adds back only what is needed, such as `CHOWN`/`SETUID`, and enables a read-only root filesystem, a `/tmp` tmpfs, `pids_limit`, and `init`.
- Do not commit `data/` or `config.yaml` to version control or place them in public directories.
- Regularly review the "Logs" page for abnormal sign-ins, entry probes, and deployment failures.
- Enable TOTP for public deployments and use a long random secret entry. An administrator session is equivalent to full control (including local deployment command execution and private CA issuance), so do not stay signed in on shared browsers or untrusted devices.
- The service limits regular API request bodies to 2 MiB by default (except backup restore) and sets read/write timeouts; configure request body size and timeouts at the reverse proxy layer as well.
