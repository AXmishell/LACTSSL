# クイックスタートと本番導入

本文は LACTSSL を初めて導入するチームと個人ユーザーを対象とし、最短の道筋で 3 つの問いに答えることを目的とします：**シナリオを満たせるか、どのような外部依存が必要か、どのように安全に本番へ移行するか**。個人サイトや小規模チームは、以下のクイックパスへ直接進んでよく、企業向けの完全な評価プロセスを踏む必要はありません。

## クイックパス：個人 / 小規模チーム

適用シナリオ：個人ブログとサイト、ホームラボ、小規模チームの社内サービス。必要なのは **Docker を実行できる Linux ホスト（VPS、NAS または小型ホスト）1 台、ドメイン 1 つと DNS API 資格情報、デプロイ先 1 つ**だけです。

4 ステップで完了し、通常 30 分以内に終わります：

1. [インストールと起動](install.md)に従い Docker でインスタンスを起動し、起動ログに表示されるセキュアエントリから初期化を完了します。
2. 「プラグイン」ページでインデックスを更新し、DNS プラグインを 1 つインストールします。パネル/CDN などのデプロイ先が必要ならデプロイプラグインを、通知が必要なら通知プラグインを追加でインストールします。
3. DNS アカウントを作成 → 「証明書申請」でタスクを作成し、パブリック CA とドメインを選択 → 「証明書をデプロイ」ノード（ローカルディレクトリ、SSH、パネル）を追加 → 必要に応じて通知ノードを追加します。
4. 手動で 1 回実行し、証明書ファイルが更新されサービスがリロードされたことを確認します。その後、自動更新を 1 回観察するか、手動で更新をトリガーして検証します。

個人シナリオの最小セキュリティベースライン：

- HTTPS ドメインで管理ページにアクセスし、TOTP またはパスキーを有効にします。
- バックアップパスワードと `config.yaml` は別々に保管します。`salt` を失うと、データベース内の暗号化された資格情報を復号できません。
- DNS API は専用のサブアカウントを使用し、必要なドメインのみを認可します。

> 企業導入では、引き続き以下の 1〜7 節に従って適合性確認、パイロット、本番導入チェックリストを完了する必要があります。

## 1. まず適合性を確認する

LACTSSL の導入に適した典型的な条件：

- 複数のドメインまたは社内サービスで TLS 証明書を一元管理する必要がある。
- 発行、デプロイ、期限監視、通知を監査可能な 1 つのコンソールにまとめたい。
- セルフホストの単一インスタンスを受け入れ、Linux ホスト 1 台、データディレクトリ 1 つ、バックアップ戦略 1 つを用意できる。
- DNS プロバイダーの API 資格情報がある、またはプライベート CA / ACME サービスを自前で構築する必要がある。
- 自動化シナリオは、マルチユーザー RBAC や企業 SSO を要求するのではなく、API キーで接続できる。

唯一のプラットフォームとして直接使用するのに適さない場合：

- マルチテナント分離、組織構造、承認フロー、複数ユーザーのロールを要求する。
- Active-Active クラスタ、拠点間の自動フェイルオーバー、HSM/KMS による秘密鍵管理を要求する。
- 企業自身のコンプライアンス評価ではなく、製品に等保/ISO 認証が付属することを要求する。

これらの境界は、LACTSSL を証明書自動化コンポーネントとして使用することを妨げませんが、ソリューション設計段階で責任分担を明確にする必要があります。

## 2. 評価前の準備チェックリスト

| 項目 | 確認が必要な内容 | 責任ロール |
| --- | --- | --- |
| ホスト | Linux amd64/arm64、Docker Compose v2 または静的バイナリの実行が可能、ディスクとバックアップ容量 | プラットフォーム/運用 |
| ドメインと DNS | パイロット用ドメイン、DNS プロバイダー、TXT レコードを作成できる API 資格情報 | ネットワーク/運用 |
| インバウンド アクセス | 管理ドメイン、リバースプロキシ、TLS 証明書、送信元 IP 許可リスト | ネットワーク/セキュリティ |
| アウトバウンド アクセス | DNS API、SMTP、Webhook、デプロイ先、監視対象への到達性 | ネットワーク/セキュリティ |
| 秘密鍵と資格情報 | DNS/デプロイ/通知資格情報の保管者、ローテーション周期、最小権限アカウント | セキュリティ |
| 変更とバックアップ | 変更ウィンドウ、バックアップ場所、復旧責任者、RPO/RTO 目標 | 運用 |
| 連携 | 接続が必要な CI/CD、CMDB、アラートプラットフォームと API 権限 | 連携開発 |

パイロット段階では**専用ドメイン、専用 DNS サブアカウント、専用通知チャネル**を使用し、本番の管理者資格情報をそのまま再利用しないことを推奨します。

## 3. 30 分パイロット

### 3.1 インスタンスを起動する

評価には Docker 方式が最適です：

```bash
git clone https://github.com/AXmishell/LACTSSL.git
cd LACTSSL
mkdir -p config data
cp config.yaml.example config/config.yaml && chmod 600 config/config.yaml
docker compose up -d
docker compose logs -f lactssl
```

リポジトリのデフォルトは 1Panel の `1panel-network` 外部ネットワークをそのまま使用します。1Panel を使用しない場合は、`docker-compose.yml` のサービス下の `networks` と末尾の `networks` セクションを削除するか、先に `docker network create 1panel-network` を実行します。GHCR イメージは最初の正式 Release から利用可能で、未リリースの場合は[インストールと起動](install.md)に従ってローカルでビルドします。パイロット段階では `http://127.0.0.1:8080` でアクセスできます。パスキー（WebAuthn）を使う場合は、HTTPS ドメインまたは localhost を使用する必要があります。

### 3.2 初期化を完了する

起動ログには 2 種類のワンタイム情報が出力されます：

1. **セキュアエントリ**：`http://127.0.0.1:8080/K7mQ2pX9vR4tY8nL6cWz/` のような形式。
2. **初期化トークン**：未初期化時に出力され、管理者の作成やバックアップの復元などの初期化操作に使用します。

セキュアエントリからページを開き、案内に従って管理者アカウントを作成します。初期化完了後、トークンは直ちに無効になります。エントリを忘れた場合は、`config.yaml` で `security.entry` を設定して再起動し上書きできます。

### 3.3 最小限のプラグインセットをインストールする

メインプログラムには DNS、デプロイ、通知プラグインが内蔵されていません。「プラグイン」ページで：

1. プラグインリポジトリのアドレスを確認し、「インデックスを更新」をクリックします。
2. 「プラグインマーケット」を開き、少なくとも DNS プラグイン 1 つ（例：よく使う DNS パッケージ）と通知プラグイン 1 つをインストールします。
3. SSH 以外のデプロイ先が必要な場合は、デプロイプラグインもインストールします。
4. 対応するリストで、必要なプロバイダー、デプロイ先、通知チャネルを有効にします。

オフライン環境では、`plugins.repo.url` を社内の `https://` ミラーまたは `file://` インデックスに向けられます。詳細は[プラグインガバナンス](plugins.md)を参照してください。

### 3.4 1 本の完全な経路を通す

最初の経路にはプライベート CA を使用し、パブリック DNS に依存しないことを推奨します：

1. 「プライベート CA」でルート CA を生成します（ECDSA P-256、有効期間はパイロットの必要に応じて）。
2. 「証明書申請」でタスクを作成し、発行機関にそのプライベート CA を選択し、テストドメインを入力します。
3. タスクフローに「証明書をデプロイ」ノードを追加し、「ローカルディレクトリ」を選択して、証明書/秘密鍵のパスと任意のリロードコマンドを入力します。
4. 「通知」ノードを追加し、有効化済みのチャネルを選択し、トリガータイミングに「常に」を選びます。
5. タスクを手動で実行し、証明書、デプロイ記録、通知が成功したか確認します。

次にパブリック経路を追加します：DNS アカウントを作成 → パブリック CA を選択 → テストドメインで DNS-01 を実行 → ターゲットへデプロイ → 自動更新の時期を観察します。両方の経路が通ったら、パイロットへ進みます。

### 3.5 重要な運用アクションを検証する

| アクション | 検証方法 | 合格基準 |
| --- | --- | --- |
| バックアップ | 設定 → バックアップと復元 → 暗号化バックアップをダウンロード | ZIP を生成でき、パスワードで復号できる |
| 復旧 | 分離したインスタンスでバックアップをインポート | アカウント、証明書、タスク、設定が完全 |
| ログ | 操作ログとシステムログの絞り込み/エクスポート | 初期化、タスク、デプロイの記録が確認できる |
| API | 読み取り専用キーを作成して `/api/certificates` を呼び出す | 200 を返し、権限外のインターフェースは 403 を返す |
| 通知 | テスト通知を送信 | 対象チャネルでメッセージを受信 |
| 監視 | 外部サイトを 1 つ追加 | 証明書を読み取り、状態を表示できる |

## 4. パイロット範囲の推奨

パイロットでは「すべての接続」を追求せず、問題が最も表面化しやすい経路をカバーすべきです：

- 実際の業務ドメイン 1〜2 件（ワイルドカードまたは複数ドメイン証明書を 1 つ含む）。
- 実際のデプロイ先 1 つ（SSH、パネル、CDN、Webhook から 1 つ）。
- 社内サービスのシナリオ 1 つ（プライベート CA または ACME エンドポイント）。
- アラート受信チャネル 1 つ（当番とエスカレーション経路を明確化）。
- 自動化呼び出し元 1 つ（CI/CD または巡回スクリプト）で API キー権限を検証。

パイロット期間は 1〜2 週間を推奨し、少なくとも 1 回は自動更新または手動更新を観察し、デプロイのリロードコマンドが業務に影響しないことを確認します。

## 5. 本番導入チェックリスト

### 5.1 ネットワークとアクセス

- [ ] 管理エントリは HTTPS リバースプロキシ経由でのみ公開し、プロキシ背後のポートを直接パブリックネットワークに公開しない。
- [ ] `server.trusted_proxies` と `security.public_url` を設定済み。
- [ ] セキュアエントリはランダムな長い文字列で、`admin`、`ssl` などの推測可能なパスを使用していない。
- [ ] 管理エントリに送信元 IP 許可リスト、VPN、ゼロトラストアクセス戦略を設定。
- [ ] ACME サーバーを有効にする場合、専用ポートを使用し送信元を制限。EAB はデフォルトで有効。

### 5.2 アイデンティティとキー

- [ ] 管理者は強力なパスワードを使用し、TOTP またはパスキーを有効化。
- [ ] 復旧メールアドレスはセキュリティチームが管理し、メール自体で多要素認証を有効化。
- [ ] 自動化システムごとに独立した API キーを作成し、最小権限で認可し有効期限を設定。
- [ ] DNS、デプロイ、通知の資格情報は専用アカウントを使用し、個人アカウントやグローバル管理者キーを使用しない。
- [ ] `config.yaml` の権限は `0600`、`data/` の権限は `0700`、所有者はサービス実行ユーザー。

### 5.3 データと復旧

- [ ] RPO/RTO を定義し、少なくとも 1 日 1 回の暗号化バックアップを設定。
- [ ] バックアップは独立した媒体に保存し、アクセスを制御し、復旧パスワードは別に保管。
- [ ] 少なくとも 1 回の復旧訓練を完了し、`salt` とデータベースが揃っていることを確認。
- [ ] ログの保持期間、エクスポート範囲、ストレージ容量を確認済み。

### 5.4 運用と変更

- [ ] サービスの責任者、アラート受信者、変更ウィンドウを明確化。
- [ ] プロセスの生存監視と、証明書期限切れ/タスク失敗のアラートを設定。
- [ ] イメージまたはバイナリのバージョンを固定し、追跡不能な `latest` を長期運用しない。
- [ ] [アップグレードと変更](upgrade.md)を読み、移行とロールバックの手順を確認済み。
- [ ] [セキュリティベースライン](security.md)の高優先度項目を完了済み。

## 6. 責任分担の推奨

| 職責 | 推奨される所属 | 説明 |
| --- | --- | --- |
| ホスト、ネットワーク、リバースプロキシ | プラットフォーム/運用 | 可用性、インバウンド/アウトバウンド戦略、TLS 終端を確保 |
| LACTSSL 管理者アカウント | プラットフォーム/運用責任者 | 単一アカウントで、個人ではなく職位が長期的に保有する必要がある |
| DNS/デプロイ/通知の資格情報 | セキュリティまたは該当システムの責任者 | 専用アカウント、定期ローテーション、最小権限 |
| API キー | 連携開発責任者 | システムごとに発行し、用途、権限、有効期限を登録 |
| バックアップと復旧訓練 | 運用 | バックアップパスワードと復旧手順を分離して保管 |
| コンプライアンス証跡 | セキュリティ/監査 | 操作ログ、システムログ、変更記録を使用 |

## 7. パイロットが失敗するよくある原因

- **セキュアエントリをセキュリティ境界とみなす**：エントリは追加の防御層にすぎず、HTTPS、強力なパスワード、ネットワークアクセス制御の代わりにはなりません。
- **個人の DNS アカウントを API 資格情報に使う**：担当者の退職や二段階認証の有効化後、自動更新が失敗します。
- **デプロイのリロードコマンドを検証しない**：証明書ファイルは更新されたが Nginx/パネルがリロードされず、業務は古い証明書を使い続けます。
- **データベースだけをバックアップし、`config.yaml` をバックアップしない**：`salt` を失うと、データベース内の暗号化資格情報を復号できません。
- **すべての自動化が 1 つの全権限 API キーを共有する**：一度漏洩すると、攻撃者が発行、デプロイ、秘密鍵のエクスポートを行えます。
- **コンテナ内で自己アップグレードする**：コンテナ再作成後にイメージのバージョンへ戻ります。本番はイメージタグでアップグレードすべきです。
