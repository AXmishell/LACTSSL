# デプロイプラグイン

デプロイプラグインは、証明書を FTP、Webhook、クラウド CDN、パネル、WAF などのターゲットへ配信します。これは**証明書の秘密キーに触れる高リスクコンポーネント**であり、企業はデプロイプラグインを導入審査と変更管理の対象にすべきです。

## 1. 組み込みターゲットとプラグインターゲット

| 種別 | ターゲット | 組み込み | 説明 |
| --- | --- | --- | --- |
| 組み込み | ローカルディレクトリ | はい | ローカルパスへ書き込み、リロードコマンドは任意 |
| 組み込み | SSH / SFTP | はい | パスワードまたは秘密キー認証、ホストフィンガープリント検証 |
| プラグイン | FTP / FTPS | いいえ | 通常の FTP、明示的 TLS、暗黙的 TLS |
| プラグイン | Webhook | いいえ | カスタム認証ヘッダー、TLS 検証のスキップ可能（非推奨） |
| プラグイン | Alibaba Cloud CDN | いいえ | ドメイン証明書を更新 |
| プラグイン | Qiniu Cloud | いいえ | CDN アクセラレーションドメインまたは Kodo カスタムオリジンドメイン |
| プラグイン | BaoTa パネル / BaoTa WAF | いいえ | サイト、パネル、または WAF |
| プラグイン | 1Panel | いいえ | サイトまたはパネル |
| プラグイン | SafeLine WAF | いいえ | 証明書 ID またはドメインでマッチ |
| プラグイン | Tencent Cloud / Volcengine / AcePanel など | いいえ | プラグインマーケットの実際のエントリに準じます |

> **デプロイプラグインは証明書の秘密キーを受け取ります。** 信頼できるソースの helper のみをインストールし、プラグインディレクトリがサービスの実行ユーザーのみ書き込み可能であることを確認してください。デプロイプラグインはデフォルトで無効で、明示的に有効化する必要があります。

## 2. 認証情報とデプロイパラメータ

「ターゲット認証情報」は認証と接続情報のみを保存します。例: ホスト、ポート、ユーザー名、パスワード、パネルアドレス、API Token。証明書パス、リロードコマンド、デプロイドメイン、サイトなどのパラメータは、タスクフローの「証明書をデプロイ」ノードで入力します。

この設計の利点:

- 同じ認証情報を複数のタスクで再利用できます。
- 認証情報のローテーションがタスク編成に影響しません。
- デプロイパラメータはタスクバージョンとともに記録され、監査とロールバックが容易になります。

## 3. 設定

```yaml
deploy_plugins:
  enabled: false          # プラグインは秘密キーに触れるため、デフォルトで無効
  dir: ""                 # 空の場合は <data_dir>/plugins/deploy
  memory_limit_mb: 128    # 単一 helper の常駐メモリ上限
  timeout_seconds: 300    # 1 回の deploy のタイムアウト。大きなファイルのアップロード時は増やせる
  max_output_kb: 64       # helper 出力の上限
```

3 種類のプラグインは `<data_dir>/plugins` 配下の独立したサブディレクトリを使用します:

- DNS: `<data_dir>/plugins/dns`
- デプロイ: `<data_dir>/plugins/deploy`
- 通知: `<data_dir>/plugins/notify`

設定変更後はサービスを再起動すると反映されます。起動時に自動スキャンします。新しい helper をインストールした後は、「プラグイン」ページで「プラグインを再スキャン」をクリックするか、次を呼び出します:

```bash
curl -X POST -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/plugins/rescan
```

## 4. インストールと有効化

1. 設定で `deploy_plugins.enabled: true` を設定し、再起動します。
2. 「プラグイン」ページを開き、リポジトリ URL を確認して「インデックスを更新」をクリックします。
3. 「プラグインマーケット」で必要なデプロイターゲットをインストールします。
4. まずプラグインファイルを有効化し、次にデプロイターゲット一覧で具体的なターゲットを有効化します。新しくダウンロードしたファイルとエントリはデフォルトで無効です。

プラグインが未インストールまたは未有効化の場合、ターゲット認証情報とタスクフローのデプロイ種別にはローカルファイルと SSH のみが表示されます。過去の認証情報は失われず、プラグインをインストール後に引き続き使用できます。

有効状態は settings テーブルの `plugins.deploy.enabled_deployers` に保存され、有効化されたターゲット ID のみを記録し、再起動と再スキャン後も保持されます。統合ターゲットは「ターゲット認証情報」でベンダーごとに 1 つの選択肢のみを表示し、具体的な製品はタスクのデプロイノードで「デプロイ対象」から選択します。

## 5. ターゲット別のベストプラクティス

### 5.1 ローカルディレクトリ

- 実行ユーザーは対象ディレクトリへの書き込み権限が必要です。
- アトミック書き込みを推奨します。まず一時ファイルに書き込み、次に `rename` で上書きし、中途半端なファイルを読まないようにします。
- リロードコマンドの例: `nginx -s reload`、`systemctl reload nginx`、`systemctl reload postfix`。
- リロードコマンドが失敗しても証明書ファイルはロールバックされません。ターゲット側で前バージョンを保持する必要があります。

### 5.2 SSH / SFTP

- デフォルトでは対象ホストのフィンガープリント（`SHA256:...`）の入力が必要です。「初回接続時にホストキーを自動信頼」を明示的に有効にした場合のみ TOFU を採用します。以降フィンガープリントが一致しない場合は接続を拒否します。
- サーバーのキー交換後は、古いフィンガープリントをクリアして再記録する必要があります。
- 専用のデプロイユーザーを使用し、対象パスへの書き込み権限と必要なリロード権限のみを付与することを推奨します（sudoers はコマンド単位で指定）。
- 秘密キー認証をパスワードより優先します。秘密キーは管理された場所に置き、パスフレーズを設定して定期的にローテーションしてください。

### 5.3 FTP / FTPS

- デフォルトは明示的 TLS です。`none` を明示的に選択した場合のみ平文 FTP を使用します。
- 証明書の秘密キーとログインパスワードがネットワークを通過します。本番では SFTP または FTPS を優先してください。
- 対象 IP、ポート、ディレクトリ権限を制限し、共有アカウントを使用しないでください。

### 5.4 Webhook

- パブリックターゲットには HTTPS を強制します。ループバック、プライベートネットワーク、`.local`、`.internal` は HTTP を許可します。
- Webhook は証明書と秘密キーを運ぶため、受信側は信頼できる必要があります。専用 Token と送信元 IP 制限を推奨します。
- 「TLS 検証をスキップ」は推奨しません。必須の場合は、内部の自己署名ターゲットに限定してください。内部 CA が発行した証明書は「システム設定 → TLS 信頼チェーン」で CA 公開キーをインポートし、デプロイプラグインが通常の検証でターゲットを信頼できるようにしてください。
- 受信側は冪等性と署名検証を行い、リプレイを防ぐ必要があります。

### 5.5 クラウド CDN / パネル / WAF

- 認証情報は専用のサブアカウントを使用し、証明書管理関連の権限のみを付与してください。
- デプロイパラメータ（ドメイン、サイト、証明書名）はターゲットシステムと一致する必要があります。BaoTa パネルのサイトと Docker サイト名は、パネル API から読み取ってドロップダウン選択できます。
- プラグインが動的オプションを実装していない、またはパネルに到達できない場合でも、名前を手動入力できます。
- ターゲットシステムで IP ホワイトリストが有効な場合は、LACTSSL の出口を許可してください。
- CDN/WAF は証明書をキャッシュする場合があります。デプロイ後に実際に有効な証明書を確認してください。

## 6. デプロイ記録と検証

- デプロイごとにデプロイ記録が生成され、証明書詳細とログで結果を確認できます。
- 手動デプロイは、証明書が属するタスクのデプロイノードパラメータを優先的に再利用できます。ターゲットごとに今回のパラメータを個別に入力することもできます。
- ローカル/SSH デプロイはリロードコマンドを実行します。API キーは `deploy:execute` を明示的に持つ必要があります。
- デプロイ失敗時にターゲットシステムの旧証明書は自動ロールバックされません。ターゲット側で前バージョンを保持するか、アトミックリリースを使用してください。

検証チェックリスト:

- [ ] 対象パス/サイトが正しい。
- [ ] 証明書チェーンが完全（fullchain）。
- [ ] 秘密キーと証明書が一致している。
- [ ] サービスがリロードされ、実際に新しい証明書をロードしている。
- [ ] マルチインスタンス/マルチノードがすべて更新されている。
- [ ] CDN/WAF のキャッシュが更新されている。
- [ ] ブラウザ/クライアントが新しい証明書のシリアル番号またはフィンガープリントを表示している。

## 7. オフラインと手動インストール

- 「プラグイン」ページで単一の helper をアップロードできます。最大 256 MB です。`deploy_plugins.enabled` を有効化した後のみ使用できます。
- アップロード後、まず `manifest`、デプロイターゲット ID、SHA-256 を検証し、通過後にデプロイプラグインディレクトリへ書き込み、直ちに再スキャンします。
- デフォルトでは同名ファイルの上書きを拒否します。アップグレード時は「同名プラグインの上書きを許可」をチェックすると、旧ファイルは先にバックアップされます。
- 組み込みデプロイターゲット ID と重複するプラグインは検出されますが、再スキャン結果では「無視済み」とマークされます。

## 8. Helper プロトコル v1（連携開発）

helper は実行ファイルで、以下のサブコマンドをサポートします:

```bash
deploy-helper manifest   # JSON マニフェストを出力
deploy-helper deploy     # stdin からリクエストを読み取り、デプロイを実行
deploy-helper options    # 動的ドロップダウンオプションを読み取る（任意）
deploy-helper verify     # 認証とターゲットスコープを読み取り専用で検証（任意）
```

`manifest` 出力例:

```json
{
  "protocol": "v1",
  "capabilities": ["verify-v1"],
  "name": "example deploy helper",
  "version": "1.0.0",
  "sha256": "省略可能な helper ファイルのチェックサム",
  "deployers": [
    {
      "id": "example-panel",
      "name": "Example Panel",
      "name_i18n": {"zh-CN": "示例面板", "en-US": "Example Panel"},
      "capabilities": ["verify-v1"],
      "description": "証明書を Example パネルへプッシュします",
      "description_i18n": {
        "zh-CN": "把证书推送到 Example 面板",
        "en-US": "Push certificates to an Example panel"
      },
      "aliases": ["example"],
      "fields": [
        {
          "key": "panel_url",
          "label": "パネルアドレス",
          "label_i18n": {"zh-CN": "面板地址", "en-US": "Panel URL"},
          "type": "text",
          "required": true
        },
        {
          "key": "api_token",
          "label": "API Token",
          "label_i18n": {"zh-CN": "API Token", "en-US": "API Token"},
          "type": "password",
          "secret": true,
          "required": true
        }
      ],
      "deploy_fields": [
        {
          "key": "sites",
          "label": "サイト",
          "label_i18n": {"zh-CN": "站点", "en-US": "Sites"},
          "type": "text",
          "required": true
        }
      ]
    }
  ]
}
```

フィールドの説明:

- `fields` はターゲット認証情報の認証と接続情報です。`secret: true` または `type: "password"` は API レスポンス時にマスクされ、認証情報とともに暗号化して保存されます。
- `deploy_fields` はタスクフローの「証明書をデプロイ」ノードのパラメータです。
- 2 種類のフィールドの `key` は重複できません。フィールドタイプは `text`、`password`、`textarea`、`number`、`select`、`switch` をサポートします。
- デプロイターゲットの `id` は小文字、数字、アンダースコア、ハイフンのみを含められます。組み込みターゲットと重複するプラグインは無視されます。
- `name` / `description` / `label` / `placeholder` / `help` はデフォルト言語の文言です。任意の `*_i18n` テーブルで言語ごとに上書きできます。
- 言語キーは BCP 47 形式（例: `zh-CN`、`en-US`）を使用します。1 つの文言テーブルは最大 32 言語です。

`deploy` の stdin:

```json
{
  "action": "deploy",
  "protocol": "v1",
  "provider": "example-panel",
  "auth": {"panel_url": "https://panel.example.com", "api_token": "..."},
  "config": {"sites": "example.com,www.example.com"},
  "certificate": {
    "domain": "example.com",
    "domains": ["example.com", "www.example.com"],
    "issuer": "Let's Encrypt",
    "serial": "...",
    "not_before": "2026-01-01T00:00:00Z",
    "not_after": "2026-04-01T00:00:00Z",
    "cert_pem": "-----BEGIN CERTIFICATE-----...",
    "fullchain_pem": "-----BEGIN CERTIFICATE-----...",
    "key_pem": "-----BEGIN PRIVATE KEY-----..."
  }
}
```

`verify` の stdin / stdout:

```json
{"action": "verify", "provider": "example-panel", "auth": {"panel_url": "...", "api_token": "..."}, "config": {"sites": "example.com"}, "mode": "read", "locale": "zh-CN"}
```

```json
{"ok": false, "checks": [{"key": "auth", "status": "failed", "message": "invalid token"}]}
```

規約:

- 終了コード `0` は成功、非 `0` は失敗を表します。stderr はデプロイ記録に入ります（機密値はマスクされます）。
- stdout は空、または 1 行の JSON `{"ok": true, "message": "..."}` を出力できます。`ok` が `false` の場合は失敗として扱います。
- `verify` は読み取り専用操作でなければなりません。証明書の書き込み、永続オブジェクトの作成、`reload_command` の実行はできません。`mode=write` の明示的な書き込みテストのみ、一意の一時オブジェクトを作成してクリーンアップできます。
- `verify-v1` 機能を宣言したデプロイターゲットのみが `verify` 呼び出しを受け取ります。宣言していないターゲットは、メインプログラムが「プラグインバージョンは検証をサポートしていません」と表示します。
- `checks` は接続、認証、スコープ、権限の問題を区別するために使用します。`status` の値: `ok`、`failed`、`skipped`、`unsupported`、`error`。
- 不正な JSON はエラーとみなされます。デバッグログは stderr に書き込んでください。
- helper は `LACTSSL_PLUGIN_MEMORY_LIMIT`（バイト）からメモリ予算を取得します。
- メインプログラムは helper の `VmRSS` を定期的に確認し、`memory_limit_mb` を超えるとプロセスグループ全体を終了してエラーを記録します。
- メインプログラムは最小限の環境変数セットのみを渡し、サーバー側のキーを漏洩しません。
- プラグインファイルは実行可能で、グループまたは他のユーザーに書き込みを許可してはなりません。`manifest.sha256` が空でない場合は検証します。
- メインプログラムはスキャン時のファイルダイジェストを記録し、各デプロイ前に再検証します。helper を置き換えた後は再スキャンが必要です。

## 9. セキュリティ推奨事項

- 信頼できる helper のみを有効化してください。デプロイプラグインは証明書の秘密キーを読み取れるため、信頼されたコードと同等です。
- プラグインディレクトリは `0700`、helper は `0755`、所有者はサービスの実行ユーザーにします。
- 本番ではマニフェストに `sha256` を記入し、アップグレード後にダイジェストを更新してください。
- 適切な `memory_limit_mb` と `timeout_seconds` を設定し、異常なプラグインがホストを停止させないようにしてください。
- `lactssl` ユーザーに追加権限を与えず、プラグインディレクトリを共有書き込み可能なパスに置かないでください。
- デプロイターゲットには最小権限のアカウントを使用し、リロードコマンドは具体的なサービスに限定してください。

## 10. トラブルシューティング

| 現象 | 原因 | 対処 |
| --- | --- | --- |
| デプロイ種別がローカル/SSH のみ | プラグインが未有効化/未インストール | `deploy_plugins.enabled` を有効化し、ターゲットをインストールして有効化 |
| プラグインのロードに失敗 | 権限/ダイジェスト/プロトコル/シンボリックリンク | 権限を修正するか再インストール |
| SSH フィンガープリントの不一致 | サーバーのキー交換/設定ミス | フィンガープリントを確認し、古い記録をクリアして再試行 |
| デプロイ成功だが実際のサービスは旧証明書のまま | 未リロード/キャッシュ/マルチインスタンス | リロードコマンドを設定し、キャッシュを更新し、すべてのノードを確認 |
| Webhook が拒否される | パブリック HTTP/証明書が信頼されていない | HTTPS または内部アドレスを使用し、TLS を確認 |
| CDN/パネルの失敗 | 認証情報の権限/パラメータ/API バージョン | ターゲット側の権限とパラメータを確認 |
| デプロイタイムアウト | ターゲットが遅い/大きなファイル | `timeout_seconds` を増やし、ネットワークを確認 |

その他のトラブルシューティングは[監視とトラブルシューティング](troubleshooting.md)を参照してください。
