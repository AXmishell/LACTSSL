# 運用マニュアル

本書は LACTSSL の日常運用を担当するオンコールおよび運用チーム向けに、バックアップとリストア、監視とアラート、容量管理、変更とアップグレード、障害対応を扱います。目的は、サービスを引き継げること、監査できること、障害後に復旧できることです。

## 1. サービス目標と責任

LACTSSL は SLA を付帯しません。企業は内部で次を明確にしてください。

| 項目 | 推奨する定義 |
| --- | --- |
| サービスレベル | 証明書の発行・デプロイを重要基盤システムと位置づける、または業務影響で分類する |
| 稼働時間 | 依存する DNS、CA、リバースプロキシ、デプロイ先と一致させる |
| RPO | 少なくとも 1 日 1 回のバックアップ。重要環境では時間単位まで短縮可能 |
| RTO | 「ホスト準備 + リストア + 起動検証」の演習結果を基準とする |
| 変更ウィンドウ | 証明書の一斉失効や業務ピークを避ける |
| アラート対応 | タスク失敗・証明書異常は 15〜30 分以内に対応（企業の規定による） |

LACTSSL の「プロセスの生存」を業務可用性と見なさないでください。実際の業務可用性は DNS API、CA、デプロイ先、通知経路にも依存します。

## 2. バックアップとリストア

### 2.1 バックアップ範囲

必ず次を同時にバックアップします。

1. `config.yaml`（または `-config` で指定したパス）
2. `data/` ディレクトリ全体

`data/` には少なくとも `lactssl.db` が含まれます。実行中は `lactssl.db-wal`、`lactssl.db-shm` が存在する場合もあります。データベース、プラグイン、ログ、ログアーカイブ、アップグレードバックアップはすべて `data/` 配下にあります。

注意: 画面の「バックアップをダウンロード」で生成される ZIP には `data/archives/logs/` のログアーカイブが**含まれません**。アーカイブファイルはデータベースと同等に機密性が高いため、別途コピーするかオフラインメディアへダウンロードしてください。コマンドで `data/` 全体をバックアップする場合は一緒に含まれます。

データベースのみをバックアップすると `salt` が失われ、暗号化された認証情報を復号できなくなります。設定のみをバックアップすると業務データが失われます。両者は必ずセットで扱ってください。

### 2.2 画面からの暗号化バックアップ（推奨）

「システム設定 → バックアップと復元」でオンライン操作を提供します。

- **バックアップをダウンロード**: ZIP を生成し、データベーススナップショット（SQLite はファイルスナップショット、PostgreSQL は Go ネイティブの ZIP + COPY 形式、MySQL はネイティブ SQL 形式）、現在の `config.yaml`、`manifest.json` のバージョン情報を含めます。PostgreSQL/MySQL のバックアップは Go が直接生成・復元し、`pg_dump`/`pg_restore`/`mysqldump`/`mysql` クライアントに依存しません。
- ダウンロード前に現在のアカウントパスワードの再入力を求めます。TOTP を有効にしている場合は動的コードも必要です。
- バックアップ暗号化パスワードはアカウントパスワードとは独立しており、12 文字以上です。
- バックアップ内容は PBKDF2-HMAC-SHA256（600,000 回反復）+ AES-256-GCM で暗号化されます。リストア時には同じパスワードの入力が必須です。
- パスワードを紛失すると、そのバックアップは復元できません。

推奨事項:

- バックアップファイルは独立したメディアやオブジェクトストレージに保存し、`data/` 配下に置かないでください。
- バックアップパスワードは企業のパスワードマネージャーに保管し、バックアップファイルとは分離して管理してください。
- バックアップの日時、サイズ、チェックサム、保管場所を記録してください。
- 少なくとも 7〜30 日を保持し、重要環境ではコンプライアンス要件に応じて延長してください。

### 2.3 コマンドによるバックアップ

ファイルレベルのバックアップが必要な場合は、SQLite を一貫した状態に保つため、先にサービスを停止してからコピーします。

```bash
# Docker
docker compose stop

# または systemd サービスを停止
sudo systemctl stop lactssl

tar czf lactssl-backup-$(date +%F).tar.gz config.yaml data
chmod 600 lactssl-backup-*.tar.gz
```

停止できない場合は、画面からの暗号化バックアップを優先してください。稼働中の SQLite を直接コピーすると、一貫性のないスナップショットになる可能性があります。

### 2.4 リストア

#### 画面からのリストア

1. ZIP バックアップまたは単体の `.db` ファイルをアップロードします。
2. 現在のパスワードを入力して確認します。暗号化バックアップの場合は復号パスワードも入力します。
3. サービスはリストア内容を `data/restore-pending/` に書き込み、自動的に再起動します。
4. Docker デプロイでは `restart: unless-stopped` により自動起動します。バイナリを直接実行している場合は手動で再起動してください。
5. バックアップ内の管理者アカウントでログインします。

#### 手動リストア

1. サービスを停止します。
2. バックアップ内の `config.yaml` と `data/` を元の場所に戻します。
3. 権限を確認します。設定ファイルは `0600`、データディレクトリは `0700`、所有者はサービス実行ユーザーです。
4. サービスを起動します。
5. セキュアエントリ、管理者ログイン、証明書、タスク、プラグインを確認します。

#### リストア時の注意

- リストア後は、バックアップ内の管理者アカウントでログインしてください。
- 既定ではセッション保持が有効なため、再起動してもセッションは保持されます。`security.session_persistence: false` にすると、起動のたびにセッションがクリアされ JWT サブキーがローテーションされます。
- バックアップ内の `config.yaml` が異なる `jwt_secret` を使用している場合、以前のトークンは検証を通過できません。
- 異なる `salt` を使用している場合、データベース内の暗号化された認証情報は対応する設定でのみ復号できます。そのため、常に完全な ZIP バックアップでリストアすることを推奨します。
- バックアップ内のセキュアエントリが現在と異なる場合は、起動ログで新しいエントリを確認してください。
- データベースのみをリストアして `config.yaml` の `salt` を失った場合、暗号化済みの DNS/デプロイ/通知の認証情報は復号できず、再入力が必要になります。

### 2.5 リストア演習

四半期に少なくとも 1 回:

- [ ] 隔離環境で最新バックアップをリストアする。
- [ ] 管理者ログイン、TOTP/パスキー、復旧用メールアドレスを検証する。
- [ ] 証明書一覧、タスク、デプロイ認証情報、通知チャネルを検証する。
- [ ] テストタスクを 1 件実行し、非本番のターゲットへデプロイする。
- [ ] 実測した RTO、問題点、改善項目を記録する。
- [ ] バックアップパスワードが引き続き権限を持つ担当者に保管されていることを確認する。

## 3. 監視とアラート

### 3.1 監視シグナル

| シグナル | 取得方法 | 推奨しきい値/アクション |
| --- | --- | --- |
| プロセス生存 | TCP ポート監視 | 30〜60 秒ごと、3 回連続失敗でアラート |
| 認証ヘルス | `GET /api/status` + `system:read` API キー | 1〜5 分ごと、200 以外または高レイテンシでアラート |
| タスク失敗 | 操作ログまたは通知 | 失敗時に即アラート、DNS/CA/デプロイ/通知を区別 |
| 証明書の期限接近 | ダッシュボード、サイト監視 | 30/14/7 日の段階的リマインド |
| デプロイ失敗 | デプロイ記録/通知 | 即アラート、ターゲットシステムとリロードコマンドを確認 |
| ディスク | ホスト/プラットフォーム監視 | 使用率 > 80% で予告、> 90% でアラート |
| バックアップ | バックアップタスク/ファイル確認 | 失敗または周期超過でアラート |
| HTTP 5xx | リバースプロキシログ | ベースラインに応じてしきい値を設定 |
| ログイン異常 | 操作ログ/システムログ | 複数回失敗、異常な送信元 IP でアラート |

### 3.2 アラートのルーティング

- タスク失敗、証明書異常、デプロイ失敗は運用オンコールのチャネルへ送ります。
- セキュリティインシデント（異常ログイン、エントリの探索、プラグイン検証失敗）はセキュリティチャネルへ送ります。
- バックアップ失敗、ディスク不足はプラットフォームチャネルへ送ります。
- テスト通知は本番のオンコールグループへ送らず、専用のチャネルを使用してください。

通知チャネルの可用性は外部サービスに依存します。単一障害点を避けるため、少なくとも 2 つの独立したチャネル（例: メール + 企業 IM）を設定することを推奨します。

### 3.3 行うべきでない監視

- 素の `/` や `/login` を匿名ヘルスチェックに使わないでください。セキュアエントリを通過しない場合は 404 を返しますが、これは想定どおりの動作です。
- 管理者パスワードや長期間有効な全権限 API キーを監視システムへ書き込まないでください。
- 証明書の秘密鍵やバックアップパスワードをアラート内容に含めないでください。

## 4. 日常メンテナンス

### 4.1 毎日

- タスク失敗、デプロイ失敗、サイト監視の異常を確認します。
- 証明書の期限ダッシュボードに新たな高リスク項目がないことを確認します。
- バックアップが計画どおりに生成されているか確認します。

### 4.2 毎週

- 自動更新タスクが正常にスケジュールされているか確認します。
- システムログのエラー、レート制限、異常ログインを確認します。
- 追加/無効化された API キーと認証情報を突き合わせます。

### 4.3 毎月

- ディスク、データベースサイズ、WAL、ログ保持を確認します。
- プラグインのバージョンとセキュリティアドバイザリを確認します。
- 操作ログと変更記録を抜き取り確認します。
- 通知チャネルを検証します。

### 4.4 四半期ごと

- バックアップとリストアの演習を完了します。
- 管理者アカウント、復旧用メールアドレス、TOTP/パスキーを見直します。
- API キーの権限と有効期限を見直します。
- アップグレードウィンドウとロールバック計画を評価します。

## 5. 容量とクリーンアップ

### 5.1 注視すべき容量

| 項目 | 増加要因 | 対応 |
| --- | --- | --- |
| SQLite | 証明書、タスクログ、操作ログ、システムログ、ACME オーダー | 履歴データの削除、データベースの最適化、ログのアーカイブ |
| ログアーカイブ | `data/archives/logs/` 配下の NDJSON.gz と manifest | 定期的に外部ストレージへ退避。必要に応じて「ログ → アーカイブ」で削除 |
| WAL | 長期稼働、書き込み頻度の高さ | `wal_checkpoint(TRUNCATE)` をアップグレード/最適化ツールが実行 |
| プラグイン | インストール/更新による旧ファイルの累積 | 不要なプラグインをアンインストールし、古い helper を削除 |
| アップグレードバックアップ | 移行スナップショット、旧バイナリ | 保持ポリシーに従って削除 |
| バックアップストレージ | 日次/週次バックアップ | 保持期間と別拠点のコピーを設定 |

### 5.2 クリーンアップの入口

- **証明書管理 → 一括クリーンアップ**: 状態、失効/取り消しからの経過時間、発行日時、ドメイン、発行機関、由来で絞り込みます。各タスクの最新証明書を保持できます。クリーンアップ後、関連タスクの証明書参照はクリアされます。
- **ACME 診断 → クリーンアップ**: エンドポイント、状態、未使用期間で無効なオーダーとアカウントを削除します。アカウントを削除すると過去のオーダーも削除されますが、発行済み証明書には影響しません。
- **ログ → 操作ログ/システムログ → クリア**: アーカイブが有効な場合は先に `data/archives/logs/` へ書き込み、その後データベースから削除します。アーカイブに失敗した場合は削除を拒否します。クリア操作は操作ログに記録されます。
- **ログ → アーカイブ**: アーカイブファイルの表示、ダウンロード、削除を行います。アーカイブは既定で永久保持されます。`archive.retention_days` または `archive.max_total_mb` が設定されている場合、メンテナンスタスクがポリシーに従って削除します。
- **アップグレード/最適化**: ピークを避けた時間帯にデータベース最適化を実行します。`VACUUM` はデータベースを一時的に排他しファイルを書き換えるため、ディスク空き容量を確保してください。

### 5.3 データベースメンテナンス

- サービスは 6 時間ごとにメンテナンスクリーンアップを実行します。ログページでスケジューラが動作しているか確認できます。
- 新バージョンの初回起動時には履歴移行が自動実行され、`data/upgrade-backups/` に移行前スナップショットが生成されます。
- ディスク容量を回収する必要がある場合は、ピークを避けた時間帯に `/upgrade` へアクセスし、「データベースと設定のみを最適化」を実行して VACUUM を有効にします。
- 実行前に利用可能なバックアップと十分なディスク容量を確保してください。`VACUUM` の失敗は警告として返され、サービスの稼働継続には影響しません。

## 6. バージョンとリリース

### 6.1 バージョンの識別

- バージョン番号は git tag を唯一の情報源とし、リポジトリでは `VERSION` ファイルを管理しません。
- ローカルビルドでは `git describe --tags --always --dirty` から導出し、`v` プレフィックスを除去します。
- ビルドスクリプトは `-ldflags -X 'lactssl/internal/api.Version=...'` でバージョンを注入します。
- 「設定 → バージョン情報」でビルドバージョン、ビルド日時、アーキテクチャを確認できます。
- `go run` や開発ビルドでは `dev` と表示されます。

### 6.2 リリースチャネル

- 安定版のタグには `latest`、`<version>`、`<major>.<minor>`、`<major>` が含まれます。
- プレリリース版は完全なバージョンタグのみをプッシュし、`latest` を上書きしません。
- 本番では明確なバージョンに固定し、追跡不能な `latest` で長期運用しないでください。

### 6.3 リリース成果物

Release では Linux/macOS/Windows のバイナリ、`checksums.txt`、`linux/amd64`・`linux/arm64` のイメージをビルドします。アーカイブにはバイナリ、`README.md`、`LICENSE`、`config.yaml.example` が含まれます。

リリース手順、署名、ローカルビルドの詳細は[拡張開発: ソースとビルド](development.md)を参照してください。

## 7. アップグレードと変更

アップグレード前:

1. 対象バージョンの変更点と移行手順を読みます。
2. `config.yaml` と `data/` をバックアップします。
3. ステージング環境で主要経路（発行、デプロイ、通知、API）を検証します。
4. ロールバックするバージョンと手順を確認します。
5. ピークを避けた時間帯を選び、関係者へ通知します。

Docker:

```bash
docker compose pull
docker compose up -d
```

バイナリ:

```bash
sudo systemctl stop lactssl
sudo cp lactssl /opt/lactssl/lactssl
sudo chown lactssl:lactssl /opt/lactssl/lactssl
sudo systemctl start lactssl
```

アップグレード後:

- ログの「データ形式のアップグレード完了」を確認します。
- `/upgrade` にログインして各ステップの状態を確認します。
- 証明書、タスク、デプロイ、通知、API を検証します。
- 1 回のスケジューリング周期（少なくとも 30 秒）と 1 回のタスク実行を観察します。

移行、ロールバック、プログラムのアップグレードの詳細は[アップグレードと変更](upgrade.md)を参照してください。

## 8. 障害対応

### 8.1 重大度

| レベル | 例 | 目標 |
| --- | --- | --- |
| P1 | 管理エントリが利用不可、多数の証明書が更新不可、秘密鍵の漏えい | 即時対応、インシデント対応の開始 |
| P2 | 単一タスクの失敗、デプロイ先の異常、通知チャネルの停止 | 30 分以内に対応 |
| P3 | 単一監視の誤検知、ログの異常、重要でないプラグインの問題 | 営業時間内に対応 |

### 8.2 共通手順

1. **影響範囲の確認**: どの証明書、タスク、デプロイ先、業務システムが影響を受けるか。
2. **現場の保全**: ログをクリアしないでください。時刻、リクエスト ID、エラーメッセージを記録します。
3. **依存関係の確認**: DNS API、CA、ネットワーク、リバースプロキシ、ターゲットシステム、SMTP/IM。
4. **変更の隔離**: 関連タスクを一時停止し、繰り返しの失敗や証明書の上書きを防ぎます。
5. **サービスの復旧**: 依存関係を修正するか変更をロールバックします。必要に応じてバックアップからリストアします。
6. **検証**: タスクを再実行し、証明書、デプロイ、通知を確認します。
7. **振り返り**: 根本原因、タイムライン、改善項目、担当者を記録します。

具体的な症状とコマンドは[監視とトラブルシューティング](troubleshooting.md)を参照してください。
