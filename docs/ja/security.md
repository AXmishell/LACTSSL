# セキュリティベースライン

本書はセキュリティ責任者、監査、プラットフォームチーム向けに、LACTSSL のセキュリティモデル、実装済みの制御、企業が補う必要のある制御、導入前の強化チェックリストを説明します。これはコンプライアンス認証の結論ではなく、企業自身のリスク評価の代わりにもなりません。

## 1. セキュリティモデルと信頼境界

LACTSSL は「セルフホストの単一インスタンス」として設計されており、信頼境界は次のとおりです。

```text
[非信頼] インターネット/企業ネットワークのユーザー
    │ HTTPS（リバースプロキシで終端）
[境界] リバースプロキシ / WAF / ネットワーク ACL
    │ HTTP（ループバックまたは内部ネットワーク）
[信頼] LACTSSL プロセス
    ├─ 管理者セッション: 完全な制御と同等
    ├─ API キー: 権限スコープにより制限
    ├─ プライベート CA 秘密鍵: 暗号化してローカルデータベースに保存
    └─ プラグインのサブプロセス: サービスアカウントで実行され、信頼済みコードと見なす
[外部] DNS API / CA / SMTP / デプロイ先 / 通知チャネル
```

重要な結論:

- **管理者セッションは完全な制御と同等**であり、ローカルのデプロイコマンドの実行、秘密鍵のエクスポート、バックアップからのリストアを含みます。
- **API キーはマシン ID** であり、自動化シナリオの権限を下げるためのもので、マルチユーザーの RBAC ではありません。
- **プラグインは信頼済みコード**です。特にデプロイプラグインは証明書の秘密鍵に触れるため、サプライチェーンのセキュリティは企業が担保する必要があります。
- **データベースと `config.yaml` は同等に機密**です。`salt` を失うと暗号化された認証情報が使えなくなり、漏えいすると認証情報が復号される可能性があります。

## 2. アイデンティティとアクセス制御

### 2.1 管理者アカウント

- 単一の管理者アカウントで、マルチユーザー、ロール、組織構造、承認フローは提供しません。
- パスワードは bcrypt ハッシュで保存され、長さは 8 文字以上です。本番では 16 文字以上のランダムなパスワードを推奨します。
- TOTP の二段階認証とパスキー（WebAuthn/Passkey）に対応します。
- TOTP の有効化、パスキーの登録、SMTP/通知ターゲットの変更、テストメール/通知の送信には再認証（現在のパスワードまたは TOTP）が必須です。セッションが盗まれた場合に、アカウントを攻撃者の認証器へ紐付けたり、保存済みの SMTP/通知キーを攻撃者のホストへ転送したりすることを防ぎます。
- パスキーは HTTPS のドメインまたは localhost 経由で使用する必要があります。IP アドレスを直接使用することは WebAuthn のオリジンとして認められません。
- パスキーでログインした後に TOTP を再度要求することはありません。パスキー自体がデバイスの指紋、顔、またはシステム PIN の検証を完了します。
- パスワードを変更するとトークンバージョンが上がり、サーバー側のすべてのセッション、API キー、パスキーが削除され、すべてのログインが即座に無効になります。
- メールによるパスワードリセットは、TOTP の無効化、パスキーと API キーの削除を同時に行います。復旧用メールアドレス自体の安全性を確保する必要があります。

### 2.2 API キー

- キーは 86 文字の Base64URL ランダム文字列（64 バイトのエントロピー）で、固定プレフィックスはなく、サーバー側には SHA-256 ダイジェストのみを保存します。
- 権限は「リソース:アクション」で区分します。`*` はすべてのシステム API 能力を表します。
- 機密性の高い権限は個別に列挙されます: `certificates:key`、`private_cas:key`、`deploy:execute`、`deploy:command`、`backup:download`、`backup:restore`、`plugins:write`、`settings:write`、`api_keys:write`、`monitors:internal` など。
- API キーで他のキーを管理する場合、自身が持たない権限を付与することはできず、自身より高い権限のキーを変更/ローテーション/削除することもできません。
- アカウントセキュリティ関連の操作（パスワード変更、パスキー、セッション管理）はブラウザのログインセッションのみに許可され、API キーからは呼び出せません。
- 自動化システムごとに独立したキーを作成し、有効期限を設定し、最小権限を付与し、定期的にローテーションすることを推奨します。

### 2.3 企業が補う必要のあるもの

- マルチユーザーの RBAC、SSO（OIDC/SAML/LDAP）、SCIM、承認フロー。
- 踏み台サーバー、PAM、ゼロトラストアクセスプロキシ。
- 管理者アカウントの二者承認と定期的な権限レビュー。
- API キーの集中管理（Vault/KMS）と送信元 IP の制限。

## 3. ネットワークと TLS

### 3.1 インバウンド

- 管理コンソールは HTTPS のリバースプロキシ経由でアクセスする必要があります。メインプログラムは HTTP のみをリッスンします。
- バックエンドポートはループバックまたは内部ネットワークのみでリッスンし、インターネットへ直接公開しないでください。
- プロキシ層で送信元 IP のホワイトリスト、VPN、ゼロトラストポリシー、または WAF を設定します。
- プロキシは `X-Forwarded-For` を上書きまたは正しく追記し、`X-Forwarded-Proto` を転送する必要があります。LACTSSL は `server.trusted_proxies` の正確な IP または最小 CIDR のみを信頼します。追記チェーンでは、チェーン上のすべてのプロキシを信頼する必要があります。
- 信頼できるプロキシが未設定の場合、すべてのリクエストがプロキシ IP からのものと見なされ、レート制限が機能せず、`Secure` Cookie の判定が誤ります。
- プロキシ層で HSTS、TLS 1.2+ を設定し、弱い暗号スイートを無効化し、リクエストボディのサイズを制限することを推奨します（バックアップのリストアとプラグインのアップロードには大きな上限が必要です）。

### 3.2 アウトバウンド

サーバーは自ら外向きのリクエストを発行します。

- DNS プロバイダーの API（TXT の作成/削除）。
- パブリック ACME CA と汎用アップストリーム。
- SMTP、Gotify、Telegram、DingTalk、WeCom、Webhook などの通知チャネル。
- SSH/SFTP、FTP/FTPS、クラウド CDN、宝塔、1Panel、雷池 WAF などのデプロイ先。
- サイト証明書監視の対象。

推奨事項:

- 本番環境ではドメインまたはネットワークセグメント単位で egress ホワイトリストを設定し、実際に必要な対象のみを許可してください。
- 企業プロキシを経由する必要がある場合は、システムの環境変数で設定してください（Go HTTP クライアントの挙動）。アプリケーション内の設定に依存しないでください。
- デプロイ Webhook や通知 Webhook などのカスタム対象は送信元を審査し、秘密鍵やトークンを信頼できないアドレスへ送らないようにしてください。
- 内部ネットワークの HTTPS 対象には、「システム設定 → TLS 信頼チェーン」で内部 CA の公開鍵をインポートしてください。TLS 検証を無効にしないでください。インポートした CA とプライベート CA は `SSL_CERT_FILE` に統合され、プラグインとデプロイコマンドが使用します。

### 3.3 SSRF 対策

- リテラルおよび解決後の対象アドレスについて、クラウドメタデータ、リンクローカル、予約済み、ドキュメント用、NAT64 などのネットワークセグメントを拒否します（例: `169.254.169.254`、`100.100.100.200`、`fd00:ec2::254`、`0.0.0.0/8`、`240.0.0.0/4`）。
- ループバックとプライベートネットワークのアドレスは引き続き許可され、Gotify、自前のパネル、内部 Webhook などの用途に便利です。不要な場合はネットワーク層でさらに制限できます。
- サイト監視は既定でパブリックな対象のみを許可します。プライベートネットワーク/ループバックの監視には、API キーに追加で `monitors:internal` が必要で、ダイヤル段階で最終的に解決された IP でもう一度検証し、DNS リバインディングを防ぎます。
- デプロイ Webhook は証明書の秘密鍵を伴うため、パブリックな対象には `https://` を強制します。ループバック、プライベートネットワーク、`.local`、`.internal` の対象には HTTP を許可します。
- ダイヤル段階では DNS 解決結果を再検証し、検証後の IP へ直接接続することで、DNS リバインディングによる回避を防ぎます。
- サードパーティへのリクエストが失敗した場合、ログへ書き込む前に URL のパスとクエリパラメータをマスキングし、Telegram bot token、Gotify token、Server酱 の SendKey などがログやバックアップに入らないようにします。

## 4. セキュアエントリ、セッション、CSRF

### 4.1 セキュアエントリ

管理ページはルートパスに直接公開されず、ランダムに生成されたエントリを経由してアクセスします。

```text
https://your-domain/<entry>/
```

- エントリは既定で 20 文字の大文字・小文字・数字の組み合わせをランダムに生成し、データベースに保存します。
- エントリを通過していないページは一律で `404` を返します。素の `/` などの一般的な探索パスも含みます。
- API は素の `/api` に固定され、ログインセッションまたは API キーで保護されます。旧版の `/<entry>/api` は互換エイリアスとして残されています。
- 正しいエントリへアクセスすると、有効期間 24 時間の署名付き `HttpOnly` セキュアエントリ Cookie が書き込まれ、サーバー側でも有効期限を検証します。
- エントリの探索には頻度制限があり、総当たりを防ぎます。
- 「設定 → セキュアエントリ」で変更でき、変更は即座に反映されます。手動のエントリは 8〜32 文字が要件です。
- 初回初期化時に完全なエントリのアドレスが起動ログへ出力されます。初期化完了後は出力されません。
- エントリを忘れた場合は、`config.yaml` の `security.entry` を変更して再起動し上書きするか、データベースの `settings` テーブルで `security.entry` を確認します。
- システムが未初期化の場合、起動ログにワンタイムの初期化トークンも出力されます。管理者の作成、初期化設定の変更、初期化プロセスの再起動、バックアップからのリストアには、このトークン（`X-LACTSSL-SETUP-TOKEN`）を必ず付与する必要があります。
- トークンは初期化の成功と同時に無効になり、サービス再起動後に再生成されます。

> エントリは追加の防御層であり、HTTPS、強力なパスワード、ネットワークアクセス制御の代わりにはなりません。

### 4.2 セッション

- ログインセッションは `HttpOnly` Cookie に保存され、フロントエンドのスクリプトからは読み取れません。Cookie は `SameSite=Strict` を使用します。
- セッショントークンは 512 文字以上に補完されます。CSRF トークンは 32 文字です。
- セキュアエントリへの初回アクセスまたはログイン時に、長期有効（1 年）の `HttpOnly` デバイス識別 Cookie（`lactssl_device`、32 文字の 16 進数）を発行します。
- HTTPS デプロイでは、セッション、CSRF、エントリの Cookie に自動的に `__Host-` プレフィックスが付き、共有親ドメイン下の兄弟サブドメインによる上書きを防ぎます。
- 既定ではサービス起動のたびにサーバー側のセッション記録がクリアされ、起動時のランダム値が JWT 署名サブキーに混ぜられます。再起動後はすべての古いログインが即座に無効になります。
- `security.session_persistence: true` を設定すると、起動時にセッションをクリアせず、固定の `jwt_secret` で署名するため、バックグラウンドでの再起動後も元のセッションを引き続き使用できます。
- パスワードを変更するとトークンバージョンが上がり、すべてのセッション、API キー、パスキーが削除されます。

### 4.3 CSRF とクロスサイト対策

- サーバー側の状態を変更するすべてのリクエスト（POST/PUT/DELETE など）は `X-LACTSSL-CSRF` リクエストヘッダーを伴い、`lactssl_csrf` Cookie と一致する必要があります。
- 旧セッションの初回リクエストではこの Cookie が自動的に再発行されます。ヘッダーのみを伴うダウングレード検証は受け入れません。
- ログイン、初期化、パスワードを忘れた場合、パスワードリセットなどの未認証インターフェースでは、追加で `Origin`/`Sec-Fetch-Site` を検証します。
- `Authorization: Bearer <token>` を明示的に使用して API を呼び出す場合は CSRF 検証の対象外となり、スクリプトや外部連携に便利です。
- ページのレスポンスはリクエストごとにランダムな CSP nonce を使用し、`script-src` は任意のインラインスクリプトを許可しなくなりました。スタイルはコンポーネントライブラリの要件を満たすためインラインを引き続き許可します。

## 5. パスワードリセットと外部アドレス

パスワードリセットメールのリンクは、固定アドレスに基づいて生成する必要があります。

```yaml
security:
  public_url: "https://ssl.example.com"
```

- `public_url` が未設定の場合、ローカルループバックアドレスからで Host が `localhost`/ループバック IP のリクエストに限り、現在の Host からリンクを推測できます。それ以外のリクエストで「パスワードを忘れた場合」を呼び出すと拒否されます。
- クライアントが偽造できる `X-Forwarded-Host` は信頼しません。
- リバースプロキシ構成では必ず `public_url` を設定し、攻撃者が Host を偽造してリセットリンク（token とセキュアエントリを含む）を自身のドメインへ誘導することを防いでください。

## 6. 認証情報とデータの保護

### 6.1 暗号化

- DNS 認証情報、デプロイ認証情報、SMTP パスワード、通知 Token、TOTP キー、プライベート CA 秘密鍵、証明書秘密鍵などの機密フィールドは、AES-256-GCM で暗号化してからデータベースへ書き込みます。
- 旧バージョンの平文データは起動時に自動移行されます。
- 暗号化キーは `config.yaml` の `security.salt` から導出します。
- JWT は `security.jwt_secret` で署名します。実際には `jwt_secret` と起動時のランダム値から HKDF で派生した独立のサブキーを使用し、データベースの AES-GCM キーとは分離されています。
- `security.jwt_secret` と `security.salt` を手動で設定する場合は 32 文字以上が必要で、短すぎると起動を拒否します。
- インターフェースが設定を返す際はキー系フィールドをマスキングします。編集時に空欄のままにすると元の値を保持します。

### 6.2 ファイルとバックアップ

- `config.yaml` は `0600`、`data/` は `0700` を維持し、所有者はサービス実行ユーザーとします。
- データベース、WAL、プラグイン、ログ、アップグレードバックアップはすべて `data/` 配下にあります。
- バックアップのダウンロード時には 12 文字以上の暗号化パスワードを設定する必要があります。バックアップパッケージは PBKDF2-HMAC-SHA256（600,000 回反復）+ AES-256-GCM で暗号化されます。
- バックアップパッケージにはデータベース、設定、バージョン情報が含まれるため、機密ファイルとして管理してください。暗号化されていないデータベースや設定のコピーを配布しないでください。
- リストアパッケージはまず設定を完全に検証し（キーの長さ、セキュアエントリ、リッスンアドレス、TLS/mTLS の組み合わせなど）、不正な設定は拒否されます。
- 初回初期化の成功後、未適用のリストアパッケージはクリアされ、初期化前に一時保存された内容が以降の再起動で新しいアカウントを上書きすることを防ぎます。

### 6.3 認証情報のローテーション

- DNS/デプロイ/通知の認証情報には専用のアカウントを使用し、定期的にローテーションしてください。
- SSH は既定でホストフィンガープリントの入力を要求します。「初回接続時にホストキーを自動信頼」を明示的に有効にした場合のみ TOFU を採用し、以降のフィンガープリントの不一致は接続を拒否します。
- FTP デプロイは既定で明示的 TLS を使用します。`none` を明示的に選択した場合のみ平文 FTP を使用します。
- API キーには有効期限を設定し、システムごとに個別に発行し、漏えい時には即座にローテーションしてください。

## 7. 監査とログ

| ログ | 内容 | 保持/エクスポート |
| --- | --- | --- |
| 操作ログ | タスク、証明書、デプロイ、通知、監視、設定変更 | 由来/レベル/時刻で絞り込み可能。直近 90 日を CSV/JSON でエクスポート。削除前にアーカイブへ書き込み |
| システムログ | 起動、HTTP、スケジューリング、プラグイン、ACME | 既定で 7 日/20,000 行。調整とクリアが可能。削除前にアーカイブへ書き込み |
| ログアーカイブ | 操作ログ/システムログの生 NDJSON と manifest | `data/archives/logs/`、既定で永久保持。「ログ → アーカイブ」でダウンロードまたは削除 |
| プロセスログ | stdout または `log.file` | サイズ/日数でローテーション。JSON 出力も可能 |
| リバースプロキシログ | アクセス、送信元 IP、ステータスコード | 企業のログ基盤で管理 |

推奨事項:

- 操作ログ、システムログ、アーカイブファイルを定期的に SIEM やログ基盤へエクスポートし、管理者によるクリア、アーカイブの削除、データ破損による監査の欠落を防いでください。
- 操作ログとシステムログは `logs` テーブルを共有しますが、`category` で分離されています。システムログをクリアしても操作ログは削除されません。
- 各レスポンスには `X-Request-ID` が付き、アクセスログ、panic、エラーの関連付けに利用できます。
- アクセスログにはクエリパラメータ、リクエストボディ、認証ヘッダーを記録しません。セキュアエントリはパス内で一律 `:entry` に置き換えられます。
- ログとアーカイブファイルにはクライアント IP、ドメイン、エラーの詳細、操作者情報が含まれる場合があります。運用データとして管理し、公開共有を避けてください。アーカイブファイルの権限は `0600`、ディレクトリは `0700` です。
- アーカイブは改ざん不能な監査ではありません。データディレクトリの権限を持つ管理者はアーカイブファイルを削除または変更できます。高いコンプライアンス要件がある場合は、外部の WORM ストレージや SIEM へ同期する必要があります。
- 重要な操作（秘密鍵のエクスポート、バックアップからのリストア、CA の生成、プラグインのインストール、セキュアエントリの変更）は変更票と関連付けることを推奨します。

## 8. プラグインとサプライチェーンのセキュリティ

- 公式プラグインリポジトリは Ed25519 のインデックス署名に対応しています。公開鍵を設定すると `index.json.sig` の検証が必須になります。
- プログラムの自己アップグレードは既定で `upgrade.program.public_key` の設定を要求します。未設定の場合はオンラインアップグレードを拒否し、管理された環境のみ `upgrade.program.allow_unsigned` を明示的に有効にできます。
- アセットは 64 桁の 16 進数 SHA-256 を提供する必要があり、ダウンロード後に強制検証します。
- インストール時に `plugin.json`、manifest 内の ID とバージョンを検証し、いずれかのステップが失敗するとロールバックします。
- インストール記録のファイルダイジェストは、検出時、登録時、および DNS/デプロイ/通知の呼び出しごとに再確認します。ファイルが置き換えられた場合は読み込みまたは実行を拒否します。
- 署名公開鍵が未設定の場合はリスクの警告が表示され、無人での自動更新はスキップされます。
- インデックスキャッシュ（304 による再利用を含む）は、キャッシュされた生バイトを現在の公開鍵で再検証する必要があります。公開鍵が変わった場合やキャッシュに署名がない場合は ETag を破棄して全量を再取得します。「公開鍵が設定済み」というだけで検証済みとマークしてはいけません。
- プラグインディレクトリの権限は `0700`、helper は `0755` で、グループやその他のユーザーの書き込みを許可しません。シンボリックリンクは拒否されます。
- デプロイプラグインは証明書の秘密鍵を受け取るため、既定で無効であり、信頼できる提供元のもののみをインストールしてください。
- メインプログラムは helper のタイムアウト、常駐メモリ、出力サイズを制限し、エラーメッセージ内の認証情報と秘密鍵をマスキングします。

本番の推奨事項:

- 企業内部のミラー（HTTPS または `file://`）を使用し、バージョンを固定して自動更新を無効にします。
- プラグインの受け入れリストを作成し、提供元、バージョン、ダイジェスト、承認者、ロールバックバージョンを記録します。
- ステージング環境でプラグインのアップグレードを検証してから本番へ適用します。

## 9. ACME サーバーのセキュリティ

- 組み込みの ACME サーバーは既定で有効ですが、エンドポイントを作成して有効化するまで外部へ証明書を発行しません。
- 有効化後は独立したプロトコルエントリを提供し、管理側のセキュアエントリ、セッション Cookie、CSRF 検証は使用しません。不要な場合は `acme.enabled` を `false` にできます。
- パブリックなデプロイでは独立したポートを使用し、ファイアウォールまたはリバースプロキシ層でアクセスを制限することを推奨します。
- 各 ACME エンドポイントにはドメインホワイトリストの設定が必須です。エンドポイントを有効化する際にホワイトリストが空だと拒否されます。
- EAB はオン/オフ可能で、既定では有効化を推奨します。EAB を無効にすると、そのポートへアクセスできる誰もがアカウントを作成できるため、ドメインホワイトリスト、mTLS、またはネットワーク ACL を併用する必要があります。
- mTLS はトランスポート層のセキュアエントリであり、ACME の JWS アカウント認証の代わりにはなりません。
- `acme.base_url` は固定のパブリックアドレスに設定し、Host ヘッダーインジェクションによってリソース URL が誤った場所を指すことを避けてください。
- HTTP-01 検証は既定でループバック、プライベートネットワーク、リンクローカル、CGNAT/予約済みセグメント（例: `100.64.0.0/10`、`192.0.0.0/24`）を拒否します。内部ネットワークのシナリオでは、エンドポイント単位の CIDR ホワイトリストで明示的に許可する必要があります。
- ACME プロトコルのリソースはランダムな公開 ID を使用し、データベースの自動増分 ID は使用しません。
- カスタム ACME アップストリームのディレクトリアドレスは HTTPS が必須です。ローカルループバックアドレスのみ HTTP を許可します。
- 単一インスタンスのデプロイではメモリ内 nonce を使用します。サービス再起動後、クライアントは `badNonce` を受け取り自動的に再試行します。
- CRL と OCSP のエンドポイントは `/pki/{ca}/...` にあり、通常はパブリックに到達可能である必要があります。CA ごとに構成されるため、ACME の登録エンドポイントを無効にしても利用可能に保つ必要があります。
- ACME を有効にする場合は固定の `acme.base_url`（または `security.public_url`）を設定することを推奨します。未設定の場合はリクエストの Host からリソース URL を推測するため、パブリックなデプロイではこのフォールバックに依存しないでください。
- CRL/OCSP のエンドポイントは IP 単位でレート制限されます。CRL は同じ失効集合の結果をキャッシュし、失効内容が変化した場合のみ CRL Number を増加させます。
- ACME サーバーのレート制限は `server.trusted_proxies` 内の信頼できるプロキシを読み取り、実際のクライアント IP でカウントします。
- CRL/OCSP は失効状態を能動的に確認するクライアントにのみ有効です。ブラウザによるプライベート CA の確認動作は一貫していません。既存の証明書は再発行しないと CRL/OCSP のアドレスが付与されません。
- 失効状態は独立した `revocations` テーブルに保存され、証明書の行を削除またはクリーンアップしても失効記録は消えません。CRL/OCSP はこのテーブルを基準とします。
- リーフ証明書を発行する前に、CA の `ExtKeyUsage`（`serverAuth` または `any` を含む必要がある）と NameConstraints（Permitted/Excluded DNS・IP）を検証します。タスクからの発行と ACME の finalize は同じ検証を共有します。

## 10. デプロイとコンテナの強化

- 専用ユーザーでサービスを実行し、`config.yaml` は `0600`、データディレクトリは `0700` を維持してください。
- Docker イメージはエントリポイントスクリプトでボリュームの権限を修正した後、非 root の `lactssl` ユーザーでメインプログラムを実行します。
- Compose は既定ですべてのケイパビリティを破棄し、必要に応じて `CHOWN`/`SETUID` などを追加し、読み取り専用のルートファイルシステム、`/tmp` の tmpfs、`pids_limit`、`init` を有効にします。
- `data/`、`config.yaml` をバージョン管理へコミットしたり、公開ディレクトリへ置いたりしないでください。
- サービスは既定で通常のインターフェースのリクエストボディを 2 MiB に制限し（バックアップのリストアとプラグインのアップロードを除く）、読み書きのタイムアウトを設定します。リバースプロキシ層でもリクエストボディのサイズとタイムアウトの設定を推奨します。
- 本番ではイメージ/バイナリのバージョンを固定し、定期的にイメージの脆弱性をスキャンし、リリースのセキュリティアドバイザリに注意してください。
- 80/443 などの特権ポートを使用する場合は、リバースプロキシによる転送を優先し、バイナリへ追加のケイパビリティを与えないでください。

## 11. 制御項目のマッピング

下表は、セキュリティ/監査チームとの「製品が提供するもの、企業が補うもの」の認識合わせに使用します。認証の結論ではなく、具体的な制御項目は企業の体系と評価範囲に合わせて取捨選択する必要があります。

| 制御テーマ | LACTSSL が提供 | 企業が補う必要のあるもの |
| --- | --- | --- |
| 資産一覧 | 証明書、タスク、CA、認証情報、デプロイ記録 | CMDB との関連付け、業務の帰属、責任者 |
| アクセス制御 | 単一管理者、TOTP/パスキー、API キーのスコープ | SSO、RBAC、踏み台サーバー、承認フロー |
| 暗号技術 | AES-256-GCM のフィールド暗号化、TLS はプロキシが提供、プライベート CA | HSM/KMS、キー管理、暗号機のコンプライアンス |
| ログ監査 | 操作ログ、システムログ、ローカルアーカイブ、リクエスト ID、エクスポート | SIEM、長期保持、改ざん防止、アラートルール |
| サプライチェーン | プラグイン署名、SHA-256、インストール記録の検証 | 内部ミラー、受け入れ審査、脆弱性スキャン |
| バックアップとリストア | 暗号化 ZIP バックアップ、リストア検証、移行スナップショット | オフラインコピー、別拠点での保存、リストア演習 |
| 変更管理 | 操作ログ、アップグレードバックアップ、ロールバック手順 | 変更票、二者承認、メンテナンスウィンドウ |
| 脆弱性管理 | CI、リリース検証、依存関係の更新 | イメージスキャン、ペネトレーションテスト、パッチ SLA |
| ネットワークセキュリティ | セキュアエントリ、レート制限、SSRF 対策、信頼できるプロキシ | ファイアウォール、WAF、ゼロトラスト、egress ホワイトリスト |
| データ保持 | ログ保持設定、証明書/ログのクリーンアップ、ローカルアーカイブ | コンプライアンス上の保持期間、外部アーカイブ、改ざん防止と破棄プロセス |

## 12. 既知の制限

- マルチユーザーと RBAC は提供しません。管理者セッションは単一障害点です。
- SSO、LDAP、OIDC、SAML、SCIM は提供しません。
- HSM/KMS は提供しません。秘密鍵はローカルデータベースに暗号化して保存されます。
- デュアルアクティブクラスタは提供しません。SQLite は単一書き込みで、複数インスタンスがデータディレクトリを共有することはできません。
- 改ざん不能な監査は提供しません。管理者はログをクリアしたりローカルアーカイブを削除したりできます。高いコンプライアンス要件がある場合は外部アーカイブと WORM/保持ロックの有効化が必須です。
- Prometheus のメトリクスエンドポイントは提供しません。監視はログ、認証 API、外部からの監視に依存します。
- デプロイ先側の自動ロールバックは提供しません。対象システムで旧バージョンを保持するか、アトミックなリリースを使用する必要があります。
- 等保（中国のサイバーセキュリティ等級保護）/ISO の認証は付帯しません。コンプライアンスの結論は企業の評価機関が示します。

## 13. 導入時のセキュリティチェックリスト

### アイデンティティ

- [ ] 管理者は強力なパスワードを使用し、TOTP またはパスキーを有効にしている。
- [ ] 復旧用メールアドレスが管理下にあり、MFA が有効になっている。
- [ ] 不明なセッションをクリア済み。
- [ ] API キーはシステムごとに独立し、最小権限で、有効期限を設定している。

### ネットワーク

- [ ] 管理エントリは HTTPS のみで、バックエンドポートはインターネットへ直接公開していない。
- [ ] `trusted_proxies` と `public_url` を設定済み。
- [ ] プロキシが `X-Forwarded-For`/`X-Forwarded-Proto` を転送している。
- [ ] 送信元の制限、WAF、またはゼロトラストポリシーを設定済み。
- [ ] アウトバウンドは対象ごとのホワイトリストで、必要に応じて企業プロキシを経由している。

### データ

- [ ] `config.yaml` 0600、`data/` 0700、所有者が正しい。
- [ ] 暗号化バックアップを生成し、別拠点へ保存済み。
- [ ] バックアップパスワードとバックアップファイルを分離して保管している。
- [ ] リストア演習を 1 回完了済み。
- [ ] ログの保持とエクスポートが監査要件を満たしている。

### プラグインと ACME

- [ ] 信頼できるリポジトリ/内部ミラーのみを使用し、署名公開鍵を設定している。
- [ ] 本番では自動更新を無効にしている。
- [ ] デプロイプラグインは必要に応じて有効化し、提供元を審査済み。
- [ ] ACME エンドポイントにドメインホワイトリストを設定し、本番では EAB を有効にしている。
- [ ] ACME エントリの送信元を制限し、必要に応じて mTLS を有効にしている。

## 14. セキュリティインシデント対応

1. **範囲の確認**: アカウント、API キー、DNS/デプロイ認証情報、プラグイン、ホストのいずれか。
2. **隔離**: セッション/API キーを取り消し、プラグインを無効化し、ACME エンドポイントを停止し、必要に応じてネットワーク層で切断します。
3. **証拠保全**: 操作ログ、システムログ、リバースプロキシログをエクスポートし、`X-Request-ID` を記録します。先にログをクリアしないでください。
4. **ローテーション**: パスワードを変更するとすべてのセッションと API キーが削除されます。DNS/デプロイ/通知の認証情報をローテーションし、`salt` の漏えいが疑われる場合はキー漏えいの手順に従います。
5. **復旧**: 信頼できるバックアップからリストアし、設定とデータの一貫性を検証し、影響を受けた可能性のある証明書を再発行します。
6. **振り返り**: Runbook、権限一覧、監視ルールを更新します。

具体的なトラブルシューティング手順は[監視とトラブルシューティング](troubleshooting.md)、バックアップとリストアは[運用マニュアル](operations.md)を参照してください。
