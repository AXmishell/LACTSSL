# プラグインガバナンス

LACTSSL の DNS、証明書デプロイ、通知の機能はすべてプラグインが提供します。メインプログラムはプラグインの読み込み、一時的な helper サブプロセスの実行、インストール・有効化・アンインストールの管理のみを担当します。企業にとってプラグインは単なる拡張ではなく、**サプライチェーンの境界**です。

- DNS プラグインはドメインプロバイダーの API 認証情報を受け取ります。
- デプロイプラグインは証明書と秘密鍵を受け取ります。
- 通知プラグインはチャネルの Token/Webhook を受け取ります。
- すべてのプラグインはサービスアカウントで実行され、信頼済みコードと同等です。

したがって、プラグインは任意のユーザーがいつでもインストールできるものではなく、変更管理と受け入れ審査の対象とすべきです。

## 1. プラグインのモデル

- **種類ごとの統合パッケージ**: 公式プラグインリポジトリは種類ごとに統合パッケージをビルドします。DNS 全量・再構築、DNS 全量・lego、DNS 全量・lego v5、デプロイ、通知です。各パッケージにはその種類の複数の実装が含まれ、Go ランタイムを 1 つ共有します。
- **必要に応じたインストール**: メインプログラムのリリースパッケージにはプラグインを一切組み込みません。必要な種類の機能に応じて、対応する統合パッケージをインストールします。
- **プロトコル v1**: プラグインは実行ファイルで、`manifest`、`present/cleanup`、`deploy`、`send` などのサブコマンドでメインプログラムと通信します。
- **独立したディレクトリ**:
  - DNS: `<data_dir>/plugins/dns`
  - デプロイ: `<data_dir>/plugins/deploy`
  - 通知: `<data_dir>/plugins/notify`
- **一時的なサブプロセス**: 呼び出しごとに起動し、実行終了後に終了します。メモリに常駐しません。

## 2. リポジトリと信頼

```yaml
plugins:
  repo:
    enabled: true
    url: "https://github.com/AXmishell/LACTSSL-Plugins/releases/download/plugin-index/index.json"
    channel: stable
    auto_update: false
    public_key: "t7Q4vd0B1zh3mRf0t6Q6qlBViL7cKhoipgpGWx5WSss="
    timeout_seconds: 30
    max_download_mb: 256
    check_interval_hours: 24
```

「プラグイン」ページでリポジトリのアドレス、チャネル、自動更新、公開鍵を変更することもできます。画面での設定はデータベースに保存され、`config.yaml` より優先されますが、設定ファイルへは書き戻されません。

### 2.1 検証チェーン

1. 公開鍵が設定されている場合、`index.json.sig`（Ed25519）の検証が必須になります。
2. ローカルにキャッシュされたインデックスは、追加でサーバー側のキーによる HMAC で保護されます。
3. ダウンロード前にインデックスがアセットの SHA-256 を提供していることを要求し、欠落または形式の誤りは即座に拒否します。
4. ダウンロード後にアセットの SHA-256 を強制検証します。
5. インストール時に `plugin.json`、manifest 内の ID とバージョン、プラットフォーム、`min_host` を検証します。
6. インストール記録にファイルダイジェストを保存し、検出時、登録時、および DNS/デプロイ/通知の呼び出しごとに再確認します。ファイルが置き換えられた場合は読み込みまたは実行を拒否します。
7. いずれかのステップが失敗するとロールバックし、中途半端な状態を残しません。

署名公開鍵が未設定の場合はリスクの警告が表示され、無人での自動更新はスキップされます。本番環境では検証を無効にしないことを推奨します。

## 3. 企業でのデプロイモデル

### 3.1 公式リポジトリへの直接接続

適用: ネットワークから GitHub にアクセスでき、プラグインの数が少なく、公式リポジトリを信頼の源として受け入れられる場合。

要件:

- 公式の公開鍵を設定し、検証を必須にする。
- 自動更新を無効にし、変更ウィンドウに従って手動でアップグレードする。
- インストール/アップグレードのたびにバージョンとダイジェストを記録する。

### 3.2 内部ミラー（推奨）

適用: 本番環境、オフライン/半オフライン、バージョン固定と受け入れ審査が必要な場合。

方法 1: インデックスを内部の HTTPS ミラーへ向けます。

```yaml
plugins:
  repo:
    url: "https://mirror.example.com/lactssl-plugins/index.json"
    public_key: "<企業の署名公開鍵>"
```

方法 2: オフラインディレクトリ:

```yaml
plugins:
  repo:
    url: "file:///srv/lactssl-plugins/index.json"
```

内部ミラーでは次を満たしてください。

- 公式のインデックスとアセットを同期し、元の SHA-256 を保持する。
- 企業自身の Ed25519 キーでインデックスに再署名する、または少なくとも公式署名を検証してから提供する。
- 受け入れ済みのバージョンのみを同期し、`latest` を自動で追従しない。
- ミラーディレクトリは読み取り専用とし、同期アカウントのみが書き込めるようにする。
- バージョン、提供元、ダイジェスト、承認者、ロールバックバージョンを記録する。

### 3.3 手動アップロード

「プラグイン」ページで単一の helper をアップロードするか、ファイルをプラグインディレクトリへ置いて再スキャンできます。一時的な検証やサードパーティ製プラグインに適しています。

- アップロードは単一の helper 実行ファイルのみを受け付け、最大 256 MB です。
- アップロード後はまず一時ファイルとして `manifest` を検査し、プロトコル、ID、SHA-256 を検証し、通過後にプラグインディレクトリへ書き込んで再スキャンします。
- 既定では同名ファイルの上書きを拒否します。アップグレード時には「同名プラグインの上書きを許可」をチェックでき、旧ファイルは先にバックアップされます。
- 手動でアップロードしたプラグインは `manual` とマークされ、公式リポジトリのアップグレード対象にはなりません。
- 信頼できるファイルのみをアップロードしてください。helper はサービスアカウントで実行されます。

## 4. インストールと有効化

### 4.1 インストール

1. 「プラグイン」ページを開き、リポジトリのアドレスを確認して「インデックスを更新」をクリックします。
2. 「プラグインマーケット」を開き、DNS / デプロイ / 通知で絞り込むか検索します。
3. 必要なプラグインをインストールします。完了後、まずプラグインファイルを有効にし、次に必要に応じてその中の項目を有効にします。

各プラグインには次が表示されます。

- 名前、ID、バージョン、サイズ。
- 現在のプラットフォームにインストールパッケージがあるか。
- 現在のホストバージョンと互換性があるか。
- インストール済みバージョンと更新可能な状態。

新しくダウンロードまたはアップロードしたプラグインは既定で無効です。helper ファイルは無効状態で保存され、`manifest` は実行されません。ファイルを有効にしても、その中の項目は引き続き既定で無効です。アップグレードまたは同名ファイルの上書きでは元の有効状態が保持されます。

### 4.2 二段階の有効化

プラグインページの各行は 1 つの helper ファイルに対応し、有効状態は 2 層に分かれます。

1. **ファイルレベル**: 行頭のスイッチで helper が検出と読み込みに参加するかを制御します。無効にするとそのファイルの `manifest` は実行されず、中の項目もランタイムへ登録されません。既存の項目のチェックは保持され、ファイルを再度有効にすると復元されます。
2. **項目レベル**: 「項目を管理」をクリックして、プロバイダー、デプロイ先、通知チャネルを個別に有効化します。チェックして一括で有効化/無効化することもできます。新しくインストールしたプラグインの項目は引き続き既定で無効です。

説明:

- ファイルが無効な場合もその項目は表示されます（ホストがキャッシュした manifest の概要に由来）が、スイッチはグレーアウトし、先にファイルを有効にする必要があります。
- 統合パッケージ（例: 194 の項目を提供する `lactssl-dns-all-native`）は、行頭のスイッチで一度にすべて有効化されることはありません。一度に 10 を超える項目を有効化する場合は確認を求められます。
- ファイルを削除するかプラグインをアンインストールすると、manifest のキャッシュ、ファイルレベルの状態もクリアされ、項目のホワイトリストからそのファイルのすべての項目が削除されます。

## 5. 更新、ロールバック、アンインストール

- **更新**: プラグインマーケットで「更新」をクリックするか、自動更新を有効にした場合は `check_interval_hours` に従って定期的にチェックします。
- **一括更新**: `POST /api/plugins/repo/update` の空のリクエストボディは、インストール済みのすべてのプラグインを更新することを意味します。
- **ロールバック**: 本番では内部ミラーに前のバージョンを保持することを推奨します。アップグレードに失敗した場合は旧バージョンを再インストールします。
- **アンインストール**: プラグインリポジトリからインストールしたプラグインのみアンインストールできます。アンインストールはプラグインファイルとインストール記録を削除し、有効化ホワイトリストからも削除します。
- **ファイルの削除**: 各プラグインタブにはプラグインディレクトリ内の実際の helper ファイル（手動アップロードと旧版の全量バンドルを含む）が一覧表示され、直接削除できます。削除するとそのファイルが提供するすべての項目、インストール記録、有効状態が削除され、即座に再スキャンされます。

アップグレードは「ダウンロード → 検証 → バックアップ → アトミックな置き換え → manifest 検証」の流れで行われ、いずれかのステップが失敗すると旧ファイルが復元されます。

### 5.1 変更プロセスの推奨

1. ステージング環境で対象バージョンをインストールします。
2. `manifest`、項目一覧、主要経路（DNS 発行、デプロイ、通知）を検証します。
3. バージョン、ダイジェスト、テスト結果を記録します。
4. 本番の変更ウィンドウ内でアップグレードし、タスクログを観察します。
5. 失敗した場合はミラー内の前のバージョンへロールバックします。

## 6. パッケージサイズとリソース

プラグインマーケットに表示されるサイズは**展開後**の値、つまりディスクへインストールされる実際の helper のサイズです。現在の公式統合パッケージ（linux/amd64）は概ね次のとおりです。

| パッケージ | 展開後 |
|---|---:|
| DNS 全量・再構築（194 プロバイダー） | 約 18 MiB |
| DNS 全量・lego（194 プロバイダー） | 約 58 MiB |
| DNS 全量・lego v5（235 項目） | 約 37 MiB |
| デプロイ（25 ターゲット） | 約 8 MiB |
| 通知（23 チャネル） | 約 7 MiB |

- ほとんどのユーザーは約 18 MiB の DNS 全量・再構築パッケージをインストールすれば、194 のプロバイダーをすべてカバーできます。
- 完全な lego v4 の機能（例: rfc2136 GSS-TSIG）が必要な場合は、約 58 MiB の DNS 全量・lego パッケージをインストールします。
- lego v5 と新しいプロバイダーに追随したい場合は、約 37 MiB の DNS 全量・lego v5 パッケージをインストールします。3 つの DNS パッケージは排他です。
- すべてをインストールしても約 73 MiB で、224 の単体プラグインパッケージの展開後総量約 1.7 GiB より約 96% 少なくなります。

インストール/更新時の展開は瞬間的なメモリピークを伴います。容量計画には余裕を見てください。[デプロイ構成](architecture.md)を参照してください。

## 7. 旧版全量プラグインの移行

アップグレード前に `lactssl-dns-helper-extra`、`lactssl-deploy-helper`、`lactssl-notify-helper` を使用していたデプロイでは、「プラグイン」ページに移行の案内が表示されます。

1. システムは旧プラグインの manifest を読み取り、現在有効な、またはアカウント/タスクでまだ使用されているプロバイダーを特定します。
2. 対応する統合パッケージをダウンロードしてインストールします。統合パッケージは旧版の単一プロバイダー/旧全量 helper を上書きします。
3. すべて成功したら旧ファイルを削除して再スキャンします。
4. いずれかのステップが失敗した場合は今回のインストールをロールバックし、旧プラグインは引き続き利用できます。

移行が完了するまで旧プラグインは削除されず、発行中のサイトの中断を避けます。

## 8. プロバイダーのアイコン

DNS とデプロイのプロバイダーのロゴはプラグインのメタデータに属し、プラグインリポジトリから配信されます。メインプログラムはアイコンテーブルを内蔵しなくなりました。

- **未インストール時**: リポジトリのインデックスの `icons` にアイコンをインラインで含め、インデックスの署名検証の対象としてプラグインマーケットの表示に使用します。
- **インストール後**: プラグインパッケージ内の `icons/` が `<data_dir>/plugin-icons/<kind>/<プラグイン ID>/` へ書き込まれ、ネットワークが切断された場合やリポジトリを無効にした後でも認証情報ページで表示できます。
- **読み取りインターフェース**: フロントエンドは `GET /api/plugins/icons` で一括取得します。アイコンが提供されていない場合、アイコンが破損している場合、旧バージョンのホストの場合は頭文字のアバターへフォールバックします。
- **エイリアス**: `aliyun_cdn`、`baota_site`、`qiniu_kodo` などの履歴的な ID は、リポジトリの `assets/icons/icons.json` によって正規のアイコンへマッピングされます。
- **統合パッケージのアイコン**: パッケージ ID に対応するパッケージレベルのアイコンのみを使用します。パッケージレベルのアイコンが提供されていない場合は表示しないか、パッケージの項目が `hide_icon: true` を宣言して強制的に無効化します。

アイコンは svg / png / webp のみ許可され、1 枚あたり 64 KB 以下です。不正な項目は破棄され、プラグインのインストールやアップグレードには影響しません。

## 9. セキュリティ制御

- 信頼できるリポジトリのみを使用し、本番では署名公開鍵を設定して検証を必須にします。
- ダウンロード前にアセットの SHA-256 を要求し、インストール後にファイルダイジェストを再確認します。
- デプロイプラグインは秘密鍵に触れるため、既定で無効とし、信頼できる提供元のもののみをインストールします。
- プラグインディレクトリは `0700`、helper は `0755` で、グループやその他のユーザーの書き込みを許可しません。
- シンボリックリンクは許可せず、ファイルが置き換えられた場合は読み込みを拒否します。
- `memory_limit_mb`、`timeout_seconds`、`max_output_kb` を制限し、異常なプラグインがホストを圧迫するのを防ぎます。
- プラグインはサービスアカウントで実行されます。`lactssl` ユーザーへ追加の権限を与えず、プラグインディレクトリを共有書き込み可能なパスに置かないでください。
- プラグインのインストール/アップグレード/アンインストール操作を記録し、変更監査の対象とします。

## 10. API

| メソッド | パス | 説明 |
|---|---|---|
| GET | `/api/plugins` | プラグインの状態、項目、ディレクトリ内の helper ファイル |
| GET | `/api/plugins/repo` | リポジトリの設定とインデックスの状態 |
| PUT | `/api/plugins/repo` | 設定を変更 |
| POST | `/api/plugins/repo/refresh` | インデックスを強制更新 |
| GET | `/api/plugins/repo/plugins` | リポジトリのプラグイン一覧 |
| POST | `/api/plugins/repo/install` | `{kind,id,version}` をインストール |
| POST | `/api/plugins/repo/update` | `{kind,id}` またはすべてを更新 |
| DELETE | `/api/plugins/repo/plugins/:kind/:id` | アンインストール |
| DELETE | `/api/plugins/files/:kind/:file` | プラグインディレクトリ内の helper ファイルを削除 |
| GET | `/api/plugins/repo/legacy` | 旧版全量プラグインを検出 |
| POST | `/api/plugins/repo/migrate` | `{kind}` を移行 |

プラグイン管理には `plugins:read` / `plugins:write` が必要です。アップロード、インストール、更新、アンインストール、リポジトリ設定の変更はすべて機密性の高い操作です。

## 11. トラブルシューティング

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| インデックスの取得に失敗 | リポジトリのアドレス、ネットワークプロキシ、TLS 証明書 | まずブラウザで `index.json` へアクセス。egress ポリシーを確認 |
| 署名の検証に失敗 | 公開鍵とリポジトリの署名キーの不一致 | 公開鍵を照合。本番で `public_key` を安易に空にしない |
| プラットフォームが利用不可 | 現在のプラットフォームに対応するプラグインパッケージがない | `GOOS/GOARCH` とインデックスの `assets` を確認 |
| ホストバージョンが非互換 | プラグインの `min_host` が現在のバージョンより高い | ホストをアップグレードするか互換バージョンをインストール |
| ID の競合 | 同じプロバイダーが旧バンドルまたは手動プラグインで提供済み | 移行を完了するか旧ファイルをアンインストール |
| インストール後に表示されない | 対応するプラグインの種類が無効、または項目が無効 | `plugins.enabled`、`deploy_plugins.enabled`、`notify_plugins.enabled` と項目のスイッチを確認 |
| ファイルが拒否される | グループ/その他のユーザーが書き込み可能、シンボリックリンク、ダイジェストの不一致 | 権限を修正するか再インストール |

その他のトラブルシューティングは[監視とトラブルシューティング](troubleshooting.md)を参照してください。

## 12. プラグイン受け入れチェックリスト

- [ ] 提供元: 公式リポジトリまたは企業内部ミラーで、バージョンが固定されている。
- [ ] 完全性: インデックス署名、アセットの SHA-256、インストール記録のダイジェスト検証に通過している。
- [ ] 権限: プラグインディレクトリとファイルの権限が要件を満たしている。
- [ ] リスク: デプロイプラグインが秘密鍵に触れるか、通知プラグインが長期 Token を保持しているか。
- [ ] 互換性: ホストバージョン、プラットフォーム、`min_host` が一致している。
- [ ] テスト: ステージング環境で DNS/デプロイ/通知の経路を検証済み。
- [ ] ロールバック: 前のバージョンとロールバック手順を保持している。
- [ ] 記録: バージョン、ダイジェスト、承認者、インストール日時、変更票。
