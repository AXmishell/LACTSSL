# 管理ワークスペース

本文は LACTSSL 管理者を対象に、アカウント、権限、キー、監査、日常運用の組織方法を説明します。製品は現在**単一管理者 + API キーによる権限分離**モデルであり、企業はこのモデルを中心に職位とプロセスを設計する必要があります。

## 1. 運用モデル

### 1.1 3 種類のアイデンティティ

| アイデンティティ | 機能 | 対象 |
| --- | --- | --- |
| 管理者アカウント | ブラウザログイン後にすべての操作を実行可能。秘密鍵のエクスポート、バックアップの復元、設定の変更を含む | プラットフォーム責任者（職位アカウント） |
| API キー | `リソース:アクション` で認可。自動化と読み取り専用連携に適する | CI/CD、巡回、CMDB、デプロイスクリプト |
| ACME クライアントアカウント | 特定の ACME エンドポイントのみにアクセス。EAB/ドメイン許可リストで制限 | certbot、lego、acme.sh など |

管理者アカウントは単一障害点であり、個人ではなく職位に紐づける必要があります。API キーは人手による承認の代替にはならず、アカウントセキュリティ系のインターフェース（パスワード変更、パスキー、セッション管理など）にもアクセスできません。

### 1.2 推奨される職責分離

| 職責 | 推奨される所属 | 管理者アカウントを使用するか |
| --- | --- | --- |
| 日常の証明書発行とデプロイ | プラットフォーム/運用 | はい、または制限付き API キーを使用 |
| DNS/デプロイ資格情報の保管 | 該当システムの責任者 | いいえ、資格情報は管理者が登録し、必要に応じてローテーション |
| 自動化連携 | 連携開発 | いいえ、独立した API キーを使用 |
| セキュリティ監査 | セキュリティ/監査 | いいえ、`logs:read` / `system_logs:read` の読み取り専用キーを使用 |
| バックアップ復元 | 運用責任者 | はい、復元はサービスを再起動する |
| プラグインとアップグレード | プラットフォーム責任者 | はい、高権限の変更に該当 |

企業が二人確認を要求する場合は、プロセス層で実装する必要があります（変更票、踏み台サーバー、承認システムなど）。製品自体は組み込みの承認フローを提供しません。

## 2. 初期化と引き継ぎ

### 2.1 初期化

1. 起動ログのセキュアエントリから入ります。
2. ワンタイム初期化トークンで管理者を作成します。
3. 直ちに TOTP またはパスキーを有効化します。
4. 復旧メールアドレスを設定して検証します。
5. `security.public_url`、信頼するプロキシ、ログを設定します。
6. 最初の暗号化バックアップを作成し、復旧パスワードが使用できることを確認します。
7. 必要なプラグインをインストールして有効化します。

### 2.2 職位の引き継ぎ

引き継ぎ時に少なくとも以下を完了します：

- 管理者パスワード、TOTP シード、パスキーデバイスの移管。
- 復旧メールアドレスの管理権の移管。
- API キー一覧の照合：用途、権限、有効期限、責任者。
- DNS/デプロイ/通知資格情報の一覧照合。
- バックアップ場所、復旧パスワード、直近の復旧訓練記録。
- 未完了のタスク、監視項目、アラートルーティングの説明。

チャットツールで平文のパスワード、API キー、バックアップパスワードを送らないでください。企業のパスワードマネージャーまたは密封引き継ぎプロセスを使用します。

## 3. アカウントセキュリティ

### 3.1 ログイン方式

- パスワードは bcrypt ハッシュで保存され、長さは 8 文字以上。本番では 16 文字以上のランダムパスワードを推奨。
- TOTP 有効化後、パスワードログインでも動的コードが必要です。同じコードは有効ウィンドウ内で再利用できません。
- パスキー（WebAuthn/Passkey）は追加のログイン方式として利用できますが、パスワードの代替にはなりません。HTTPS ドメインまたは localhost で使用する必要があります。
- パスワード変更はトークンバージョンを上げ、サーバー側のすべてのセッション、API キー、パスキーを削除し、すべてのログインが即座に無効になります。
- メールによるパスワードリセットは TOTP を無効化し、パスキーと API キーを削除します。認証器を失った場合の復旧手段として機能します。

### 3.2 セッション

- デフォルトではサービス起動のたびにサーバー側セッションをクリアし JWT サブキーをローテーションするため、再起動後に再ログインが必要です。
- `security.session_persistence: true` を設定すると、バックグラウンド再起動後もセッションを保持します。可用性は向上しますがセッション寿命も延びるため、企業ポリシーと合わせて判断してください。
- 「設定 → セッション」で定期的に不明なデバイスを確認し、取り消します。
- ログイン済みセッションは管理者権限と同等です。共有ブラウザや信頼できないデバイスでログインを維持しないでください。

### 3.3 復旧パス

少なくとも 2 つの独立した復旧パスを準備します：

1. **メールリセット**：パスワードを忘れたがメールを管理できる場合に適用。TOTP、パスキー、API キーをクリアします。
2. **バックアップ復元**：アカウント、データベース、設定が破損した場合に適用。バックアップの復号パスワードと初期化トークン（未初期化インスタンス）が必要です。

復旧手順を Runbook に書き、定期的に訓練してください。復旧パスワードとバックアップファイルを同じ場所に置かないでください。

## 4. API キーガバナンス

API キーはマシン ID に適しており、人には適していません。「1 システム 1 キー」で管理することを推奨します。

### 4.1 ロールから権限へのマッピング

| 利用者 | 推奨権限 | 説明 |
| --- | --- | --- |
| 読み取り専用巡回/CMDB | `system:read`、`dashboard:read`、`certificates:read`、`tasks:read`、`monitors:read`、`deployments:read` | `*:write` は一切付与しない |
| 証明書一覧の同期 | `certificates:read`、`tasks:read` | 秘密鍵権限は付与しない |
| CI/CD による更新トリガー | `tasks:read`、`tasks:run`。デプロイノードを含む場合は `deploy:execute` も追加 | タスク範囲で制御 |
| 証明書のダウンロードと配布 | `certificates:read`、`certificates:key`、`deploy:execute` | 高機密。送信元と有効期限を必ず制限 |
| ログ監査 | `logs:read`、`system_logs:read` | 読み取り専用キー、短い有効期限を設定 |
| 監視アラート | `system:read`、`monitors:read` | `/api/status` と監視の読み取りに使用 |
| プラットフォーム自動化 | 実際の必要に応じて組み合わせ、`*` は避ける | `*` はすべてのシステム機能と同等 |

### 4.2 ライフサイクル

1. 用途、責任者、権限、有効期限を登録します。
2. 作成後直ちに企業のパスワードマネージャーまたはキー管理システムへ保存し、コードリポジトリへ平文で残さない。
3. 呼び出し元にキーを設定し、最小権限を検証します。
4. 期限前にローテーションし、ローテーション後は旧トークンが即座に無効になります。
5. システム廃止または担当者変更時に直ちに無効化/削除します。

### 4.3 保護要件

- キーをログ、スクリーンショット、チケット、公開リポジトリに置かない。
- HTTPS でのみ送信し、信頼できないプロキシを経由しない。
- キーに送信元 IP 制限を設定します（ネットワーク層またはゲートウェイ層で実装）。
- `api_keys:read` 権限のキーを定期的に確認し、権限の拡散を防ぎます。
- 漏洩が疑われる場合は直ちにローテーションまたは削除し、操作ログの異常な呼び出しを確認します。

> API キーはパスワード変更、パスキーのバインド、他のセッションのログアウトはできません。これらの操作はブラウザのログインセッションのみ許可されます。

## 5. 証明書と CA のガバナンス

### 5.1 パブリック CA

- ACME アカウントには専用メールアドレスを使用し、個人メールを紐づけない。
- CA ごとに EAB 資格情報を管理し、アクセス範囲を制限。
- CA のレート制限とドメイン検証要件に注意し、重要なドメインには予備 CA を準備。
- 汎用 ACME アップストリームは HTTPS を使用する必要があります（ローカルループバックを除く）。

### 5.2 プライベート CA

- ルート CA の秘密鍵は中間 CA の署名にのみ使用し、エンドエンティティ証明書の直接署名は推奨しません。
- 中間 CA にはパス長、Key Usage、Name Constraints、有効期間を設定します。
- ルート CA の秘密鍵はエクスポート後オフラインで保管すべきです。LACTSSL データベース内の秘密鍵は `security.salt` で保護されますが、HSM ではありません。
- CA を削除する前に、下位 CA と依存証明書がないことを確認します。
- 既存の証明書は CRL/OCSP 拡張を自動的に取得しないため、再発行が必要です。

### 5.3 ACME サーバー

- 各エンドポイントは 1 つのプライベート CA にバインドし、ドメイン許可リストを設定します。
- 本番ではデフォルトで EAB を有効化します。EAB を無効にすると、エンドポイントにアクセスできる誰もがアカウントを作成できます。
- パブリックネットワークのエンドポイントは専用ポート、送信元制限、mTLS（クライアントが対応する場合）を使用します。
- 無効なオーダーと長期間未使用のアカウントを定期的にクリーンアップします。アカウントのクリーンアップは履歴オーダーを削除しますが、発行済み証明書には影響しません。

## 6. プラグインとサプライチェーン

- 公式リポジトリまたは企業の社内ミラーのみを使用してください。
- Ed25519 公開鍵を設定し署名検証を強制します。未設定の場合 UI がリスクを表示し、無人自動更新をスキップします。
- 本番では自動更新を無効にし、変更ウィンドウに従って手動でアップグレードします。
- デプロイプラグインは証明書の秘密鍵に触れるため、デフォルトで無効です。信頼できるヘルパーのみ有効化します。
- プラグインディレクトリは `0700`、ヘルパーは `0755`、所有者はサービス実行ユーザー。
- ロールバックのためにプラグインのバージョン、インストール時刻、変更記録を保持します。

詳細なフローは[プラグインガバナンス](plugins.md)を参照してください。

## 7. 監査と証跡

LACTSSL は 2 種類のログを提供します：

| ログ | 内容 | 用途 |
| --- | --- | --- |
| 操作ログ | タスク、証明書、デプロイ、通知、監視、設定変更 | 業務監査、変更追跡 |
| システムログ | 起動、HTTP、スケジューリング、プラグイン、ACME などのプロセスログ | 運用トラブルシューティング、セキュリティインシデント分析 |
| プロセスログ | stdout または `log.file` | ログプラットフォームでの収集、panic 分析 |

推奨：

- 操作ログは少なくとも 90 日保持します（エクスポート範囲の上限）。より長い保持が必要な場合は企業のログプラットフォームへ定期的にエクスポートします。
- システムログはデフォルトで 7 日または 20,000 行を保持し、コンプライアンス要件に応じて `log.system.retention_days` と `max_rows` を調整します。
- リバースプロキシのアクセスログは独立して保存し、送信元 IP、ステータスコード、`X-Request-ID` を記録します。
- CSV エクスポート時は数式インジェクション対策に注意し、資格情報を含むログを外部へ送らないでください。
- 重要な変更（CA 生成、秘密鍵エクスポート、バックアップ復元、プラグインインストール、セキュアエントリ変更）には変更票またはチケットを関連付けます。

## 8. 日常運用チェックリスト

### 毎日

- [ ] タスク失敗、デプロイ失敗、証明書異常のアラートを確認する。
- [ ] サイト監視の異常/期限間近項目を確認する。
- [ ] バックアップタスクの成功を確認する（外部スケジューラの場合）。

### 毎週

- [ ] 期限間近の証明書と自動更新状態を確認する。
- [ ] システムログのエラー、レート制限、異常ログインを確認する。
- [ ] 追加/無効化した API キーと資格情報を照合する。

### 毎月

- [ ] ディスク、データベースサイズ、WAL、ログ保持を確認する。
- [ ] プラグインバージョンとセキュリティアドバイザリを確認する。
- [ ] 操作ログと変更記録が一致しているか抜き打ち確認する。
- [ ] 通知チャネルの到達性を検証する。

### 四半期ごと

- [ ] バックアップ復旧訓練を 1 回完了する。
- [ ] 管理者アカウント、復旧メール、TOTP/パスキーを確認する。
- [ ] API キーの権限と有効期限を再確認する。
- [ ] アップグレードウィンドウとロールバック計画を評価する。

## 9. 変更管理

高リスク操作は変更票を経由することを推奨します：

| 操作 | リスク | 推奨される統制 |
| --- | --- | --- |
| セキュアエントリの変更 | 管理エントリがロックされる可能性 | 新しいエントリを記録し、`config.yaml` による上書き方法を保持 |
| `security.salt` の変更 | 既存の暗号化資格情報を復号できない | 無断変更を禁止。移行を伴う必要がある |
| プライベート CA の削除 | 下位 CA と依存証明書に影響 | 先に依存関係を確認し、バックアップをエクスポート |
| バックアップの復元 | 現在のデータを上書きして再起動 | 二人確認、低負荷時間帯を選択 |
| デプロイプラグインのインストール | 証明書の秘密鍵を読み取れる | ソースレビュー、署名検証、最小権限 |
| プログラムのアップグレード | データ移行は不可逆 | バックアップ、ステージング検証、ロールバック計画 |
| 証明書/ログの一括クリーンアップ | データは復旧不可 | 先にプレビュー、エクスポート、二人確認 |
