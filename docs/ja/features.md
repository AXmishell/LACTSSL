# 製品機能

本文は業務機能ごとに LACTSSL ができること、主要パラメータ、制限を説明し、設計と受け入れに役立てます。具体的な操作手順は[クイックスタートと本番導入](getting-started.md)、[管理ワークスペース](administration.md)、[API 連携](api.md)に分かれています。

## 機能マップ

| 機能領域 | 主な内容 | 主な利用者 |
| --- | --- | --- |
| 証明書資産 | パブリック CA 申請、自動更新、証明書の詳細とクリーンアップ | プラットフォーム/運用 |
| タスク編成 | 通常フロー：申請 → デプロイ（複数可）→ 通知、ターゲットフロー Beta：サイト読み取り → 証明書グループ → 申請 → デプロイ | プラットフォーム/運用 |
| 証明書配信 | ローカルディレクトリ、SSH/SFTP、FTP、Webhook、クラウド CDN、パネル | プラットフォーム/運用、業務システム |
| 社内 PKI | プライベート CA の生成/インポート、階層、CRL/OCSP アドレス | セキュリティ、インフラ |
| ACME サーバー | 社内向けに標準 ACME v2 エンドポイントを提供 | 社内プラットフォーム、デバイス、テスト環境 |
| 監視とアラート | 外部サイト証明書監視、タスク/デプロイ通知 | 運用、当番 |
| 監査と復旧 | 操作ログ、システムログ、暗号化バックアップ | セキュリティ、監査、運用 |
| 連携 | API キー、REST API、自動化 | 連携開発 |

## 1. 証明書の申請と更新

### 1.1 検証方式

- パブリック CA への申請は **DNS-01** 検証のみを使用し、単一ドメイン、複数ドメイン、ワイルドカード証明書に対応します。
- DNS-01 では「DNS アカウント」でプロバイダーの API 資格情報を設定する必要があり、タスク実行時に TXT レコードを自動で作成/削除します。
- プライベート CA による署名は ACME 検証を経ず、システムが直接署名します。
- 内蔵 ACME サーバーは HTTP-01、DNS-01、TLS-ALPN-01 に対応し、社内クライアントに提供します。

### 1.2 内蔵認証局

| CA | 説明 |
| --- | --- |
| Let's Encrypt | デフォルトのパブリック CA、EAB 不要 |
| ZeroSSL | EAB が必要 |
| Google Trust Services | EAB が必要 |
| LiteSSL | EAB が必要 |
| ZoTrus | EAB が必要（KID は登録メールアドレス）。手動 DNS 検証を使用し、ワイルドカードには未対応 |
| Actalis | EAB が必要 |
| SSL.com | EAB が必要（鍵種別に応じて ECDSA/RSA エンドポイントを自動選択） |

「パブリック認証局」では複数の**汎用 ACME アップストリーム**を追加できます：

- ACME ディレクトリアドレス、ACME v1/v2 プロトコルバージョン、任意の EAB を設定します。
- 汎用アップストリームはタスクとデフォルト CA の選択リストに表示されます。
- カスタムディレクトリアドレスは HTTPS を使用する必要があり、ローカルループバックのみ HTTP を許可します。
- ACME v1 は DNS-01 のみ対応し、EAB はサポートしません。

### 1.3 キーと更新

- 秘密鍵の種類：`ecdsa`（デフォルト）、`ecdsa384`、`rsa2048`、`rsa4096`。
- 自動更新はデフォルトで期限前 30 日にトリガーされ、タスクごとに調整できます。
- 申請ノードで「証明書の秘密鍵をサーバーに保存しない」を選択できます。秘密鍵は今回の発行とデプロイ中のみメモリ上に保持され、データベースには保存されず、ダウンロードもできません。自動更新時は再発行して再デプロイします。標準フローでは有効なデプロイモジュールが少なくとも 1 つ必要です。
- バックグラウンドスケジューラは 30 秒ごとに期限タスクを確認します。
- タスク失敗の原因はタスクログで確認できます。資格情報、ドメイン、CA の問題は明確なエラーが表示されます。
- 証明書管理ページは検索、状態フィルター、ソース（タスク発行、ACME サーバー、CSR リクエスト）フィルター、詳細、セキュリティ分析に対応します。
- 証明書チェーンのダウンロード、秘密鍵の表示またはダウンロードはすべてログインセッションに依存します。API で証明書チェーンをダウンロードするには `certificates:read`、秘密鍵の表示またはダウンロードには `certificates:key` も必要です。
- ワンクリッククリーンアップは状態（期限切れ、失効済み、すべて）、期間、発行時刻、ドメイン、発行機関、ソース、「各タスクの最新証明書を保持」で絞り込めます。クリーンアップ後、関連タスクの証明書参照はクリアされます。

### 1.4 デフォルト設定

「パブリック認証局」では以下を設定できます：

- ACME アカウントのメールアドレス。
- デフォルト CA。
- デフォルトの秘密鍵種別。
- デフォルトの更新日数。
- 各 CA の EAB 資格情報。

### 1.5 ターゲットフロー Beta

ターゲットフロー Beta は「証明書をパネルの Web サイトに追従させる」シナリオに適しています：まずデプロイプラグインの `plan` 機能でターゲット内の実際の Web サイトとバインドされたドメインを読み取り、次にポリシーに従ってグループ化して証明書を申請し、最後に対応する Web サイトへデプロイします。

- タスクページでは「すべて / 通常フロー / ターゲットフロー Beta」タブで 2 種類のフローを分離し、新規作成/編集ダイアログでも同じ切り替え UI を使用します。
- 複数のサイトソースに対応し、Web サイト一覧はターゲットシステムから取得され、サイト名の手入力に依存しません。
- 証明書割り当てポリシー：
  - スマート推奨：サイト数、ドメイン数、メインドメインの分布に基づいて自動選択。
  - 1 サイトにつき 1 証明書。
  - メインドメインごとに統合。
  - 選択したすべてのサイトを 1 枚の証明書に統合。
  - ターゲットソースごとに 1 枚の証明書。
  - カスタムグループ：任意のサイトを手動で同じ証明書グループに組み合わせ。
- サイトの選択、ドメインの包含/除外ルール、追加ドメインの付加に対応します。
- 自動更新時はターゲットサイトを再読み取りします：`すべてのサイト` モードでは新しいサイトが自動的に含まれ、`選択したサイトのみ` モードでは保存済みの安定したサイトキーのみを保持します。
- 1 つの Beta タスクに複数の証明書を関連付けられます。`certificates.task_id` はすべての証明書を保持し、タスク一覧にはサイト/証明書グループの概要が表示されます。
- ワンクリッククリーンアップで「各タスクの最新証明書を保持」を有効にすると、Beta タスクの証明書はクリーンアップされず、同じタスクの他の証明書グループを誤って削除することを防ぎます。

### 1.6 クライアント CSR 申請

- API はクライアントからの CSR 提出に対応し、サーバーは中間としてパブリック認証局への DNS-01 検証を完了して証明書を発行します。
- サーバーは秘密鍵を生成も保存もしません。証明書はクライアント CSR の公開鍵にバインドされ、秘密鍵は常にクライアントが保持します。
- 申請は非同期で実行され、状態の照会、キャンセル、再試行、申請単位での証明書チェーンのダウンロードが可能です。
- ACME v2 パブリック認証局と DNS-01 のみに対応します。ワイルドカード証明書は DNS-01 を使用する必要があります。
- 新しい API キー権限 `certificates:request` が必要で、`csr.allowed_domains` で申請可能なドメインを制限できます。

## 2. DNS プロバイダー

DNS プロバイダーは DNS プラグインが提供します。メインプログラムにはプロバイダーが内蔵されておらず、プラグインをインストールして有効化するとプロバイダー一覧が表示されます。

よく使うプロバイダーと資格情報：

| プロバイダー | 主な資格情報 |
| --- | --- |
| 阿里云 DNS（alidns） | AccessKey ID / Secret、任意で Region |
| 阿里云 ESA（aliesa） | AccessKey ID / Secret、任意で Region |
| Cloudflare | API Token、または Email + Global API Key、任意で API アップストリームアドレス |
| DNSPod | API Token |
| 腾讯云（tencentcloud） | SecretId / SecretKey、任意で Region |
| 华为云（huaweicloud） | AccessKey ID / SecretAccessKey / Region |
| 火山引擎（volcengine） | AccessKey / SecretKey、任意で Region、API ホストとプロトコル |
| AWS Route 53 | AccessKey / SecretAccessKey、任意で Region、Hosted Zone、プライベートゾーン |
| Google Cloud DNS | サービスアカウント JSON、任意でプロジェクト ID |
| Azure DNS | Tenant ID / Client ID / Client Secret / Subscription ID / リソースグループ |
| 西部数码（westcn） | ユーザー名 / パスワード |
| PowerDNS（pdns） | API アドレス / API Key、任意で Server 名と API バージョン |
| RFC 2136 動的更新 | DNS サーバー、任意で TSIG Key / Secret / アルゴリズムと Zone リスト |

- 公式 DNS プラグインをインストールすると lego のすべてのプロバイダー（約 190 社）に対応します。
- `manual` プロバイダーは TXT レコードの手動追加が必要で、自動フローには含まれません。
- 資格情報はデータベースへ書き込む前に暗号化されます。編集時にキー項目を空にすると既存値を保持します。
- Cloudflare、DNSimple、PowerDNS、火山引擎などはカスタム API アップストリームアドレスに対応し、プロキシ、自前サービス、互換ゲートウェイに利用できます。
- 完全なプロバイダー一覧は「DNS アカウント」ページのプロバイダードロップダウンを基準とします。

プラグインのインストール、オフラインミラー、サプライチェーンガバナンスは[プラグインガバナンス](plugins.md)と[DNS プラグイン](dns-plugins.md)を参照してください。

## 3. タスク編成

タスクはノードで構成され、デフォルトフローは「申請 → デプロイ（複数可）→ 通知」です。

| ノード | 主要パラメータ |
| --- | --- |
| 申請 | ドメイン、DNS アカウント、CA、秘密鍵種別、自動更新、事前日数 |
| デプロイ | ターゲット資格情報、証明書/秘密鍵パス、サイト/ドメイン/証明書名、リロードコマンド |
| 通知 | チャネル、トリガータイミング（常に / 成功時のみ / 失敗時のみ） |

要点：

- ノードは有効/無効の切り替えと並べ替えができ、タスクには複数のデプロイノードを含めて同じ証明書を複数のターゲットへ配信できます。
- 明示的なフローがない旧タスクでは、システムが既存のドメイン、ターゲット資格情報などのフィールドから同等のフローを推測します。
- アップグレード時は旧資格情報のデプロイパス、サイト、ドメインをタスクのデプロイノードへ移行し、その後資格情報のデプロイパラメータをクリーンアップします。
- タスク一覧はヘッダーの全選択と複数選択に対応し、一括実行、一時停止、自動更新の開始が可能です。
- 一括実行は実行中のタスクをスキップします。一括の有効化/停止はスケジュール状態のみを調整し、開始済みの発行を中断しません。
- 実行前には有効期間内かつ更新ウィンドウに入っていない同一ドメインの証明書を再利用し、デプロイのみを再実行します。再発行が必要な場合は「強制再発行」または API の `?force=1` を使用します。アップストリーム CA のレート制限時はタスクが「レート制限待ち」になり、CA が示す復旧時刻に再試行し、通常の失敗のように 6 時間ごとに再試行することはありません。

## 4. 証明書のデプロイ

「ターゲット資格情報」は認証と接続情報のみを保存します。証明書パス、リロードコマンド、デプロイドメイン、サイトなどのパラメータはタスクのデプロイノードで入力します。そのため同じ資格情報を複数のタスクで再利用できます。

### 4.1 内蔵ターゲット

| ターゲット | 資格情報 | デプロイパラメータ |
| --- | --- | --- |
| ローカルディレクトリ | なし | 証明書/秘密鍵パス、任意のリロードコマンド |
| SSH / SFTP | ホスト、ポート、ユーザー名、パスワードまたは秘密鍵、ホストフィンガープリント | リモートの証明書/秘密鍵パス、任意のリモートリロードコマンド |

SSH はデフォルトでターゲットホストのフィンガープリント（`SHA256:...`）の入力が必須です。明示的に「初回接続時にホスト鍵を自動信頼」を有効にした場合のみ TOFU で記録されます。以降フィンガープリントが一致しない場合は接続を拒否します。

### 4.2 プラグインターゲット

以下のターゲットはデプロイプラグインが提供し、インストールして有効化すると使用できます：

- FTP / FTPS：通常の FTP、明示的 TLS、暗黙的 TLS に対応。
- Webhook：コールバックアドレス、カスタム認証ヘッダー、TLS 検証をスキップするか。
- 阿里云 CDN、七牛云、宝塔パネル、1Panel、雷池 WAF など。
- 具体的な製品とパラメータはタスクのデプロイノードの「デプロイ対象」で選択します。

デプロイプラグインは証明書と秘密鍵を受け取るため、信頼されたコードと同等であり、デフォルトでは無効です。プラグイン未インストール時はローカルファイルと SSH のみ表示され、過去の資格情報は引き続き保持されます。

### 4.3 内部 CA 信頼チェーン

「システム設定 → TLS 信頼チェーン」で内部 CA の公開鍵（PEM、ルート CA と下位 CA を同時に含められます）をインポートできます。インポート後：

- ターゲット資格情報プラグインが内部 HTTPS サービスへアクセスする際、システムルート証明書とインポートした CA で TLS 検証を完了し、検証をスキップする必要がありません。
- 証明書監視はこれらの CA が署名したサイト証明書を信頼します。本プログラムのプライベート CA の証明書は自動的に信頼チェーンに追加されます。
- デプロイ、リロードコマンド、プラグインの子プロセスはマージされた `SSL_CERT_FILE` で信頼チェーンを読み取り、`CURL_CA_BUNDLE` と `REQUESTS_CA_BUNDLE` にも対応します。
- 信頼チェーンファイルはデータディレクトリの `trusted-ca-bundle.pem` に保存され、設定ページからダウンロードもできます。

実際に管理下にある内部 CA のみをインポートすべきです。誤った CA は TLS 検証を弱めます。CA を削除すると、その CA が署名した証明書を使用するターゲットは再び信頼されなくなります。CA のインポートは「証明書が信頼されない」問題のみを解決します。証明書の期限切れ、未発効、アクセスドメイン/IP との不一致がある場合は、証明書の更新または一致するアドレスへの変更が必要です。

### 4.4 デプロイ記録

- デプロイごとにデプロイ記録が生成され、証明書の詳細とログで結果を確認できます。
- 手動デプロイは証明書が属するタスクのデプロイノードパラメータを優先的に再利用し、ターゲットごとに今回のパラメータを個別に入力することもできます。
- ローカル/SSH デプロイはリロードコマンドを実行し、API キーが明示的に `deploy:execute` を持つ場合のみトリガーできます。
- デプロイ失敗時にターゲットシステム上の旧証明書へ自動ロールバックしません。ターゲット側で前バージョンのファイルを保持するか、アトミックなリリース機構を使用する必要があります。

## 5. サイト証明書監視

外部サイトを追加すると、サービスは定期的に TLS 接続で証明書を読み取ります：

- ターゲットは `example.com`、`example.com:8443`、完全な URL に対応し、デフォルトポートは `443`。
- デフォルトで 24 時間ごとに確認し、監視項目ごとに調整できます。
- 証明書のホスト名、発行者、有効期限、状態を検証します。
- 残り 30 日以内は「期限間近」とマークされ、期限切れ、接続失敗、チェーンが信頼されない、チェーンが不完全、ホスト名不一致は異常とマークされます。
- 状態が正常から期限間近、期限切れ、異常へ変わると通知を送信します。
- 監視はシステムの信頼チェーンを検証し、中間者攻撃が自己署名証明書で実際の証明書問題を隠すのを防ぎます。管理者がインポートした内部 CA とプライベート CA も信頼チェーンに含まれます。

## 6. 通知

### 6.1 内蔵チャネル

- **メール（SMTP）**：サーバー、ポート、ユーザー名、パスワード、送信者、SSL 対応。
- デフォルトで暗黙的 TLS を使用します（`smtp.ssl=true`）。暗黙的 TLS を無効にした場合、サーバーが STARTTLS に対応していなければ送信を拒否し、リセットトークンなどの機密メールの平文送信を防ぎます。

### 6.2 プラグインチャネル

Gotify、ServerChan、ntfy、GoCQHTTP、PushDeer、Bark、Telegram、钉钉、企业微信机器人、企业微信应用、企业微信智能机器人、iGot、PushPlus、WePlus、WxPusher、WxPusher SPT、OpenILink、WPush、Synology Chat、飞书、PushMe、ChronoCat、および汎用カスタム Webhook。

- メール以外のチャネルは通知プラグインが提供します。
- チャネルは個別に有効化し、テストメッセージを送信できます。
- タスクの通知ノードでは特定のチャネルを選択するか、有効化済みのすべてのチャネルを使用できます。
- トリガータイミングは常に、成功時のみ、失敗時のみに対応します。

## 7. プライベート CA

「プライベート CA」で内部認証局を管理します。

### 7.1 生成

- 秘密鍵種別：ECDSA P-256 / P-384、RSA 2048 / 4096。
- 有効期間は必要に応じて設定。
- ルート CA を生成でき、「中間/発行 CA」を選択して既存のプライベート CA から下位 CA を署名することもできます。
- 生成時に完全な X.509 フィールドと PKI パラメータを設定できます：
  - サブジェクト：ST、L、OU、Email、カスタムシリアル番号。
  - 拡張：パス長、Key Usage、Extended Key Usage、SAN（DNS/IP）、Name Constraints（許可/除外する DNS ドメインと IP セグメント）。
  - インフラ：上位 CA、CRL 配布ポイント、OCSP レスポンスアドレス、CA 発行者アドレス、証明書ポリシー OID と CPS アドレス。
- SKI、AKI、CA 基本制約はシステムが自動生成します。
- 上位 CA を選択すると、有効期間とパス長は上位 CA が許可する範囲に自動的に収束します。

### 7.2 インポート

- PEM 形式の CA 証明書と秘密鍵を貼り付けます。
- CA 基本制約、証明書の署名用途、証明書と秘密鍵の一致を検証します。
- 中間 CA をインポートする際に上位 CA を選択でき、システムが署名を検証して階層関係を構築します。

### 7.3 ダウンロードと削除

- CA 証明書、秘密鍵、完全な証明書チェーン（中間 CA + 上位 CA チェーン）をダウンロードできます。
- 一覧 API は証明書や秘密鍵の内容を返しません。秘密鍵のダウンロードには `private_cas:key` が必要です。
- 削除するとサーバーに保存された CA レコードと秘密鍵が削除されます。下位 CA が存在する場合は先に下位 CA を削除する必要があります。

### 7.4 制限

- プライベート CA の秘密鍵はデータベースへ書き込む前に暗号化されますが、HSM/KMS による管理ではありません。
- ルート CA と中間/発行 CA の両方を「証明書申請」の発行機関として使用できます。完全な証明書チェーンは証明書とともに保存されデプロイされます。
- 証明書のデフォルト有効期間は 365 日で、CA の有効期限を超えません。
- CRL/OCSP 配布アドレスは新規証明書に書き込まれますが、実際の失効リストとオンライン状態サービスは外部 PKI インフラが提供する必要があります。
- 既存の証明書は CDP/AIA 拡張を自動的に取得しないため、再発行が必要です。

## 8. ACME サーバー

内蔵 ACME v2 サーバーはデフォルトで有効で、プライベート CA を certbot、lego、acme.sh などのクライアントに公開できます。エンドポイントを作成して有効化しない限り証明書は発行されません。

### 8.1 エンドポイント

- 各エンドポイントは 1 つのプライベート CA にバインドされます。
- ランダムな URL slug を使用します。例 `/acme/internal/directory`。
- EAB スイッチ、ドメイン許可リスト、HTTP-01 / DNS-01 / TLS-ALPN-01 機能スイッチに対応します。
- 独立したリッスンポートを使用でき、直接 TLS と任意の mTLS に対応します。
- 証明書の有効期間、オーダーのレート制限、HTTP-01 の社内 CIDR 許可リストを設定できます。

### 8.2 プロトコル機能

- アカウントは公開鍵のみを保存し、クライアントの秘密鍵は保存しません。
- アカウントキーのローテーション（`keyChange`）に対応します。
- ARI（RFC 9773）更新提案に対応：デフォルトで証明書の期限前約 1/3 ライフサイクル（最大 30 日）に更新ウィンドウを示します。失効または期限切れの証明書は過去のウィンドウを返し、即時更新を促します。
- ARI の `replaces` フィールドに対応：新規オーダーは置き換える旧証明書を宣言でき、サーバーは旧証明書の帰属、識別子の重複、重複置換を検証します。
- DNS と IP 識別子に対応します。IP 識別子は HTTP-01 / TLS-ALPN-01 のみ許可され、IP セグメント許可リストの設定が必要です。
- 新規発行証明書には CRL Distribution Point と OCSP AIA 拡張が書き込まれ、`/pki/{ca}/crl` と `/pki/{ca}/ocsp` で失効状態を確認できます。
- プライベート CA は `cRLSign` 用途を持つ必要があり、ACME エンドポイント有効化時に検証されます。

### 8.3 診断とクリーンアップ

- 「ACME 診断」ページでアカウント、オーダー、認可、チャレンジ、証明書の状態を確認できます。
- エンドポイント、状態、時間で無効なオーダーと長期間未使用のアカウントをクリーンアップできます。
- アカウントをクリーンアップすると履歴オーダーが削除されますが、発行済みの証明書には影響しません。
- CRL/OCSP は CA ごとに編成され、ACME 登録エンドポイントを停止した後も到達可能に保つ必要があります（クライアントが失効を確認する場合）。

## 9. ダッシュボードとログ

### 9.1 ダッシュボード

UI は簡体字中国語と英語に対応し、設定で切り替えられます。ホームページの概要：

- 証明書の総数、期限間近/期限切れの数。
- タスクと監視の状態。
- デプロイ成功率。
- 期限分布と発行トレンド。

### 9.2 ログ：操作ログ

- システムログと同じ「その他 → ログ」ページに属し、上部タブで切り替えます。
- タスク実行、証明書発行、デプロイ、通知、監視、設定変更を記録します。
- ソース、レベル、キーワード、時間範囲で絞り込め、自動更新を有効にできます。
- キーワードは保存された元の内容とパラメータ値（タスク名、ドメインなど）に一致し、現在の言語でレンダリングされたテンプレート文言には一致しません。
- CSV または JSON でエクスポートでき、CSV は UTF-8 BOM 付きで Excel/WPS で直接開けます。エクスポートと一覧は同じフィルター条件を使用します。
- クリアでき、アーカイブが有効な場合は先に `data/archives/logs/` へ書き込んでから削除します。クリア操作自体が監査ログを 1 件書き込みます。この機能には独立した機密権限 `logs:write` が必要で、ページ上で二段階確認を行います。
- エクスポート範囲は直近 90 日に限られます。
- エクスポート時刻はデフォルトでブラウザのタイムゾーンに従い、指定がない場合はサーバーの `TZ` を使用します。

### 9.3 ログ：システムログ

- 操作ログと同じ「その他 → ログ」ページに属し、上部タブで切り替えます。
- プロセスログから絞り込んだ後、非同期でデータベースへ書き込みます。
- レベル、コンポーネント、キーワード、時間範囲で絞り込めます。
- CSV/JSON でエクスポートでき、クリアも可能です。アーカイブが有効な場合は先にアーカイブへ書き込み、クリア操作は操作ログに記録されます。
- デフォルトで `info` 以上のレベルを記録し、7 日または 20,000 行を保持します。
- HTTP アクセスログはデフォルトでデータベースへ書き込まず、`log.system` で調整できます。

### 9.4 ログ：アーカイブ

- 操作ログ/システムログと同じ「その他 → ログ」ページに属し、3 番目のタブから入ります。
- 手動クリア、90 日の操作ログクリーンアップ、システムログの保持日数/最大行数クリーンアップは削除前に自動でアーカイブを生成します。
- アーカイブは `*.ndjson.gz` と `*.manifest.json` で構成され、元のログフィールド、行数、ID/時間範囲、トリガー理由、実行者、SHA-256、ファイルサイズを保存します。
- カテゴリ、理由、キーワード、時間範囲で絞り込み、アーカイブをダウンロードまたは削除できます。
- アーカイブはデフォルトで永久保持されます。`log.archive.retention_days`、`max_total_mb`、`quota_policy` を設定できます。
- アーカイブ失敗時は削除がブロックされ、手動クリアはエラーを返し、自動クリーンアップは次回の再試行を待ちます。
- アーカイブディレクトリはデフォルトの ZIP バックアップに含まれず、別途転送する必要があります。アーカイブファイルはデータディレクトリの権限を持つ管理者が削除でき、改ざん不可の監査には該当しません。

## 10. 機能の境界

| 境界 | 説明 |
| --- | --- |
| パブリック証明書の検証 | DNS-01 のみ。パブリック CA への HTTP-01 申請は非対応 |
| マルチユーザー | 単一管理者アカウント、RBAC/組織構造なし |
| アイデンティティフェデレーション | LDAP/OIDC/SAML/SCIM なし |
| 高可用性 | 組み込みクラスタ/Active-Active なし。SQLite 単一書き込み |
| 秘密鍵管理 | ローカル暗号化保存、HSM/KMS なし |
| 監視出力 | Prometheus メトリクスエンドポイントなし。ログと認証 API を提供 |
| デプロイのロールバック | ターゲットシステムの旧証明書へ自動ロールバックしない。ターゲット側でバージョン保持が必要 |
| コンプライアンス認証 | 等保/ISO 認証は付属しない。企業自身の評価が必要 |
