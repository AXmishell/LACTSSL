# デプロイアーキテクチャ

本文はプラットフォームアーキテクトと運用責任者を対象に、LACTSSL のデプロイ単位、ネットワーク境界、容量見積もり、可用性設計を説明します。**デフォルトのデプロイは引き続き単一インスタンス、シングルテナント、SQLite 単一書き込み**です。現行バージョンからは明示的に PostgreSQL 18 を選択でき、`/upgrade` で 2 つのバックエンド間を変換できます。複数インスタンスによる PostgreSQL 共有はデフォルトで拒否され、HA は引き続き内蔵機能の範囲外です。

## 1. デプロイ単位

LACTSSL は自己完結型の Go バイナリです：

- フロントエンドのビルド成果物はバイナリに埋め込まれ、独立した Web サーバーや Node ランタイムは不要です。
- データはローカル SQLite に保存され、外部データベース、キャッシュ、メッセージキューに依存しません。
- DNS、デプロイ、通知プラグインはワンショットの子プロセスとして実行され、プラグインファイルはデータディレクトリに配置されます。
- 実行時の永続入力は 2 種類のみです：`config.yaml` と `data/` ディレクトリ。

```text
/opt/lactssl/
├── lactssl                   # バイナリ
├── config.yaml               # 設定とキー、0600
└── data/                     # 0700
    ├── lactssl.db            # SQLite メイン DB
    ├── lactssl.db-wal        # WAL（実行時）
    ├── lactssl.db-shm        # 共有メモリ（実行時）
    ├── plugins/              # dns / deploy / notify ヘルパー
    ├── plugin-icons/         # プラグインアイコンのキャッシュ
    ├── upgrade-backups/      # 移行とプログラムアップグレードのバックアップ
    └── restore-pending/      # 適用待ちの復元パッケージ
```

バックアップ境界は `config.yaml` + `data/` です。データベースのみをバックアップすると `salt` が失われ、暗号化資格情報を復号できなくなります。

## 2. 参考トポロジー

### 2.1 単一ホスト + リバースプロキシ（推奨の起点）

```text
インターネット / 企業内ネットワーク
        │ HTTPS 443
┌───────▼────────┐
│ Nginx / Caddy  │  TLS 終端、送信元制限、アクセスログ
│ / WAF / LB     │
└───────┬────────┘
        │ HTTP 127.0.0.1:8080
┌───────▼─────────────────────────────┐
│ LACTSSL                             │
│  ├─ 管理コンソール / API            │
│  ├─ スケジューラ（30 秒間隔）       │
│  ├─ プライベート CA / ACME（任意）  │
│  └─ SQLite + ローカルプラグイン     │
└───┬──────────┬──────────┬───────────┘
    │          │          │
 DNS API    デプロイ先   通知/メール
```

適用：大多数の企業の単一環境デプロイ、数十〜数千枚の証明書。

要点：

- メインプログラム自体は管理ポートの TLS 設定を提供せず、本番ではリバースプロキシが TLS を終端する必要があります。
- リバースプロキシと LACTSSL は同一ホストまたは同一セグメントが望ましく、バックエンドポートはループバックまたは社内ネットワークのみをリッスンします。
- リバースプロキシは `X-Forwarded-For` を上書きまたは正しく追記し、`X-Forwarded-Proto` を渡す必要があります。`server.trusted_proxies` にはプロキシの正確な IP または最小 CIDR を登録し、追記チェーンではチェーン上のすべてのプロキシを登録します。
- `security.public_url` は固定の外部アドレスを設定する必要があり、パスワードリセットなどのリンクはリクエストの Host に依存しません。

### 2.2 DMZ プロキシ + 社内アプリケーション

```text
ユーザー ──HTTPS──► DMZ リバースプロキシ ──社内 HTTP──► LACTSSL（アプリ網）
                                              │
                                              ├─► DNS API / パブリック CA（アウトバウンド 443）
                                              ├─► SSH / パネル / CDN（ターゲット別）
                                              └─► SMTP / Webhook（チャネル別）
```

適用：セキュリティ要件が高く、管理面を業務セグメントに直接公開しない場合。

要点：

- ファイアウォールでは、プロキシから LACTSSL の管理ポートへの通信のみを許可します。
- LACTSSL のアウトバウンドアクセスはターゲット別に許可リスト化します。ドメイン許可リストができない場合でも、少なくとも宛先ポートとセグメントを制限します。
- DMZ で ACME サーバーを別途公開する必要がある場合は、専用のリッスンポートを使用し、管理ポートを再利用しないでください。

### 2.3 社内 PKI / ACME サービス

```text
社内サービス / certbot / lego / acme.sh
        │ ACME v2（HTTPS または mTLS）
┌───────▼────────────────────────┐
│ LACTSSL ACME エンドポイント    │  専用ポート :14000
│ プライベート CA をバインド     │ ドメイン許可リスト / EAB / チャレンジ種別
└───────┬────────────────────────┘
        │
   プライベート CA 階層
```

適用：社内サービスの証明書、デバイス証明書、テスト環境の証明書。

要点：

- ACME エンドポイントを作成して有効化しない限り証明書は発行されません。各エンドポイントにはドメイン許可リストの設定が必須です。
- パブリックネットワークから到達可能な場合は EAB を有効にし、ネットワーク層で送信元を制限することを推奨します。より高い要件では mTLS を使用します。
- `acme.base_url` はクライアントが実際にアクセスする固定アドレスである必要があり、パブリックネットワークへのデプロイではリクエストの Host に依存しないでください。
- CRL/OCSP エンドポイントは CA ごとに編成され、ACME 登録エンドポイントを停止した後も到達可能に保つ必要があります（クライアントが失効を確認する場合）。

### 2.4 コンテナプラットフォーム

```text
Ingress / Service
        │
┌───────▼────────┐
│ Pod: lactssl   │
│  /app/config    │── PVC または設定ボリューム
│  /app/data      │── PVC
└────────────────┘
```

要点：

- 公式イメージを使用する場合、コンテナ内では常に `/app/config/config.yaml` を読み取り、データディレクトリは `/app/data` です。
- エントリスクリプトはマウントディレクトリの所有者を修正した後、`lactssl` ユーザーに権限を落として実行します。Compose はデフォルトで読み取り専用ルートファイルシステムを使用し、capabilities をドロップします。
- **単一レプリカ**：複数の Pod が同時に同じ SQLite データボリュームへ書き込まないでください。
- コンテナ内の自己アップグレードはイメージを変更せず、再作成後はイメージのバージョンへ戻ります。本番ではイメージタグでアップグレードします。
- `restart: unless-stopped` またはオーケストレーションプラットフォームの同等の戦略を使用し、バックアップ復元後に自動起動させます。

## 3. ポートとネットワークフロー

| 方向 | ポート/プロトコル | 用途 | 推奨 |
| --- | --- | --- | --- |
| インバウンド | 443/TCP | 管理コンソールと API（リバースプロキシ経由） | 管理された送信元のみに公開 |
| インバウンド | 8080/TCP | LACTSSL メインリスン（デフォルト） | ループバック/社内ネットワークのみをリッスンし、プロキシからアクセス |
| インバウンド | カスタム/TCP | ACME 専用リスン（任意） | 専用ポート、送信元を制限 |
| アウトバウンド | 443/TCP | DNS プロバイダー API、パブリック ACME CA、通知、Webhook、パネル、クラウド CDN | ドメイン/セグメント別の許可リスト |
| アウトバウンド | 22/TCP またはカスタム | SSH/SFTP デプロイ | 対象ホストのみ許可 |
| アウトバウンド | 21/990/TCP | FTP/FTPS デプロイ（プラグイン） | FTPS を優先し、ターゲットを制限 |
| アウトバウンド | 25/465/587/TCP | SMTP 通知 | 企業のメールゲートウェイを使用 |
| アウトバウンド | カスタム | 自前の Gotify、社内 Webhook、監視対象 | 必要に応じて許可、SSRF 境界に注意 |

説明：

- サーバーはアウトバウンド先に対して SSRF 検証を行い、クラウドメタデータ、リンクローカル、予約ネットワークなどのアドレスを拒否します。ループバックとプライベートネットワークは引き続き許可され、社内連携が容易です。
- デプロイ Webhook は証明書の秘密鍵を伴うため、パブリックネットワークのターゲットには HTTPS を強制します。ループバック、プライベートネットワーク、`.local`、`.internal` は HTTP を許可します。
- リバースプロキシで TLS 終端を行う場合、バックエンドは HTTP でアクセスします。`X-Forwarded-Proto` を正しく渡す必要があり、そうしないと Cookie の `Secure` 判定とレート制限の識別が誤ります。

## 4. 容量計画

以下は**参考の起点**であり、ベンダーの保証ではありません。実際の容量は証明書数、タスク頻度、ログ量、プラグイン種別、バックアップ戦略に依存します。本番前に実際の負荷で負荷テストすることを推奨します。

| 規模 | 証明書/タスク量 | 推奨構成 | 説明 |
| --- | --- | --- | --- |
| パイロット/小規模 | 証明書 100 枚未満、タスク少数 | 2 vCPU / 1 GB / 10 GB | 大型プラグインパッケージの同時インストールを避ける |
| 中規模 | 100〜1,000 枚、日常的な更新 | 2〜4 vCPU / 2 GB / 20 GB | ログローテーションと定期クリーンアップの有効化を推奨 |
| やや大規模 | 1,000〜5,000 枚、頻繁なデプロイ | 4〜8 vCPU / 4 GB / 50 GB+ | SQLite の書き込み増幅、バックアップウィンドウ、プラグインのピークに注意 |

メモリの要点：

- メインプロセスのアイドル時ベースラインは数十 MB です。プラグインは呼び出しごとに起動する子プロセスで、単一のヘルパーは `memory_limit_mb`（デフォルト 128 MB）で制限されます。
- プラグインのインストール/更新時の展開で一時的なメモリピークが発生し、大型 DNS パッケージではより顕著です。コンテナのメモリをアイドル時の使用量ちょうどまで抑えないでください。
- 複数のタスクが同時実行されると複数のヘルパーが同時に起動する可能性があるため、ピーク分の余裕を確保してください。

ストレージの要点：

- データベースの増加は主に証明書、タスクログ、操作ログ、システムログ、ACME オーダーによるものです。
- 操作ログとシステムログは `logs` テーブルを共有し、`category` で区別します。保持とクリアの戦略はカテゴリごとに分離され、システムログをクリアしても操作ログには影響しません。
- 証明書、ログ、ACME 診断データにはクリーンアップ入口が用意されています。システムログには `retention_days` と `max_rows` があります。
- `data/upgrade-backups/` はデフォルトで直近 5 件の移行スナップショットを保持し、プログラムアップグレードはデフォルトで 3 件の旧バイナリを保持します。
- バックアップファイルを同じデータディレクトリへ書き戻さないでください。バックアップ容量はデータベースサイズの数倍を見込んでください。

## 5. 可用性と災害復旧

### 5.1 現行バージョンの可用性境界

- **組み込みクラスタ/Active-Active は非対応**。SQLite は単一書き込みのため、複数インスタンスが同じデータディレクトリを同時にマウントするとロック競合やデータ破損を招きます。
- **自動フェイルオーバーは提供しない**。リバースプロキシは生存を検知できますが、同じデータを書き込む別インスタンスへ自動的にトラフィックを切り替えるべきではありません。
- **単一管理者アカウント**は単一障害点です：アカウントを失った場合はバックアップまたはパスワードリセットで復旧する必要があります。管理者の職責を職位に紐づけ、引き継ぎを確実に行うことを推奨します。

### 5.2 単一アクティブ + 迅速復旧（推奨）

```text
プライマリインスタンス ──定期暗号化バックアップ──► 独立バックアップストレージ
   │
   └─ 障害 ──► 新ホスト/新コンテナ ──バックアップ復元──► トラフィック切替
```

推奨目標：

| 指標 | 推奨 |
| --- | --- |
| RPO | 業務の許容度に応じて、少なくとも 1 日 1 回。重要な環境では時間単位まで短縮可能 |
| RTO | 「ホスト準備 + バックアップ復元 + 起動検証」で見積もり、訓練後に Runbook へ記載することを推奨 |
| バックアップ保持 | 少なくとも 7〜30 日。重要な環境ではコンプライアンス要件に応じて延長 |
| 訓練頻度 | 四半期ごとに少なくとも 1 回の完全復旧訓練 |

復旧手順は[運用マニュアル](operations.md)を参照してください。

### 5.3 コンテナとホスト層の高可用性

オーケストレーションプラットフォームで**プロセス**の再起動を保証できますが、データの単一書き込み問題は解決できません：

- レプリカ数は 1 に固定します。
- 永続ボリュームを使用し、Pod 再作成後のデータ消失を防ぎます。
- ヘルスチェックには TCP ポートまたは認証付き `/api/status` を使用します。セキュアエントリ Cookie が必要なページを未認証の監視に使用しないでください。
- ノード障害時はプラットフォームが単一レプリカを再スケジュールします。データボリュームが再マウントできる必要があります。

### 5.4 マルチ環境の分離

本番、ステージング、テストは独立したインスタンスを使用すべきです：

- 独立した `config.yaml`、独立した `security.salt`、独立したデータディレクトリ。
- 独立した DNS サブアカウントとデプロイ資格情報を使用し、テストタスクが本番に影響しないようにします。
- 独立した通知チャネルを使用し、テストのアラートが本番の当番グループへ入らないようにします。
- 本番データベースをテスト環境へコピーした後、同じ資格情報を使い続けないでください。コピーが必要な場合は先に資格情報をローテーションします。

## 6. 監視と可観測性

LACTSSL は Prometheus メトリクスエンドポイントを提供しませんが、以下のシグナルで監視を構築できます：

| シグナル | 方法 | 推奨 |
| --- | --- | --- |
| プロセス生存 | TCP ポート監視 | 30〜60 秒に 1 回 |
| 詳細ヘルス | `GET /api/status`、`system:read` を持つ API キーを使用 | 1〜5 分に 1 回、200 と応答時間を確認 |
| タスク失敗 | 操作ログの絞り込みまたは通知チャネル | タスク失敗/デプロイ失敗を即時アラート |
| 証明書期限間近 | ダッシュボード、サイト監視、タスク更新状態 | 期限前 30/14/7 日に段階的に通知 |
| ログ異常 | システムログのキーワード、リバースプロキシの 5xx | 企業のログプラットフォームに接続 |
| ディスク/バックアップ | ホストまたはプラットフォーム監視 | ディスク < 20% でアラート、バックアップ失敗でアラート |

`/api/status` は認証が必要で、匿名のヘルスチェックとして直接使用できません。匿名監視ではポートに接続できるかしか判断できません。

## 7. TLS と証明書の境界

- 管理コンソールの TLS はリバースプロキシが提供し、LACTSSL のメインポートには直接 TLS を設定しません。
- リバースプロキシは企業 CA またはパブリック CA が発行した証明書を使用し、HSTS、TLS 1.2+ を設定し、弱い暗号スイートを無効化すべきです。
- ACME の専用リスンは直接 TLS を提供でき（`acme.tls.cert/key`）、リバースプロキシで終端することもできます。mTLS を有効にする場合は ACME TLS 証明書と秘密鍵を同時に設定する必要があります。
- LACTSSL が管理する証明書の秘密鍵はデータベースに保存され、`security.salt` から派生したキーで暗号化されます。HSM/KMS による管理は提供しません。
- バックアップパッケージ内のデータベースと設定には暗号化資格情報とキー素材が含まれるため、機密ファイルとして管理してください。

## 8. アーキテクチャ決定チェックリスト

設計レビューでは以下の決定を明確にすることを推奨します：

| 決定 | 選択肢 | 推奨 |
| --- | --- | --- |
| デプロイ方式 | Docker / バイナリ / オーケストレーションプラットフォーム | コンテナプラットフォームがあればイメージを優先。なければバイナリ + systemd |
| TLS 終端 | リバースプロキシ / ACME 専用リスン | 管理面は統一的にリバースプロキシ経由 |
| データストレージ | ローカルディスク / 永続ボリューム / ネットワークディスク | 単一書き込みマウントのみ使用。ネットワークディスクは SQLite のロックセマンティクスを検証 |
| 可用性 | 単一アクティブ + バックアップ / プラットフォーム再起動 | Active-Active は使用しない。RTO/RPO を明確化 |
| アウトバウンド戦略 | 全許可 / ドメイン許可リスト / プロキシ | 本番はターゲット別許可リスト、必要に応じて企業プロキシ経由 |
| プラグインソース | 公式リポジトリ / 社内ミラー / 手動アップロード | 本番は社内ミラー + 署名検証を優先 |
| アップグレード方式 | イメージタグ / バイナリ置換 | コンテナはイメージ、バイナリはリリースパッケージでロールバックを保持 |
