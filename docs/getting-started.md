# 快速上手与上线

本文面向第一次引入 LACTSSL 的团队和个人用户，目标是用最短路径回答三个问题：**能不能满足场景、需要哪些外部依赖、如何安全地上生产**。个人站点和小团队可以直接跳到下面的快速路径，不需要走完整的企业评估流程。

## 快速路径：个人 / 小团队

适用场景：个人博客与站点、家庭实验室、小团队内部服务。你需要的只是**一台能跑 Docker 的 Linux 主机（VPS、NAS 或小主机）、一个域名和 DNS API 凭据、一个部署目标**。

四步跑通，通常 30 分钟内完成：

1. 按[安装与启动](install.md)用 Docker 启动实例，通过启动日志中的门禁入口完成初始化。
2. 进入「插件」页刷新索引，安装一个 DNS 插件；需要面板/CDN 等部署目标就再装部署插件，需要提醒就装通知插件。
3. 创建 DNS 账户 → 在「证书申请」创建任务，选择公共 CA 和域名 → 添加「部署证书」节点（本地目录、SSH 或面板）→ 可选添加通知节点。
4. 手动运行一次，确认证书文件已更新且服务已重载；之后观察一次自动续期或手动触发续期验证。

个人场景的最小安全基线：

- 用 HTTPS 域名访问管理页，并启用 TOTP 或通行密钥。
- 备份密码与 `config.yaml` 分开保管；丢失 `salt` 后数据库中的加密凭据无法解密。
- DNS API 使用专用子账号，只授权需要的域名。

> 企业引入仍需按下面的 1–7 节完成适用性确认、试点和生产上线检查表。

## 1. 先确认适用性

适合引入 LACTSSL 的典型条件：

- 有多个域名或内部服务需要统一管理 TLS 证书。
- 希望把签发、部署、到期监控和通知放进一个可审计的控制台。
- 接受自托管单实例，能够提供一台 Linux 主机、一个数据目录和一份备份策略。
- 有 DNS 服务商 API 凭据，或需要自建私有 CA / ACME 服务。
- 自动化场景可以通过 API 密钥接入，而不是要求多用户 RBAC 或企业 SSO。

不适合直接作为唯一平台的情况：

- 要求多租户隔离、组织架构、审批流或多用户角色。
- 要求双活集群、跨机房自动故障切换或 HSM/KMS 托管私钥。
- 要求产品自带等保/ISO 认证证书，而不是由企业自身完成合规测评。

这些边界不影响 LACTSSL 作为证书自动化组件使用，但需要在方案设计阶段明确责任分工。

## 2. 评估前的准备清单

| 项目 | 需要确认的内容 | 责任角色 |
| --- | --- | --- |
| 主机 | Linux amd64/arm64；Docker Compose v2 或可运行静态二进制；磁盘与备份空间 | 平台/运维 |
| 域名与 DNS | 试点域名、DNS 服务商、可创建 TXT 记录的 API 凭据 | 网络/运维 |
| 入站访问 | 管理域名、反向代理、TLS 证书、来源 IP 白名单 | 网络/安全 |
| 出站访问 | DNS API、SMTP、Webhook、部署目标、监控目标的可达性 | 网络/安全 |
| 私钥与凭据 | DNS/部署/通知凭据的保管人、轮换周期、最小权限账号 | 安全 |
| 变更与备份 | 变更窗口、备份位置、恢复责任人、RPO/RTO 目标 | 运维 |
| 集成 | 需要接入的 CI/CD、CMDB、告警平台和 API 权限 | 集成开发 |

建议在试点阶段使用**独立域名、独立 DNS 子账号、独立通知频道**，不要直接复用生产管理员凭据。

## 3. 30 分钟试点

### 3.1 启动实例

Docker 方式最适合评估：

```bash
git clone https://github.com/AXmishell/LACTSSL.git
cd LACTSSL
mkdir -p config data
cp config.yaml.example config/config.yaml && chmod 600 config/config.yaml
docker compose up -d
docker compose logs -f lactssl
```

仓库默认沿用 1Panel 的 `1panel-network` 外部网络；不使用 1Panel 时删除 `docker-compose.yml` 中服务下的 `networks` 和末尾的 `networks` 段，或先执行 `docker network create 1panel-network`。GHCR 镜像从首个正式 Release 起可用，未发布时可按[安装与启动](install.md)在本地构建。试点阶段可以用 `http://127.0.0.1:8080` 访问；涉及通行密钥（WebAuthn）时必须使用 HTTPS 域名或 localhost。

### 3.2 完成初始化

启动日志会打印两类一次性信息：

1. **门禁入口**：形如 `http://127.0.0.1:8080/K7mQ2pX9vR4tY8nL6cWz/`。
2. **初始化令牌**：未初始化时打印，用于创建管理员、恢复备份等初始化操作。

通过门禁入口打开页面，按提示创建管理员账户。初始化完成后令牌立即失效；忘记入口时可在 `config.yaml` 中设置 `security.entry` 并重启覆盖。

### 3.3 安装最小插件集

主程序不内置 DNS、部署和通知插件。进入「插件」页：

1. 确认插件仓库地址，点击「刷新索引」。
2. 打开「插件市场」，至少安装一个 DNS 插件（如常用 DNS 包）、一个通知插件。
3. 如需 SSH 以外的部署目标，再安装部署插件。
4. 在对应列表中启用需要的服务商、部署目标或通知渠道。

离线环境可以把 `plugins.repo.url` 指向内部 `https://` 镜像或 `file://` 索引，详见[插件治理](plugins.md)。

### 3.4 跑通一条完整链路

推荐用私有 CA 做第一条链路，不依赖公网 DNS：

1. 在「私有CA」生成一个根 CA（ECDSA P-256，有效期按试点需要）。
2. 在「证书申请」创建任务，签发机构选择该私有 CA，填写测试域名。
3. 在任务流程中添加「部署证书」节点，选择「本地目录」，填写证书/私钥路径和可选重载命令。
4. 添加「通知」节点，选择已启用的渠道，触发时机选「始终」。
5. 手动运行任务，检查证书、部署记录和通知是否成功。

再补一条公网链路：创建 DNS 账户 → 选择公共 CA → 用测试域名走 DNS-01 → 部署到目标 → 观察自动续期时间。两条链路都跑通后，再进入试点。

### 3.5 验证关键运维动作

| 动作 | 验证方式 | 通过标准 |
| --- | --- | --- |
| 备份 | 设置 → 备份与恢复 → 下载加密备份 | 能生成 ZIP，密码可解密 |
| 恢复 | 在隔离实例导入备份 | 账户、证书、任务和设置完整 |
| 日志 | 操作日志与系统日志筛选/导出 | 能看到初始化、任务和部署记录 |
| API | 创建只读密钥调用 `/api/certificates` | 返回 200，越权接口返回 403 |
| 通知 | 发送测试通知 | 目标频道收到消息 |
| 监控 | 添加一个外部站点 | 能读取证书并显示状态 |

## 4. 试点范围建议

试点不要追求“全量接入”，应覆盖最能暴露问题的链路：

- 1–2 个真实业务域名，包含一个通配符或多域名证书。
- 1 个真实部署目标（SSH、面板、CDN 或 Webhook 中选一个）。
- 1 个内部服务场景（私有 CA 或 ACME 端点）。
- 1 个告警接收渠道，明确值班人和升级路径。
- 1 个自动化调用方（CI/CD 或巡检脚本），验证 API 密钥权限。

试点周期建议 1–2 周，至少观察一次自动续期或手动续期，确认部署重载命令不会影响业务。

## 5. 生产上线检查表

### 5.1 网络与访问

- [ ] 管理入口只通过 HTTPS 反向代理暴露，代理后端口不直接对公网开放。
- [ ] 已配置 `server.trusted_proxies` 和 `security.public_url`。
- [ ] 门禁入口为随机长字符串，未使用 `admin`、`ssl` 等可猜测路径。
- [ ] 管理入口配置来源 IP 白名单、VPN 或零信任访问策略。
- [ ] 如启用 ACME 服务端，使用独立端口并限制来源；EAB 默认开启。

### 5.2 身份与密钥

- [ ] 管理员使用强密码，并启用 TOTP 或通行密钥。
- [ ] 恢复邮箱由安全团队控制，邮箱本身启用多因素认证。
- [ ] 为每个自动化系统创建独立 API 密钥，按最小权限授权并设置过期时间。
- [ ] DNS、部署、通知凭据使用专用账号，不使用个人账号或全局管理员密钥。
- [ ] `config.yaml` 权限 `0600`，`data/` 权限 `0700`，属主为服务运行用户。

### 5.3 数据与恢复

- [ ] 已定义 RPO/RTO，并配置至少每日一次加密备份。
- [ ] 备份存放在独立介质，访问受控，恢复密码单独保管。
- [ ] 至少完成一次恢复演练，确认 `salt` 与数据库配套。
- [ ] 已确认日志保留期、导出范围和存储容量。

### 5.4 运行与变更

- [ ] 明确服务责任人、告警接收人和变更窗口。
- [ ] 配置进程存活探测和证书到期/任务失败告警。
- [ ] 固定镜像或二进制版本，不使用不可追溯的 `latest` 长期运行。
- [ ] 已阅读[升级与变更](upgrade.md)，确认迁移与回滚步骤。
- [ ] 已完成[安全基线](security.md)中的高优先级项。

## 6. 责任分工建议

| 职责 | 建议归属 | 说明 |
| --- | --- | --- |
| 主机、网络、反向代理 | 平台/运维 | 保障可用性、入站出站策略和 TLS 终止 |
| LACTSSL 管理员账户 | 平台/运维负责人 | 单账户，必须由岗位而非个人长期占有 |
| DNS/部署/通知凭据 | 安全或对应系统负责人 | 专用账号、定期轮换、最小权限 |
| API 密钥 | 集成开发负责人 | 按系统发放，登记用途、权限和过期时间 |
| 备份与恢复演练 | 运维 | 备份密码与恢复流程分离保管 |
| 合规证据 | 安全/审计 | 使用操作日志、系统日志和变更记录 |

## 7. 常见试点失败原因

- **把门禁入口当成安全边界**：入口只是额外一层防护，不能替代 HTTPS、强密码和网络访问控制。
- **用个人 DNS 账号做 API 凭据**：人员离职或开启二次验证后，自动续期会失败。
- **部署重载命令未验证**：证书文件更新了，但 Nginx/面板没有重载，业务仍使用旧证书。
- **只备份数据库，不备份 `config.yaml`**：丢失 `salt` 后，数据库中的加密凭据无法解密。
- **所有自动化共用一个全权限 API 密钥**：一旦泄露，攻击者可签发、部署和导出私钥。
- **在容器内使用自升级**：重建容器后会回到镜像版本；生产应通过镜像标签升级。
