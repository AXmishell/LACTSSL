# 运维手册

本文面向负责 LACTSSL 日常运行的值班和运维团队，覆盖备份恢复、监控告警、容量维护、变更升级和故障响应。目标是让服务可被交接、可被审计、可在故障后恢复。

## 1. 服务目标与责任

LACTSSL 不附带 SLA。企业应在内部明确：

| 项目 | 建议定义 |
| --- | --- |
| 服务级别 | 证书签发/部署为关键支撑系统，或按业务影响分级 |
| 可用时间 | 与依赖的 DNS、CA、反向代理和部署目标一致 |
| RPO | 至少每日一次备份；关键环境可缩短到小时级 |
| RTO | 以“准备主机 + 恢复 + 启动验证”演练结果为准 |
| 变更窗口 | 避开证书集中到期和业务高峰 |
| 告警响应 | 任务失败/证书异常 15–30 分钟内响应（按企业制度） |

不要把 LACTSSL 的“进程存活”当成业务可用。真正的业务可用还取决于 DNS API、CA、部署目标和通知链路。

## 2. 备份与恢复

### 2.1 备份范围

必须同时备份：

1. `config.yaml`（或 `-config` 指定的路径）
2. 整个 `data/` 目录

`data/` 至少包含 `lactssl.db`；运行时还可能有 `lactssl.db-wal`、`lactssl.db-shm`。数据库、插件、日志、升级备份都在 `data/` 下。

只备份数据库会丢失 `salt`，导致加密凭据无法解密；只备份配置会丢失业务数据。两者必须配套。

### 2.2 界面加密备份（推荐）

「系统设置 → 备份与恢复」提供在线操作：

- **下载备份**：生成 ZIP，包含 SQLite 快照、当前 `config.yaml` 和 `manifest.json` 版本信息。
- 下载前需要重新输入当前账户密码；启用 TOTP 时还需动态验证码。
- 备份加密密码与账户密码相互独立，至少 12 位。
- 备份内容使用 PBKDF2-HMAC-SHA256（600,000 次迭代）+ AES-256-GCM 加密；恢复时必须输入同一密码。
- 密码遗失将无法恢复该备份。

建议：

- 备份文件存到独立介质或对象存储，不要留在 `data/` 下。
- 备份密码存入企业密码管理器，与备份文件分离保管。
- 记录备份时间、大小、校验值和保管位置。
- 至少保留 7–30 天，关键环境按合规要求延长。

### 2.3 命令备份

需要文件级备份时，先停止服务再复制，确保 SQLite 处于一致状态：

```bash
# Docker
docker compose stop

# 或停止 systemd 服务
sudo systemctl stop lactssl

tar czf lactssl-backup-$(date +%F).tar.gz config.yaml data
chmod 600 lactssl-backup-*.tar.gz
```

如果无法停机，优先使用界面加密备份；直接复制运行中的 SQLite 可能得到不一致快照。

### 2.4 恢复

#### 界面恢复

1. 上传 ZIP 备份包或单独的 `.db` 文件。
2. 输入当前密码确认；加密备份还需输入备份解密密码。
3. 服务会把恢复内容写入 `data/restore-pending/` 并自动重启。
4. Docker 部署由 `restart: unless-stopped` 自动拉起；直接运行二进制时需要自行重启。
5. 使用备份中的管理员账户登录。

#### 手工恢复

1. 停止服务。
2. 将备份中的 `config.yaml` 与 `data/` 放回原位置。
3. 确认权限：配置文件 `0600`，数据目录 `0700`，属主为服务运行用户。
4. 启动服务。
5. 检查门禁入口、管理员登录、证书、任务和插件。

#### 恢复注意事项

- 恢复后请使用备份中的管理员账户登录。
- 默认每次启动都会清空会话并轮换 JWT 子密钥，旧登录会失效。
- 若备份中的 `config.yaml` 使用不同的 `jwt_secret`，旧令牌无法通过校验。
- 若使用不同的 `salt`，数据库中的加密凭据只能在配套配置下解密；因此建议始终用完整 ZIP 备份恢复。
- 若备份中的门禁入口与当前不同，查看启动日志中的新入口。
- 如果只恢复数据库而丢失 `config.yaml` 中的 `salt`，已加密的 DNS/部署/通知凭据将无法解密，需要重新填写。

### 2.5 恢复演练

每季度至少一次：

- [ ] 在隔离环境恢复最近备份。
- [ ] 验证管理员登录、TOTP/通行密钥和恢复邮箱。
- [ ] 验证证书列表、任务、部署凭据和通知渠道。
- [ ] 运行一条测试任务并部署到非生产目标。
- [ ] 记录实际 RTO、问题和改进项。
- [ ] 确认备份密码仍由授权人持有。

## 3. 监控与告警

### 3.1 监控信号

| 信号 | 采集方式 | 建议阈值/动作 |
| --- | --- | --- |
| 进程存活 | TCP 端口探测 | 30–60 秒一次，连续 3 次失败告警 |
| 认证健康 | `GET /api/status` + `system:read` API 密钥 | 1–5 分钟一次，非 200 或高延迟告警 |
| 任务失败 | 操作日志或通知 | 失败即告警，区分 DNS/CA/部署/通知 |
| 证书临期 | 仪表盘、站点监控 | 30/14/7 天分级提醒 |
| 部署失败 | 部署记录/通知 | 立即告警，检查目标系统和重载命令 |
| 磁盘 | 主机/平台监控 | 使用率 > 80% 预警，> 90% 告警 |
| 备份 | 备份任务/文件检查 | 失败或超过周期未备份告警 |
| HTTP 5xx | 反向代理日志 | 按基线设置阈值 |
| 登录异常 | 操作日志/系统日志 | 多次失败、异常来源 IP 告警 |

### 3.2 告警路由

- 任务失败、证书异常、部署失败进入运维值班渠道。
- 安全事件（异常登录、入口探测、插件校验失败）进入安全渠道。
- 备份失败、磁盘不足进入平台渠道。
- 测试通知不要发到生产值班群；使用独立频道。

通知渠道的可用性由外部服务决定，建议至少配置两个独立渠道（如邮件 + 企业 IM），避免单点。

### 3.3 不要做的监控

- 不要用裸 `/` 或 `/login` 做匿名健康检查：未通过门禁会返回 404，这是预期行为。
- 不要把管理员密码或长期全权限 API 密钥写进监控系统。
- 不要把证书私钥或备份密码放进告警内容。

## 4. 日常维护

### 4.1 每日

- 查看任务失败、部署失败和站点监控异常。
- 确认证书到期看板没有新增高风险项。
- 检查备份是否按计划生成。

### 4.2 每周

- 检查自动续期任务是否正常调度。
- 查看系统日志中的错误、限流和异常登录。
- 核对新增/停用的 API 密钥和凭据。

### 4.3 每月

- 检查磁盘、数据库大小、WAL 和日志保留。
- 检查插件版本和安全公告。
- 抽查操作日志与变更记录。
- 验证通知渠道。

### 4.4 每季度

- 完成备份恢复演练。
- 复核管理员账户、恢复邮箱、TOTP/通行密钥。
- 复核 API 密钥权限和过期时间。
- 评估升级窗口和回滚方案。

## 5. 容量与清理

### 5.1 需要关注的容量

| 项目 | 增长来源 | 处理 |
| --- | --- | --- |
| SQLite | 证书、任务日志、操作日志、系统日志、ACME 订单 | 清理历史数据、优化数据库、归档日志 |
| WAL | 长期运行、写入频繁 | `wal_checkpoint(TRUNCATE)` 由升级/优化工具执行 |
| 插件 | 安装/更新累积旧文件 | 卸载不用插件，删除旧 helper |
| 升级备份 | 迁移快照、旧二进制 | 按保留策略清理 |
| 备份存储 | 每日/每周备份 | 设置保留和异地副本 |

### 5.2 清理入口

- **证书管理 → 一键清理**：按状态、过期/撤销时长、签发时间、域名、颁发机构、来源筛选；可保留每个任务最新证书。清理后相关任务的证书引用会被清空。
- **ACME 诊断 → 清理**：按端点、状态和未使用时长清理失效订单与账户；清理账户会删除历史订单，但不影响已签发证书。
- **系统日志 → 清空**：清空操作会写入操作日志；建议先导出。
- **升级/优化**：在低峰期执行数据库优化；`VACUUM` 会短暂独占数据库并重写文件，需预留磁盘空间。

### 5.3 数据库维护

- 服务每 6 小时执行一次维护清理；可在日志页面确认调度器是否运行。
- 新版本首次启动会自动执行历史迁移，并在 `data/upgrade-backups/` 生成迁移前快照。
- 需要回收磁盘空间时，在低峰期访问 `/upgrade`，执行「仅优化数据库与配置」并开启 VACUUM。
- 执行前确保有可用备份和足够磁盘空间；`VACUUM` 失败会作为警告返回，不影响服务继续运行。

## 6. 版本与发布

### 6.1 版本识别

- 版本号以 git tag 为唯一来源，仓库不维护 `VERSION` 文件。
- 本地构建由 `git describe --tags --always --dirty` 推导，去掉 `v` 前缀。
- 构建脚本通过 `-ldflags -X 'lactssl/internal/api.Version=...'` 注入版本。
- 可在「设置 → 关于」查看构建版本、构建时间与架构。
- `go run` 或开发构建显示 `dev`。

### 6.2 发布通道

- 稳定版标签包括 `latest`、`<version>`、`<major>.<minor>`、`<major>`。
- 预发布版本只推送完整版本标签，不覆盖 `latest`。
- 生产固定到明确版本，不使用不可追溯的 `latest` 长期运行。

### 6.3 发布产物

Release 会构建 Linux/macOS/FreeBSD/Windows 二进制、`checksums.txt` 和 `linux/amd64`、`linux/arm64` 镜像。归档包含二进制、`README.md`、`LICENSE` 和 `config.yaml.example`。

发布流程、签名和本地构建细节见[扩展开发：源码与构建](development.md)。

## 7. 升级与变更

升级前：

1. 阅读目标版本的变更说明和迁移说明。
2. 备份 `config.yaml` 与 `data/`。
3. 在预发环境验证关键链路（签发、部署、通知、API）。
4. 确认回滚版本和回滚步骤。
5. 选择低峰期，通知相关方。

Docker：

```bash
docker compose pull
docker compose up -d
```

二进制：

```bash
sudo systemctl stop lactssl
sudo cp lactssl /opt/lactssl/lactssl
sudo chown lactssl:lactssl /opt/lactssl/lactssl
sudo systemctl start lactssl
```

升级后：

- 查看日志中的“数据格式升级完成”。
- 登录 `/upgrade` 确认步骤状态。
- 验证证书、任务、部署、通知和 API。
- 观察一个调度周期（至少 30 秒）和一次任务执行。

完整迁移、回滚和程序升级说明见[升级与变更](upgrade.md)。

## 8. 故障响应

### 8.1 分级

| 级别 | 示例 | 目标 |
| --- | --- | --- |
| P1 | 管理入口不可用；大量证书无法续期；私钥泄露 | 立即响应，启动应急 |
| P2 | 单个任务失败；部署目标异常；通知渠道不可用 | 30 分钟内响应 |
| P3 | 单个监控误报；日志异常；非关键插件问题 | 工作时间内处理 |

### 8.2 通用步骤

1. **确认影响范围**：哪些证书、任务、部署目标和业务系统受影响。
2. **保留现场**：不要清空日志；记录时间、请求 ID、错误信息。
3. **检查依赖**：DNS API、CA、网络、反向代理、目标系统、SMTP/IM。
4. **隔离变更**：暂停相关任务，避免重复失败或覆盖证书。
5. **恢复服务**：修复依赖或回滚变更；必要时从备份恢复。
6. **验证**：重新运行任务，检查证书、部署和通知。
7. **复盘**：记录根因、时间线、改进项和责任人。

具体症状和命令见[监控与排障](troubleshooting.md)。
