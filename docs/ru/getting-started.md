# Быстрый старт и ввод в эксплуатацию

Эта статья предназначена для команд и частных пользователей, впервые внедряющих LACTSSL. Цель — кратчайшим путём ответить на три вопроса: **подходит ли продукт для сценария, какие внешние зависимости нужны, как безопасно вывести его в продакшен**. Владельцы личных сайтов и небольшие команды могут сразу перейти к быстрому пути ниже, не проходя полный корпоративный процесс оценки.

## Быстрый путь: частные лица / небольшие команды

Применимые сценарии: личные блоги и сайты, домашние лаборатории, внутренние службы небольших команд. Вам нужны только **Linux-хост, на котором можно запустить Docker (VPS, NAS или небольшой хост), домен и учётные данные DNS API, одна цель развёртывания**.

Четыре шага, обычно завершаются за 30 минут:

1. Согласно разделу [Установка и запуск](install.md) запустите экземпляр в Docker и завершите инициализацию через защищённую точку входа из журнала запуска.
2. Перейдите на страницу «Плагины», обновите индекс, установите DNS-плагин; если нужны цели развёртывания, такие как панель/CDN, установите плагин развёртывания, если нужны напоминания — плагин уведомлений.
3. Создайте учётную запись DNS → на странице «Заявка на сертификат» создайте задачу, выберите публичный CA и домен → добавьте узел «Развернуть сертификат» (локальный каталог, SSH или панель) → при необходимости добавьте узел уведомления.
4. Запустите вручную один раз, убедитесь, что файлы сертификата обновлены и служба перезагружена; затем наблюдайте одно автоматическое продление или запустите продление вручную для проверки.

Минимальная базовая безопасность для частного сценария:

- Доступ к странице управления по HTTPS-домену, включите TOTP или ключ доступа.
- Храните пароль резервной копии и `config.yaml` раздельно; после потери `salt` зашифрованные учётные данные в базе данных невозможно расшифровать.
- Для DNS API используйте отдельную субучётную запись с правами только на нужные домены.

> Корпоративному внедрению всё ещё нужно пройти разделы 1–7 ниже: подтверждение применимости, пилот и контрольный список вывода в продакшен.

## 1. Сначала подтвердите применимость

Типичные условия для внедрения LACTSSL:

- Есть несколько доменов или внутренних служб, требующих единого управления TLS-сертификатами.
- Есть желание объединить выдачу, развёртывание, мониторинг сроков действия и уведомления в одну аудируемую консоль.
- Приемлем самостоятельный хостинг одного экземпляра, есть возможность предоставить Linux-хост, каталог данных и стратегию резервного копирования.
- Есть учётные данные API DNS-провайдера или потребность в собственном частном CA / службе ACME.
- Сценарии автоматизации могут подключаться через API-ключи, а не требовать многопользовательского RBAC или корпоративного SSO.

Случаи, когда продукт не подходит как единственная платформа:

- Требуется мультиарендная изоляция, организационная структура, процесс согласования или многопользовательские роли.
- Требуется кластер «активный-активный», автоматическое переключение при сбое между площадками или HSM/KMS для хранения закрытых ключей.
- Требуется, чтобы продукт сам имел сертификаты MLPS/ISO, а не чтобы предприятие самостоятельно прошло оценку соответствия.

Эти границы не мешают использовать LACTSSL как компонент автоматизации сертификатов, но на этапе проектирования решения нужно явно распределить ответственность.

## 2. Контрольный список подготовки к оценке

| Пункт | Что нужно подтвердить | Ответственная роль |
| --- | --- | --- |
| Хост | Linux amd64/arm64; Docker Compose v2 или возможность запуска статического бинарного файла; место на диске и для резервных копий | Платформа/эксплуатация |
| Домен и DNS | Пилотный домен, DNS-провайдер, учётные данные API с правом создания TXT-записей | Сеть/эксплуатация |
| Входящий доступ | Домен управления, обратный прокси, TLS-сертификат, белый список исходных IP | Сеть/безопасность |
| Исходящий доступ | Доступность DNS API, SMTP, Webhook, целей развёртывания и целей мониторинга | Сеть/безопасность |
| Закрытые ключи и учётные данные | Хранитель учётных данных DNS/развёртывания/уведомлений, период ротации, учётные записи с минимальными правами | Безопасность |
| Изменения и резервные копии | Окно изменений, место хранения резервных копий, ответственный за восстановление, целевые RPO/RTO | Эксплуатация |
| Интеграция | CI/CD, CMDB, платформа оповещений и права API, которые нужно подключить | Разработка интеграций |

На этапе пилота рекомендуется использовать **отдельный домен, отдельную субучётную запись DNS, отдельный канал уведомлений** и не переиспользовать напрямую продакшен-учётные данные администратора.

## 3. Пилот за 30 минут

### 3.1 Запуск экземпляра

Способ Docker лучше всего подходит для оценки:

```bash
git clone https://github.com/AXmishell/LACTSSL.git
cd LACTSSL
mkdir -p config data
cp config.yaml.example config/config.yaml && chmod 600 config/config.yaml
docker compose up -d
docker compose logs -f lactssl
```

Репозиторий по умолчанию использует внешнюю сеть `1panel-network` от 1Panel; если 1Panel не используется, удалите `networks` в сервисе и блок `networks` в конце `docker-compose.yml` или сначала выполните `docker network create 1panel-network`. Образ GHCR доступен с первого официального Release; до публикации можно собрать локально согласно разделу [Установка и запуск](install.md). На этапе пилота можно обращаться по `http://127.0.0.1:8080`; при использовании ключей доступа (WebAuthn) обязательно нужен HTTPS-домен или localhost.

### 3.2 Завершение инициализации

Журнал запуска выводит два типа одноразовой информации:

1. **Защищённая точка входа**: вида `http://127.0.0.1:8080/K7mQ2pX9vR4tY8nL6cWz/`.
2. **Токен инициализации**: выводится до инициализации и используется для создания администратора, восстановления резервной копии и других операций инициализации.

Откройте страницу через защищённую точку входа и создайте учётную запись администратора по подсказкам. После завершения инициализации токен сразу становится недействительным; если вы забыли точку входа, можно задать `security.entry` в `config.yaml` и перезапустить, чтобы переопределить её.

### 3.3 Установка минимального набора плагинов

Основная программа не содержит встроенных плагинов DNS, развёртывания и уведомлений. Перейдите на страницу «Плагины»:

1. Подтвердите адрес репозитория плагинов и нажмите «Обновить индекс».
2. Откройте «Магазин плагинов» и установите как минимум один DNS-плагин (например, пакет для популярного DNS) и один плагин уведомлений.
3. Если нужны цели развёртывания, отличные от SSH, установите плагин развёртывания.
4. В соответствующих списках включите нужных провайдеров, цели развёртывания или каналы уведомлений.

В офлайн-среде можно указать `plugins.repo.url` на внутреннее зеркало `https://` или индекс `file://`; подробнее см. [Управление плагинами](plugins.md).

### 3.4 Проверка полной цепочки

Рекомендуется использовать частный CA для первой цепочки, не зависящей от публичного DNS:

1. В разделе «Частный CA» создайте корневой CA (ECDSA P-256, срок действия по потребностям пилота).
2. На странице «Заявка на сертификат» создайте задачу, выберите этот частный CA в качестве органа выдачи и укажите тестовый домен.
3. Добавьте в процесс задачи узел «Развернуть сертификат», выберите «Локальный каталог», укажите пути к сертификату/закрытому ключу и необязательную команду перезагрузки.
4. Добавьте узел «Уведомление», выберите включённый канал, момент срабатывания — «Всегда».
5. Запустите задачу вручную, проверьте успешность сертификата, записи о развёртывании и уведомления.

Затем добавьте публичную цепочку: создайте учётную запись DNS → выберите публичный CA → пройдите DNS-01 с тестовым доменом → разверните на цель → наблюдайте время автоматического продления. После успешной проверки обеих цепочек переходите к пилоту.

### 3.5 Проверка ключевых эксплуатационных действий

| Действие | Способ проверки | Критерий прохождения |
| --- | --- | --- |
| Резервное копирование | Настройки → Резервное копирование и восстановление → Скачать зашифрованную резервную копию | Создаётся ZIP, пароль позволяет расшифровать |
| Восстановление | Импортировать резервную копию в изолированный экземпляр | Учётные записи, сертификаты, задачи и настройки сохранены полностью |
| Журналы | Фильтрация/экспорт журнала операций и системного журнала | Видны записи инициализации, задач и развёртывания |
| API | Создать ключ только для чтения и вызвать `/api/certificates` | Возвращает 200, запрос к несанкционированному интерфейсу возвращает 403 |
| Уведомления | Отправить тестовое уведомление | Целевой канал получает сообщение |
| Мониторинг | Добавить внешний сайт | Сертификат читается и отображается статус |

## 4. Рекомендации по объёму пилота

Пилот не должен стремиться к «полному подключению»; он должен охватывать цепочки, наиболее вероятно выявляющие проблемы:

- 1–2 реальных бизнес-домена, включая один подстановочный сертификат или сертификат на несколько доменов.
- 1 реальная цель развёртывания (одна из SSH, панели, CDN или Webhook).
- 1 сценарий внутренней службы (частный CA или конечная точка ACME).
- 1 канал получения оповещений с явным дежурным и путём эскалации.
- 1 вызывающая автоматизация (CI/CD или скрипт проверки), проверяющая права API-ключа.

Рекомендуемая продолжительность пилота — 1–2 недели, как минимум одно наблюдение автоматического или ручного продления, подтверждение того, что команда перезагрузки при развёртывании не влияет на бизнес.

## 5. Контрольный список вывода в продакшен

### 5.1 Сеть и доступ

- [ ] Точка входа управления публикуется только через HTTPS-обратный прокси; порт за прокси не открыт напрямую в публичную сеть.
- [ ] Настроены `server.trusted_proxies` и `security.public_url`.
- [ ] Защищённая точка входа — случайная длинная строка, не используются угадываемые пути вроде `admin`, `ssl`.
- [ ] Для точки входа управления настроены белый список исходных IP, VPN или стратегия доступа по принципу нулевого доверия.
- [ ] Если включён сервер ACME, используется отдельный порт и ограничен доступ по источникам; EAB включён по умолчанию.

### 5.2 Идентификация и ключи

- [ ] Администратор использует надёжный пароль и включает TOTP или ключ доступа.
- [ ] Почта восстановления контролируется командой безопасности, на самой почте включена многофакторная аутентификация.
- [ ] Для каждой автоматизированной системы создан отдельный API-ключ с минимальными правами и сроком действия.
- [ ] Учётные данные DNS, развёртывания и уведомлений используют отдельные учётные записи, а не личные учётные записи или глобальные ключи администратора.
- [ ] Права `config.yaml` — `0600`, `data/` — `0700`, владелец — пользователь, под которым работает служба.

### 5.3 Данные и восстановление

- [ ] Определены RPO/RTO и настроено как минимум одно зашифрованное резервное копирование в день.
- [ ] Резервные копии хранятся на отдельном носителе, доступ контролируется, пароль восстановления хранится отдельно.
- [ ] Выполнено как минимум одно учение по восстановлению, подтверждено соответствие `salt` и базы данных.
- [ ] Определены срок хранения журналов, объём экспорта и ёмкость хранилища.

### 5.4 Эксплуатация и изменения

- [ ] Определены ответственный за службу, получатель оповещений и окно изменений.
- [ ] Настроены проверка живучести процесса и оповещения об истечении сертификатов/сбое задач.
- [ ] Зафиксирована версия образа или бинарного файла, `latest` не используется долго без возможности отслеживания.
- [ ] Прочитан раздел [Обновление и изменения](upgrade.md), подтверждены шаги миграции и отката.
- [ ] Выполнены высокоприоритетные пункты из [Базовая безопасность](security.md).

## 6. Рекомендации по распределению ответственности

| Ответственность | Рекомендуемое закрепление | Пояснение |
| --- | --- | --- |
| Хост, сеть, обратный прокси | Платформа/эксплуатация | Обеспечение доступности, входящих/исходящих политик и завершения TLS |
| Учётная запись администратора LACTSSL | Руководитель платформы/эксплуатации | Одна учётная запись, должна принадлежать должности, а не человеку на постоянной основе |
| Учётные данные DNS/развёртывания/уведомлений | Безопасность или ответственный за соответствующую систему | Отдельные учётные записи, регулярная ротация, минимальные права |
| API-ключи | Руководитель разработки интеграций | Выдаются по системам, регистрируются назначение, права и срок действия |
| Резервное копирование и учения по восстановлению | Эксплуатация | Пароль резервной копии и процесс восстановления хранятся раздельно |
| Доказательства соответствия | Безопасность/аудит | Используются журнал операций, системный журнал и записи об изменениях |

## 7. Частые причины провала пилота

- **Отношение к защищённой точке входа как к границе безопасности**: точка входа — лишь дополнительный уровень защиты, она не заменяет HTTPS, надёжный пароль и сетевой контроль доступа.
- **Использование личной учётной записи DNS как учётных данных API**: после увольнения сотрудника или включения двухфакторной проверки автоматическое продление завершится сбоем.
- **Непроверенная команда перезагрузки при развёртывании**: файлы сертификата обновились, но Nginx/панель не перезагрузились, и бизнес продолжает использовать старый сертификат.
- **Резервное копирование только базы данных без `config.yaml`**: после потери `salt` зашифрованные учётные данные в базе данных невозможно расшифровать.
- **Один API-ключ с полными правами для всей автоматизации**: при утечке злоумышленник сможет выдавать сертификаты, развёртывать их и экспортировать закрытые ключи.
- **Самообновление внутри контейнера**: после пересоздания контейнера версия вернётся к версии образа; в продакшене обновляйтесь через тег образа.
