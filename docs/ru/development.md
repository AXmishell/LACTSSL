# Разработка расширений: исходный код и сборка

Эта статья предназначена для команд разработки и интеграции, которым требуется доработка, приватная сборка или участие в проекте. **Специалистам по эксплуатации и конечным пользователям читать её не нужно**; о производственном развёртывании см. [Установка и запуск](install.md), об использовании плагинов — [Управление плагинами](plugins.md).

## 1. Структура репозитория

```text
cmd/server/           точка входа программы, запуск и инициализация защищённой точки входа
internal/api/         маршруты Gin, обработчики, сеансы и ограничение частоты
internal/auth/        логика JWT и паролей/TOTP
internal/config/      загрузка и проверка config.yaml
internal/db/          открытие и миграции SQLite
internal/i18n/        серверная интернационализация и языковые ресурсы
internal/logging/     журнал процесса, уровни, формат, ротация файлов и асинхронная запись в базу данных
internal/model/       сущности базы данных и процесс задачи
internal/acme/        встроенный протокол сервера ACME
internal/service/     клиент ACME, развёртывание, уведомления, мониторинг, планировщик
internal/plugin/      хост плагинов и официальные реализации: пакеты хоста + impl/
plugins/             SDK для внешних плагинов: протокол v1, helper-фреймворк, общие утилиты
internal/store/       слой доступа к данным
internal/util/        шифрование, проверка и другие утилиты
internal/webui/       встроенные артефакты сборки внешнего интерфейса
web/                  внешний интерфейс Vue 3 + Element Plus
scripts/              скрипты разработки и CI (TypeScript, запускается напрямую через Node)
docs/                 документация на упрощённом китайском языке
docs/en/              документация на английском языке
docs/zh-hant/         документация на традиционном китайском языке
docs/ja/              документация на японском языке
docs/ru/              документация на русском языке
```

Официальные реализации DNS/развёртывания/уведомлений находятся в `internal/plugin/impl/` этого репозитория и собираются вместе с основным модулем. `plugins/` — SDK для разработки внешних плагинов (протокол, helper-фреймворк и общие утилиты). Загруженные плагины по-прежнему выполняются как подпроцессы протокола v1. Основная программа не зависит от внешнего репозитория плагинов или подписанного индекса.

## 2. Локальная разработка

### 2.1 Окружение

- Go 1.27+
- Node.js 22.12+ и npm (требуется для Vite 8)
- Необязательно: Docker / Docker Compose v2

### 2.2 Основные команды

```bash
make dev          # запустить Vite + Go в режиме разработки в фоне
make dev-down     # остановить процессы разработки
make dev-restart  # перезапустить процессы разработки
make dev-status   # посмотреть PID / порты / состояние работоспособности
make dev-logs     # отслеживать журналы бэкенда и Vite
make build        # производственная сборка, результат bin/lactssl
make backend      # собрать только бэкенд, результат bin/lactssl
make server-dev   # бэкенд в режиме разработки, результат bin/lactssl-dev (без встроенного интерфейса)
make run          # напрямую go run ./cmd/server
make test         # go test ./...
make typecheck    # vue-tsc внешнего интерфейса + tsc для scripts
make ci           # полный локальный CI
make i18n-check   # проверить согласованность ключей перевода (по умолчанию включая китайский, английский и традиционный китайский)
make i18n-check-all # полная проверка всех языков (включая русский и японский)
make tidy         # go mod tidy + установка зависимостей внешнего интерфейса
make clean        # очистить артефакты сборки
make docs-build   # собрать документацию на китайском и английском (strict)
make docs-serve   # локальный предпросмотр двуязычной документации
```

### 2.3 Порты режима разработки

`make dev` запускает:

- Vite: `:5173`, с HMR, исходный код внешнего интерфейса.
- Go: по умолчанию `:8080`, читает `server.addr` / `server.port` из `config.yaml`.

Откройте `http://<host>:5173/<entry>/`. Vite проксирует `/api` и устаревший `/<entry>/api` в Go; Go `8080` **не** выполняет обратное проксирование на `5173`, в производственном режиме Vite отсутствует.

Скрипты режима разработки:

```bash
./scripts/dev.sh start            # запустить бэкенд Go + Vite в фоне
./scripts/dev.sh status           # PID / порты / состояние работоспособности
./scripts/dev.sh logs panel       # отслеживать журнал бэкенда (logs / logs web / logs all)
./scripts/dev.sh restart --build  # перекомпилировать bin/lactssl-dev и перезапустить
./scripts/dev.sh stop             # остановить
```

Файлы PID и журналы находятся в `data/run/`:

```text
data/run/panel.pid  data/run/panel.log
data/run/web.pid    data/run/web.log
```

Основные параметры:

| Параметр | Описание |
| --- | --- |
| `--no-web` | Запустить только бэкенд, без Vite |
| `--build` | Перед запуском/перезапуском выполнить `make server-dev` для перекомпиляции |
| `WEB_PORT` / `DEV_HOST` | Порт Vite (по умолчанию `5173`) и адрес прослушивания (по умолчанию `0.0.0.0`) |

Порт бэкенда и защищённая точка входа единообразно читаются из `config.yaml`; если файл конфигурации отсутствует, он создаётся из `config.yaml.example`.

## 3. Сборка и внедрение версии

- Артефакты сборки внешнего интерфейса сначала выводятся в `web/dist`, затем копируются в `internal/webui/dist` и встраиваются в бинарный файл с помощью тега `embed`.
- Номер версии имеет единственный источник — git tag; он выводится через `scripts/version.sh` вызовом `git describe --tags --always --dirty` (с удалением префикса `v`) и внедряется с помощью `-ldflags -X 'lactssl/internal/api.Version=...'`.
- Время сборки и архитектура внедряются аналогично; если внедрение не выполнено, версия отображается как `dev`.
- Репозиторий не ведёт файл `VERSION`.
- При необходимости зафиксировать версию можно явно переопределить:

```bash
LACTSSL_VERSION=1.2.3 make build
VERSION=1.2.3 make docker-context
docker build --build-arg VERSION=1.2.3 -t lactssl:1.2.3 .
```

## 4. Тестирование и CI

```bash
make test
make typecheck
make i18n-check
make ci
```

`make ci` эквивалентен `.github/workflows/ci.yml`, его также можно разделить:

```bash
./scripts/ci.sh --backend-only
./scripts/ci.sh --frontend-only
./scripts/ci.sh --no-build
```

CI также запускает проверку `gofmt`, `go vet`, тесты с `-race` и статистику покрытия, а также проверку типов и сборку внешнего интерфейса.

## 5. Интернационализация

- Серверные языковые ресурсы находятся в `internal/i18n/locales/`.
- Языковые ресурсы внешнего интерфейса находятся в `web/src/i18n/locales/`.
- При добавлении текста необходимо одновременно дополнить `zh-CN`, `en-US` и `zh-TW`, затем запустить `make i18n-check`.
- В настоящее время встроены традиционный китайский `zh-TW`, русский `ru-RU` и японский `ja-JP`: `zh-TW` по умолчанию участвует в проверке и при отсутствии текста напрямую откатывается на `zh-CN`; русский и японский по умолчанию не участвуют в проверке и при отсутствии текста откатываются по цепочке `язык → en-US → zh-CN`; после синхронизации перевода можно выполнить полную проверку с помощью `make i18n-check-all` (или `I18N_CHECK_ALL=1`).
- Скрипт проверки написан на TypeScript (`scripts/check-i18n.ts`) и запускается напрямую встроенным в Node удалением типов, требуется Node 22.18+.
- Проверка типов самого скрипта включена в `make typecheck` (конфигурация в `scripts/tsconfig.json`).

## 6. Сборка документации

Документация использует Zensical/MkDocs:

```bash
make docs-build   # собрать все языки в режиме strict
make docs-serve   # предпросмотр в фоне (порт 8000, -l задаёт язык, остановка: scripts/docs-serve.sh stop)
```

- Английская конфигурация: `mkdocs.yml`, вывод в `site` (сайт по умолчанию).
- Упрощённый китайский: `mkdocs.zh.yml` → `site/zh`.
- Традиционный китайский: `mkdocs.zh-hant.yml` → `site/zh-hant`.
- Японский: `mkdocs.ja.yml` → `site/ja`.
- Русский: `mkdocs.ru.yml` → `site/ru`.
- `docs-internal/` — внутренние записи проектирования, не входят в сайт.
- При добавлении страницы необходимо синхронно создать зеркало в `docs/<язык>/` и обновить nav в конфигурациях всех языков.

## 7. Процесс выпуска

Релиз использует tag как единственный источник. GitHub Release запускает workflow `Release`, который автоматически собирает и загружает артефакты для каждой платформы:

```bash
gh release create v1.0.1 --generate-notes
```

Артефакты включают:

- `lactssl_<version>_linux_amd64.tar.xz`
- `lactssl_<version>_linux_amd64.tar.gz`
- `lactssl_<version>_linux_arm64.tar.xz`
- `lactssl_<version>_linux_arm64.tar.gz`
- `lactssl_<version>_darwin_amd64.tar.xz`
- `lactssl_<version>_darwin_amd64.tar.gz`
- `lactssl_<version>_darwin_arm64.tar.xz`
- `lactssl_<version>_darwin_arm64.tar.gz`
- `lactssl_<version>_windows_amd64.zip`
- `checksums.txt` (SHA-256)

Архив содержит бинарный файл, `README.md`, `LICENSE` и `config.yaml.example`. Номер версии берётся непосредственно из tag (с удалением префикса `v`) и не зависит от локального вывода git. Для не-Windows платформ публикуются оба архива: `.tar.xz` меньше по размеру, а `.tar.gz` обеспечивает совместимость со старыми клиентами автообновления.

Одновременно собираются образы `linux/amd64`, `linux/arm64` и публикуются в GHCR:

```text
ghcr.io/axmishell/lactssl:<version>
ghcr.io/axmishell/lactssl:<major>.<minor>
ghcr.io/axmishell/lactssl:<major>
ghcr.io/axmishell/lactssl:latest
```

Предварительные версии публикуют только полный тег `<version>` и не обновляют `latest`, `<major>.<minor>` и `<major>`. После первого релиза пакет GHCR по умолчанию приватный; его нужно изменить на Public в настройках пакета.

Примечания:

- workflow запускается только при официальном релизе Release; `gh release create --draft` начнёт сборку только после нажатия кнопки публикации.
- Перед первым использованием `.github/workflows/release.yml` должен уже присутствовать в коммите, на который указывает tag.
- Одноимённые файлы, предварительно загруженные с помощью `gh release create <tag> <files>...`, будут перезаписаны workflow с `--clobber`; рекомендуется не передавать файлы при создании.
- После публикации Release артефакты собираются несколько минут; если нужно «опубликовать после готовности артефактов», сначала отправьте tag, дождитесь завершения сборки CI и только затем создайте Release (потребуется отдельно настроить процесс по push tag).
- Пересобрать указанный tag: `gh workflow run release.yml -f tag=v1.0.1`.
- Подпись релиза: после настройки `ED25519_PRIVATE_KEY_B64` для `checksums.txt` создаётся отсоединённая подпись.

Локальный скрипт выпуска:

```bash
make release TAG=v1.0.1
./scripts/release.sh v1.0.1 --no-docker
./scripts/release.sh v1.0.1 --multiarch
./scripts/release.sh v1.1.0-rc.1 --docker-only
./scripts/release.sh v1.0.1 --publish-only
./scripts/release.sh v1.0.1 --upload
```

`--multiarch` требует Docker Buildx. QEMU не нужен: образ только копирует бинарники, собранные кросс-компиляцией на хосте, и не выполняет команды целевой архитектуры при сборке.

## 8. Совместная отладка плагинов

Официальные реализации находятся в `internal/plugin/impl/`; `plugins/` содержит только SDK для внешних плагинов и подключается через локальный `replace` в `go.mod` основного репозитория. После изменения официальной реализации собирайте из корня репозитория:

```bash
go work init . ../LACTSSL-Plugins
```

После изменения реализации плагина выполните в репозитории плагинов `make gen` и `make plugin KIND=dns GOOS=linux GOARCH=amd64` для сборки объединённого пакета; после завершения интеграции удалите `go.work` (файл уже включён в gitignore).

Протокол плагинов, поля и подписи см. в разделе [Разработка плагинов](plugin-development.md).

## 9. Рекомендации по участию

- Не коммитьте `config.yaml`, `data/`, резервные копии, журналы или любые реальные учётные данные.
- При изменении логики, связанной с безопасностью, одновременно обновляйте [Базовую безопасность](security.md) и тесты.
- При изменении поведения API/конфигурации/плагинов одновременно обновляйте документацию на китайском и английском.
- Для новых интерфейсов необходимо добавить политику разрешений API-ключей и тесты.
- При миграции данных предоставляйте идемпотентные шаги, резервную копию и инструкции по откату.
- Перед коммитом запускайте `make ci` и `make docs-build`.
