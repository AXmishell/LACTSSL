# Архитектура развёртывания

Эта статья предназначена для архитекторов платформ и руководителей эксплуатации и описывает единицы развёртывания LACTSSL, сетевые границы, оценку ёмкости и проектирование доступности. **Развёртывание по умолчанию по-прежнему — один экземпляр, один арендатор, SQLite с одной записью**; начиная с текущей версии можно также явно выбрать PostgreSQL 18 и переключаться между двумя бэкендами через `/upgrade`. Совместное использование PostgreSQL несколькими экземплярами по умолчанию отклоняется; HA по-прежнему не входит во встроенные возможности.

## 1. Единицы развёртывания

LACTSSL — самодостаточный бинарный файл Go:

- Артефакты сборки фронтенда встроены в бинарный файл, отдельный веб-сервер или среда выполнения Node не нужны.
- Данные хранятся в локальном SQLite, без внешней базы данных, кеша или очереди сообщений.
- Плагины DNS, развёртывания и уведомлений запускаются как одноразовые дочерние процессы, файлы плагинов размещаются в каталоге данных.
- Во время работы есть только два постоянных входных источника: `config.yaml` и каталог `data/`.

```text
/opt/lactssl/
├── lactssl                 # бинарный файл
├── config.yaml             # конфигурация и ключи, 0600
└── data/                   # 0700
    ├── lactssl.db          # основная база SQLite
    ├── lactssl.db-wal      # WAL (во время работы)
    ├── lactssl.db-shm      # разделяемая память (во время работы)
    ├── plugins/            # загруженные helper (dns / deploy / notify)
    ├── plugin-icons/       # кеш иконок плагинов
    ├── upgrade-backups/    # резервные копии миграций и обновлений программы
    └── restore-pending/    # пакеты восстановления, ожидающие применения
```

Граница резервного копирования — это `config.yaml` + `data/`. Резервное копирование только базы данных приведёт к потере `salt`, и зашифрованные учётные данные нельзя будет расшифровать.

## 2. Эталонная топология

### 2.1 Один хост + обратный прокси (рекомендуемая отправная точка)

```text
Интернет / внутренняя сеть предприятия
        │ HTTPS 443
┌───────▼────────────────┐
│ Nginx / Caddy          │  завершение TLS, ограничение источников, журнал доступа
│ / WAF / балансировщик  │
└───────┬────────────────┘
        │ HTTP 127.0.0.1:8080
┌───────▼────────────────────────────────────────────┐
│ LACTSSL                                            │
│  ├─ Консоль управления / API                       │
│  ├─ Планировщик (проверка задач каждые 30 секунд)  │
│  ├─ Частный CA / служба ACME (опционально)         │
│  └─ SQLite + локальные плагины                     │
└───┬─────────────────┬───────────────┬──────────────┘
    │                 │               │
API DNS      цель развёртывания    уведомления/почта
```

Применение: большинство корпоративных развёртываний в одной среде, от десятков до тысяч сертификатов.

Ключевые моменты:

- Основная программа сама не предоставляет конфигурацию TLS для порта управления; в продакшене TLS обязательно завершается на обратном прокси.
- Обратный прокси и LACTSSL лучше размещать на одной машине или в одной подсети; порт бэкенда должен слушать только loopback или внутреннюю сеть.
- Обратный прокси должен перезаписывать или корректно добавлять `X-Forwarded-For` и передавать `X-Forwarded-Proto`, а в `server.trusted_proxies` нужно зарегистрировать точный IP или минимальный CIDR прокси. В цепочке добавления регистрируйте все прокси цепочки.
- `security.public_url` должен быть настроен на фиксированный внешний адрес, чтобы ссылки сброса пароля и т. п. не зависели от Host запроса.

### 2.2 Прокси в DMZ + внутреннее приложение

```text
Пользователь ──HTTPS──► обратный прокси в DMZ ──HTTP внутренней сети──► LACTSSL (сегмент приложений)
                                                                            │
                                                                            ├─► DNS API / публичный CA (исходящий 443)
                                                                            ├─► SSH / панель / CDN (в зависимости от цели)
                                                                            └─► SMTP / Webhook (в зависимости от канала)
```

Применение: повышенные требования безопасности, плоскость управления не открыта напрямую в сегменте бизнеса.

Ключевые моменты:

- На брандмауэре разрешайте только порт управления от прокси к LACTSSL.
- Исходящий доступ LACTSSL настраивается по белому списку целей; если белый список доменов невозможен, как минимум ограничьте целевые порты и подсети.
- Если нужно отдельно открыть сервер ACME в DMZ, используйте отдельный порт прослушивания и не переиспользуйте порт управления.

### 2.3 Внутренний PKI / служба ACME

```text
Внутренние службы / certbot / lego / acme.sh
        │ ACME v2 (HTTPS или mTLS)
┌───────▼──────────────────────────────────┐
│ Конечная точка ACME LACTSSL              │  отдельный порт :14000
│ привязка к частному CA                   │  белый список доменов / EAB / типы проверок
└───────┬──────────────────────────────────┘
        │
   иерархия частного CA
```

Применение: сертификаты внутренних служб, сертификаты устройств, сертификаты тестовых сред.

Ключевые моменты:

- Если конечная точка ACME не создана и не включена, сертификаты не выдаются; для каждой конечной точки должен быть настроен белый список доменов.
- Если конечная точка доступна из публичной сети, рекомендуется включить EAB и ограничить источники на сетевом уровне; при более высоких требованиях используйте mTLS.
- `acme.base_url` должен быть фиксированным адресом, по которому клиенты фактически обращаются; при развёртывании в публичной сети не полагайтесь на Host запроса.
- Конечные точки CRL/OCSP организуются по CA; после отключения конечной точки регистрации ACME они всё равно должны оставаться доступными (если клиентам нужно проверять отзыв).

### 2.4 Контейнерная платформа

```text
Ingress / Service
        │
┌────────▼───────────┐
│ Pod: lactssl       │
│  /app/config       │  ── PVC или том конфигурации
│  /app/data         │  ── PVC
└────────────────────┘
```

Ключевые моменты:

- При использовании официального образа контейнер всегда читает `/app/config/config.yaml`, каталог данных — `/app/data`.
- Входной скрипт исправляет владельца смонтированных каталогов, затем понижает права и запускается от пользователя `lactssl`; Compose по умолчанию использует корневую файловую систему только для чтения и отбрасывает capabilities.
- **Одна реплика**: не позволяйте нескольким Pod одновременно записывать в один том данных SQLite.
- Самообновление внутри контейнера не меняет образ, после пересоздания версия вернётся к версии образа; в продакшене обновляйтесь через тег образа.
- Используйте `restart: unless-stopped` или эквивалентную политику платформы оркестрации; после восстановления резервной копии служба должна автоматически подняться.

## 3. Порты и сетевые потоки

| Направление | Порт/протокол | Назначение | Рекомендация |
| --- | --- | --- | --- |
| Входящий | 443/TCP | Консоль управления и API (через обратный прокси) | Открывать только для контролируемых источников |
| Входящий | 8080/TCP | Основной прослушиватель LACTSSL (по умолчанию) | Слушать только loopback/внутреннюю сеть, доступ через прокси |
| Входящий | произвольный/TCP | Отдельный прослушиватель ACME (опционально) | Отдельный порт, ограничение источников |
| Исходящий | 443/TCP | API DNS-провайдеров, публичные ACME CA, уведомления, Webhook, панели, облачные CDN | Белый список по доменам/подсетям |
| Исходящий | 22/TCP или произвольный | Развёртывание по SSH/SFTP | Открывать только целевые хосты |
| Исходящий | 21/990/TCP | Развёртывание по FTP/FTPS (плагин) | Предпочитать FTPS, ограничить цели |
| Исходящий | 25/465/587/TCP | Уведомления по SMTP | Использовать корпоративный почтовый шлюз |
| Исходящий | произвольный | Собственный Gotify, внутренний Webhook, цели мониторинга | Открывать по необходимости, учитывать границы SSRF |

Пояснения:

- Сервер выполняет проверку SSRF для исходящих целей и отклоняет адреса облачных метаданных, link-local, зарезервированных подсетей и т. п.; loopback и частные сети по-прежнему разрешены для удобства внутренних интеграций.
- При развёртывании Webhook передаётся закрытый ключ сертификата, для публичных целей принудительно используется HTTPS; для loopback, частных сетей, `.local`, `.internal` разрешён HTTP.
- Если обратный прокси выполняет завершение TLS, бэкенд доступен по HTTP; необходимо корректно передавать `X-Forwarded-Proto`, иначе определение `Secure` для Cookie и распознавание ограничения частоты будут работать неверно.

## 4. Планирование ёмкости

Ниже приведены **справочные отправные точки**, а не обязательства производителя. Фактическая ёмкость зависит от количества сертификатов, частоты задач, объёма журналов, типов плагинов и стратегии резервного копирования; перед продакшеном рекомендуется провести нагрузочное тестирование с реальной нагрузкой.

| Масштаб | Объём сертификатов/задач | Рекомендуемая конфигурация | Пояснение |
| --- | --- | --- | --- |
| Пилот/малый масштаб | < 100 сертификатов, небольшое количество задач | 2 vCPU / 1 GB / 10 GB | Избегайте одновременной установки больших пакетов плагинов |
| Средний масштаб | 100–1 000, ежедневное продление | 2–4 vCPU / 2 GB / 20 GB | Рекомендуется включить ротацию журналов и периодическую очистку |
| Крупный масштаб | 1 000–5 000, частое развёртывание | 4–8 vCPU / 4 GB / 50 GB+ | Следите за усилением записи SQLite, окнами резервного копирования и пиками плагинов |

Память:

- Базовая линия простоя основного процесса — несколько десятков MB; плагины — дочерние процессы, запускаемые при каждом вызове, отдельный helper ограничен `memory_limit_mb` (по умолчанию 128 MB).
- Распаковка при установке/обновлении плагинов вызывает кратковременный пик памяти, особенно заметный для больших DNS-пакетов; не сжимайте память контейнера ровно до объёма простоя.
- При одновременном выполнении нескольких задач может запускаться несколько helper, нужно оставлять запас на пики.

Хранилище:

- Рост базы данных в основном обусловлен сертификатами, журналами задач, журналом операций, системным журналом и заказами ACME.
- Журнал операций и системный журнал используют общую таблицу `logs` и различаются по `category`; политики хранения и очистки изолированы по категориям, очистка системного журнала не влияет на журнал операций.
- Для сертификатов, журналов и диагностических данных ACME предусмотрены точки очистки; для системного журнала есть `retention_days` и `max_rows`.
- `data/upgrade-backups/` по умолчанию хранит последние 5 снимков миграции, при обновлении программы по умолчанию сохраняются 3 старых бинарных файла.
- Не записывайте файлы резервных копий обратно в тот же каталог данных; место для резервных копий резервируйте с запасом в несколько раз больше размера базы данных.

## 5. Доступность и аварийное восстановление

### 5.1 Границы доступности текущей версии

- **Встроенный кластер/режим «активный-активный» не поддерживается**. SQLite с одной записью; одновременное монтирование одного каталога данных несколькими экземплярами приведёт к конкуренции блокировок или повреждению данных.
- **Автоматическое переключение при сбое не предоставляется**. Обратный прокси может проверять живучесть, но не должен автоматически переключать трафик на другой экземпляр, записывающий те же данные.
- **Одна учётная запись администратора** — единая точка: при потере учётной записи нужно восстановление из резервной копии или сброс пароля; рекомендуется привязать обязанности администратора к должности и обеспечить передачу.

### 5.2 Один активный экземпляр + быстрое восстановление (рекомендуется)

```text
Основной экземпляр ──периодическая зашифрованная резервная копия──► отдельное хранилище резервных копий
   │
   └─ сбой ──► новый хост/новый контейнер ──восстановление резервной копии──► переключение трафика
```

Рекомендуемые целевые показатели:

| Показатель | Рекомендация |
| --- | --- |
| RPO | По допустимости бизнеса, минимум раз в день; для критичных сред можно сократить до часового уровня |
| RTO | Оценивается как «подготовка хоста + восстановление резервной копии + проверка запуска», после учений рекомендуется внести в Runbook |
| Хранение резервных копий | Не менее 7–30 дней, для критичных сред продлевать по требованиям соответствия |
| Частота учений | Не менее одного полного учения по восстановлению в квартал |

Шаги восстановления см. в [Руководство по эксплуатации](operations.md).

### 5.3 Высокая доступность на уровне контейнеров и хостов

Платформа оркестрации может обеспечить перезапуск **процесса**, но не решает проблему одной записи данных:

- Количество реплик фиксировано — 1.
- Используйте постоянные тома, чтобы избежать потери данных после пересоздания Pod.
- Для проверки работоспособности используйте TCP-порт или `/api/status` с аутентификацией; не используйте для неаутентифицированной проверки страницу, требующую Cookie защищённой точки входа.
- При сбое узла платформа перепланирует единственную реплику; том данных должен иметь возможность повторного монтирования.

### 5.4 Изоляция нескольких сред

Продакшен, предпродакшен и тестовая среда должны использовать отдельные экземпляры:

- Отдельный `config.yaml`, отдельный `security.salt`, отдельный каталог данных.
- Отдельные субучётные записи DNS и учётные данные развёртывания, чтобы тестовые задачи не влияли на продакшен.
- Отдельные каналы уведомлений, чтобы тестовые оповещения не попадали в продакшен-группу дежурных.
- Не копируйте продакшен-базу данных в тестовую среду и не продолжайте использовать те же учётные данные; если копирование необходимо, сначала смените учётные данные.

## 6. Мониторинг и наблюдаемость

LACTSSL не предоставляет конечную точку метрик Prometheus, но мониторинг можно построить по следующим сигналам:

| Сигнал | Способ | Рекомендация |
| --- | --- | --- |
| Живучесть процесса | Проверка TCP-порта | Раз в 30–60 секунд |
| Глубокая проверка работоспособности | `GET /api/status` с API-ключом, имеющим `system:read` | Раз в 1–5 минут, проверять код 200 и время ответа |
| Сбой задачи | Фильтрация журнала операций или канал уведомлений | Немедленное оповещение о сбое задачи/развёртывания |
| Приближение срока сертификата | Панель управления, мониторинг сайтов, статус продления задач | Поэтапные напоминания за 30/14/7 дней до истечения |
| Аномалии журналов | Ключевые слова системного журнала, 5xx обратного прокси | Подключение к корпоративной платформе журналов |
| Диск/резервные копии | Мониторинг хоста или платформы | Оповещение при заполнении диска < 20%, оповещение о сбое резервного копирования |

`/api/status` требует аутентификации и не может напрямую использоваться как анонимная проверка работоспособности; анонимная проверка может определить только доступность порта.

## 7. Границы TLS и сертификатов

- TLS консоли управления обеспечивается обратным прокси; основной порт LACTSSL не настраивает TLS напрямую.
- Обратный прокси должен использовать сертификат, выданный корпоративным CA или публичным CA, и настроить HSTS, TLS 1.2+, отключение слабых наборов шифров.
- Отдельный прослушиватель ACME может напрямую предоставлять TLS (`acme.tls.cert/key`) или завершаться обратным прокси; при включении mTLS необходимо одновременно настроить сертификат и закрытый ключ TLS ACME.
- Закрытые ключи сертификатов, управляемых LACTSSL, хранятся в базе данных и шифруются ключом, производным от `security.salt`; HSM/KMS не поддерживается.
- База данных и конфигурация в пакете резервной копии содержат зашифрованные учётные данные и материалы ключей; обращайтесь с ними как с конфиденциальными файлами.

## 8. Контрольный список архитектурных решений

При рассмотрении решения рекомендуется явно определить следующие решения:

| Решение | Варианты | Рекомендация |
| --- | --- | --- |
| Способ развёртывания | Docker / бинарный файл / платформа оркестрации | При наличии контейнерной платформы предпочитайте образ; иначе бинарный файл + systemd |
| Завершение TLS | Обратный прокси / отдельный прослушиватель ACME | Плоскость управления — единообразно через обратный прокси |
| Хранение данных | Локальный диск / постоянный том / сетевой диск | Только монтирование с одной записью; для сетевого диска нужно проверить семантику блокировок SQLite |
| Доступность | Один активный + резервные копии / перезапуск платформой | Не использовать «активный-активный»; явно определить RTO/RPO |
| Исходящая политика | Полный доступ / белый список доменов / прокси | В продакшене белый список по целям, при необходимости через корпоративный прокси |
| Источник плагинов | Официальный репозиторий / внутреннее зеркало / ручная загрузка | В продакшене предпочитайте внутреннее зеркало + проверку подписи |
| Способ обновления | Тег образа / замена бинарного файла | В контейнерах — образ, для бинарного файла — пакет релиза с сохранением возможности отката |
