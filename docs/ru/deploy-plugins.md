# Плагины развёртывания

Плагины развёртывания доставляют сертификаты в такие цели, как FTP, Webhook, облачный CDN, панели и WAF. Это **высокорисковый компонент, имеющий доступ к закрытым ключам сертификатов**; предприятия должны включать плагины развёртывания в управление допуском и изменениями.

## 1. Встроенные и плагинные цели

| Тип | Цель | Встроенная | Описание |
| --- | --- | --- | --- |
| Встроенная | Локальный каталог | Да | Запись в локальный путь, необязательная команда перезагрузки |
| Встроенная | SSH / SFTP | Да | Аутентификация по паролю или закрытому ключу, проверка отпечатка хоста |
| Плагин | FTP / FTPS | Нет | Обычный FTP, явный TLS, неявный TLS |
| Плагин | Webhook | Нет | Настраиваемые заголовки аутентификации, возможность пропуска проверки TLS (не рекомендуется) |
| Плагин | Alibaba Cloud CDN | Нет | Обновление сертификата домена |
| Плагин | Qiniu Cloud | Нет | Домен ускорения CDN или пользовательский домен источника Kodo |
| Плагин | Панель Baota / Baota WAF | Нет | Сайт, панель или WAF |
| Плагин | 1Panel | Нет | Сайт или панель |
| Плагин | SafeLine WAF | Нет | Сопоставление по ID сертификата или домену |
| Плагин | Tencent Cloud / Volcano Engine / AcePanel и др. | Нет | Ориентируйтесь на фактические записи магазина плагинов |

> **Плагины развёртывания получают закрытые ключи сертификатов.** Устанавливайте helper только из доверенных источников и убедитесь, что каталог плагинов доступен для записи только пользователю сервиса. Плагины развёртывания по умолчанию отключены и требуют явного включения.

## 2. Учётные данные и параметры развёртывания

«Учётные данные цели» хранят только информацию аутентификации и подключения, например хост, порт, имя пользователя, пароль, адрес панели и API Token. Пути сертификатов, команды перезагрузки, домены развёртывания, сайты и другие параметры заполняются в узле «Развернуть сертификат» процесса задачи.

Преимущества такого дизайна:

- Одни учётные данные можно повторно использовать в нескольких задачах.
- Ротация учётных данных не влияет на оркестрацию задач.
- Параметры развёртывания сохраняются в истории версий задачи, что упрощает аудит и откат.

## 3. Конфигурация

```yaml
deploy_plugins:
  enabled: false          # плагин получает доступ к закрытым ключам, по умолчанию отключён
  dir: ""                 # пусто означает <data_dir>/plugins/deploy
  memory_limit_mb: 128    # верхний предел постоянной памяти одного helper
  timeout_seconds: 300    # тайм-аут одного deploy, можно увеличить при загрузке больших файлов
  max_output_kb: 64       # верхний предел вывода helper
```

Три типа плагинов используют отдельные подкаталоги в `<data_dir>/plugins`:

- DNS: `<data_dir>/plugins/dns`
- Развёртывание: `<data_dir>/plugins/deploy`
- Уведомления: `<data_dir>/plugins/notify`

Изменения конфигурации вступают в силу после перезапуска сервиса. При запуске выполняется автоматическое сканирование; после установки нового helper на странице «Плагины» можно нажать «Пересканировать плагины» или вызвать:

```bash
curl -X POST -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/plugins/rescan
```

## 4. Установка и включение

1. Установите `deploy_plugins.enabled: true` в конфигурации и перезапустите сервис.
2. Откройте страницу «Плагины», проверьте адрес репозитория и нажмите «Обновить индекс».
3. В «Магазине плагинов» установите нужную цель развёртывания.
4. Сначала включите файл плагина, затем включите конкретную цель в списке целей развёртывания; новые загруженные файлы и записи по умолчанию отключены.

Если плагин не установлен или не включён, в типах развёртывания учётных данных цели и процесса задачи будут доступны только локальный файл и SSH; прежние учётные данные не теряются и остаются доступными после установки плагина.

Состояние включения хранится в таблице settings в `plugins.deploy.enabled_deployers` и содержит только ID включённых целей; оно сохраняется после перезапуска и повторного сканирования. Объединённые цели в «Учётных данных цели» отображаются как одна запись производителя, конкретный продукт выбирается в узле развёртывания задачи через «Объект развёртывания».

## 5. Рекомендации по целям

### 5.1 Локальный каталог

- Пользователь, от имени которого работает сервис, должен иметь права на запись в целевой каталог.
- Рекомендуется атомарная запись: сначала записать временный файл, затем перезаписать через `rename`, чтобы избежать чтения половины файла.
- Примеры команд перезагрузки: `nginx -s reload`, `systemctl reload nginx`, `systemctl reload postfix`.
- Сбой команды перезагрузки не откатывает файлы сертификатов; необходимо сохранять предыдущую версию на целевой стороне.

### 5.2 SSH / SFTP

- По умолчанию требуется указать отпечаток целевого хоста (`SHA256:...`). TOFU применяется только при явном включении «Автоматически доверять ключу хоста при первом подключении»; при последующем несовпадении отпечатка подключение отклоняется.
- После смены ключа сервера необходимо очистить старый отпечаток и записать его заново.
- Рекомендуется использовать выделенного пользователя развёртывания, предоставив только права на запись в целевой путь и необходимые права на перезагрузку (sudoers с точностью до команды).
- Аутентификация по закрытому ключу имеет приоритет над паролем; храните закрытый ключ в контролируемом месте, устанавливайте парольную фразу и регулярно выполняйте ротацию.

### 5.3 FTP / FTPS

- По умолчанию используется явный TLS; открытый FTP применяется только при явном выборе `none`.
- Закрытый ключ сертификата и пароль для входа передаются по сети; в производственной среде предпочитайте SFTP или FTPS.
- Ограничьте целевые IP, порты и права на каталоги; не используйте общие учётные записи.

### 5.4 Webhook

- Для публичных целей принудительно используется HTTPS; для loopback, частных сетей, `.local`, `.internal` допускается HTTP.
- Webhook передаёт сертификат и закрытый ключ, поэтому получатель должен быть доверенным; рекомендуется использовать отдельный Token и ограничение по IP источника.
- Не рекомендуется включать «Пропускать проверку TLS»; если это необходимо, ограничьте внутренними самоподписанными целями. Для сертификатов, выпущенных внутренним CA, импортируйте открытый ключ CA через «Системные настройки → Цепочка доверия TLS», чтобы плагин развёртывания доверял цели при обычной проверке.
- Получатель должен обеспечивать идемпотентность и проверку подписи, чтобы избежать повторного воспроизведения.

### 5.5 Облачный CDN / панели / WAF

- Используйте для учётных данных выделенную субучётную запись, предоставляя только права, связанные с управлением сертификатами.
- Параметры развёртывания (домен, сайт, имя сертификата) должны совпадать с целевой системой; названия сайтов и Docker-сайтов панели Baota можно прочитать через API панели и выбрать из раскрывающегося списка.
- Если плагин не реализует динамические параметры или панель недостижима, название можно ввести вручную.
- Если в целевой системе включён белый список IP, разрешите исходящий адрес LACTSSL.
- В CDN/WAF может быть кэш сертификатов; после развёртывания проверьте фактически действующий сертификат.

## 6. Записи развёртывания и проверка

- Каждое развёртывание создаёт запись развёртывания; результат можно посмотреть в сведениях о сертификате и журналах.
- При ручном развёртывании приоритетно используются параметры узла развёртывания задачи, которой принадлежит сертификат; также можно отдельно указать параметры для конкретной цели.
- Локальное/SSH-развёртывание выполняет команду перезагрузки; API-ключ должен явно иметь `deploy:execute`.
- При сбое развёртывания старый сертификат в целевой системе не откатывается автоматически; необходимо сохранять предыдущую версию на целевой стороне или использовать атомарную публикацию.

Контрольный список проверки:

- [ ] Целевой путь/сайт указан верно.
- [ ] Цепочка сертификатов полная (fullchain).
- [ ] Закрытый ключ соответствует сертификату.
- [ ] Служба перезагружена и фактически загрузила новый сертификат.
- [ ] Все экземпляры/узлы обновлены.
- [ ] Кэш CDN/WAF обновлён.
- [ ] Браузер/клиент показывает серийный номер или отпечаток нового сертификата.

## 7. Офлайн- и ручная установка

- На странице «Плагины» загрузите один helper, не более 256 MB; использовать его можно только после включения `deploy_plugins.enabled`.
- После загрузки сначала проверяются `manifest`, ID цели развёртывания и SHA-256; только после успешной проверки файл записывается в каталог плагинов развёртывания и немедленно выполняется повторное сканирование.
- По умолчанию перезапись одноимённого файла запрещена; при обновлении отметьте «Разрешить перезапись одноимённого плагина», старый файл будет предварительно сохранён в резервной копии.
- Плагин с ID, совпадающим со встроенной целью развёртывания, будет обнаружен, но результат повторного сканирования помечается как «проигнорирован».

## 8. Протокол Helper v1 (разработка интеграций)

helper — это исполняемый файл, поддерживающий следующие подкоманды:

```bash
deploy-helper manifest   # вывести JSON-манифест
deploy-helper deploy     # прочитать запрос из stdin и выполнить развёртывание
deploy-helper options    # прочитать динамические параметры раскрывающегося списка (необязательно)
deploy-helper verify     # проверить только для чтения аутентификацию и область действия цели (необязательно)
```

Пример вывода `manifest`:

```json
{
  "protocol": "v1",
  "capabilities": ["verify-v1"],
  "name": "example deploy helper",
  "version": "1.0.0",
  "sha256": "необязательная контрольная сумма файла helper",
  "deployers": [
    {
      "id": "example-panel",
      "name": "Example Panel",
      "name_i18n": {"zh-CN": "示例面板", "en-US": "Example Panel"},
      "capabilities": ["verify-v1"],
      "description": "Отправка сертификатов в панель Example",
      "description_i18n": {
        "zh-CN": "把证书推送到 Example 面板",
        "en-US": "Push certificates to an Example panel"
      },
      "aliases": ["example"],
      "fields": [
        {
          "key": "panel_url",
          "label": "Адрес панели",
          "label_i18n": {"zh-CN": "面板地址", "en-US": "Panel URL"},
          "type": "text",
          "required": true
        },
        {
          "key": "api_token",
          "label": "API Token",
          "label_i18n": {"zh-CN": "API Token", "en-US": "API Token"},
          "type": "password",
          "secret": true,
          "required": true
        }
      ],
      "deploy_fields": [
        {
          "key": "sites",
          "label": "Сайт",
          "label_i18n": {"zh-CN": "站点", "en-US": "Sites"},
          "type": "text",
          "required": true
        }
      ]
    }
  ]
}
```

Описание полей:

- `fields` — информация аутентификации и подключения в учётных данных цели; `secret: true` или `type: "password"` маскируются при возврате через интерфейс и хранятся в зашифрованном виде вместе с учётными данными.
- `deploy_fields` — параметры в узле «Развернуть сертификат» процесса задачи.
- Ключи `key` двух типов полей не должны повторяться; поддерживаемые типы полей: `text`, `password`, `textarea`, `number`, `select`, `switch`.
- ID цели развёртывания `id` может содержать только строчные буквы, цифры, подчёркивания или дефисы; плагины с ID, совпадающим со встроенной целью, игнорируются.
- `name` / `description` / `label` / `placeholder` / `help` — текст языка по умолчанию; необязательные таблицы `*_i18n` переопределяют его по языкам.
- Языковые ключи используют форму BCP 47, например `zh-CN`, `en-US`; одна таблица текстов поддерживает не более 32 языков.

stdin для `deploy`:

```json
{
  "action": "deploy",
  "protocol": "v1",
  "provider": "example-panel",
  "auth": {"panel_url": "https://panel.example.com", "api_token": "..."},
  "config": {"sites": "example.com,www.example.com"},
  "certificate": {
    "domain": "example.com",
    "domains": ["example.com", "www.example.com"],
    "issuer": "Let's Encrypt",
    "serial": "...",
    "not_before": "2026-01-01T00:00:00Z",
    "not_after": "2026-04-01T00:00:00Z",
    "cert_pem": "-----BEGIN CERTIFICATE-----...",
    "fullchain_pem": "-----BEGIN CERTIFICATE-----...",
    "key_pem": "-----BEGIN PRIVATE KEY-----..."
  }
}
```

stdin / stdout для `verify`:

```json
{"action": "verify", "provider": "example-panel", "auth": {"panel_url": "...", "api_token": "..."}, "config": {"sites": "example.com"}, "mode": "read", "locale": "zh-CN"}
```

```json
{"ok": false, "checks": [{"key": "auth", "status": "failed", "message": "invalid token"}]}
```

Соглашения:

- Код выхода `0` означает успех, отличный от `0` — ошибку; stderr попадает в запись развёртывания (чувствительные значения маскируются).
- stdout может быть пустым или содержать одну строку JSON: `{"ok": true, "message": "..."}`; если `ok` равен `false`, результат считается ошибкой.
- `verify` должен быть операцией только для чтения: запрещено записывать сертификаты, создавать постоянные объекты или выполнять `reload_command`; только явный тест записи с `mode=write` может создавать и очищать уникальный временный объект.
- Вызов `verify` получают только цели развёртывания, объявившие возможность `verify-v1`; для необъявивших целей основная программа показывает «версия плагина не поддерживает проверку».
- `checks` служит для различения проблем подключения, аутентификации, области действия и прав; значения `status`: `ok`, `failed`, `skipped`, `unsupported`, `error`.
- Некорректный JSON считается ошибкой; отладочные журналы записывайте в stderr.
- helper получает бюджет памяти из `LACTSSL_PLUGIN_MEMORY_LIMIT` (в байтах).
- Основная программа периодически проверяет `VmRSS` helper и при превышении `memory_limit_mb` завершает всю группу процессов и записывает ошибку.
- Основная программа передаёт только минимальный набор переменных окружения и не раскрывает серверные ключи.
- Файл плагина должен быть исполняемым и не должен допускать запись группой или другими пользователями; если `manifest.sha256` не пуст, выполняется проверка.
- Основная программа записывает дайджест файла при сканировании и повторно проверяет его перед каждым развёртыванием; после замены helper требуется повторное сканирование.

## 9. Рекомендации по безопасности

- Включайте только доверенные helper; плагин развёртывания может читать закрытые ключи сертификатов и эквивалентен доверенному коду.
- Каталог плагинов `0700`, helper `0755`, владелец — пользователь, от имени которого работает сервис.
- В производственной среде указывайте `sha256` в манифесте и обновляйте дайджест после обновления.
- Устанавливайте разумные `memory_limit_mb` и `timeout_seconds`, чтобы аномальный плагин не перегрузил хост.
- Не давайте пользователю `lactssl` дополнительных прав и не размещайте каталог плагинов в общем доступном для записи пути.
- Используйте для целей развёртывания учётные записи с минимальными правами, а команды перезагрузки ограничивайте конкретным сервисом.

## 10. Устранение неполадок

| Симптом | Причина | Действие |
| --- | --- | --- |
| В типах развёртывания только локальный/SSH | Плагин не включён/не установлен | Включите `deploy_plugins.enabled`, установите и включите цель |
| Не удаётся загрузить плагин | Права/дайджест/протокол/символическая ссылка | Исправьте права или переустановите |
| Несовпадение отпечатка SSH | Сервер сменил ключ/ошибка конфигурации | Сверьте отпечаток, очистите старую запись и повторите |
| Развёртывание успешно, но бизнес-система использует старый сертификат | Нет перезагрузки/кэш/несколько экземпляров | Настройте команду перезагрузки, обновите кэш, проверьте все узлы |
| Webhook отклонён | Публичный HTTP/сертификат не доверен | Используйте HTTPS или внутренний адрес, проверьте TLS |
| Сбой CDN/панели | Права учётных данных/параметры/версия API | Проверьте права и параметры на целевой стороне |
| Тайм-аут развёртывания | Медленная цель/большие файлы | Увеличьте `timeout_seconds`, проверьте сеть |

Дополнительные сведения об устранении неполадок см. в разделе [Мониторинг и устранение неполадок](troubleshooting.md).
