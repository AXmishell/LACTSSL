# Интеграция по API

Интерфейсы консоли LACTSSL можно вызывать как через сеанс входа в браузере, так и с помощью API-ключа. API-ключи подходят для длительно работающих программ: CI/CD, мониторинговых проверок, синхронизации с CMDB, распространения сертификатов. Для каждого ключа отдельно настраиваются разрешения, срок действия и состояние включения, что позволяет избежать совместного использования пароля администратора.

> Чувствительные операции, такие как безопасность учётной записи, ключи доступа и управление сеансами, можно вызывать только из сеанса входа в браузере; API-ключи не могут изменить пароль для входа, привязать ключ доступа или завершить другие сеансы.

## 1. Выбор способа интеграции

| Сценарий | Рекомендуемый способ | Причина |
| --- | --- | --- |
| Ручной выпуск, устранение неполадок, изменение конфигурации | Консоль браузера | Доступны полный аудит и интерактивное подтверждение |
| Запуск продления/развёртывания из CI/CD | API-ключ + `tasks:run` / `deploy:execute` | Минимальные права, возможность ротации |
| Синхронизация списка сертификатов с CMDB | API-ключ + права только для чтения | Закрытый ключ не раскрывается |
| Скачивание и распространение сертификатов | API-ключ + `certificates:key` + `deploy:execute` | Высокая чувствительность, требуются дополнительные сетевые ограничения |
| Мониторинговые проверки | API-ключ + `system:read` / `monitors:read` | Только чтение, короткий срок действия |
| Аудит журналов | API-ключ + `logs:read` / `system_logs:read` | Только чтение, экспорт в SIEM |

API-ключи не являются многопользовательским RBAC. Если требуется разделение полномочий между несколькими людьми, следует реализовать согласование и прокси-вызовы через корпоративный IAM, бастионный хост или вышестоящую платформу.

## 2. Аутентификация

Поместите ключ в заголовок запроса `Authorization: Bearer` или `X-API-Key`:

```bash
curl -H "Authorization: Bearer xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx" \
  https://ssl.example.com/api/certificates
```

```bash
curl -H "X-API-Key: xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx" \
  https://ssl.example.com/api/certificates
```

Ключевые моменты:

- Интерфейсы всегда находятся по пути `/api`; устаревший `/<entry>/api` сохранён как совместимый псевдоним.
- Запросы по-прежнему требуют аутентификации через сеанс входа или API-ключ и не зависят от защищённой точки входа.
- Запросы с API-ключом не зависят от Cookie, поэтому заголовок `X-LACTSSL-CSRF` не требуется.
- Все запросы рекомендуется выполнять через HTTPS; ключ не должен присутствовать в параметрах URL.
- Заголовки ответа содержат `X-Request-ID`; при устранении неполадок передайте его поставщику или службе эксплуатации.

## 3. Жизненный цикл API-ключа

### 3.1 Создание

1. Войдите в консоль с учётной записью администратора.
2. Откройте страницу «API-ключи» и нажмите «Создать ключ».
3. Укажите имя, срок действия и при необходимости отметьте разрешения.
4. Страница покажет полный ключ один раз; после закрытия диалога просмотреть его снова нельзя, доступна только ротация.

Формат ключа — 86-символьная случайная строка Base64URL (64 байта энтропии) без фиксированного префикса. Сервер хранит только дайджест, поэтому при утечке базы данных восстановить открытый ключ напрямую невозможно.

Пример запроса на создание:

```bash
curl -X POST \
  -H "Authorization: Bearer xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "CI deployment",
    "scopes": ["tasks:read", "tasks:run", "deploy:execute"],
    "expires_at": "2027-01-01T00:00:00Z"
  }' \
  https://ssl.example.com/api/api-keys
```

Если `expires_at` оставить пустым, ключ никогда не истечёт; в производственной среде бессрочные ключи не рекомендуются. Создание и изменение ключей относятся к операциям высокого риска: сеансы браузера полагаются на идентификатор входа, а вызовы с API-ключом — на его разрешение `api_keys:write`.

### 3.2 Ротация и отключение

- После ротации старый токен немедленно становится недействительным.
- После отключения или удаления все вызовы с использованием этого ключа возвращают `401`.
- При управлении другими ключами через API-ключ нельзя выдавать разрешения, которых нет у него самого, а также изменять, ротировать или удалять ключ с более высокими правами, чем у него.

### 3.3 Хранение

- Храните ключ в корпоративном менеджере паролей или системе управления секретами, не записывайте его в репозиторий кода, образы или журналы.
- Выдавайте отдельный ключ для каждой системы; включайте в имя ключа название системы и среды.
- Устанавливайте разумный срок действия и выполняйте ротацию до его истечения.
- При подозрении на утечку немедленно выполните ротацию или удаление и проверьте журналы операций на наличие подозрительных вызовов.

## 4. Модель разрешений

Разрешения разделяются по схеме «ресурс:действие». `*` обозначает все возможности API системы, включая все чувствительные операции.

| Разрешение | Описание | Чувствительное |
| --- | --- | --- |
| `*` | Все возможности API системы | Да |
| `profile:read` | Просмотр учётной записи, которой принадлежит текущий ключ | Нет |
| `system:read` | Просмотр версии, состояния и метаданных | Нет |
| `dashboard:read` | Просмотр статистики панели управления | Нет |
| `certificates:read` | Просмотр сертификатов, скачивание цепочек сертификатов и анализ сертификатов | Нет |
| `certificates:write` | Очистка и удаление сертификатов | Нет |
| `certificates:key` | Просмотр или скачивание закрытых ключей сертификатов | Да |
| `certificates:request` | Отправка CSR клиента, чтобы сервер выполнил проверку и выпуск в публичном CA, либо подписал сертификат приватным CA (также требуется `private_cas:write`) | Да |
| `deploy:execute` | Ручное развёртывание сертификатов, а также создание, изменение и запуск задач с узлами развёртывания (запись файлов; для выполнения команд дополнительно требуется `deploy:command`) | Да |
| `deploy:command` | Разрешает локальному/SSH-развёртыванию выполнять команду reload (эквивалентно выполнению произвольных команд от имени служебной учётной записи) | Да |
| `tasks:read` | Просмотр списка задач и журналов задач | Нет |
| `tasks:write` | Создание, изменение, удаление, включение и отключение задач (для создания сразу выполняемой задачи также требуется `tasks:run`; при наличии узлов развёртывания — `deploy:execute`; для частного CA — `private_cas:write`) | Нет |
| `tasks:run` | Ручной или пакетный запуск задач (при наличии узлов развёртывания требуется `deploy:execute`; для частного CA — `private_cas:write`) | Нет |
| `monitors:read` | Просмотр мониторинга сертификатов сайтов | Нет |
| `monitors:write` | Создание, изменение, удаление и немедленная проверка мониторинга | Нет |
| `dns_accounts:read` | Просмотр учётных записей DNS-провайдеров (ключи маскируются) | Нет |
| `dns_accounts:write` | Создание, изменение и удаление учётных записей DNS-провайдеров | Да |
| `deploy_accounts:read` | Просмотр учётных записей целей развёртывания (ключи маскируются) | Нет |
| `deploy_accounts:write` | Создание, изменение и удаление учётных записей целей развёртывания | Да |
| `deployments:read` | Просмотр истории развёртывания сертификатов | Нет |
| `ca:read` | Просмотр ACME CA, конечных точек, учётных записей и заказов | Нет |
| `ca:write` | Изменение ACME CA, конечных точек и EAB, очистка диагностических данных | Да |
| `private_cas:read` | Просмотр сертификатов частного CA и цепочек сертификатов | Нет |
| `private_cas:write` | Создание, импорт и удаление частных CA | Да |
| `private_cas:key` | Скачивание закрытых ключей частного CA | Да |
| `plugins:read` | Просмотр плагинов, репозитория плагинов и состояния включения | Нет |
| `plugins:write` | Загрузка, установка, обновление, удаление и включение плагинов | Да |
| `logs:read` | Просмотр и экспорт журналов операций, просмотр/скачивание архивов журналов | Нет |
| `logs:write` | Очистка всех журналов операций, удаление архивов журналов (сама очистка оставляет запись аудита) | Да |
| `system_logs:read` | Просмотр и экспорт журналов процессов, просмотр/скачивание архивов журналов | Нет |
| `system_logs:write` | Удаление всех системных журналов и архивов журналов | Да |
| `settings:read` | Просмотр системных настроек и цепочки доверия внутреннего CA | Нет |
| `settings:write` | Изменение системных настроек, отправка тестовых уведомлений, импорт или удаление внутреннего CA | Да |
| `backup:read` | Просмотр состояния и размера резервной копии | Нет |
| `backup:download` | Экспорт зашифрованной резервной копии | Да |
| `backup:restore` | Загрузка и восстановление резервной копии, перезапускает сервис | Да |
| `upgrade:read` | Просмотр состояния миграции базы данных и обновления программы | Нет |
| `upgrade:write` | Выполнение миграций, оптимизация базы данных и замена программы | Да |
| `security:write` | Изменение защищённой точки входа | Да |
| `api_keys:read` | Просмотр списка API-ключей и разрешений | Нет |
| `api_keys:write` | Создание, изменение, ротация и удаление API-ключей | Да |

### 4.1 Рекомендуемое сопоставление ролей

| Роль | Разрешения |
| --- | --- |
| Плановая проверка только для чтения | `system:read`, `dashboard:read`, `certificates:read`, `tasks:read`, `monitors:read`, `deployments:read` |
| Продление CI/CD | `tasks:read`, `tasks:run`; при наличии узлов развёртывания добавьте `deploy:execute` |
| Распространение сертификатов | `certificates:read`, `certificates:key`, `deploy:execute` |
| Аудит журналов | `logs:read`, `system_logs:read` |
| Мониторинг | `system:read`, `monitors:read` |

Разрешения на закрытые ключи являются дополнительными:

- Для скачивания закрытого ключа сертификата также требуется `certificates:read`.
- Для скачивания закрытого ключа частного CA также требуется `private_cas:read`.
- Для создания/запуска задач с узлами развёртывания необходимо явно иметь `deploy:execute`; `certificates:write` и `tasks:*` не подразумевают возможность выполнения развёртывания.
- Для `reload_command` при локальном/SSH-развёртывании также необходимо явно иметь `deploy:command`; только `deploy:execute` позволяет лишь записывать файлы сертификатов.
- Задачи, выпускающие сертификаты из частного CA, требуют `private_cas:write`; `tasks:write` не подразумевает возможность выпуска из частного CA.
- Создание задачи с `enabled:true` немедленно запускает выпуск, поэтому помимо `tasks:write` требуется `tasks:run`.

## 5. Формат ответа

Успех:

```json
{
  "success": true,
  "data": {}
}
```

Ошибка:

```json
{
  "success": false,
  "code": "api.error.api_key_scope_denied",
  "message": "У API-ключа отсутствует требуемое разрешение: certificates:read",
  "params": { "scope": "certificates:read" }
}
```

Распространённые коды состояния:

| Код состояния | Значение |
| --- | --- |
| `400` | Ошибка параметров, сбой проверки конфигурации |
| `401` | Не аутентифицировано; ключ не существует, отключён, истёк или удалён |
| `403` | Недостаточно прав, или интерфейс допускает вызов только из сеанса браузера |
| `404` | Ресурс не найден или неверный путь |
| `409` | Конфликт состояний (например, уже выполняется, повторная операция) |
| `429` | Слишком частые запросы; повторите с учётом `Retry-After` |
| `500` | Ошибка сервера; запишите `X-Request-ID` и выполните диагностику |

## 6. Основные интерфейсы

### 6.1 Просмотр состояния и сертификатов

```bash
# Состояние процесса (требуется system:read)
curl -fsS -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/status

# Список сертификатов (требуется certificates:read)
curl -fsS -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/certificates
```

Интерфейсы списков возвращают массив напрямую; интерфейсы журналов возвращают объект с постраничной разбивкой:

```bash
curl -fsS -H "Authorization: Bearer $LACTSSL_TOKEN" \
  "https://ssl.example.com/api/logs?page=1&size=50&level=error&source=task&q=demo"
```

`size` — не более 200; `q` сопоставляется с исходным сохранённым содержимым и значениями параметров. Для очистки журналов операций используется `DELETE /api/logs`, требуется `logs:write`.

При очистке журналов, если включён `log.archive.enabled`, сервис сначала записывает архив, затем удаляет журналы, а ответ дополнительно содержит объект `archived`; при сбое архивирования возвращается 500, и журналы не удаляются.

Интерфейсы архивов журналов:

```bash
# Список: поддерживаются page, size, category, reason, from, to, q
curl -fsS -H "Authorization: Bearer $LACTSSL_TOKEN" \
  "https://ssl.example.com/api/log-archives?page=1&size=20&category=operation"

# Скачивание файла архива
curl -fsS -OJ -H "Authorization: Bearer $LACTSSL_TOKEN" \
  "https://ssl.example.com/api/log-archives/<archive_id>/download"

# Удаление архива
curl -fsS -X DELETE -H "Authorization: Bearer $LACTSSL_TOKEN" \
  "https://ssl.example.com/api/log-archives/<archive_id>"
```

Интерфейсы архивов принимают соответствующие разрешения `logs:*` или `system_logs:*`: для просмотра/скачивания достаточно любого разрешения на чтение, для удаления — любого разрешения на запись. `category` принимает значение `operation` или `runtime`; `reason` — `manual_clear`, `retention` или `max_rows`.

### 6.2 Предварительный просмотр целевого потока

Целевой поток Beta позволяет перед сохранением задачи прочитать целевой сайт и предварительно просмотреть группировку сертификатов. Интерфейс доступен только для чтения, требуется `deploy:execute`:

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer $LACTSSL_TOKEN" \
  -H "Content-Type: application/json" \
  https://ssl.example.com/api/tasks/target-flow/preview \
  -d '{
    "sources": [{"deploy_account_id": 3, "deploy_config": {"target": "site"}}],
    "selection": {"mode": "all"},
    "policy": {"strategy": "smart", "max_domains_per_cert": 100},
    "public_ca": true
  }'
```

При создании задачи передайте `flow_mode: "target_beta"` и `target_flow`; `target_flow.policy.strategy` поддерживает `smart`, `per_site`, `per_base_domain`, `single`, `per_source`, `custom`. Одна задача Beta может быть связана с несколькими сертификатами; связи сертификатов записываются в `task_certificate_links`.

### 6.3 Запуск задачи

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/tasks/123/run
```

Если задача содержит включённые узлы развёртывания, ключ должен также иметь `deploy:execute`.

По умолчанию повторно используется сертификат, который ещё действителен и не вошёл в окно продления; повторно выполняются только узлы развёртывания, новый заказ вышестоящему CA не отправляется. Если действительно требуется принудительный повторный выпуск, используйте `?force=1` или отправьте `{"force":true}`; принудительный выпуск расходует квоту сертификатов CA.

### 6.4 Скачивание сертификатов

```bash
# Полная цепочка (требуется certificates:read)
curl -fL -H "Authorization: Bearer $LACTSSL_TOKEN" \
  -o example.com.fullchain.pem \
  "https://ssl.example.com/api/certificates/42/download?type=fullchain"

# Закрытый ключ (требуется certificates:read + certificates:key)
curl -fL -H "Authorization: Bearer $LACTSSL_TOKEN" \
  -o example.com.key \
  "https://ssl.example.com/api/certificates/42/download?type=key"
```

`type` поддерживает `fullchain` (по умолчанию), `cert`, `key`. Интерфейс скачивания возвращает исходный PEM, не обёрнутый в JSON; сохраняйте его с соответствующими правами на файл и не записывайте в журналы.

### 6.5 Мониторинг сайтов

```bash
curl -fsS -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/monitors

curl -fsS -X POST \
  -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/monitors/7/check
```

### 6.6 Управление API-ключами

| Интерфейс | Метод | Разрешение | Описание |
| --- | --- | --- | --- |
| `/api-keys` | GET | `api_keys:read` | Список ключей без возврата токенов в открытом виде |
| `/api-keys/scopes` | GET | `api_keys:read` | Получение списка разрешений и локализованных описаний |
| `/api-keys` | POST | `api_keys:write` | Создание ключа; `token` возвращается в ответе только один раз |
| `/api-keys/:id` | PUT | `api_keys:write` | Изменение имени, разрешений, состояния включения и срока действия |
| `/api-keys/:id/rotate` | POST | `api_keys:write` | Ротация ключа; старый токен немедленно становится недействительным |
| `/api-keys/:id` | DELETE | `api_keys:write` | Удаление ключа |

### 6.7 Использование клиентского CSR для запроса сертификата

Сервер выступает промежуточным звеном: принимает CSR клиента и выпускает сертификат либо после проверки DNS-01 с использованием настроенного публичного CA и учётной записи DNS, либо напрямую через приватный CA, управляемый сервером. Сервер не генерирует и не сохраняет закрытый ключ; после выпуска сертификата закрытый ключ остаётся у клиента.

Для создания запроса требуется разрешение `certificates:request`. Для приватного CA также требуется `private_cas:write`:

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer $LACTSSL_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "csr": "-----BEGIN CERTIFICATE REQUEST-----\n...\n-----END CERTIFICATE REQUEST-----\n",
    "ca": "letsencrypt",
    "challenge": "dns01",
    "dns_account_id": 3,
    "idempotency_key": "order-20261118-001",
    "wait_seconds": 0
  }' \
  https://ssl.example.com/api/certificate-requests
```

Для приватного CA укажите `ca` как `private-ca:<id>` или передайте `private_ca_id`. Запросы к приватному CA не используют DNS-01, `dns_account_id` и контактный email ACME; внутренние домены, например `app.internal`, разрешены:

```bash
curl -fsS -X POST \
  -H "Authorization: Bearer $LACTSSL_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "csr": "-----BEGIN CERTIFICATE REQUEST-----\n...\n-----END CERTIFICATE REQUEST-----\n",
    "private_ca_id": 2,
    "idempotency_key": "internal-20261121-001"
  }' \
  https://ssl.example.com/api/certificate-requests
```

Интерфейс возвращает `202 Accepted` и ID запроса. Запрос выполняется асинхронно, состояние можно опрашивать:

```bash
curl -fsS -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/certificate-requests/csr_xxxxxxxx
```

После перехода в состояние `issued` можно скачать цепочку сертификатов; закрытый ключ не предоставляется:

```bash
curl -fsS -H "Authorization: Bearer $LACTSSL_TOKEN" \
  "https://ssl.example.com/api/certificate-requests/csr_xxxxxxxx/certificate?type=fullchain" \
  -o example.com.fullchain.crt
```

Ключевые моменты:

- Запросы к публичному CA поддерживают только DNS-01; для wildcard-сертификатов необходимо использовать DNS-01. Запросы к приватному CA подписываются напрямую и не используют проверку домена.
- `ca` — это ACME-вышестоящий со страницы «Публичные CA» либо `private-ca:<id>` для приватного CA. Для выпуска приватным CA также требуется `private_cas:write`; применяются ограничения ExtKeyUsage и NameConstraints этого CA.
- Сервер строго проверяет подпись CSR, стойкость открытого ключа, корректность SAN и общее имя. Внутренние домены отклоняются для публичного CA и разрешены для приватного CA. CSR уже подписан клиентом, и сервер не может исправить его за клиента.
- `idempotency_key` рекомендуется передавать обязательно; для одного CSR, CA и набора DNS-маршрутов допускается только один незавершённый запрос.
- С помощью параметра `csr.allowed_domains` можно ограничить домены, разрешённые для запроса; несколько доменов разделяются запятыми или пробелами. Для приватного CA пустой список не добавляет ограничений и используются NameConstraints CA; после настройки список применяется к обоим типам CA.
- Значение `key_available` в списке сертификатов равно `false`, что означает отсутствие закрытого ключа на сервере; скачивание закрытого ключа и развёртывание, зависящее от закрытого ключа, невозможны.

В репозитории есть готовый к использованию клиентский скрипт Python `scripts/csr_client.py`; он локально генерирует закрытый ключ и CSR, отправляет запрос, опрашивает состояние и после скачивания проверяет соответствие сертификата и закрытого ключа:

```bash
export LACTSSL_URL="https://ssl.example.com"
export LACTSSL_TOKEN="xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"

python3 scripts/csr_client.py \
  --domains example.com,www.example.com \
  --dns-account-id 3 \
  --ca letsencrypt \
  --out-dir ./certs

# Запрос к приватному CA (закрытый ключ по-прежнему создаётся локально)
python3 scripts/csr_client.py \
  --domains app.internal,api.internal \
  --private-ca-id 2 \
  --out-dir ./certs
```

Также можно использовать интерактивный мастер и заполнять поля по порядку, не запоминая параметры (при запуске в терминале без параметров мастер открывается автоматически):

```bash
python3 scripts/csr_client.py --interactive
```

Продление, проверка состояния и пакетные операции:

```bash
# Продление: создать новый CSR с существующим ключом (ключ не копируется и не изменяется)
python3 scripts/csr_client.py \
  --key ./certs/example.com.key \
  --domains example.com,www.example.com \
  --out-dir ./certs \
  --force

# Или продлить напрямую по файлу состояния (ключ, CA, DNS-аккаунт и имя вывода переиспользуются)
python3 scripts/csr_client.py --renew-from ./certs/example.com.request.json

# Состояние / отмена (--json удобен для скриптов)
python3 scripts/csr_client.py --status csr_xxxxxxxx --json
python3 scripts/csr_client.py --cancel csr_xxxxxxxx --yes

# Пакетный режим: последовательно, по умолчанию остановка на первой ошибке
python3 scripts/csr_client.py --manifest ./certs.json --json
```

Формат пакетного манифеста:

```json
{
  "defaults": {"ca": "letsencrypt", "dns_account_id": 3, "out_dir": "./certs"},
  "certificates": [
    {"domains": ["example.com", "www.example.com"]},
    {"domains": ["api.example.com"], "name": "api", "key_type": "rsa2048"}
  ]
}
```

Скрипт загружает только CSR, закрытый ключ всегда остаётся на клиенте; результаты включают `.key`, `.csr`, `.crt`, `.fullchain.crt` и `.request.json`. Локально созданные ключ и CSR сначала сохраняются как `.new` и атомарно заменяют итоговые файлы только после успешного скачивания и проверки сертификата, поэтому неудачный запрос не уничтожает предыдущий рабочий набор. Файл состояния `.request.json` записывается сразу после создания запроса; даже при обрыве связи или использовании `--quiet` можно продолжить с `--request-id csr_xxxxxxxx`, при этом автоматически находятся предыдущие `.key.new`/`.key`. Временные сетевые ошибки по умолчанию повторяются 3 раза (`--retries`), при повторяемой ошибке сервера выполняется один автоматический `/retry` (`--auto-retry`), а HTTP 429 соблюдает `Retry-After`. Прогресс выводится в stderr; с `--json` в stdout попадает только итоговый JSON. Токен можно читать через `LACTSSL_TOKEN_FILE` или `--token-file`, чтобы он не оставался в аргументах командной строки. Интерфейс клиента поддерживает `zh-CN`, `zh-TW`, `en-US`, `ja-JP` и `ru-RU` через `--lang` или `LACTSSL_LANG`; ошибки API запрашиваются на том же языке. Коды выхода: 0 успех, 1 общая ошибка, 2 аргументы/конфигурация, 3 аутентификация/авторизация, 4 сеть, 5 ошибка запроса на сервере, 6 локальная проверка, 130 отменено пользователем.

### 6.8 Проверка доступности учётных данных

После добавления или изменения учётной записи DNS или учётных данных цели можно активно проверить, действительно ли они доступны. Интерфейс проверки использует разрешения `dns_accounts:write` / `deploy_accounts:write`; для сеанса браузера повторная аутентификация по текущему паролю или TOTP больше не требуется. Результат проверки носит информационный характер и не блокирует сохранение или запуск.

| Метод | Путь | Описание |
| --- | --- | --- |
| POST | `/api/dns-accounts/:id/verify` | Проверка сохранённой учётной записи DNS; можно передать `domain`, `mode` |
| POST | `/api/dns-accounts/verify` | Проверка несохранённой конфигурации DNS; ключ необходимо передать явно |
| POST | `/api/deploy-accounts/:id/verify` | Проверка сохранённых учётных данных цели; можно передать `deploy_config` |
| POST | `/api/deploy-accounts/verify` | Проверка несохранённой конфигурации учётных данных цели; ключ необходимо передать явно |
| POST | `/api/deploy-accounts/:id/options` | Получение динамических параметров полей развёртывания с использованием сохранённых учётных данных, например списка сайтов панели Baota |

Пример запроса:

```bash
curl -X POST \
  -H "Authorization: Bearer $LACTSSL_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"domain":"example.com","mode":"auto"}' \
  https://ssl.example.com/api/dns-accounts/3/verify
```

Интерфейс динамических параметров применим только к полям развёртывания, для которых в манифесте объявлен `options_source`; API-ключу требуется разрешение `deploy_accounts:write`. В теле запроса передаются имя поля и текущие параметры развёртывания, а учётные данные сервер читает из учётных данных цели:

```bash
curl -X POST \
  -H "Authorization: Bearer $LACTSSL_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"field":"sites","config":{"target":"docker"}}' \
  https://ssl.example.com/api/deploy-accounts/3/options
```

Возвращается `{"options":[{"label":"Название сайта","value":"Название сайта"}]}`. Если плагин недоступен или панель недостижима, возвращается явная ошибка, а интерфейс сохраняет возможность ручного ввода.

Структура ответа содержит отдельные проверки, что позволяет отличить сбой аутентификации, непринадлежность домена этим учётным данным, недоступность каталога для записи и другие причины:

```json
{
  "success": true,
  "data": {
    "ok": false,
    "mode": "write",
    "checks": [
      {"key": "init", "status": "ok"},
      {"key": "domain", "status": "ok", "message": "example.com"},
      {"key": "write", "status": "failed", "message": "..."}
    ],
    "message": "...",
    "verified_at": "2026-11-18T12:00:00Z"
  }
}
```

Описание поведения:

- DNS-проверка по умолчанию использует режим `auto`: если плагин объявляет `verify-v1`, сначала выполняется чтение списка зон и проверка принадлежности домена; если возможность не объявлена или возвращается «не поддерживается», выполняется тест записи (запись случайного значения TXT в `_acme-challenge` с последующим немедленным удалением). `mode=read` принудительно включает режим только для чтения; если плагин не поддерживает его, возвращается `unsupported`.
- Для сохранённых учётных записей используется только конфигурация из базы данных; для несохранённой конфигурации ключ необходимо передать явно, сохранённый ключ не переиспользуется, чтобы нельзя было отправить учётные данные на другой сервер путём изменения endpoint.
- Проверка учётных данных цели поддерживает встроенные `local`/`ssh`: подключение и аутентификация, создание и удаление временного файла в целевом каталоге, без выполнения `reload_command`. Другие плагины развёртывания до реализации возможности `verify` возвращают `unsupported`.
- Передача `deploy_config` позволяет проверить область действия конкретного узла развёртывания (сайт, каталог, бакет, домен); это рекомендуемый способ проверки «доступно ли новое разрешение».

## 7. Примеры CI/CD

### 7.1 Распространение после продления сертификата

```bash
#!/usr/bin/env bash
set -euo pipefail

BASE_URL="${LACTSSL_URL:?}"
TOKEN="${LACTSSL_TOKEN:?}"

# Запуск задачи (ID задачи передаётся из CMDB или системы управления конфигурацией)
curl -fsS -X POST \
  -H "Authorization: Bearer ${TOKEN}" \
  "${BASE_URL}/api/tasks/${TASK_ID}/run"

# После завершения задачи скачать по ID сертификата и распространить
curl -fL \
  -H "Authorization: Bearer ${TOKEN}" \
  -o /run/secrets/example.com.fullchain.pem \
  "${BASE_URL}/api/certificates/${CERT_ID}/download?type=fullchain"
```

Внимание:

- У API нет ключа идемпотентности; повторный вызов `run` снова выполнит процесс задачи, но если сертификат ещё действителен, выпуск будет пропущен и выполнено только развёртывание; скрипт должен самостоятельно обеспечивать дедупликацию.
- Запуск задачи асинхронен; если нужно дождаться завершения, опрашивайте список задач или подпишитесь на уведомления, не предполагайте, что POST означает завершение.
- Для скачивания закрытого ключа требуются дополнительные разрешения; в большинстве сценариев распространения достаточно цепочки сертификатов, а закрытый ключ записывается узлом развёртывания напрямую в цель; не рекомендуется передавать закрытый ключ через CI.

### 7.2 Плановая проверка

```bash
#!/usr/bin/env bash
set -euo pipefail

curl -fsS -H "Authorization: Bearer ${LACTSSL_TOKEN}" \
  "${LACTSSL_URL}/api/status" >/dev/null

curl -fsS -H "Authorization: Bearer ${LACTSSL_TOKEN}" \
  "${LACTSSL_URL}/api/certificates" |
  jq -e '[.data[] | select(.not_after < (now + 14*86400 | todate))] | length == 0'
```

(В примере используется `jq`; фактические имена полей определяются ответом интерфейса.)

## 8. Обработка ошибок и повторные попытки

- При `429` выполняйте отступление с учётом `Retry-After`, не повторяйте запрос немедленно.
- При `5xx` используйте экспоненциальное отступление и записывайте `X-Request-ID`.
- При `401` не повторяйте запрос; проверьте, не истёк ли ключ, не отключён ли он и не была ли выполнена ротация.
- При `403` проверьте разрешения и ограничения интерфейса (некоторые интерфейсы допускают только сеанс браузера).
- При `400`/`409` не повторяйте запрос автоматически; сначала исправьте параметры или состояние.
- Запросы, связанные с выпуском/развёртыванием, могут вызывать внешние побочные эффекты; перед повтором сначала проверьте состояние задачи/развёртывания.

## 9. Рекомендации по безопасности

- Создавайте отдельный ключ для каждой автоматизированной задачи, не используйте общий.
- Выдавайте только те разрешения, которые действительно нужны задаче; не выдавайте `*` задачам только для чтения.
- Устанавливайте разумный срок действия и регулярно выполняйте ротацию.
- Не раскрывайте полный ключ в журналах, снимках экрана или публичных репозиториях.
- При подозрении на утечку немедленно отключите или удалите ключ; ротация немедленно делает старый ключ недействительным.
- Ограничьте источники вызовов на сетевом уровне, чтобы после утечки ключ нельзя было использовать с любого адреса.
- Связывайте журналы вызовов API с журналами операций, сохраняйте вызывающую сторону, время и `X-Request-ID`.
