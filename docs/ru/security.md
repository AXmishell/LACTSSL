# Базовая безопасность

Этот документ предназначен для руководителей по безопасности, аудиторов и платформенных команд. В нём описаны модель безопасности LACTSSL, реализованные меры контроля, меры, которые предприятие должно добавить самостоятельно, и чек-лист усиления перед вводом в эксплуатацию. Он не является заключением о соответствии требованиям и не заменяет собственную оценку рисков предприятия.

## 1. Модель безопасности и границы доверия

LACTSSL спроектирован как «самостоятельно размещаемый одиночный экземпляр»; границы доверия следующие:

```text
[недоверенная] Пользователи интернета/корпоративной сети
    │ HTTPS (TLS завершается на обратном прокси)
[граница] Обратный прокси / WAF / сетевой ACL
    │ HTTP (loopback или внутренняя сеть)
[доверенная] Процесс LACTSSL
    ├─ Сеанс администратора: эквивалентен полному контролю
    ├─ Ключ API: ограничен областью прав
    ├─ Закрытый ключ частного CA: хранится в зашифрованном виде в локальной базе данных
    └─ Подпроцесс плагина: работает под учётной записью службы, считается доверенным кодом
[внешняя] DNS API / CA / SMTP / цели развёртывания / каналы уведомлений
```

Ключевые выводы:

- **Сеанс администратора эквивалентен полному контролю**, включая выполнение локальных команд развёртывания, экспорт закрытых ключей и восстановление резервных копий.
- **Ключ API — это машинная идентичность**, используемая для ограничения прав в сценариях автоматизации, а не многопользовательский RBAC.
- **Плагины — доверенный код**, особенно плагины развёртывания, которые получают доступ к закрытым ключам сертификатов; безопасность цепочки поставок должна обеспечиваться предприятием.
- **База данных и `config.yaml` одинаково чувствительны**; потеря `salt` делает зашифрованные учётные данные непригодными, а утечка может привести к их расшифровке.

## 2. Идентификация и управление доступом

### 2.1 Административная учётная запись

- Одна административная учётная запись; многопользовательский режим, роли, организационная структура и маршруты согласования не поддерживаются.
- Пароль хранится в виде хеша bcrypt, длина — не менее 8 символов; для продуктивной среды рекомендуется случайный пароль длиной не менее 16 символов.
- Поддерживаются двухфакторная аутентификация TOTP и ключи доступа (WebAuthn/Passkey).
- Включение TOTP, регистрация ключа доступа, изменение целей SMTP/уведомлений, а также отправка тестовых писем/уведомлений требуют повторной аутентификации (текущий пароль или TOTP), чтобы украденный сеанс не позволил привязать учётную запись к аутентификатору злоумышленника или перенаправить сохранённые ключи SMTP/уведомлений на хост злоумышленника.
- Ключи доступа должны использоваться через HTTPS-домен или localhost; прямой IP-адрес не может быть источником WebAuthn.
- После входа по ключу доступа TOTP повторно не запрашивается; сам ключ доступа выполняет проверку отпечатка устройства, лица или системного PIN.
- Смена пароля повышает версию токена и удаляет все серверные сеансы, ключи API и ключи доступа; все входы немедленно становятся недействительными.
- Сброс пароля по электронной почте одновременно отключает TOTP, удаляет ключи доступа и ключи API; необходимо обеспечить безопасность самой почты восстановления.

### 2.2 Ключи API

- Ключ представляет собой 86-символьную случайную строку Base64URL (энтропия 64 байта) без фиксированного префикса; сервер хранит только дайджест SHA-256.
- Права разделены по принципу «ресурс:действие»; `*` обозначает все возможности системного API.
- Чувствительные права перечислены отдельно: `certificates:key`, `private_cas:key`, `deploy:execute`, `deploy:command`, `backup:download`, `backup:restore`, `plugins:write`, `settings:write`, `api_keys:write`, `monitors:internal` и др.
- При управлении другими ключами через ключ API нельзя выдавать права, которых нет у самого ключа, а также изменять, ротировать или удалять ключи с более высокими правами.
- Операции, связанные с безопасностью учётной записи (смена пароля, ключи доступа, управление сеансами), разрешены только для сеанса входа в браузере; ключи API не могут их вызывать.
- Рекомендуется создавать отдельный ключ для каждой системы автоматизации, задавать срок действия, выдавать минимально необходимые права и регулярно выполнять ротацию.

### 2.3 Что предприятие должно добавить

- Многопользовательский RBAC, SSO (OIDC/SAML/LDAP), SCIM и маршруты согласования.
- Bastion-хост, PAM или прокси доступа с нулевым доверием.
- Двойную проверку административной учётной записи и регулярный пересмотр прав.
- Централизованное хранение ключей API (Vault/KMS) и ограничение по исходному IP.

## 3. Сеть и TLS

### 3.1 Входящий трафик

- Консоль управления должна быть доступна через HTTPS-обратный прокси; основная программа прослушивает только HTTP.
- Порт бэкенда должен прослушиваться только на loopback или во внутренней сети и не должен быть напрямую доступен из интернета.
- На уровне прокси настройте белый список исходных IP, VPN, политику нулевого доверия или WAF.
- Прокси должен перезаписывать или корректно добавлять `X-Forwarded-For` и передавать `X-Forwarded-Proto`; LACTSSL доверяет только точным IP или минимальным CIDR из `server.trusted_proxies`. В цепочке добавления нужно доверять всем прокси цепочки.
- Если доверенные прокси не настроены, все запросы будут считаться запросами с IP прокси, из-за чего ограничение скорости перестанет работать, а `Secure` Cookie будут определяться неверно.
- Рекомендуется настроить на уровне прокси HSTS, TLS 1.2+, отключить слабые наборы шифров и ограничить размер тела запроса (для восстановления резервных копий и загрузки плагинов требуются большие лимиты).

### 3.2 Исходящий трафик

Сервер активно инициирует исходящие запросы:

- API DNS-провайдеров (создание/очистка TXT).
- Публичные ACME CA и универсальные вышестоящие сервисы.
- Каналы уведомлений: SMTP, Gotify, Telegram, DingTalk, WeCom, Webhook и др.
- Цели развёртывания: SSH/SFTP, FTP/FTPS, облачный CDN, Baota, 1Panel, SafeLine WAF и др.
- Цели мониторинга сертификатов сайтов.

Рекомендации:

- В продуктивной среде настройте белый список исходящих подключений по доменам или подсетям и разрешайте только фактически необходимые цели.
- Если требуется корпоративный прокси, настройте его через системные переменные окружения (поведение HTTP-клиента Go), не полагайтесь на конфигурацию внутри приложения.
- Проверяйте источник пользовательских целей, таких как Webhook развёртывания и Webhook уведомлений, чтобы не отправлять закрытые ключи или токены на недоверенные адреса.
- Для внутренних HTTPS-целей импортируйте открытый ключ внутреннего CA через «Системные настройки → Цепочка доверия TLS», а не отключайте проверку TLS; импортированные CA и частные CA объединяются в `SSL_CERT_FILE` для использования плагинами и командами развёртывания.

### 3.3 Защита от SSRF

- Для буквальных и разрешённых адресов назначения отклоняются диапазоны облачных метаданных, link-local, зарезервированные, documentation, NAT64 и другие (например, `169.254.169.254`, `100.100.100.200`, `fd00:ec2::254`, `0.0.0.0/8`, `240.0.0.0/4`).
- Адреса loopback и частных сетей по-прежнему разрешены для таких сценариев, как Gotify, собственные панели и внутренние Webhook; при необходимости их можно дополнительно ограничить на сетевом уровне.
- Мониторинг сайтов по умолчанию разрешает только публичные цели; для мониторинга частных сетей/loopback ключ API должен дополнительно иметь `monitors:internal`, а на этапе установления соединения выполняется повторная проверка по окончательно разрешённому IP для предотвращения DNS rebinding.
- Webhook развёртывания передаёт закрытый ключ сертификата; для публичных целей принудительно используется `https://`; для целей loopback, частных сетей, `.local`, `.internal` допускается HTTP.
- На этапе установления соединения повторно проверяется результат DNS-разрешения и подключение выполняется напрямую к проверенному IP, чтобы предотвратить обход через DNS rebinding.
- Перед записью ошибок сторонних запросов в журнал URL-путь и параметры запроса маскируются, чтобы токены ботов Telegram, токены Gotify, SendKey Server酱 и т. п. не попадали в журналы или резервные копии.

## 4. Защищённая точка входа, сеансы и CSRF

### 4.1 Защищённая точка входа

Страница управления не публикуется напрямую по корневому пути, а доступна только через случайно сгенерированную точку входа:

```text
https://your-domain/<entry>/
```

- По умолчанию точка входа генерируется случайно из 20 букв в обоих регистрах и цифр и сохраняется в базе данных.
- Страницы без прохождения точки входа единообразно возвращают `404`, включая голый `/` и другие распространённые пути зондирования.
- API всегда расположен по голому `/api` и защищён сеансом входа или ключом API; старый `/<entry>/api` сохранён как совместимый псевдоним.
- После доступа по правильной точке входа записывается подписанный `HttpOnly` Cookie защищённой точки входа со сроком действия 24 часа; сервер также проверяет время истечения.
- Для зондирования точки входа действует ограничение частоты, чтобы предотвратить перебор.
- Точку входа можно изменить в «Настройки → Защищённая точка входа»; изменение вступает в силу немедленно; для ручной точки входа требуется 8–32 символа.
- При первой инициализации полный адрес точки входа выводится в журнал запуска; после завершения инициализации он больше не выводится.
- Если точка входа забыта, можно изменить `security.entry` в `config.yaml` и перезапустить сервис для переопределения либо посмотреть `security.entry` в таблице `settings` базы данных.
- Пока система не инициализирована, журнал запуска также выводит одноразовый токен инициализации; создание администратора, изменение конфигурации инициализации, перезапуск процесса инициализации и восстановление из резервной копии должны выполняться с этим токеном (`X-LACTSSL-SETUP-TOKEN`).
- Токен становится недействительным сразу после успешной инициализации и генерируется заново после перезапуска сервиса.

> Точка входа — дополнительный уровень защиты, но она не заменяет HTTPS, надёжные пароли и сетевой контроль доступа.

### 4.2 Сеансы

- Сеанс входа хранится в `HttpOnly` Cookie и недоступен для чтения клиентским скриптам; Cookie использует `SameSite=Strict`.
- Токен сеанса дополняется как минимум до 512 символов; токен CSRF состоит из 32 символов.
- При первом доступе к защищённой точке входа или входе выдаётся долгоживущий (1 год) `HttpOnly` Cookie идентификатора устройства (`lactssl_device`, 32 шестнадцатеричных символа).
- При развёртывании по HTTPS Cookie сеанса, CSRF и точки входа автоматически используют префикс `__Host-`, чтобы избежать перезаписи соседними поддоменами в общем родительском домене.
- По умолчанию при каждом запуске сервиса серверные записи сеансов очищаются, а случайное значение запуска подмешивается в подключ подписи JWT; после перезапуска все старые входы немедленно становятся недействительными.
- После установки `security.session_persistence: true` сеансы при запуске больше не очищаются, а подпись выполняется фиксированным `jwt_secret`; после перезапуска в фоновом режиме можно продолжить использовать прежний сеанс.
- Смена пароля повышает версию токена и удаляет все сеансы, ключи API и ключи доступа.

### 4.3 CSRF и межсайтовая защита

- Все запросы, изменяющие состояние сервера (POST/PUT/DELETE и т. п.), должны содержать заголовок `X-LACTSSL-CSRF`, совпадающий с Cookie `lactssl_csrf`.
- Для старых сеансов при первом запросе Cookie выдаётся автоматически; пониженная проверка только по заголовку запроса не принимается.
- Для неаутентифицированных интерфейсов, таких как вход, инициализация, забытый пароль и сброс пароля, дополнительно проверяются `Origin`/`Sec-Fetch-Site`.
- При явном вызове API с `Authorization: Bearer <token>` проверка CSRF не применяется, что удобно для скриптов и внешних интеграций.
- В ответах страниц используется случайный CSP nonce для каждого запроса, `script-src` больше не разрешает произвольные встроенные скрипты; встроенные стили по-прежнему разрешены для нужд библиотеки компонентов.

## 5. Сброс пароля и внешний адрес

Ссылка в письме для сброса пароля должна формироваться на основе фиксированного адреса:

```yaml
security:
  public_url: "https://ssl.example.com"
```

- Если `public_url` не настроен, ссылка выводится из текущего Host только для запросов с локального loopback-адреса и Host `localhost`/loopback IP; для остальных запросов вызов «Забыли пароль» будет отклонён.
- Клиентский `X-Forwarded-Host`, который можно подделать, не считается доверенным.
- В сценарии с обратным прокси необходимо настроить `public_url`, чтобы злоумышленник не мог подделать Host и направить ссылку сброса (включая token и защищённую точку входа) на свой домен.

## 6. Защита учётных данных и данных

### 6.1 Шифрование

- Чувствительные поля, такие как учётные данные DNS, учётные данные развёртывания, пароль SMTP, токены уведомлений, ключи TOTP, закрытые ключи частного CA и закрытые ключи сертификатов, записываются в базу данных после шифрования AES-256-GCM.
- Данные старых версий в открытом виде автоматически мигрируются при запуске.
- Ключ шифрования берётся из `security.salt` в `config.yaml`.
- JWT подписывается с помощью `security.jwt_secret`; фактически используется отдельный подключ, производный от `jwt_secret` и случайного значения запуска через HKDF, отделённый от ключа AES-GCM базы данных.
- При ручной настройке `security.jwt_secret` и `security.salt` должны содержать не менее 32 символов; при слишком коротком значении запуск отклоняется.
- При возврате конфигурации через API поля ключей маскируются; при редактировании пустое значение означает сохранение прежнего.

### 6.2 Файлы и резервные копии

- `config.yaml` должен иметь права `0600`, `data/` — `0700`, владелец — пользователь, от имени которого работает сервис.
- База данных, WAL, плагины, журналы и резервные копии обновлений находятся в `data/`.
- При скачивании резервной копии необходимо задать пароль шифрования не короче 12 символов; пакет резервной копии шифруется с помощью PBKDF2-HMAC-SHA256 (600 000 итераций) + AES-256-GCM.
- Пакет резервной копии содержит базу данных, конфигурацию и информацию о версии; обращайтесь с ним как с конфиденциальным файлом, не распространяйте незашифрованные копии базы данных или конфигурации.
- Пакет восстановления сначала проходит полную проверку конфигурации (длина ключей, защищённая точка входа, адрес прослушивания, сочетание TLS/mTLS и т. п.); недопустимая конфигурация отклоняется.
- После успешной первой инициализации не применённые пакеты восстановления очищаются, чтобы сохранённое до инициализации содержимое не перезаписало новую учётную запись при последующем перезапуске.

### 6.3 Ротация учётных данных

- Для учётных данных DNS/развёртывания/уведомлений используйте выделенные учётные записи и регулярно выполняйте ротацию.
- SSH по умолчанию требует указать отпечаток хоста; TOFU применяется только при явном включении «Автоматически доверять ключу хоста при первом подключении», а при последующем несовпадении отпечатка подключение отклоняется.
- Развёртывание по FTP по умолчанию использует явный TLS; открытый FTP применяется только при явном выборе `none`.
- Для ключей API задавайте срок действия, выпускайте их отдельно для каждой системы и немедленно ротируйте при утечке.

## 7. Аудит и журналирование

| Журнал | Содержимое | Хранение/экспорт |
| --- | --- | --- |
| Журнал операций | Задачи, сертификаты, развёртывание, уведомления, мониторинг, изменения настроек | Фильтрация по источнику/уровню/времени, экспорт последних 90 дней в CSV/JSON; перед удалением записывается в архив |
| Системный журнал | Запуск, HTTP, планирование, плагины, ACME | По умолчанию 7 дней/20 000 строк, можно изменить и очистить; перед удалением записывается в архив |
| Архивы журналов | Исходный NDJSON журнала операций/системного журнала и манифест | `data/archives/logs/`, по умолчанию хранится бессрочно; можно скачать или удалить в «Журнал → Архивы» |
| Журнал процесса | stdout или `log.file` | Ротация по размеру/количеству дней, возможен вывод в JSON |
| Журнал обратного прокси | Доступ, исходный IP, коды состояния | Управляется корпоративной платформой журналирования |

Рекомендации:

- Регулярно экспортируйте журнал операций, системный журнал и архивные файлы в SIEM или платформу журналирования, чтобы очистка администратором, удаление архивов или повреждение данных не привели к потере данных аудита.
- Журнал операций и системный журнал используют общую таблицу `logs`, но разделены по `category`; очистка системного журнала не удаляет журнал операций.
- Каждый ответ содержит `X-Request-ID`, что позволяет связать журналы доступа, panic и ошибки.
- Журнал доступа не записывает параметры запроса, тело запроса и заголовки аутентификации; защищённая точка входа в пути единообразно заменяется на `:entry`.
- Журналы и архивные файлы могут содержать IP клиентов, домены, подробности ошибок и сведения об операторе; обращайтесь с ними как с эксплуатационными данными и не публикуйте их. Права на архивные файлы — `0600`, на каталог — `0700`.
- Архив не является неизменяемым аудитом: администратор с правами на каталог данных может удалить или изменить архивные файлы. В сценариях с высокими требованиями к соответствию необходимо синхронизировать данные во внешнее WORM-хранилище или SIEM.
- Критичные операции (экспорт закрытых ключей, восстановление из резервной копии, генерация CA, установка плагинов, изменение защищённой точки входа) рекомендуется связывать с заявкой на изменение.

## 8. Безопасность плагинов и цепочки поставок

- Официальный репозиторий плагинов поддерживает подпись индекса Ed25519; после настройки открытого ключа принудительно проверяется `index.json.sig`.
- Самообновление программы по умолчанию требует настройки `upgrade.program.public_key`; если ключ не настроен, онлайн-обновление отклоняется, и только в контролируемой среде можно явно включить `upgrade.program.allow_unsigned`.
- Артефакты должны иметь 64-символьный шестнадцатеричный SHA-256; после скачивания выполняется принудительная проверка.
- При установке проверяются `plugin.json`, ID и версия в манифесте; сбой на любом шаге приводит к откату.
- Дайджесты файлов из записи установки повторно проверяются при обнаружении, регистрации и перед каждым вызовом DNS/развёртывания/уведомлений; при замене файла загрузка или выполнение отклоняется.
- Если открытый ключ подписи не настроен, отображается предупреждение о риске и пропускается автоматическое обновление без участия оператора.
- Кеш индекса (включая повторное использование 304) должен заново проходить проверку подписи текущим открытым ключом по исходным байтам кеша; при изменении открытого ключа или отсутствии подписи в кеше ETag отбрасывается и выполняется полная повторная загрузка; нельзя помечать кеш как проверенный только потому, что «открытый ключ настроен».
- Права на каталог плагинов — `0700`, на helper — `0755`; запись для группы или других пользователей не допускается; символические ссылки отклоняются.
- Плагины развёртывания получают закрытые ключи сертификатов, по умолчанию отключены и должны устанавливаться только из доверенных источников.
- Основная программа ограничивает тайм-аут, постоянную память и размер вывода helper, а также маскирует учётные данные и закрытые ключи в сообщениях об ошибках.

Рекомендации для продуктивной среды:

- Используйте внутреннее корпоративное зеркало (HTTPS или `file://`), фиксируйте версии и отключайте автоматическое обновление.
- Ведите список допуска плагинов с указанием источника, версии, дайджеста, утверждающего лица и версии для отката.
- Проверяйте обновление плагинов в среде предварительного развёртывания, прежде чем выводить его в продуктивную среду.

## 9. Безопасность сервера ACME

- Внутренний сервер ACME по умолчанию включён, но до создания и включения конечной точки он не выпускает сертификаты наружу.
- После включения он предоставляет отдельный протокольный вход и не использует защищённую точку входа административной панели, Cookie сеанса или проверку CSRF; если сервер не нужен, можно задать `acme.enabled` равным `false`.
- При публичном развёртывании рекомендуется использовать отдельный порт и ограничить доступ на уровне межсетевого экрана или обратного прокси.
- Для каждой конечной точки ACME необходимо настроить белый список доменов; при включении конечной точки с пустым белым списком она будет отклонена.
- EAB можно включать и отключать; по умолчанию рекомендуется включать. При отключённом EAB любой, кто может подключиться к этому порту, сможет создать учётную запись, поэтому необходимо использовать белый список доменов, mTLS или сетевой ACL.
- mTLS — это контроль доступа на транспортном уровне, он не заменяет аутентификацию учётной записи ACME по JWS.
- `acme.base_url` следует настраивать как фиксированный публичный адрес, чтобы внедрение заголовка Host не привело к указанию URL ресурсов на неверное место.
- Проверка HTTP-01 по умолчанию отклоняет loopback, частные сети, link-local и диапазоны CGNAT/зарезервированные (например, `100.64.0.0/10`, `192.0.0.0/24`); во внутренних сценариях необходимо явно разрешить их через белый список CIDR на уровне конечной точки.
- Ресурсы протокола ACME используют случайные публичные ID, а не автоинкрементные ID базы данных.
- Адрес каталога пользовательского вышестоящего ACME должен использовать HTTPS; только loopback-адрес локального хоста допускает HTTP.
- При развёртывании одного экземпляра nonce хранится в памяти; после перезапуска сервиса клиент получит `badNonce` и автоматически повторит попытку.
- Конечные точки CRL и OCSP расположены по пути `/pki/{ca}/...` и обычно должны быть доступны из интернета; они организованы по CA и должны оставаться доступными даже при отключении конечной точки регистрации ACME.
- При включённом ACME рекомендуется настроить фиксированный `acme.base_url` (или `security.public_url`); если он не настроен, URL ресурсов выводится из заголовка Host запроса, и публичное развёртывание не должно полагаться на этот резервный вариант.
- Конечные точки CRL/OCSP ограничиваются по IP; CRL кеширует результат для одного и того же набора отозванных сертификатов и увеличивает CRL Number только при изменении содержимого отзыва.
- Ограничение скорости сервера ACME учитывает доверенные прокси из `server.trusted_proxies` и считает по реальному IP клиента.
- CRL/OCSP действуют только для клиентов, которые активно проверяют статус отзыва; поведение браузеров при проверке частных CA различается. Существующие сертификаты необходимо выпустить заново, чтобы они содержали адреса CRL/OCSP.
- Статус отзыва хранится в отдельной таблице `revocations`; удаление или очистка строк сертификатов не стирает записи об отзыве; CRL/OCSP используют эту таблицу как источник.
- Перед выпуском конечного сертификата проверяются `ExtKeyUsage` CA (должен содержать `serverAuth` или `any`) и NameConstraints (Permitted/Excluded DNS·IP); выпуск в задаче и ACME finalize используют одну и ту же проверку.

## 10. Усиление развёртывания и контейнеров

- Запускайте сервис под отдельным пользователем, сохраняйте `config.yaml` с правами `0600`, а каталог данных — `0700`.
- Образ Docker после исправления прав тома скриптом точки входа запускает основную программу под непривилегированным пользователем `lactssl`.
- Compose по умолчанию отбрасывает все capabilities, затем при необходимости добавляет `CHOWN`/`SETUID` и т. п., а также включает корневую файловую систему только для чтения, tmpfs для `/tmp`, `pids_limit` и `init`.
- Не добавляйте `data/`, `config.yaml` в систему контроля версий и не размещайте их в общедоступном каталоге.
- Сервис по умолчанию ограничивает тело запроса обычных интерфейсов до 2 MiB (кроме восстановления резервных копий и загрузки плагинов) и задаёт тайм-ауты чтения и записи; на уровне обратного прокси также рекомендуется настроить размер тела запроса и тайм-ауты.
- В продуктивной среде фиксируйте версии образов/бинарников, регулярно сканируйте образы на уязвимости и следите за бюллетенями безопасности выпусков.
- При использовании привилегированных портов, таких как 80/443, предпочтительно перенаправлять трафик через обратный прокси и не выдавать бинарнику дополнительные capabilities.

## 11. Сопоставление мер контроля

Таблица ниже предназначена для согласования с командой безопасности/аудита того, «что предоставляет продукт и что предприятие добавляет самостоятельно». Это не заключение о соответствии; конкретные меры контроля необходимо адаптировать с учётом системы предприятия и области оценки.

| Тема контроля | Предоставляет LACTSSL | Предприятие должно добавить |
| --- | --- | --- |
| Инвентаризация активов | Сертификаты, задачи, CA, учётные данные, записи развёртывания | Связь с CMDB, принадлежность к бизнесу, ответственные лица |
| Управление доступом | Один администратор, TOTP/ключи доступа, области прав ключей API | SSO, RBAC, bastion-хост, маршруты согласования |
| Криптография | Шифрование полей AES-256-GCM, TLS на уровне прокси, частный CA | HSM/KMS, хранение ключей, соответствие требованиям к аппаратным модулям безопасности |
| Аудит журналов | Журнал операций, системный журнал, локальный архив, ID запроса, экспорт | SIEM, долгосрочное хранение, защита от изменений, правила оповещений |
| Цепочка поставок | Подпись плагинов, SHA-256, проверка записи установки | Внутреннее зеркало, проверка допуска, сканирование уязвимостей |
| Резервное копирование и восстановление | Зашифрованные ZIP-резервные копии, проверка восстановления, снимки миграции | Офлайн-копии, хранение в другом месте, учения по восстановлению |
| Управление изменениями | Журнал операций, резервные копии обновлений, инструкции по откату | Заявки на изменение, двойная проверка, окна обслуживания |
| Управление уязвимостями | CI, проверка выпусков, обновление зависимостей | Сканирование образов, тестирование на проникновение, SLA на исправления |
| Сетевая безопасность | Защищённая точка входа, ограничение скорости, защита от SSRF, доверенные прокси | Межсетевой экран, WAF, нулевое доверие, белый список исходящих подключений |
| Хранение данных | Настройки хранения журналов, очистка сертификатов/журналов, локальный архив | Сроки хранения по требованиям соответствия, внешнее архивирование, защита от изменений и процедура уничтожения |

## 12. Известные ограничения

- Многопользовательский режим и RBAC не предоставляются; сеанс администратора является единственной точкой отказа.
- SSO, LDAP, OIDC, SAML, SCIM не предоставляются.
- HSM/KMS не предоставляются; закрытые ключи хранятся в зашифрованном виде в локальной базе данных.
- Активно-активный кластер не предоставляется; SQLite работает в режиме одной записи, и несколько экземпляров не могут совместно использовать каталог данных.
- Неизменяемый аудит не предоставляется; администратор может очистить журналы или удалить локальный архив, поэтому в сценариях с высокими требованиями к соответствию необходимо внешнее архивирование с WORM/блокировкой хранения.
- Конечная точка метрик Prometheus не предоставляется; мониторинг опирается на журналы, API аутентификации и внешние проверки.
- Автоматический откат на стороне цели развёртывания не предоставляется; целевая система должна сохранять предыдущую версию или использовать атомарный выпуск.
- Сертификаты соответствия требованиям многоуровневой защиты (等保)/ISO не прилагаются; заключение о соответствии выдаётся аккредитованной организацией предприятия.

## 13. Чек-лист проверки безопасности перед вводом в эксплуатацию

### Идентификация

- [ ] Администратор использует надёжный пароль, включены TOTP или ключ доступа.
- [ ] Почта восстановления контролируется и защищена MFA.
- [ ] Неизвестные сеансы очищены.
- [ ] Ключи API выпущены отдельно для каждой системы, с минимальными правами и сроком действия.

### Сеть

- [ ] Административная точка входа доступна только по HTTPS, порт бэкенда не опубликован напрямую в интернет.
- [ ] Настроены `trusted_proxies` и `public_url`.
- [ ] Прокси передаёт `X-Forwarded-For`/`X-Forwarded-Proto`.
- [ ] Настроены ограничения по источнику, WAF или политика нулевого доверия.
- [ ] Исходящие подключения ограничены белым списком целей, при необходимости направляются через корпоративный прокси.

### Данные

- [ ] `config.yaml` — 0600, `data/` — 0700, владелец указан верно.
- [ ] Зашифрованная резервная копия создана и сохранена в другом месте.
- [ ] Пароль резервной копии хранится отдельно от файлов резервных копий.
- [ ] Проведены учения по восстановлению.
- [ ] Хранение и экспорт журналов удовлетворяют требованиям аудита.

### Плагины и ACME

- [ ] Используются только доверенные репозитории/внутреннее зеркало, настроен открытый ключ подписи.
- [ ] В продуктивной среде отключено автоматическое обновление.
- [ ] Плагины развёртывания включены по необходимости, их источник проверен.
- [ ] Для конечных точек ACME настроен белый список доменов, в продуктивной среде включён EAB.
- [ ] Вход ACME ограничен по источнику, при необходимости включён mTLS.

## 14. Реагирование на инциденты безопасности

1. **Определите масштаб**: учётная запись, ключ API, учётные данные DNS/развёртывания, плагин или хост.
2. **Изолируйте**: отзовите сеансы/ключи API, отключите плагины, отключите конечные точки ACME, при необходимости отключите на сетевом уровне.
3. **Соберите доказательства**: экспортируйте журнал операций, системный журнал и журналы обратного прокси, запишите `X-Request-ID`; не очищайте журналы заранее.
4. **Выполните ротацию**: смена пароля удаляет все сеансы и ключи API; ротируйте учётные данные DNS/развёртывания/уведомлений; при подозрении на утечку `salt` действуйте по процедуре утечки ключей.
5. **Восстановите**: восстановитесь из доверенной резервной копии, проверьте согласованность конфигурации и данных, повторно выпустите потенциально затронутые сертификаты.
6. **Проведите разбор**: обновите Runbook, список прав и правила мониторинга.

Конкретные шаги диагностики см. в разделе [Мониторинг и устранение неполадок](troubleshooting.md), а резервное копирование и восстановление — в разделе [Руководство по эксплуатации](operations.md).
