# Обновление и изменения

Обновление версии — одно из самых рискованных повседневных изменений платформы сертификатов: нужно и обеспечить откат миграции базы данных, и избежать простоя при массовом истечении сертификатов. В этом документе приведены оценка перед обновлением, механизм миграции, обновление программы, откат и чек-лист окна изменений.

## 1. Принципы изменений

- **Сначала резервная копия, затем обновление**: `config.yaml` + весь `data/` либо зашифрованная резервная копия через интерфейс.
- **Сначала предварительная среда, затем продуктивная**: проверьте как минимум четыре цепочки — выпуск, развёртывание, уведомления и API.
- **Фиксированная версия**: в продуктивной среде не используйте `latest` для длительной работы, поскольку его нельзя отследить.
- **Сохранение точки отката**: снимок миграции базы данных, старый бинарник/старый тег образа.
- **Избегание пиковой нагрузки**: не допускайте пересечения с периодами массового истечения сертификатов, массового развёртывания или выпуска бизнес-версий.
- **Наблюдаемость**: после обновления наблюдайте как минимум один цикл планирования и одно выполнение задачи.

## 2. Что делает обновление

За время длительного развития в LACTSSL накопился ряд исторических форматов данных и веток совместимости. `internal/upgrade` автоматически выполняет миграцию унаследованных данных при первом запуске новой версии; также можно после входа открыть `/upgrade` для предварительной проверки, ручной миграции и оптимизации базы данных.

### 2.1 Порядок автоматической миграции

1. Считывает и проверяет `config.yaml`.
2. Открывает настроенную базу данных (по умолчанию SQLite, также возможен PostgreSQL) и выполняет базовое создание таблиц.
3. Создаёт инструмент обновления и считывает `upgrade.schema_version`.
4. Если версия устарела, сначала создаёт резервную копию базы данных и конфигурации, затем по порядку выполняет шаги миграции.
5. Записывает новый номер версии и выполняет недорогую оптимизацию базы данных.
6. Продолжает инициализацию учётных записей, планировщика и HTTP-сервиса.

- Автоматическая миграция управляется параметром `upgrade.auto` и по умолчанию включена.
- Все шаги миграции идемпотентны; при сбое номер версии не продвигается, и при следующем запуске неудавшийся шаг будет повторён.
- Резервная копия перед миграцией находится в `data/upgrade-backups/<время UTC>/`; по умолчанию сохраняются последние 5 копий.

### 2.2 Содержание миграции

| Проблема | Поведение старой версии | Обработка инструментом обновления |
| --- | --- | --- |
| У базы данных нет версии формата | Структура выводится только по `ensureColumn` и разрозненным ключам миграции | Записывается `upgrade.schema_version`, идемпотентные шаги выполняются в порядке версий |
| Чувствительные поля в открытом виде | В старых версиях ключи TOTP и закрытые ключи сертификатов записывались в базу напрямую | Используется шифрование AES-256-GCM; записи, уже являющиеся шифротекстом, пропускаются автоматически |
| Файлы ключей старых версий | Ключ хранится в двух местах: `data/jwt.secret` и `config.yaml` | После подтверждения, что ключ сохранён в конфигурации, файл переносится в каталог резервных копий обновления и удаляется |
| Глобальные учётные данные EAB | `acme.eab_kid` / `acme.eab_hmac` применяются только к CA по умолчанию | Переносятся в отдельные настройки CA по умолчанию, старые ключи удаляются |
| Параметры развёртывания смешаны с учётными данными | Путь, сайт и команда перезагрузки хранятся в учётных данных цели | Выносятся в узел развёртывания в задаче; в учётных данных остаётся только информация аутентификации |
| Дублирующиеся цели развёртывания | Старые ID, такие как `qiniu_cdn`, `baota_site`, разбросаны | Объединяются в канонические ID; выбор сайта/панели и CDN/Kodo записывается в узел |
| Старые настройки уведомлений | Gotify / Server酱 используют отдельные ключи настроек | Преобразуются в конфигурацию универсального канала уведомлений, затем старые ключи удаляются |
| Остатки миграции плагинов | Старые полные helper, список отключённых, отсутствующий белый список включённых | Инициализируются белые списки DNS/развёртывания/уведомлений; состояния включения по умолчанию для встроенных элементов сохраняются |
| Старые режимы аутентификации | Исторические значения, такие как `password_passkey` | Приводятся к `passkey`, недопустимые значения откатываются |
| Разрастание базы данных | После удаления сертификатов, журналов и заказов ACME остаются свободные страницы | `VACUUM` освобождает пространство, `ANALYZE` обновляет статистику |
| Слишком большой WAL | После длительной работы файл `-wal` постоянно растёт | `wal_checkpoint(TRUNCATE)` сворачивает и усекает |
| Отсутствие индексов горячих путей | Фильтрация сертификатов, планирование и очистка журналов выполняют полное сканирование таблиц | Индексы добавляются автоматически, повторное выполнение безопасно |
| Разделение таблиц журналов | Системные журналы хранятся в `system_logs`, журнал операций — в `logs` | Системные журналы копируются в `logs(category=runtime)`, старая таблица сохраняется для отката |
| Устаревшая структура конфигурации | Отсутствуют новые разделы, такие как `plugins.repo`, `notify_plugins`, `log.system`, `upgrade` | Недостающие поля дополняются по текущей версии; комментарии сохраняются, эквивалентные записи нормализуются |

## 3. Проверка перед обновлением

- [ ] Прочитайте описание изменений и миграции целевой версии.
- [ ] Уточните текущую версию, версию формата данных и предстоящие шаги миграции.
- [ ] Создайте резервную копию `config.yaml` и `data/` и проверьте её читаемость.
- [ ] Убедитесь в достаточном дисковом пространстве (`VACUUM` требует временного пространства).
- [ ] Проверьте выпуск, развёртывание, уведомления и API в среде предварительного развёртывания.
- [ ] Убедитесь в доступности бинарника/тега образа старой версии.
- [ ] Уведомите заинтересованные стороны и выберите окно низкой нагрузки.
- [ ] Приостановите пакетные задачи, чтобы избежать параллельной записи во время обновления.

## 4. Способы обновления

### 4.1 Docker (рекомендуется)

```bash
# Зафиксируйте целевую версию: сначала измените тег image в docker-compose.yml на 1.2.3
docker compose pull
docker compose up -d
docker compose logs -f lactssl
```

- Используйте явный тег версии для удобства отката.
- Не используйте самообновление внутри контейнера: после пересоздания контейнер вернётся к версии образа.
- В официальном Compose по умолчанию корневая файловая система доступна только для чтения, каталог программы недоступен для записи, и страница сообщит о неподдерживаемом самообновлении; это ожидаемое поведение.

### 4.2 Бинарник

```bash
sudo systemctl stop lactssl
sudo cp lactssl /opt/lactssl/lactssl
sudo chown lactssl:lactssl /opt/lactssl/lactssl
sudo chmod 0755 /opt/lactssl/lactssl
sudo systemctl start lactssl
sudo journalctl -u lactssl -f
```

Примечания:

- При обновлении сохраняются биты прав доступа исходного файла, но не сохраняются расширенные атрибуты, такие как `setcap`; при развёртывании с привилегированными портами или файловыми capability их нужно настроить заново после обновления.
- Самообновление с прямым `exec` нового бинарника работает в Linux/macOS/FreeBSD; в Windows требуется повторный запуск через менеджер служб.
- Для сборок `dev`/из исходного кода, а также для пакетов выпуска, в которых нет ни `checksums.txt`, ни SHA-256 артефактов, самообновление отклоняется; необходимо заменить вручную и самостоятельно проверить.

### 4.3 Самообновление программы (опционально)

В верхней части страницы `/upgrade` доступно «Обновление программы»:

- **Проверить обновления**: запрашивает Release согласно `upgrade.program.channel`; `stable` принимает только стабильные версии, `beta` включает предварительные.
- **Установить обновление**: скачивает `lactssl_<version>_<os>_<arch>.tar.gz` (в Windows — `.zip`), принудительно проверяет SHA-256 по `checksums.txt`, распаковывает `lactssl` и заменяет текущий исполняемый файл.
- **Подпись выпуска**: после настройки `upgrade.program.public_key` принудительно проверяется `checksums.txt.sig`; при отсутствии подписи или её ошибке установка сразу отклоняется. **Если открытый ключ не настроен, онлайн-обновление по умолчанию отклоняется**; для установки неподписанного пакета необходимо явно задать `upgrade.program.allow_unsigned: true` в контролируемой среде.
- **Резервная копия и откат**: перед заменой старый бинарник копируется в `<data_dir>/upgrade-backups/program/`; по умолчанию сохраняются последние 3 копии.
- **Перезапуск для применения**: после установки страница предлагает перезапуск; по умолчанию перезапуск очищает сеансы, а при включённом `security.session_persistence` можно продолжить использовать прежний сеанс.

Ограничения:

- При файловой системе только для чтения, на платформах без пакетов выпуска и в сборках `dev` обновление отображается как недоступное.
- Обновление внутри контейнера не изменяет образ; после пересоздания контейнер вернётся к версии образа.
- Без настроенного токена GitHub API действует анонимное ограничение скорости; токен можно задать через `upgrade.program.token`.
- Если требуется исходящий прокси, настройте его через переменные окружения системного прокси (поведение HTTP-клиента Go).

## 5. Проверка после обновления

1. Проверьте в журнале запуска сообщение «Обновление формата данных завершено».
2. После входа откройте `/upgrade` и убедитесь, что все шаги имеют статус «Завершено» или «Пропущено».
3. Проверьте версию, время сборки и архитектуру.
4. Проверьте вход администратора, TOTP/ключи доступа.
5. Проверьте список сертификатов, задачи, учётные данные развёртывания, каналы уведомлений и плагины.
6. Вручную запустите тестовую задачу и убедитесь в выпуске, развёртывании и уведомлении.
7. Проверьте права ключей API и их вызовы.
8. Наблюдайте как минимум один цикл планирования (30 секунд) и одно автоматическое продление.

## 6. Откат

### 6.1 Откат данных

Инструмент обновления создаёт снимок перед изменением структуры:

```text
data/upgrade-backups/20260101-120000/
├── lactssl.db
└── config.yaml
```

Шаги:

1. Остановите сервис.
2. Замените текущую базу данных файлом `lactssl.db` из резервной копии и удалите `lactssl.db-wal`, `lactssl.db-shm`.
3. Если нужно откатить и конфигурацию, замените текущую конфигурацию файлом `config.yaml` из резервной копии.
4. Запустите программу старой версии.

Примечания:

- Программа старой версии может не читать формат данных, записанный новой версией; при откате между крупными версиями следует одновременно откатывать бинарник и данные резервной копии.
- Не удаляйте вручную `upgrade.schema_version`, иначе шаги миграции будут выполнены повторно.
- Если автоматическая миграция завершилась сбоем, сервис откажется запускаться и выведет неудавшийся шаг; после устранения проблем с правами, диском или данными достаточно перезапустить сервис, чтобы повторить попытку.

### 6.2 Откат программы

Резервные копии обновления программы находятся в:

```text
data/upgrade-backups/program/
├── 20260101-120000-lactssl-1.2.2
└── 20260102-090000-lactssl-1.2.3
```

Шаги:

1. Остановите сервис.
2. Замените текущий бинарник файлом из резервной копии и восстановите права на выполнение (`chmod 0755`).
3. Если нужно откатить данные, выполните действия из предыдущего раздела.
4. Запустите сервис и убедитесь в номере версии и состоянии миграции формата данных.

## 7. Переключение базы данных онлайн (SQLite ↔ PostgreSQL)

Страница `/upgrade` предоставляет переключение бэкенда базы данных. Переключение выполняется внутри процесса сервиса и не требует ручного выполнения SQL или замены файлов базы данных.

### 7.1 Предварительные условия

- Для целевого PostgreSQL рекомендуется версия 18; приложение проверяет версию сервера.
- Целевая база PostgreSQL по умолчанию должна быть пустой; если она не пуста, на странице необходимо установить флажок «Очистить текущую схему», и эта операция удаляет только таблицы в текущей схеме.
- По умолчанию второй экземпляр не может использовать ту же базу данных PostgreSQL (`database.allow_multi_instance: false`); это также проверяется перед переключением.
- Перед переключением принудительно создаётся резервная копия исходной базы: для SQLite используется `VACUUM INTO`, для PostgreSQL — `pg_dump --format=custom`; резервная копия находится в `data/db-convert/backups/<время>/`.
- Сервис должен управляться systemd, политикой перезапуска Docker или аналогичным менеджером процессов, иначе после переключения его придётся запускать вручную.

### 7.2 Порядок выполнения

1. В `/upgrade` выберите целевой бэкенд. Для PostgreSQL можно указать хост, порт, имя пользователя, пароль, имя базы данных и режим SSL либо переключиться на «Нативный DSN» и вставить полный DSN; для SQLite укажите путь к файлу (он должен находиться внутри `data_dir`).
2. Нажмите «Проверить подключение» и «Предварительная проверка», чтобы убедиться в версии целевой системы, состоянии пустой базы, таблицах и числе строк.
3. Введите пароль учётной записи/TOTP и выполните арифметическое подтверждение на странице, после чего начнётся переключение (интерфейс больше не требует ручного ввода `CONVERT`, но API по-прежнему использует это слово подтверждения).
4. Во время переключения включается режим обслуживания, обычные API-интерфейсы приостанавливаются; приложение сначала создаёт резервную копию, затем замораживает запись, копирует таблицы по одной, проверяет число строк и хеш каждой таблицы, выборочно расшифровывает чувствительные поля.
5. После успешной проверки атомарно перезаписывает `config.yaml`, записывает `data/db-convert/state.json` и автоматически перезапускается.
6. Новый процесс открывает целевую базу и выполняет самопроверку при запуске; при сбое автоматически восстанавливает старую конфигурацию и возвращается к исходной базе. После успешной самопроверки автоматически удаляет старый файл базы SQLite (включая `-wal`/`-shm`/`-journal`); резервная копия, созданная перед переключением, сохраняется.

Время заморозки записи зависит от объёма данных; для типичной небольшой базы оно составляет секунды, при большом числе журналов и сертификатов — минуты. Во время копирования и проверки страница может опрашивать ход выполнения.

### 7.3 Откат одним нажатием

После завершения переключения `/upgrade` показывает «Откат одним нажатием» (кроме однотипной миграции). Откат — это не просто возврат к старой конфигурации, а обратное переключение **самых свежих данных текущей базы** на бэкенд, использовавшийся до переключения, с последующим переключением конфигурации и перезапуском, чтобы не потерять записи, сделанные после переключения.

Откат также принудительно создаёт резервную копию текущей базы, замораживает запись и выполняет проверку; необходимо пройти арифметическое подтверждение на странице и ввести пароль учётной записи/TOTP (API по-прежнему использует `ROLLBACK` в качестве слова подтверждения). Резервная копия конфигурации перед переключением сохраняется в `config.yaml.before-db-convert-<время>`. После успешной самопроверки переключения старый файл SQLite удаляется автоматически, но резервная копия перед переключением в `data/db-convert/backups/<время>/` сохраняется; откат заново создаёт базу SQLite на основе текущих данных PostgreSQL.

### 7.4 CLI

При остановленном сервисе ту же базовую логику можно выполнить через CLI:

```bash
./lactssl-dbconvert   -config config.yaml   -source-driver sqlite -source data/lactssl.db   -target-driver postgres -target "postgres://user:pass@host:5432/lactssl?sslmode=verify-full"   -switch -yes
```

`-switch` перезаписывает `config.yaml`, но не запускает сервис автоматически. Если целевая база не пуста, по умолчанию выполнение отклоняется; для подтверждения очистки добавьте `-force`.

### 7.5 Ограничения

- Переключение без простоя с двойной записью/CDC не предоставляется; запись приостанавливается на этапе копирования и переключения.
- При совместном использовании PostgreSQL несколькими экземплярами безопасное переключение невозможно; v1 сразу отклоняет такое переключение.
- Если задана переменная окружения `LACTSSL_DATABASE_DSN`, перезапись файла конфигурации не вступит в силу; перед переключением необходимо удалить эту переменную и перезапустить сервис.
- Перед переключением необходимо убедиться, что нет выполняющихся задач массового развёртывания/выпуска.

### 7.6 Однотипная миграция (SQLite → SQLite / PostgreSQL → PostgreSQL)

Однотипная миграция по умолчанию запрещена. Если действительно нужно перенести базу данных в другой файл или экземпляр PostgreSQL, необходимо установить на странице флажок подтверждения «Однотипная миграция»; в теле запроса API передаётся `allow_same_driver: true`, в CLI используется `-allow-same-driver`. Дополнительные ограничения однотипной миграции:

- Цель должна быть пустой базой/пустым файлом; при однотипной миграции нельзя устанавливать флажок «Очистить схему», чтобы избежать случайного удаления исходной базы.
- Цель не может совпадать с текущей базой: SQLite сравнивает реальные файлы (включая символические и жёсткие ссылки); PostgreSQL сравнивает время запуска экземпляра и имя базы данных, и одна и та же база в одном экземпляре (включая разные схемы) будет отклонена.
- После успешного переключения PostgreSQL → PostgreSQL исходная база данных не удаляется; её необходимо очистить вручную после подтверждения администратором.
- После успешной самопроверки переключения SQLite → SQLite старый файл SQLite удаляется, а резервная копия перед переключением сохраняется в `data/db-convert/backups/`.
- Однотипная миграция не поддерживает «Откат одним нажатием» на странице; восстановите вручную из резервной копии, созданной перед переключением. Исходная база PostgreSQL сохраняется, а старый файл SQLite можно восстановить из резервной копии.
- Однотипную миграцию и `-force` нельзя использовать одновременно.

## 8. Ручная миграция и оптимизация базы данных

После входа откройте `/upgrade` (боковое меню «Система → Обновление версии»):

- **Предварительная проверка**: показывает версию программы, версию формата данных, состояние шагов миграции, целостность базы данных, свободные страницы, изменения конфигурации и предупреждения о рисках; не изменяет никаких данных.
- **Выполнить миграцию и оптимизацию**: повторно выполняет шаги миграции, затем оптимизирует файл конфигурации и базу данных.
- **Только оптимизация базы данных и конфигурации**: не повторяет миграцию, подходит для повседневного обслуживания.
- **Освободить дисковое пространство**: при включении выполняет `VACUUM`, который на короткое время монопольно захватывает базу данных; рекомендуется использовать в период низкой нагрузки.

Результаты выполнения записываются в системный журнал и настройку `upgrade.last_run`.

### 7.1 Содержание оптимизации базы данных

- `PRAGMA quick_check(1)`: быстрая проверка целостности.
- Базовая структура таблиц использует `PRAGMA user_version` для записи версии; если структура уже актуальна, создание таблиц и сканирование `ensureColumn` пропускаются.
- Добавляются индексы горячих путей: статус сертификата и срок действия, состояние включения задачи и следующее выполнение, проверки мониторинга, уровень и время журнала, заказы/challenge ACME, записи развёртывания.
- `PRAGMA optimize`: обновляет статистику в соответствии с шаблонами запросов.
- `ANALYZE`: полный анализ таблиц и индексов (ручная оптимизация).
- `PRAGMA wal_checkpoint(TRUNCATE)`: сворачивает и усекает WAL.
- `VACUUM`: освобождает свободные страницы, оставшиеся от удалённых данных, и уменьшает размер файла.

`VACUUM` не удаляет бизнес-данные, но перезаписывает файл базы данных. Перед выполнением инструмент создаёт снимок базы данных; при недостатке дискового пространства возможен сбой, который возвращается как предупреждение и не влияет на дальнейшую работу сервиса.

### 7.2 Содержание оптимизации файла конфигурации

- Дополняются все стандартные разделы конфигурации и значения по умолчанию текущей версии.
- Нормализуются пробелы в `server.addr`, `acme.addr` и аналогичных полях.
- Удаляются завершающие слэши в `security.public_url`, `acme.base_url`.
- `log.level`, `log.format`, `log.system.level`, `plugins.repo.channel` приводятся к нижнему регистру.
- `server.trusted_proxies` дедуплицируется и очищается от пробелов.
- Проверяются риски: ACME без настроенного фиксированного адреса, репозиторий плагинов без настроенного открытого ключа подписи, доступ плагинов развёртывания к закрытым ключам, слишком короткие ключи и т. п.
- Перед записью выполняется полная проверка по логике загрузки при запуске; при сбое проверки исходный файл не перезаписывается.
- Используется редактирование узлов YAML с сохранением комментариев и порядка полей.

## 9. Параметры конфигурации

```yaml
upgrade:
  auto: true              # автоматически выполнять миграцию унаследованных данных при запуске
  auto_optimize: true     # выполнять недорогую оптимизацию при запуске; без VACUUM
  vacuum: true            # разрешить VACUUM при ручной оптимизации в /upgrade
  program:
    enabled: true
    repo: "AXmishell/LACTSSL"
    channel: stable
    check_interval_hours: 6
    max_download_mb: 128
    public_key: ""
    # если public_key не настроен, онлайн-обновление по умолчанию отклоняется; неподписанные пакеты разрешены только в контролируемой среде
    allow_unsigned: false
    token: ""
```

После отключения `upgrade.auto` журнал запуска сообщит о наличии данных, ожидающих миграции, но сервис продолжит запуск. В этом случае следует как можно скорее войти в `/upgrade` и выполнить миграцию вручную, чтобы новый код не читал данные старого формата; исторические системные журналы не отображаются на вкладке «Журнал → Системный журнал» до завершения шага объединения журналов.

## 10. API

Инструмент обновления использует существующий сеанс входа; интерфейсы всегда расположены в `/api`:

| Интерфейс | Метод | Права | Описание |
| --- | --- | --- | --- |
| `/upgrade` | GET | `upgrade:read` | Состояние предварительной проверки |
| `/upgrade/run` | POST | `upgrade:write` | Миграция, оптимизация конфигурации и базы данных |
| `/upgrade/optimize` | POST | `upgrade:write` | Только оптимизация конфигурации и базы данных |
| `/upgrade/database` | GET | `upgrade:read` | Текущий бэкенд и ход переключения |
| `/upgrade/database/test` | POST | `upgrade:read` | Проверка подключения к цели и состояния пустой базы |
| `/upgrade/database/preflight` | POST | `upgrade:read` | Предварительная проверка переключения |
| `/upgrade/database/convert` | POST | `upgrade:write` | Запуск переключения (требуется повторная аутентификация) |
| `/upgrade/database/convert` | GET | `upgrade:read` | Запрос хода переключения |
| `/upgrade/database/convert/cancel` | POST | `upgrade:write` | Отмена незавершённого переключения |
| `/upgrade/database/rollback` | POST | `upgrade:write` | Обратное переключение на старый бэкенд одним нажатием |
| `/upgrade/program` | GET | `upgrade:read` | Состояние обновления программы |
| `/upgrade/program/check` | POST | `upgrade:write` | Немедленный запрос GitHub Release |
| `/upgrade/program/apply` | POST | `upgrade:write` | Скачивание и установка указанной версии |
| `/upgrade/program/restart` | POST | `upgrade:write` | Перезапуск сервиса после установки |

Тело запроса может содержать логические поля `vacuum`, `analyze`, `config`, `optimize` и т. п. Для интерфейсов записи достаточно сеанса входа или ключа API с соответствующими правами.

## 11. Чек-лист окна изменений

- [ ] Заинтересованные стороны уведомлены, период массового истечения сертификатов исключён.
- [ ] Резервная копия создана, пароль восстановления проверен.
- [ ] Дисковое пространство подтверждено (резервная копия + временное пространство для VACUUM).
- [ ] Подготовлен бинарник/тег образа старой версии.
- [ ] Пакетные задачи и автоматические триггеры приостановлены.
- [ ] Обновление и проверка завершены.
- [ ] Пакетные задачи и автоматизация возобновлены.
- [ ] Записаны заявка на изменение, версия, время и результат.
