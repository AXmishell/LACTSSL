# Мониторинг и устранение неполадок

В этом документе приведены наиболее частые сбои, пути диагностики и аварийные действия на этапах внедрения и эксплуатации на предприятии. При устранении неполадок сначала сохраните текущее состояние, затем ищите причину в порядке «зависимости → аутентификация → бизнес → данные», избегая немедленной перезагрузки или очистки журналов.

## 1. Первичная диагностика

### 1.1 Определение масштаба влияния

- Сбой затрагивает один сертификат, одну задачу или все задачи?
- Недоступна административная точка входа или сбоит только выпуск/развёртывание?
- Затронута одна цель развёртывания или все цели?
- Проблема появилась после обновления/изменения конфигурации или возникла внезапно во время работы?
- Затронуты ли одновременно уведомления, мониторинг или клиенты ACME?

### 1.2 Сбор базовой информации

```bash
# Версия и процесс
curl -fsS -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/status

# Журналы Docker
docker compose logs --since=30m lactssl

# Журналы systemd
sudo journalctl -u lactssl --since "30 min ago"

# Порты
ss -lntp | grep -E '8080|14000'
```

Также запишите:

- Время возникновения, часовой пояс и попадание в окно изменений.
- ID соответствующих задач/сертификатов/записей развёртывания.
- Заголовок ответа `X-Request-ID`.
- Исходный текст ошибки (после маскирования).

### 1.3 Проверка зависимостей

| Зависимость | Способ проверки |
| --- | --- |
| Обратный прокси | Журналы прокси, порт бэкенда, заголовки пересылки |
| DNS API | Права учётных данных, квоты, домен/зона, записи TXT |
| Публичный CA | Страница состояния, ограничения частоты, CAA, EAB |
| Цель развёртывания | Сеть, аутентификация, путь, права, команда перезагрузки |
| SMTP/IM | Связность, аутентификация, конфигурация канала |
| Хост | Диск, память, права файлов, синхронизация времени |

## 2. Доступ и вход

### 2.1 Корневой путь возвращает 404

**Симптом**: `https://ssl.example.com/` возвращает 404.

**Причина**: запрос не прошёл через защищённую точку входа. Точка входа — случайный путь, а голый корневой путь всегда возвращает 404.

**Решение**:

1. Посмотрите защищённую точку входа в журнале запуска.
2. Либо посмотрите значение `security.entry` в таблице `settings` базы данных.
3. Либо задайте `security.entry` в `config.yaml` и перезапустите сервис, чтобы переопределить значение.

### 2.2 Забыта защищённая точка входа

- Журнал запуска (при инициализации выводится полная точка входа).
- Значение `security.entry` в таблице `settings` базы данных.
- Измените `security.entry` в `config.yaml` перед запуском; после перезапуска значение будет переопределено.

После изменения точки входа старые ссылки сразу перестают работать; запишите новую точку входа и уведомите заинтересованные стороны.

### 2.3 Сразу после входа сеанс завершается/становится недействительным

**Возможные причины**:

- Сервис перезапущен, а `security.session_persistence` был явно отключён.
- Пароль изменён, и все сеансы удалены.
- Сервис запущен с другим `jwt_secret`.
- Обратный прокси не передаёт `X-Forwarded-Proto`, из-за чего `Secure` Cookie работают некорректно.
- Браузер или прокси закешировал старые Cookie.

**Решение**:

1. Уточните, не был ли сервис только что перезапущен и не менялся ли пароль.
2. Проверьте заголовки прокси и `trusted_proxies`.
3. Очистите Cookie браузера и войдите заново через защищённую точку входа.
4. Сохранение сеансов включено по умолчанию; если было задано `security.session_persistence: false`, верните `true`, чтобы сеансы сохранялись после перезапуска.

### 2.4 Аномалии Cookie и неточное ограничение скорости

**Симптом**: циклы входа, сбой CSRF, все запросы используют одну квоту IP.

**Причина**: не настроен доверенный прокси, прокси не передаёт заголовки пересылки, или в многоуровневой схеме доверен только ближайший узел.

**Решение**:

```yaml
server:
  trusted_proxies: ["127.0.0.1"]
security:
  public_url: "https://ssl.example.com"
```

Убедитесь, что прокси задаёт:

```nginx
proxy_set_header X-Real-IP $remote_addr;
# Рекомендуемый режим перезаписи: достаточно доверять этому прокси
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
```

Если используется режим добавления (`$proxy_add_x_forwarded_for`), в цепочке CDN → Nginx → LACTSSL нужно перечислить в `trusted_proxies` все прокси, которые могут появиться в XFF; иначе IP клиента остановится на вышестоящем прокси.

Проверьте в «Настройки → Файл конфигурации → Автоопределение»:

- `peer_ip`: TCP-peer;
- `applied_trusted_proxies`: действующий список доверенных прокси;
- `effective_client_ip` / `client_ip_source`: итоговый результат и его источник;
- `trusted_skipped`: сколько доверенных элементов пропущено справа налево;
- `header_warnings`: некорректный или слишком длинный XFF и другие проблемы разбора.

В журнале доступа также есть `ip_source`, `ip_skipped`, `ip_warnings`. После сохранения нужен перезапуск; до него `configured_trusted_proxies` и `applied_trusted_proxies` могут различаться.

### 2.5 429 Слишком много запросов

- Повторите попытку позже с задержкой согласно заголовку ответа `Retry-After`.
- Проверьте, не используется ли общий IP прокси; после настройки доверенных прокси квота считается по реальному IP клиента.
- Для входа, TOTP, сброса пароля, скачивания резервных копий, экспорта закрытых ключей и протокола ACME действуют независимые ограничения скорости.
- Не повышайте пороги ограничения скорости, чтобы скрыть подбор паролей или вышедшие из-под контроля скрипты.

### 2.6 Ключи доступа недоступны

- Доступ должен осуществляться через HTTPS-домен или localhost; IP-адрес не может быть источником WebAuthn.
- Проверьте, поддерживает ли браузер WebAuthn и включена ли на системе биометрия/PIN.
- Ключ доступа не заменяет пароль; при утере устройства используйте пароль + TOTP или другой путь восстановления.

## 3. Сбой выпуска сертификата

### 3.1 Сбой проверки DNS-01

| Возможная причина | Проверка |
| --- | --- |
| Учётные данные не имеют прав | Есть ли у ключа API права на чтение и запись целевой зоны |
| Домен/зона не совпадает | Находится ли домен в зоне, видимой текущей учётной записи |
| Медленное распространение TXT | Подождите TTL; проверьте, возвращает ли авторитетный DNS запись TXT |
| Многоуровневый домен/CNAME | Убедитесь в пути разрешения `_acme-challenge` |
| Wildcard | Для wildcard-доменов необходимо использовать DNS-01 |
| Ограничения провайдера | Квоты, ограничения частоты, изменения API |
| Прокси/шлюз | Доступность пользовательского адреса API, доверие к сертификату |

Обработка:

1. Посмотрите конкретную ошибку DNS-провайдера в журнале задачи.
2. С помощью `dig`/`nslookup` проверьте TXT для `_acme-challenge.<domain>`.
3. С теми же учётными данными вручную создайте/удалите TXT в консоли провайдера, чтобы подтвердить права.
4. Проверьте, разрешает ли запись CAA у CA использование этого CA.
5. После исправления повторно запустите задачу.

### 3.2 Ограничения частоты CA/ошибки EAB

- Публичные CA, такие как Let's Encrypt, имеют ограничения частоты для учётных записей, доменов и неудачных проверок; смотрите страницу состояния CA и подробности ошибки.
- ZeroSSL, Google Trust Services, LiteSSL, ZoTrus, Actalis и SSL.com требуют EAB; убедитесь, что EAB KID/HMAC указаны верно и не истекли (для ZoTrus KID — зарегистрированная почта).
- ZoTrus формирует имя записи dns-01 из `tokenPath`, который возвращает сервер (обычно `_<tokenPath>.<domain>`), а не из стандартного `_acme-challenge`. После запуска задача с ZoTrus переходит в состояние «Ожидание DNS-проверки»; добавьте записи из журнала задачи или панели «DNS-проверка» и нажмите «Продолжить проверку». ZoTrus пока не поддерживает подстановочные сертификаты, пулы CA и Target Flow Beta.
- Каталог универсального вышестоящего ACME должен использовать HTTPS; исключение — loopback на локальном хосте.
- Для критичных доменов подготовьте резервный CA, чтобы ограничение частоты одного CA не привело к полному сбою.

### 3.3 Сертификат выпущен, но браузер не доверяет ему

- Сертификаты публичных CA должны быть доверенными; проверьте, развёрнута ли полная цепочка (fullchain).
- Для сертификатов частного CA необходимо установить корневой CA в хранилище доверия клиента.
- Проверьте, не развёрнута ли неправильная пара сертификат/закрытый ключ.
- Проверьте соответствие SNI, домена и SAN сертификата.
- Проверьте точность системного времени.

### 3.4 Сбой выпуска в частном CA

- Убедитесь, что CA не истёк, имеет назначение выпуска и длину пути, допускающую подчинённый CA.
- Убедитесь, что срок действия сертификата не превышает срок действия CA.
- У импортируемого CA сертификат должен соответствовать закрытому ключу и иметь базовые ограничения CA.
- Перед удалением CA сначала удалите подчинённые CA.

## 4. Сбой развёртывания

### 4.1 SSH/SFTP

| Симптом | Причина | Обработка |
| --- | --- | --- |
| Несовпадение отпечатка хоста | Сервер сменил ключ или конфигурация неверна | Сверьте отпечаток; очистите старый отпечаток и запишите заново |
| Первое подключение отклонено | Отпечаток не указан и TOFU не включён | Укажите `SHA256:...` или явно включите доверие при первом подключении |
| Сбой аутентификации | Неверны имя пользователя/пароль/закрытый ключ | Проверьте учётные данные и конфигурацию SSH на цели |
| Нет прав на путь | У пользователя развёртывания нет прав на запись | Настройте права каталога или используйте пользователя с правами |
| Сбой команды перезагрузки | Команда отсутствует/недостаточно прав/неверное имя службы | Выполните вручную на целевом хосте для проверки |

### 4.2 Локальный каталог

- Пользователь, от имени которого работает сервис, не имеет прав на запись в целевой каталог.
- Путь не существует; каталог нужно создать заранее.
- Ограничения SELinux/AppArmor.
- Команда перезагрузки завершилась сбоем, но файлы сертификатов обновлены; проверьте, загружает ли служба новые файлы на самом деле.

### 4.3 Панель/CDN/Webhook

- Учётные данные истекли, недостаточно прав или версия API не совпадает.
- Параметры развёртывания (сайт, домен, имя сертификата) не соответствуют целевой системе.
- В целевой системе включён белый список IP, и исходящий адрес LACTSSL не разрешён.
- Публичные цели Webhook должны использовать HTTPS; loopback/частная сеть допускают HTTP.
- Плагин развёртывания не установлен, не включён или проверка файлов завершилась сбоем.

### 4.4 Сертификат обновлён, но бизнес использует старый

- В узле развёртывания не настроена команда перезагрузки или команда не вступила в силу.
- В целевой системе есть кеш (CDN, WAF, балансировщик нагрузки).
- Развёртывание выполнено в неверный путь/сайт.
- При развёртывании на нескольких экземплярах обновлён только один.
- Проверьте, совпадают ли серийный номер/отпечаток сертификата с целевой системой.

## 5. Уведомления и мониторинг

### 5.1 Уведомление не доставлено

- Включён ли канал на странице плагинов и включена ли отправка уведомлений на странице уведомлений.
- Не истекли ли Token/Webhook и доступна ли цель.
- Использует ли SMTP неявный TLS; если сервер не поддерживает STARTTLS, отправка будет отклонена.
- Включён ли узел уведомлений в задаче и соответствует ли момент срабатывания.
- Проверьте ошибки отправки в журнале операций/системном журнале; чувствительные значения маскируются.

### 5.2 Ложные срабатывания мониторинга сайтов

- Мониторинг проверяет имя хоста и системную цепочку доверия; самоподписанные сертификаты, неполная цепочка и несовпадение имени хоста помечаются как аномалия.
- Проверьте целевой порт, SNI, системное хранилище доверия CA и время.
- Разные узлы за балансировщиком нагрузки могут возвращать разные сертификаты; убедитесь в стабильности цели мониторинга.
- Проверьте, разумны ли частота и тайм-аут мониторинга; избегайте частых оповещений по нестабильным целям.

### 5.3 Напоминания об истечении не приходят

- Включено ли автоматическое продление задачи, разумен ли `RenewDays`.
- Работает ли планировщик (смотрите записи планирования в журнале).
- Доступны ли каналы уведомлений.
- Не были ли сертификаты очищены или ссылки на них в задачах обнулены.

## 6. Проблемы с плагинами

| Симптом | Причина | Обработка |
| --- | --- | --- |
| Список магазина плагинов пуст | Индекс не обновлён/репозиторий недоступен | Проверьте адрес репозитория, сеть, TLS |
| Сбой установки | Несовпадение подписи, SHA-256, платформы, `min_host` | Посмотрите подробности ошибки; сверьте открытый ключ и версию |
| После установки провайдер не появился | Файл/элемент не включён | Включите файл helper и конкретные элементы |
| Плагин отклонён при загрузке | Каталог доступен на запись группе/другим пользователям, символическая ссылка, изменение дайджеста | Исправьте права или переустановите |
| Сбой миграции старого плагина | Занят старый helper/конфликт файлов | Действуйте по подсказке миграции; при сбое выполняется откат |
| Плагин развёртывания недоступен | `deploy_plugins.enabled: false` | Явно включите и перезапустите |
| Отсутствует канал уведомлений | helper не установлен/не включён | Установите и включите плагин уведомлений |

Каталоги плагинов:

```text
data/plugins/dns
data/plugins/deploy
data/plugins/notify
```

Требования к правам: каталог `0700`, helper `0755`, владелец — пользователь, от имени которого работает сервис.

### 6.1 После импорта цепочки доверия плагин всё равно сообщает о сбое проверки TLS

Сначала определите причину по конкретному сообщению:

- **Сертификат истёк или ещё не вступил в силу**: продлите или обновите целевой сертификат; импорт CA не продлевает срок действия сертификата.
- **Сертификат не соответствует адресу доступа**: используйте для доступа домен из SAN сертификата; при доступе по IP сертификат должен содержать соответствующий IP SAN.
- **Сертификат не является доверенным**: убедитесь, что импортирован открытый ключ CA, выпустившего этот сертификат (корневой или промежуточный CA), а не конечный сертификат сайта; один импорт PEM может содержать несколько CA. После импорта перезапуск не требуется.
- В остальных случаях проверьте с помощью `openssl s_client -connect host:port -servername host -showcerts`, полна ли цепочка сертификатов, фактически возвращаемая целью.

Подпроцесс плагина читает `<data_dir>/trusted-ca-bundle.pem` через `SSL_CERT_FILE`. Цепочка доверия объединяет системные корневые сертификаты, импортированные CA и частные CA; импортировать следует только действительно контролируемые внутренние CA.

## 7. Резервное копирование и восстановление

### 7.1 Сбой скачивания резервной копии

- Требуется повторно ввести текущий пароль; при включённом TOTP также требуется динамический код проверки.
- Пароль резервной копии должен содержать не менее 12 символов.
- Ограничения размера тела запроса/ответа на обратном прокси.
- Недостаточно дискового пространства.
- Проверьте журнал операций и системный журнал.

### 7.2 После восстановления учётные данные не расшифровываются

- `config.yaml` в резервной копии не соответствует базе данных, отличается `salt`.
- Восстановлена только база данных, конфигурация потеряна.
- Решение: восстановитесь из полной ZIP-резервной копии; не заменяйте базу данных отдельно.

### 7.3 После восстановления не удаётся войти

- Используйте административную учётную запись из резервной копии.
- По умолчанию перезапуск очищает сеансы, и нужно войти заново.
- Защищённая точка входа могла измениться; посмотрите журнал запуска.
- Разный `jwt_secret` приводит к недействительности старых токенов.
- Пакет восстановления находится в `data/restore-pending/`; проверьте, применён ли он.

### 7.4 После восстановления сервис не поднялся автоматически

- Docker: убедитесь в наличии `restart: unless-stopped`.
- systemd: убедитесь, что служба запущена.
- Прямой запуск бинарника: требуется ручной перезапуск.
- Проверьте ошибки проверки конфигурации в журнале запуска.

## 8. База данных, диск и память

### 8.1 База данных растёт

- Растут сертификаты, журналы задач, журнал операций, системный журнал и заказы ACME.
- Используйте очистку сертификатов одним нажатием, очистку в диагностике ACME и очистку системного журнала.
- В период низкой нагрузки выполните в `/upgrade` «Только оптимизация базы данных и конфигурации», при необходимости с включённым VACUUM.
- Проверьте размер WAL; инструмент оптимизации выполняет `wal_checkpoint(TRUNCATE)`.

### 8.2 Недостаточно диска

- Проверьте `data/`, журналы, `upgrade-backups/`, файлы резервных копий.
- Очистите старые снимки обновления и резервные копии старых бинарников (согласно политике хранения).
- Убедитесь, что резервные копии не записываются обратно в тот же каталог данных.
- VACUUM требует временного пространства; при нехватке диска он завершится сбоем.

### 8.3 Высокое потребление памяти/OOM

- Базовая память основного процесса в простое — несколько десятков MB; плагин — одноразовый подпроцесс, ограниченный `memory_limit_mb`.
- Распаковка при установке/обновлении плагинов даёт кратковременный пик, особенно заметный для крупных DNS-пакетов.
- При параллельных задачах одновременно запускается несколько helper.
- Проверьте, не слишком ли низок лимит памяти контейнера; оставьте запас на пики.
- Снизьте параллелизм или уменьшите лимит памяти helper, но убедитесь, что плагины работают нормально.

### 8.4 Блокировка базы данных/сбой записи

- Убедитесь, что каталог данных подключён только к одному экземпляру.
- Не размещайте SQLite на общем хранилище с множественной записью.
- Проверьте заполнение диска, права, файловую систему только для чтения.
- Во время резервного копирования/восстановления избегайте большого числа параллельных задач.

## 9. Обновление и миграция

### 9.1 Сбой миграции при запуске

- Посмотрите неудавшийся шаг в журнале.
- Проверьте диск, права, целостность базы данных.
- После исправления просто перезапустите сервис для повторной попытки; шаги миграции идемпотентны, и при сбое номер версии не продвигается.
- Не удаляйте вручную `upgrade.schema_version`.

### 9.2 После обновления страница недоступна

- Проверьте обратный прокси/кеш статических ресурсов.
- Выполните принудительное обновление или очистите кеш CDN.
- Проверьте соответствие версии бинарника/образа.
- Посмотрите журнал запуска и консоль браузера.

### 9.3 Самообновление программы отклонено

- Файловая система только для чтения, сборка `dev`, платформа без пакетов выпуска, отсутствие контрольной суммы/подписи — всё это приводит к отказу.
- Обновление внутри контейнера не изменяет образ; обновляйтесь через тег образа.
- Проверьте ограничения частоты GitHub API и исходящий прокси.

## 10. Устранение неполадок сервера ACME

| Ошибка клиента | Возможная причина | Обработка |
| --- | --- | --- |
| `badNonce` | Перезапуск сервиса или истечение nonce | Клиент повторяет автоматически; проверьте, не используется ли сервис несколькими экземплярами |
| `unauthorized` | Ошибка учётной записи/JWS, отсутствует EAB | Проверьте EAB, ключ учётной записи, конечную точку |
| `rejectedIdentifier` | Домен отсутствует в белом списке | Проверьте белый список доменов конечной точки |
| `caa` | CAA не разрешает этот CA | Измените CAA или смените CA |
| `orderNotReady` | challenge не завершён | Завершите авторизацию и выполните finalize |
| `rateLimited` | Сработало ограничение частоты конечной точки | Повторите попытку позже с задержкой согласно `Retry-After` |
| Сбой HTTP-01 | Цель недоступна/частная сеть отклонена | Проверьте белый список CIDR, порт, маршрутизацию |
| Сбой mTLS | Сертификат клиента не является доверенным | Проверьте `mtls.client_ca` и цепочку сертификатов клиента |
| Неверный URL ресурса | `base_url` не настроен | Настройте фиксированный `acme.base_url` |

Диагностика:

- «Диагностика ACME» показывает учётные записи, заказы, авторизации, challenge и сертификаты.
- Проверьте `acme.base_url`, белый список конечных точек, EAB, тип challenge.
- При публичном развёртывании не полагайтесь на вывод URL из заголовка Host запроса.
- Конечные точки CRL/OCSP организованы по CA; убедитесь в их доступности для клиентов.

## 11. Аварийные действия

### 11.1 Подозрение на утечку ключа API

1. На странице «Ключи API» отключите или удалите этот ключ.
2. Создайте новый ключ и обновите вызывающую сторону.
3. Проверьте в журнале операций аномальные вызовы, развёртывания и скачивания закрытых ключей.
4. Если затронуты цели развёртывания, ротируйте соответствующие учётные данные.
5. Запишите инцидент и проведите разбор.

### 11.2 Подозрение на компрометацию административной учётной записи

1. Немедленно смените пароль; это удалит все сеансы, ключи API и ключи доступа.
2. Проверьте, не была ли изменена почта восстановления.
3. Проверьте журнал операций, системный журнал и журналы обратного прокси.
4. Ротируйте учётные данные DNS/развёртывания/уведомлений.
5. При подозрении на утечку `salt` действуйте по процедуре утечки ключей; при необходимости пересоздайте экземпляр и заново введите учётные данные.
6. Оцените необходимость повторного выпуска затронутых сертификатов.

### 11.3 Сертификат развёрнут/перезаписан ошибочно

1. Приостановите связанные задачи, чтобы избежать дальнейшей перезаписи.
2. Восстановите предыдущую версию из резервной копии целевой системы или истории сертификатов.
3. Проверьте параметры узла развёртывания задачи и команду перезагрузки.
4. Разверните правильный сертификат заново и проверьте серийный номер/отпечаток.
5. Запишите первопричину и добавьте проверку перед развёртыванием.

### 11.4 Злоупотребление конечной точкой ACME

1. Отключите конечную точку или выключите `acme.enabled`.
2. Проверьте учётные записи, заказы и исходные IP.
3. Включите EAB, mTLS или сетевой ACL.
4. Очистите аномальные учётные записи и заказы.
5. Оцените, не были ли выпущены непредусмотренные сертификаты.

## 12. Сбор информации для обращения

При обращении к поставщику или сообществу предоставьте:

- Версию LACTSSL, время сборки, архитектуру, способ развёртывания.
- Операционную систему, версию контейнера/оркестратора, тип обратного прокси.
- Шаги воспроизведения, ожидаемый и фактический результат.
- Соответствующие фрагменты журналов (с маскированием): время, `X-Request-ID`, код ошибки.
- ID задач/сертификатов/записей развёртывания.
- Были ли недавно обновления, изменения конфигурации, замена плагинов или ротация учётных данных.
- Уже предпринятые действия и их результаты.

Не предоставляйте:

- Пароль администратора, seed-значение TOTP, ключи API в открытом виде.
- Закрытые ключи сертификатов, закрытые ключи CA, пароли резервных копий.
- Немаскированные учётные данные DNS/развёртывания/уведомлений.
