# 部署架構

本文面向平臺架構師和運維負責人，說明 LACTSSL 的部署單元、網路邊界、容量估算和可用性設計。**預設部署仍是單例項、單租戶、SQLite 單寫**；從當前版本起也可以顯式選擇 PostgreSQL 18，並透過 `/upgrade` 在兩種後端之間轉換。多例項共享 PostgreSQL 預設被拒絕，HA 仍不在內建能力範圍內。

## 1. 部署單元

LACTSSL 是一個自包含的 Go 二進位制：

- 前端構建產物嵌入二進位制，不需要獨立的 Web 伺服器或 Node 執行時。
- 資料儲存在本地 SQLite，不依賴外部資料庫、快取或訊息佇列。
- DNS、部署、通知外掛以一次性子程序執行，外掛檔案放在資料目錄下。
- 執行時只有兩類持久化輸入：`config.yaml` 和 `data/` 目錄。

```text
/opt/lactssl/
├── lactssl                 # 二進位制
├── config.yaml             # 配置與金鑰，0600
└── data/                   # 0700
    ├── lactssl.db          # SQLite 主庫
    ├── lactssl.db-wal      # WAL（執行時）
    ├── lactssl.db-shm      # 共享記憶體（執行時）
    ├── plugins/            # dns / deploy / notify helper
    ├── plugin-icons/       # 外掛圖示快取
    ├── upgrade-backups/    # 遷移與程式升級備份
    └── restore-pending/    # 待應用的恢復包
```

備份邊界就是 `config.yaml` + `data/`。只備份資料庫會丟失 `salt`，導致加密憑據無法解密。

## 2. 參考拓撲

### 2.1 單機 + 反向代理（推薦起點）

```text
Internet / 企業內網
        │ HTTPS 443
┌───────▼────────┐
│ Nginx / Caddy  │  TLS 終止、來源限制、訪問日誌
│ / WAF / 負載均衡│
└───────┬────────┘
        │ HTTP 127.0.0.1:8080
┌───────▼─────────────────────────────┐
│ LACTSSL                             │
│  ├─ 管理控制台 / API                │
│  ├─ 排程器（每 30 秒檢查到期任務）  │
│  ├─ 私有 CA / ACME 服務（可選）     │
│  └─ SQLite + 本地外掛               │
└───┬──────────┬──────────┬───────────┘
    │          │          │
 DNS API    部署目標    通知/郵件
```

適用：大多數企業單環境部署，幾十到數千張證書。

要點：

- 主程式本身不提供管理埠的 TLS 配置，生產必須由反向代理終止 TLS。
- 反向代理與 LACTSSL 最好同機或同網段；後端埠只監聽迴環或內網。
- 反向代理必須覆蓋或正確追加 `X-Forwarded-For` 並傳遞 `X-Forwarded-Proto`，並在 `server.trusted_proxies` 中登記代理的精確 IP/最小 CIDR；多級追加鏈路需登記鏈上所有代理。
- `security.public_url` 必須配置為對外固定地址，密碼重置等連結不依賴請求 Host。

### 2.2 DMZ 代理 + 內網應用

```text
使用者 ──HTTPS──► DMZ 反向代理 ──內網 HTTP──► LACTSSL（應用網段）
                                              │
                                              ├─► DNS API / 公網 CA（出站 443）
                                              ├─► SSH / 面板 / CDN（按目標）
                                              └─► SMTP / Webhook（按渠道）
```

適用：安全要求較高，管理面不直接暴露在業務網段。

要點：

- 在防火牆上只放行代理到 LACTSSL 的管理埠。
- LACTSSL 的出站訪問按目標做白名單；如果無法做網域白名單，至少限制目的埠和網段。
- 如需在 DMZ 單獨暴露 ACME 服務端，使用獨立監聽埠，不要複用管理埠。

### 2.3 內網 PKI / ACME 服務

```text
內部服務 / certbot / lego / acme.sh
        │ ACME v2（HTTPS 或 mTLS）
┌───────▼─────────────┐
│ LACTSSL ACME 端點    │ 獨立埠 :14000
│ 繫結私有 CA          │ 網域白名單 / EAB / 挑戰型別
└───────┬─────────────┘
        │
   私有 CA 層級
```

適用：內部服務證書、裝置證書、測試環境證書。

要點：

- ACME 端點未建立並啟用時不會簽發證書；每個端點必須配置網域白名單。
- 公網可達時建議開啟 EAB，並在網路層限制來源；更高要求使用 mTLS。
- `acme.base_url` 必須是客戶端實際訪問的固定地址；公網部署不要依賴請求 Host。
- CRL/OCSP 端點按 CA 組織，停用 ACME 報名端點後仍應保持可達（如客戶端需要檢查吊銷）。

### 2.4 容器平臺

```text
Ingress / Service
        │
┌───────▼────────┐
│ Pod: lactssl    │
│  /app/config    │── PVC 或配置卷
│  /app/data      │── PVC
└────────────────┘
```

要點：

- 使用官方映象時，容器內固定讀取 `/app/config/config.yaml`，資料目錄為 `/app/data`。
- 入口腳本會修正掛載目錄歸屬後降權到 `lactssl` 使用者執行；Compose 預設只讀根檔案系統、丟棄 capabilities。
- **單副本**：不要讓多個 Pod 同時寫同一個 SQLite 資料卷。
- 容器內自升級不會改變映象，重建後仍回到映象版本；生產透過映象標籤升級。
- 使用 `restart: unless-stopped` 或編排平臺的等價策略，恢復備份後需要自動拉起。

## 3. 埠與網路流

| 方向 | 埠/協議 | 用途 | 建議 |
| --- | --- | --- | --- |
| 入站 | 443/TCP | 管理控制台與 API（經反向代理） | 僅對受控來源開放 |
| 入站 | 8080/TCP | LACTSSL 主監聽（預設） | 只監聽迴環/內網，由代理訪問 |
| 入站 | 自定義/TCP | ACME 獨立監聽（可選） | 獨立埠，限制來源 |
| 出站 | 443/TCP | DNS 服務商 API、公共 ACME CA、通知、Webhook、面板、雲 CDN | 按網域/網段白名單 |
| 出站 | 22/TCP 或自定義 | SSH/SFTP 部署 | 僅放行目標主機 |
| 出站 | 21/990/TCP | FTP/FTPS 部署（外掛） | 優先 FTPS，限制目標 |
| 出站 | 25/465/587/TCP | SMTP 通知 | 使用企業郵件閘道器 |
| 出站 | 自定義 | 自建 Gotify、內網 Webhook、監控目標 | 按需放行，注意 SSRF 邊界 |

說明：

- 服務端會對出站目標做 SSRF 校驗，拒絕雲後設資料、鏈路本地、保留網段等地址；迴環與私網仍允許，便於內網整合。
- 部署 Webhook 會攜帶證書私鑰，公網目標強制 HTTPS；迴環、私網、`.local`、`.internal` 允許 HTTP。
- 反向代理如果做 TLS 終止，後端按 HTTP 訪問；必須正確傳遞 `X-Forwarded-Proto`，否則 Cookie 的 `Secure` 判斷和限流識別會出錯。

## 4. 容量規劃

以下為**參考起點**，不是廠商承諾。實際容量取決於證書數量、任務頻率、日誌量、外掛型別和備份策略，建議在生產前用真實負載壓測。

| 規模 | 證書/任務量 | 建議配置 | 說明 |
| --- | --- | --- | --- |
| 試點/小規模 | < 100 張證書，少量任務 | 2 vCPU / 1 GB / 10 GB | 避免同時安裝大型外掛包 |
| 中等規模 | 100–1,000 張，日常續期 | 2–4 vCPU / 2 GB / 20 GB | 建議開啟日誌輪轉和定期清理 |
| 較大規模 | 1,000–5,000 張，頻繁部署 | 4–8 vCPU / 4 GB / 50 GB+ | 關注 SQLite 寫放大、備份視窗和外掛峰值 |

記憶體要點：

- 主程序空閒基線約幾十 MB；外掛是每次呼叫啟動的子程序，單個 helper 受 `memory_limit_mb` 限制（預設 128 MB）。
- 外掛安裝/更新解包會帶來瞬時記憶體峰值，大型 DNS 包更明顯；不要把容器記憶體壓到剛好等於空閒佔用。
- 多個任務併發執行時可能同時拉起多個 helper，需為峰值留餘量。

儲存要點：

- 資料庫增長主要來自證書、任務日誌、操作日誌、系統日誌和 ACME 訂單。
- 操作日誌與系統日誌共用 `logs` 表，透過 `category` 區分；保留與清空策略按分類隔離，清空系統日誌不會影響操作日誌。
- 證書、日誌和 ACME 診斷資料都提供清理入口；系統日誌有 `retention_days` 和 `max_rows`。
- `data/upgrade-backups/` 預設保留最近 5 份遷移快照，程式升級預設保留 3 份舊二進位制。
- 備份檔案不要寫回同一資料目錄；備份空間按資料庫大小的數倍預留。

## 5. 可用性與災難恢復

### 5.1 當前版本的可用性邊界

- **不支援內建叢集/雙活**。SQLite 單寫，多個例項同時掛載同一資料目錄會造成鎖競爭或資料損壞。
- **不提供自動故障切換**。反向代理可以探測存活，但不應把流量自動切到另一個寫同一份資料的例項。
- **單管理員帳戶**是單點：帳戶丟失需要透過備份或密碼重置恢復，建議把管理員職責繫結到崗位並做好交接。

### 5.2 單活 + 快速恢復（推薦）

```text
主例項 ──定時加密備份──► 獨立備份儲存
   │
   └─ 故障 ──► 新主機/新容器 ──恢復備份──► 切流量
```

建議目標：

| 指標 | 建議 |
| --- | --- |
| RPO | 按業務容忍度，至少每日一次；關鍵環境可縮短到小時級 |
| RTO | 以“準備主機 + 恢復備份 + 啟動驗證”估算，建議演練後寫入 Runbook |
| 備份保留 | 至少 7–30 天，關鍵環境按合規要求延長 |
| 演練頻率 | 每季度至少一次完整恢復演練 |

恢復步驟見[運維手冊](operations.md)。

### 5.3 容器與主機層高可用

可以用編排平臺保證**程序**重啟，但不能解決資料單寫問題：

- 副本數固定為 1。
- 使用持久卷，避免 Pod 重建後資料丟失。
- 健康檢查使用 TCP 埠或帶認證的 `/api/status`；不要用需要門禁 Cookie 的頁面做未認證探測。
- 節點故障時，由平臺重新排程單副本；資料卷必須能重新掛載。

### 5.4 多環境隔離

生產、預發、測試應使用獨立例項：

- 獨立 `config.yaml`、獨立 `security.salt`、獨立資料目錄。
- 獨立 DNS 子帳號和部署憑據，避免測試任務影響生產。
- 獨立通知頻道，避免測試告警進入生產值班群。
- 不要把生產資料庫複製到測試環境後繼續使用同一套憑據；如必須複製，先輪換憑據。

## 6. 監控與可觀測性

LACTSSL 不提供 Prometheus 指標端點，但可以透過以下訊號建立監控：

| 訊號 | 方式 | 建議 |
| --- | --- | --- |
| 程序存活 | TCP 埠探測 | 30–60 秒一次 |
| 深度健康 | `GET /api/status`，使用具備 `system:read` 的 API 金鑰 | 1–5 分鐘一次，檢查 200 與回應時間 |
| 任務失敗 | 操作日誌篩選或通知渠道 | 任務失敗/部署失敗即時告警 |
| 證書臨期 | 儀表盤、站點監控、任務續期狀態 | 到期前 30/14/7 天分級提醒 |
| 日誌異常 | 系統日誌關鍵字、反向代理 5xx | 接入企業日誌平臺 |
| 磁碟/備份 | 主機或平臺監控 | 磁碟 < 20% 告警，備份失敗告警 |

`/api/status` 需要認證，不能直接作為匿名健康檢查；匿名探測只能判斷埠是否可連。

## 7. TLS 與證書邊界

- 管理控制台的 TLS 由反向代理提供；LACTSSL 主埠不直接配置 TLS。
- 反向代理應使用企業 CA 或公共 CA 簽發的證書，並配置 HSTS、TLS 1.2+、禁用弱套件。
- ACME 獨立監聽可以直接提供 TLS（`acme.tls.cert/key`），也可以由反向代理終止；啟用 mTLS 時必須同時配置 ACME TLS 證書和私鑰。
- LACTSSL 管理的證書私鑰儲存在資料庫中，使用 `security.salt` 派生的金鑰加密；不提供 HSM/KMS 託管。
- 備份包內的資料庫與配置包含加密憑據和金鑰材料，按機密檔案管理。

## 8. 架構決策清單

在方案評審時建議明確以下決策：

| 決策 | 選項 | 建議 |
| --- | --- | --- |
| 部署方式 | Docker / 二進位制 / 編排平臺 | 有容器平臺時優先映象；否則二進位制 + systemd |
| TLS 終止 | 反向代理 / ACME 獨立監聽 | 管理面統一走反向代理 |
| 資料儲存 | 本地盤 / 持久卷 / 網路盤 | 只用單寫掛載；網路盤需驗證 SQLite 鎖語義 |
| 可用性 | 單活 + 備份 / 平臺重啟 | 不用雙活；明確 RTO/RPO |
| 出站策略 | 全放行 / 網域白名單 / 代理 | 生產按目標白名單，必要時經企業代理 |
| 外掛來源 | 官方倉庫 / 內部映象 / 手動上傳 | 生產優先內部映象 + 簽名校驗 |
| 升級方式 | 映象標籤 / 二進位制替換 | 容器用映象，二進位制用釋出包並保留回滾 |
