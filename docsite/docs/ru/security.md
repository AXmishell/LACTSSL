# Базовая безопасность
Документ для разработчиков, развёртывающих и интегрирующих LACTSSL: модель безопасности, реализованные меры и чек-лист перед запуском.

## Модель безопасности и границы доверия
LACTSSL — «самостоятельно размещаемый одиночный экземпляр» со следующими границами:

```text
[недоверенная] Пользователи интернета/внешней сети
    │ HTTPS (TLS завершается на обратном прокси)
[граница] Обратный прокси / WAF / сетевой ACL
    │ HTTP (loopback или внутренняя сеть)
[доверенная] Процесс LACTSSL
    ├─ Сеанс администратора: эквивалентен полному контролю
    ├─ Ключ API: ограничен областью прав
    ├─ Закрытый ключ частного CA: хранится в зашифрованном виде в локальной базе данных
    └─ Подпроцесс плагина: работает под учётной записью службы, считается доверенным кодом
[внешняя] DNS API / CA / SMTP / цели развёртывания / каналы уведомлений
```

- **Сеанс администратора эквивалентен полному контролю**, включая команды развёртывания, экспорт ключей и восстановление копий.
- **Ключ API — машинная идентичность** для ограничения прав автоматизации, а не многопользовательский RBAC.
- **Плагины — доверенный код**, особенно цели развёртывания с доступом к закрытым ключам; цепочку поставок обеспечивает сторона развёртывания.
- **База данных и `config.yaml` одинаково чувствительны**: потеря `salt` делает зашифрованные данные непригодными, утечка может привести к расшифровке.

## Идентификация и управление доступом
### Административная учётная запись
- Одна учётная запись; многопользовательский режим и RBAC не поддерживаются.
- Пароль хранится как bcrypt-хеш, не менее 8 символов; в продакшене — случайный от 16 символов. TOTP и ключи доступа (WebAuthn/Passkey) поддерживаются.
- Включение TOTP и регистрация ключа требуют повторной аутентификации (пароль, при TOTP — код), чтобы украденный сеанс не привязал аутентификатор злоумышленника. Смена целей SMTP/уведомлений и тестовые отправки требуют только сеанса или API-scope.
- После повторной аутентификации конфиденциальные операции доступны 5 минут; смена пароля, email, TOTP и ключей доступа по-прежнему требует подтверждения.
- Ключи доступа работают только через HTTPS-домен или localhost; после входа по ключу TOTP повторно не запрашивается.
- Смена пароля повышает версию токена и удаляет сеансы, API-ключи и ключи доступа; сброс по почте также отключает TOTP и удаляет ключи — защитите почту восстановления.
- В продакшене используйте отдельный ключ для каждого сценария и пересматривайте права.

### Ключи API
- Ключ — 86-символьная строка Base64URL (64 байта энтропии) без префикса; сервер хранит только SHA-256.
- Права — «ресурс:действие»; `*` обозначает все возможности API. Чувствительные права: `certificates:key`, `private_cas:key`, `deploy:execute`, `deploy:command`, `plugins:write`, `settings:write`, `api_keys:write`, `monitors:internal`.
- Загрузка/восстановление копий, изменение точки входа и переключение базы — только сеанс браузера. Ключ не может выдать права выше своих или изменить более привилегированный ключ.
- Создавайте отдельный ключ на систему, задавайте срок, минимальные права и ротацию.

## Сеть и TLS
### Входящий трафик
- Консоль доступна только через HTTPS-обратный прокси; основная программа слушает HTTP.
- Порт бэкенда — только loopback или внутренняя сеть, не интернет.
- На прокси настройте белый список IP, VPN, нулевое доверие или WAF; HSTS, TLS 1.2+, отключение слабых шифров и лимит тела запроса.
- Прокси перезаписывает или корректно добавляет `X-Forwarded-For` и передаёт `X-Forwarded-Proto`; LACTSSL доверяет только точным IP или минимальным CIDR из `server.trusted_proxies`, в цепочке добавления — всем прокси.
- Без доверенных прокси все запросы выглядят как запросы прокси: ограничение частоты и `Secure` Cookie работают неверно.

### Исходящий трафик
- Исходящие запросы идут к DNS API, публичным ACME CA, SMTP, Gotify, Telegram, DingTalk, WeCom, Webhook, SSH/SFTP, FTP/FTPS, CDN, Baota, 1Panel, SafeLine и целям мониторинга.
- В продакшене разрешайте только необходимые домены/подсети; прокси задавайте через системные переменные окружения Go.
- Проверяйте источник Webhook развёртывания и уведомлений, чтобы не отправлять ключи и токены на недоверенные адреса.
- Для внутренних HTTPS-целей импортируйте CA через «Системные настройки → Цепочка доверия TLS», а не отключайте проверку; импортированные и частные CA объединяются в `SSL_CERT_FILE`.

### Защита от SSRF
- Для адресов назначения отклоняются облачные метаданные, link-local, зарезервированные, documentation и NAT64 (например, `169.254.169.254`, `100.100.100.200`, `fd00:ec2::254`, `0.0.0.0/8`, `240.0.0.0/4`).
- Loopback и частные сети разрешены для Gotify, собственных панелей и внутренних Webhook; при необходимости ограничьте их на сети.
- Мониторинг по умолчанию разрешает только публичные цели; для частных сетей и loopback ключу нужен `monitors:internal`, а при соединении выполняется повторная проверка по разрешённому IP против DNS rebinding.
- Webhook развёртывания передаёт закрытый ключ; для публичных целей обязателен HTTPS, для loopback, частных сетей, `.local`, `.internal` допускается HTTP.
- В журналах маскируются URL-путь и параметры сторонних запросов, чтобы токены ботов и SendKey не попадали в журналы и копии.

## Защищённая точка входа, сеансы и CSRF
### Защищённая точка входа
Страница управления доступна только через случайную точку входа:

```text
https://your-domain/<entry>/
```

- По умолчанию — 20 букв в обоих регистрах и цифр, хранится в базе. Страницы без точки входа возвращают `404`, включая голый `/`.
- API всегда по `/api` и защищён сеансом или ключом; старый `/<entry>/api` — совместимый псевдоним.
- После входа по точке входа выдаётся подписанный `HttpOnly` Cookie на 24 часа; сервер проверяет срок. Для зондирования действует ограничение частоты.
- Точку входа можно сменить в «Настройки → Защищённая точка входа» (8–32 символа); при инициализации адрес выводится в журнал, позже — нет. Забытую точку переопределяют через `security.entry` и перезапуск или смотрят в таблице `settings`.
- До инициализации журнал выводит одноразовый токен; создание администратора, изменение конфигурации, перезапуск инициализации и восстановление копии требуют `X-LACTSSL-SETUP-TOKEN`. После инициализации токен недействителен и генерируется заново после перезапуска.

> Точка входа — дополнительный уровень, но не замена HTTPS, надёжным паролям и сетевому контролю.

### Сеансы
- Сеанс хранится в `HttpOnly` Cookie с `SameSite=Lax`; изменяющие запросы защищены double-submit CSRF и проверкой Origin.
- Токен сеанса — компактный JWT, ID сеанса — 24 байта (192 бита), CSRF-токен — 32 символа.
- При первом доступе выдаётся `HttpOnly` Cookie устройства `lactssl_device` на 1 год (32 hex-символа).
- По HTTPS Cookie сеанса, CSRF и точки входа используют префикс `__Host-`, чтобы избежать перезаписи соседними поддоменами.
- По умолчанию сеансы сохраняются при перезапуске (`jwt_secret` фиксирован); при `security.session_persistence: false` они очищаются, а случайное значение запуска подмешивается в JWT. Смена пароля удаляет все сеансы, ключи API и доступа.

### CSRF и межсайтовая защита
- Изменяющие запросы (POST/PUT/DELETE) содержат `X-LACTSSL-CSRF`, совпадающий с Cookie `lactssl_csrf`; для старых сеансов Cookie выдаётся автоматически.
- Для входа, инициализации, забытого пароля и сброса дополнительно проверяются `Origin`/`Sec-Fetch-Site`.
- При `Authorization: Bearer` проверка CSRF не применяется.
- CSP nonce генерируется для каждого ответа; `script-src` не разрешает произвольные встроенные скрипты, встроенные стили разрешены для библиотеки компонентов.

## Сброс пароля и внешний адрес
```yaml
security:
  public_url: "https://ssl.example.com"
```

- Без `public_url` ссылка выводится из Host только для loopback и `localhost`; остальные запросы «Забыли пароль» отклоняются.
- Клиентский `X-Forwarded-Host` не считается доверенным.
- За прокси `public_url` обязателен, иначе злоумышленник подделает Host и направит ссылку сброса (с токеном и точкой входа) на свой домен.

## Защита учётных данных и данных
### Шифрование
- Учётные данные DNS/развёртывания, SMTP, токены уведомлений, ключи TOTP, закрытые ключи CA и сертификатов шифруются AES-256-GCM перед записью в базу.
- Данные старых версий в открытом виде мигрируются при запуске. Ключ берётся из `security.salt` в `config.yaml`.
- JWT подписывается `security.jwt_secret`; используется отдельный подключ, производный от `jwt_secret` и случайного значения запуска через HKDF.
- `security.jwt_secret` и `security.salt` при ручной настройке — не менее 32 символов; короткое значение отклоняется при запуске.
- В ответах API ключи маскируются; пустое значение при редактировании сохраняет прежнее.

### Файлы и резервные копии
- `config.yaml` — `0600`, `data/` — `0700`, владелец — пользователь службы.
- В `data/` находятся база, WAL, плагины, журналы и резервные копии обновлений.
- Пароль резервной копии — не короче 12 символов; пакет шифруется PBKDF2-HMAC-SHA256 (600 000 итераций) + AES-256-GCM и содержит базу, конфигурацию и версию.
- Пакет восстановления проходит проверку конфигурации (ключи, точка входа, адрес, TLS/mTLS); недопустимая конфигурация отклоняется.
- После инициализации неприменённые пакеты восстановления очищаются, чтобы старое содержимое не перезаписало новую учётную запись.

### Ротация учётных данных
- Для DNS/развёртывания/уведомлений используйте выделенные учётные записи и регулярную ротацию.
- SSH по умолчанию требует отпечаток хоста; TOFU — только при явном включении, при несовпадении подключение отклоняется.
- FTP по умолчанию использует явный TLS; открытый FTP — только при явном `none`. API-ключи имеют срок, отдельны для каждой системы и немедленно ротируются при утечке.

## Аудит и журналирование
| Журнал | Содержимое | Хранение/экспорт |
| --- | --- | --- |
| Журнал операций | Задачи, сертификаты, развёртывание, уведомления, мониторинг, изменения настроек | Фильтрация и экспорт последних 90 дней в CSV/JSON; перед удалением создаётся архив |
| Системный журнал | Запуск, HTTP, планирование, плагины, ACME | По умолчанию 7 дней/20 000 строк; перед удалением создаётся архив |
| Архивы журналов | Исходный NDJSON и манифест | `data/archives/logs/`, по умолчанию бессрочно; скачивание и удаление |
| Журнал процесса | stdout или `log.file` | Ротация по размеру/дням, возможен JSON |
| Журнал обратного прокси | Доступ, исходный IP, коды состояния | Внешняя система журналирования |

- Экспортируйте журналы и архивы в SIEM: администратор с доступом к данным может удалить или изменить архив, это не неизменяемый аудит. Для защиты от изменений используйте WORM-хранилище.
- Журнал операций и системный журнал используют таблицу `logs` и разделены по `category`; очистка системного не удаляет операции.
- Каждый ответ содержит `X-Request-ID`; журнал доступа не пишет параметры, тело и заголовки аутентификации, а точка входа заменяется на `:entry`. Права архивов — `0600`, каталога — `0700`.

## Безопасность плагинов и цепочки поставок
- Официальные реализации встроены в программу и поставляются с её подписью/дайджестом; репозитория плагинов больше нет.
- Загружаемые helper проверяются по `manifest`, ID, версии, платформе, `min_host` и SHA-256; сбой приводит к откату. Дайджест повторно проверяется при обнаружении, регистрации и перед каждым вызовом.
- Для релизов программы проверяется подпись Ed25519 (`upgrade.program.public_key`); сборки без ключа отклоняют онлайн-обновление, `allow_unsigned` — только в контролируемой среде.
- Без ключа подписи показывается предупреждение, автоматическое обновление без оператора пропускается.
- Каталог плагинов — `0700`, helper — `0755`; запись для группы/других и символические ссылки запрещены.
- Цели развёртывания получают закрытые ключи и по умолчанию включены; включайте только доверенные источники и отключайте ненужные цели; программа ограничивает тайм-аут, память и вывод helper, маскирует учётные данные в ошибках.

Для продакшена: используйте внутреннее зеркало (HTTPS или `file://`), фиксируйте версии, отключайте автообновление, ведите перечень с источником, версией, дайджестом, проверившим и версией отката, проверяйте обновления на предпродакшене.

## Безопасность сервера ACME
- ACME включён по умолчанию, но до создания и включения конечной точки не выпускает сертификаты; при ненужности задайте `acme.enabled: false`.
- После включения это отдельный протокольный вход без Cookie сеанса и CSRF; при публичном развёртывании используйте отдельный порт и ограничение на firewall/прокси.
- Для каждой конечной точки нужен белый список доменов; пустой список отклоняется. EAB по умолчанию рекомендуется: без него любой, кто достучится до порта, создаст учётную запись. mTLS не заменяет аутентификацию JWS.
- `acme.base_url` — фиксированный публичный адрес, чтобы внедрение Host не перенаправило URL ресурсов; без него URL выводится из Host, что недопустимо для публичного развёртывания.
- HTTP-01 по умолчанию отклоняет loopback, частные сети, link-local, CGNAT и зарезервированные диапазоны (например, `100.64.0.0/10`, `192.0.0.0/24`); для внутренних сценариев разрешите их белым списком CIDR.
- Ресурсы ACME используют случайные публичные ID, а не автоинкремент базы; nonce хранится в памяти, после перезапуска клиент получает `badNonce` и повторяет запрос.
- CRL/OCSP (`/pki/{ca}/...`) ограничены по IP, кешируют результат и увеличивают CRL Number при изменении отзыва; они должны оставаться доступными после отключения регистрации ACME.
- Статус отзыва хранится в таблице `revocations` и не стирается очисткой сертификатов. Перед выпуском проверяются `ExtKeyUsage` CA (`serverAuth`/`any`) и NameConstraints; задача и ACME finalize используют одну проверку.

## Усиление развёртывания и контейнеров
- Запускайте службу под отдельным пользователем; `config.yaml` — `0600`, `data/` — `0700`.
- Образ Docker после исправления прав запускает программу под `lactssl`; Compose отбрасывает capabilities, включает read-only rootfs, tmpfs для `/tmp`, `pids_limit` и `init`.
- Не добавляйте `data/` и `config.yaml` в систему контроля версий и не размещайте в общедоступном каталоге.
- Ограничивайте тело запроса (2 MiB, кроме копий и плагинов) и тайм-ауты; на прокси также настройте лимиты. Фиксируйте версии, сканируйте образы и следите за бюллетенями; для портов 80/443 используйте прокси, а не capabilities.

## Известные ограничения
- Многопользовательский режим и RBAC не предоставляются; сеанс администратора — единственная точка отказа.
- SSO, LDAP, OIDC, SAML и SCIM не предоставляются.
- HSM/KMS не предоставляются; закрытые ключи хранятся зашифрованными в локальной базе.
- Кластер «активный-активный» не предоставляется; SQLite работает с одной записью, общий каталог данных невозможен.
- Неизменяемый аудит не предоставляется; при необходимости защиты от изменений используйте внешнее WORM-хранилище.
- Метрики Prometheus не предоставляются; мониторинг — журналы, API и внешние проверки. Автоматический откат на цели также не предоставляется.

## Чек-лист проверки безопасности перед вводом в эксплуатацию
### Идентификация
- [ ] Надёжный пароль, TOTP или ключ доступа; почта восстановления защищена MFA.
- [ ] Неизвестные сеансы очищены; API-ключи отдельны для каждой системы, с минимальными правами и сроком.

### Сеть
- [ ] Точка входа только по HTTPS, порт бэкенда не опубликован; настроены `trusted_proxies` и `public_url`.
- [ ] Прокси передаёт `X-Forwarded-For`/`X-Forwarded-Proto`; настроены ограничения источников, WAF или нулевое доверие.
- [ ] Исходящие подключения ограничены белым списком, при необходимости — прокси.

### Данные
- [ ] `config.yaml` — 0600, `data/` — 0700, владелец верный.
- [ ] Зашифрованная копия создана и хранится в другом месте; пароль — отдельно; проведены учения.
- [ ] Хранение и экспорт журналов удовлетворяют требованиям аудита.

### Плагины и ACME
- [ ] Используются доверенные источники/зеркало, проверяются подпись и дайджест; автообновление отключено.
- [ ] Цели развёртывания включены по необходимости, источник проверен.
- [ ] Для ACME настроен белый список доменов и EAB; вход ограничен по источнику, при необходимости включён mTLS.

## Реагирование на инциденты безопасности
1. **Определите масштаб**: учётная запись, API-ключ, учётные данные DNS/развёртывания, плагин или хост.
2. **Изолируйте**: отзовите сеансы и ключи, отключите плагины и конечные точки ACME, при необходимости — сетевой доступ.
3. **Соберите доказательства**: экспортируйте журналы операций, системный и прокси, запишите `X-Request-ID`; не очищайте журналы заранее.
4. **Выполните ротацию**: смена пароля удаляет сеансы и ключи; ротируйте учётные данные DNS/развёртывания/уведомлений; при утечке `salt` действуйте по процедуре утечки ключей.
5. **Восстановите**: используйте доверенную копию, проверьте согласованность конфигурации и данных, перевыпустите затронутые сертификаты.
6. **Проведите разбор**: обновите Runbook, список прав и правила мониторинга.

Шаги диагностики — в [Мониторинге и устранении неполадок](troubleshooting.md), восстановление — в [Руководстве по эксплуатации](operations.md).
