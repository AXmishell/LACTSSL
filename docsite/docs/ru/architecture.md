# Архитектура развёртывания
Статья для разработчиков, развёртывающих и сопровождающих LACTSSL: единицы развёртывания, сетевые границы, ёмкость и доступность. **По умолчанию — один экземпляр, SQLite с одной записью**; можно явно выбрать PostgreSQL 18 и переключаться между бэкендами через `/upgrade`. Совместное использование PostgreSQL несколькими экземплярами отклоняется; HA не входит во встроенные возможности.

## Единицы развёртывания
LACTSSL — самодостаточный бинарный файл Go:

- Фронтенд встроен в бинарник, отдельный веб-сервер или Node не нужны.
- Данные хранятся в локальном SQLite, без внешней БД, кеша и очереди.
- Официальные реализации DNS, развёртывания и уведомлений встроены в хост; сторонние helper запускаются как одноразовые дочерние процессы и размещаются в каталоге данных.
- Во время работы есть только два входных источника: `config.yaml` и каталог `data/`.
```text
/opt/lactssl/
├── lactssl                 # бинарный файл
├── config.yaml             # конфигурация и ключи, 0600
└── data/                   # 0700
    ├── lactssl.db          # основная база SQLite
    ├── lactssl.db-wal      # WAL (во время работы)
    ├── lactssl.db-shm      # разделяемая память (во время работы)
    ├── plugins/            # загруженные helper (dns / deploy / notify)
    ├── plugin-icons/       # кеш иконок плагинов
    ├── upgrade-backups/    # резервные копии миграций и обновлений программы
    └── restore-pending/    # пакеты восстановления, ожидающие применения
```
Граница резервного копирования — `config.yaml` + `data/`. Копия только базы данных приведёт к потере `salt`, и зашифрованные учётные данные нельзя будет расшифровать.

## Эталонная топология
### Один хост + обратный прокси (рекомендуемая отправная точка)
```text
Интернет / внутренняя сеть
        │ HTTPS 443
┌───────▼────────────────┐
│ Nginx / Caddy          │  завершение TLS, ограничение источников, журнал доступа
│ / WAF / балансировщик  │
└───────┬────────────────┘
        │ HTTP 127.0.0.1:8080
┌───────▼────────────────────────────────────────────┐
│ LACTSSL                                            │
│  ├─ Консоль управления / API                       │
│  ├─ Планировщик (проверка задач каждые 30 секунд)  │
│  ├─ Частный CA / служба ACME (опционально)         │
│  └─ SQLite + локальные плагины                     │
└───┬─────────────────┬───────────────┬──────────────┘
    │                 │               │
API DNS      цель развёртывания    уведомления/почта
```
Применение: большинство развёртываний в одной среде, от десятков до тысяч сертификатов.

Ключевые моменты:

- Основная программа не предоставляет TLS для порта управления; в продакшене TLS завершается на обратном прокси, а порт бэкенда слушает только loopback или внутреннюю сеть.
- Прокси должен перезаписывать или корректно добавлять `X-Forwarded-For` и передавать `X-Forwarded-Proto`; в `server.trusted_proxies` регистрируется точный IP или минимальный CIDR, в цепочке добавления — все прокси.
- `security.public_url` задаётся фиксированным внешним адресом, чтобы ссылки сброса пароля не зависели от Host запроса.

### Прокси в DMZ + внутреннее приложение
```text
Пользователь ──HTTPS──► обратный прокси в DMZ ──HTTP внутренней сети──► LACTSSL (сегмент приложений)
                                                                            │
                                                                            ├─► DNS API / публичный CA (исходящий 443)
                                                                            ├─► SSH / панель / CDN (в зависимости от цели)
                                                                            └─► SMTP / Webhook (в зависимости от канала)
```
Применение: повышенные требования безопасности, плоскость управления не открыта напрямую во внутреннем сегменте.

Ключевые моменты:

- На брандмауэре разрешается только порт управления от прокси к LACTSSL.
- Исходящий доступ настраивается по белому списку целей; если белый список доменов невозможен, ограничьте целевые порты и подсети.
- Для сервера ACME в DMZ используйте отдельный порт и не переиспользуйте порт управления.

### Внутренний PKI / служба ACME
```text
Внутренние службы / certbot / lego / acme.sh
        │ ACME v2 (HTTPS или mTLS)
┌───────▼──────────────────────────────────┐
│ Конечная точка ACME LACTSSL              │  отдельный порт :14000
│ привязка к частному CA                   │  белый список доменов / EAB / типы проверок
└───────┬──────────────────────────────────┘
        │
   иерархия частного CA
```
Применение: сертификаты внутренних служб, устройств и тестовых сред.

Ключевые моменты:

- Без созданной и включённой конечной точки сертификаты не выдаются; для каждой конечной точки нужен белый список доменов.
- Для публичной конечной точки включите EAB и ограничьте источники на сети; при повышенных требованиях используйте mTLS.
- `acme.base_url` — фиксированный адрес, по которому клиенты фактически обращаются. CRL/OCSP организуются по CA и остаются доступными после отключения конечной точки регистрации ACME.

### Контейнерная платформа
```text
Ingress / Service
        │
┌────────▼───────────┐
│ Pod: lactssl       │
│  /app/config       │  ── PVC или том конфигурации
│  /app/data         │  ── PVC
└────────────────────┘
```
Ключевые моменты:

- Контейнер всегда читает `/app/config/config.yaml` и `/app/data`; входной скрипт исправляет владельца каталогов, понижает права до `lactssl`, Compose использует read-only rootfs и отбрасывает capabilities.
- **Одна реплика**: несколько Pod не должны одновременно писать в один том SQLite.
- Самообновление внутри контейнера не меняет образ; обновляйтесь через тег образа. Используйте `restart: unless-stopped`, чтобы служба поднялась после восстановления копии.

## Порты и сетевые потоки
| Направление | Порт/протокол | Назначение | Рекомендация |
| --- | --- | --- | --- |
| Входящий | 443/TCP | Консоль управления и API (через обратный прокси) | Открывать только для контролируемых источников |
| Входящий | 8080/TCP | Основной прослушиватель LACTSSL (по умолчанию) | Только loopback/внутренняя сеть, доступ через прокси |
| Входящий | произвольный/TCP | Отдельный прослушиватель ACME (опционально) | Отдельный порт, ограничение источников |
| Исходящий | 443/TCP | DNS API, публичные ACME CA, уведомления, Webhook, панели, CDN | Белый список по доменам/подсетям |
| Исходящий | 22/TCP или произвольный | Развёртывание по SSH/SFTP | Только целевые хосты |
| Исходящий | 21/990/TCP | Развёртывание по FTP/FTPS | Предпочитать FTPS, ограничить цели |
| Исходящий | 25/465/587/TCP | Уведомления по SMTP | SMTP-сервис |
| Исходящий | произвольный | Gotify, внутренний Webhook, цели мониторинга | По необходимости, с учётом границ SSRF |

Пояснения:

- Сервер проверяет исходящие цели на SSRF и отклоняет адреса облачных метаданных, link-local и зарезервированные подсети; loopback и частные сети разрешены для внутренних интеграций.
- Webhook развёртывания передаёт закрытый ключ; для публичных целей принудительно используется HTTPS, для loopback, частных сетей, `.local` и `.internal` разрешён HTTP. При завершении TLS на прокси передавайте `X-Forwarded-Proto`, иначе `Secure` Cookie и ограничение частоты работают неверно.

## Планирование ёмкости
Значения ниже — **справочные отправные точки**, а не гарантии по ёмкости. Ёмкость зависит от числа сертификатов, частоты задач, журналов, типов плагинов и резервного копирования; перед продакшеном проведите нагрузочное тестирование.

| Масштаб | Объём сертификатов/задач | Рекомендуемая конфигурация | Пояснение |
| --- | --- | --- | --- |
| Пилот/малый | < 100 сертификатов, немного задач | 2 vCPU / 1 GB / 10 GB | Избегайте одновременного включения больших наборов плагинов |
| Средний | 100–1 000, ежедневное продление | 2–4 vCPU / 2 GB / 20 GB | Включите ротацию журналов и периодическую очистку |
| Крупный | 1 000–5 000, частое развёртывание | 4–8 vCPU / 4 GB / 50 GB+ | Следите за записью SQLite, окнами копирования и пиками плагинов |

Память: простой основного процесса — несколько десятков MB; helper ограничен `memory_limit_mb` (по умолчанию 128 MB). Загрузка helper и несколько одновременных задач вызывают пики — оставляйте запас. Хранилище: база растёт из-за сертификатов, журналов задач, журнала операций, системного журнала и заказов ACME. Журналы используют таблицу `logs` и различаются по `category`; очистка системного журнала не влияет на журнал операций. Для системного журнала есть `retention_days` и `max_rows`; `data/upgrade-backups/` хранит последние 5 снимков миграции, при обновлении сохраняются 3 старых бинарных файла. Не записывайте резервные копии в каталог данных; резервируйте место с запасом в несколько раз больше базы.

## Доступность и аварийное восстановление
### Границы доступности текущей версии
- **Кластер/«активный-активный» не поддерживается**. SQLite с одной записью; одновременное монтирование каталога данных несколькими экземплярами приводит к конкуренции блокировок или повреждению данных.
- **Автоматическое переключение при сбое не предоставляется**. Прокси может проверять живучесть, но не должен переключать трафик на экземпляр, записывающий те же данные.
- **Одна учётная запись администратора** — единая точка: при потере нужны восстановление из копии или сброс пароля; закрепите обязанности за должностью и обеспечьте передачу.

### Один активный экземпляр + быстрое восстановление (рекомендуется)
```text
Основной экземпляр ──периодическая зашифрованная резервная копия──► отдельное хранилище резервных копий
   │
   └─ сбой ──► новый хост/новый контейнер ──восстановление резервной копии──► переключение трафика
```
| Показатель | Рекомендация |
| --- | --- |
| RPO | По допустимому времени простоя, минимум раз в день; для критичных сред — до часового уровня |
| RTO | «Подготовка хоста + восстановление копии + проверка запуска»; результат учений внесите в Runbook |
| Хранение резервных копий | Не менее 7–30 дней, для критичных сред — при необходимости дольше |
| Частота учений | Не менее одного полного учения по восстановлению в квартал |

Шаги восстановления — в [Руководстве по эксплуатации](operations.md).

### Высокая доступность на уровне контейнеров и хостов
Платформа оркестрации перезапускает **процесс**, но не решает проблему одной записи данных:

- Количество реплик — 1; используйте постоянные тома, чтобы не потерять данные после пересоздания Pod.
- Для проверки работоспособности используйте TCP-порт или `/api/status` с аутентификацией; не используйте страницу с Cookie защищённой точки входа.
- При сбое узла платформа перепланирует единственную реплику; том данных должен допускать повторное монтирование.

### Изоляция нескольких сред
Продакшен, предпродакшен и тестовая среда используют отдельные экземпляры:

- Отдельные `config.yaml`, `security.salt` и каталог данных.
- Отдельные субучётные записи DNS, учётные данные развёртывания и каналы уведомлений, чтобы тестовые задачи и оповещения не влияли на продакшен.
- Не копируйте продакшен-базу в тест и не переиспользуйте учётные данные; при копировании сначала смените их.

## Мониторинг и наблюдаемость
LACTSSL не предоставляет метрики Prometheus, но мониторинг строится по сигналам:

| Сигнал | Способ | Рекомендация |
| --- | --- | --- |
| Живучесть процесса | Проверка TCP-порта | Раз в 30–60 секунд |
| Глубокая проверка | `GET /api/status` с ключом `system:read` | Раз в 1–5 минут, проверять код 200 и время ответа |
| Сбой задачи | Журнал операций или канал уведомлений | Немедленное оповещение о сбое задачи/развёртывания |
| Срок сертификата | Панель, мониторинг сайтов, статус продления | Напоминания за 30/14/7 дней |
| Аномалии журналов | Системный журнал, 5xx обратного прокси | Подключение к внешней системе журналирования |
| Диск и копии | Мониторинг хоста или платформы | Оповещение при заполнении < 20% и сбое копирования |

`/api/status` требует аутентификации; анонимная проверка определяет только доступность порта.

## Границы TLS и сертификатов
- TLS консоли обеспечивается обратным прокси (сертификат внутреннего или публичного CA, HSTS, TLS 1.2+, отключение слабых шифров); основной порт LACTSSL не настраивает TLS напрямую.
- Отдельный прослушиватель ACME может предоставлять TLS (`acme.tls.cert/key`) или завершаться прокси; при mTLS настройте сертификат и ключ TLS ACME.
- Закрытые ключи сертификатов хранятся в базе данных и шифруются ключом от `security.salt`; HSM/KMS не поддерживается.
- База и конфигурация в резервной копии содержат зашифрованные учётные данные и ключи — обращайтесь с ними как с конфиденциальными файлами.

## Контрольный список архитектурных решений
| Решение | Варианты | Рекомендация |
| --- | --- | --- |
| Способ развёртывания | Docker / бинарный файл / оркестрация | При наличии контейнерной платформы — образ; иначе бинарный файл + systemd |
| Завершение TLS | Обратный прокси / прослушиватель ACME | Плоскость управления — единообразно через прокси |
| Хранение данных | Локальный диск / постоянный том / сетевой диск | Только монтирование с одной записью; для сетевого диска проверьте блокировки SQLite |
| Доступность | Один активный + копии / перезапуск платформой | Не использовать «активный-активный»; определить RTO/RPO |
| Исходящая политика | Полный доступ / белый список / прокси | В продакшене белый список целей, при необходимости прокси |
| Плагины и обновление | Встроенные реализации / сторонние helper; тег образа / замена бинарного файла | Официальные встроены, сторонние helper — из доверенного источника; в контейнерах обновляйте образ, для бинарного файла используйте пакет релиза с откатом |
