# Справочник по конфигурации

Конфигурация приложения LACTSSL берётся только из `config.yaml` и встроенных значений по умолчанию; переменные окружения уровня приложения не читаются. После изменения конфигурации для вступления в силу требуется перезапуск сервиса; некоторые параметры времени выполнения (защищённая точка входа, репозиторий плагинов, состояние включения плагинов) хранятся в базе данных и имеют приоритет над файлом конфигурации.

## 1. Модель файла конфигурации

По умолчанию читается `config.yaml` в текущем рабочем каталоге; при запуске можно указать другой путь с помощью `-config`.

- Если файл не существует, при первом запуске он создаётся автоматически, и в него записываются случайно сгенерированные `jwt_secret` и `salt`.
- Содержит ключи, поэтому рекомендуется сохранять права `0600`.
- Конфигурация приложения берётся только из `config.yaml` и встроенных значений по умолчанию; поведение HTTP-клиента Go, например системный прокси, по-прежнему можно настроить через переменные окружения.
- Изменения конфигурации вступают в силу после перезапуска; защищённую точку входа можно изменить в интерфейсе, и это вступит в силу немедленно.
- Полный пример с комментариями находится в корне репозитория: [`config.yaml.example`](https://github.com/AXmishell/LACTSSL/blob/main/config.yaml.example).

### 1.1 Минимальная продуктивная конфигурация

```yaml
server:
  host: "127.0.0.1"
  port: 8080
  trusted_proxies: ["127.0.0.1"]

data_dir: "data"

security:
  public_url: "https://ssl.example.com"
  session_persistence: true

log:
  level: info
  format: json
  file: "data/logs/lactssl.log"
  also_stdout: true
  max_size_mb: 50
  max_backups: 10
  max_age_days: 30
  compress: true
  access_log: true
  system:
    enabled: true
    level: info
    access: false
    retention_days: 30
    max_rows: 200000
  archive:
    enabled: true
    compress: true
    retention_days: 0
    max_total_mb: 0
    quota_policy: fail
```

### 1.2 Приоритет конфигурации

| Конфигурация | Источник | Описание |
| --- | --- | --- |
| Адрес прослушивания, журналы, ключи, ACME | `config.yaml` | Вступает в силу после перезапуска |
| Защищённая точка входа | База данных, `config.yaml` может переопределить | Изменение в интерфейсе вступает в силу сразу; при непустом `security.entry` значение переопределяется при запуске |
| Адрес/канал/автообновление/открытый ключ репозитория плагинов | Приоритет у базы данных, `config.yaml` задаёт значения по умолчанию | Сохранение на странице плагинов не записывается обратно в файл конфигурации |
| Состояние включения плагинов | Белый список в базе данных | Сохраняется после перезапуска и повторного сканирования |
| Язык системы, каналы уведомлений и т. п. | База данных | Изменяются в интерфейсе |

### 1.3 Редактирование файла конфигурации через веб-интерфейс

После входа в «Системные настройки → Файл конфигурации» можно изменить поля белого списка `config.yaml`, включая адрес прослушивания, доверенные обратные прокси, `security.public_url`, сохранение сеансов, пороги ограничения скорости, ACME, журналы, обновление и параметры работы плагинов.

- Вкладка ограничения скорости показывает действующие правила после объединения со встроенными значениями по умолчанию; при сохранении они записываются в `config.yaml` и вступают в силу после перезапуска.
- Высокорисковые поля, такие как `jwt_secret`, `salt`, `data_dir`, `database.path`, файлы журналов, каталоги плагинов и корни доверия репозиториев, по-прежнему можно редактировать только на сервере.
- Перед сохранением автоматически создаётся снимок конфигурации в `<data_dir>/config-backups/`; снимок можно создать и вручную. Снимок содержит только `config.yaml` и отличается от зашифрованной полной резервной копии, включающей базу данных.
- Восстановление снимка записывает обратно только поля белого списка; текущие `jwt_secret`, `salt`, `data_dir`, `database.path` остаются без изменений, чтобы не нарушить расшифровку базы данных.
- После сохранения для вступления в силу требуется перезапуск сервиса. При изменении порта прослушивания сначала выполняется предварительная проверка порта; если новый адрес недоступен, сервис может не восстановиться автоматически, поэтому сохраните доступ по SSH или через консоль.
- «Доверенные обратные прокси» поддерживают автоматическое определение: определение использует только TCP-адрес текущего запроса, а заголовки пересылки, такие как `X-Forwarded-For`, только отображаются и не добавляются автоматически в список доверенных. Результат различает сохранённый и действующий списки, показывает источник IP клиента, пропущенные доверенные элементы и предупреждения разбора заголовков. В сценарии с обратным прокси рекомендуется также настроить `security.public_url`.

## 2. Полный пример полей

```yaml

  addr: ""              # полный адрес прослушивания, например ":8080"; если не пуст, имеет приоритет над host + port
  host: ""              # сетевой интерфейс; пусто — все интерфейсы
  port: 8080            # порт прослушивания
  trusted_proxies: []   # CIDR доверенных обратных прокси

data_dir: "data"        # каталог данных для плагинов, журналов и резервных копий обновлений

database:
  driver: "sqlite"      # sqlite (по умолчанию) или postgres
  path: ""              # путь SQLite; пусто — <data_dir>/lactssl.db
  dsn: ""               # DSN PostgreSQL; обязателен при driver=postgres
  max_open_conns: 10    # пул соединений PostgreSQL
  max_idle_conns: 5
  conn_max_lifetime_minutes: 30
  allow_multi_instance: false  # разрешать нескольким экземплярам совместно использовать одну базу PostgreSQL

log:
  level: info           # уровень журнала процесса: debug, info, warn, error
  format: text          # формат вывода: text или json
  file: ""              # файл журнала; пусто — только stdout
  also_stdout: true     # выводить ли одновременно в stdout при записи в файл
  max_size_mb: 20       # максимальный размер файла; после превышения выполняется ротация
  max_backups: 5        # число сохраняемых исторических файлов; 0 — без ограничения
  max_age_days: 30      # срок хранения исторических файлов в днях; 0 — без ограничения
  compress: true        # сжимать ли исторические файлы
  access_log: true      # записывать ли журнал доступа HTTP
  system:
    enabled: true       # записывать ли в базу данных для просмотра на вкладке «Журнал → Системный журнал»
    level: info         # минимальный уровень для записи в базу данных
    access: false       # записывать ли журнал доступа HTTP также в базу данных
    retention_days: 7   # срок хранения в днях

  archive:

    max_total_mb: 0     # верхний предел объёма каталога архивов (MB); 0 — без ограничения
    quota_policy: fail  # fail или prune_oldest

security:
  entry: ""             # защищённая точка входа; пусто — случайная генерация при первом запуске
  public_url: ""        # внешний адрес, например "https://ssl.example.com"
  session_persistence: true  # при false сеанс входа очищается при перезапуске процесса
  jwt_secret: ""        # ключ подписи JWT; пусто — автоматическая генерация и запись; при ручной настройке не менее 32 символов
  salt: ""              # соль шифрования чувствительных полей; пусто — автоматическая генерация и запись; при ручной настройке не менее 32 символов
```

## 3. `server`

- `addr`: полный адрес прослушивания, например `:8080`, `127.0.0.1:8080`.
- `host`, `port`: если `addr` не задан, объединяются в адрес прослушивания. Этот порт напрямую обслуживает страницы и API бинарником Go; ресурсы фронтенда встроены в бинарник, и обратный прокси на Vite `5173` не используется; `5173` существует только при `make dev`.
- `trusted_proxies`: список IP/CIDR доверенных обратных прокси. Пустое значение означает, что заголовки прокси не считаются доверенными, что подходит для прямого развёртывания; при завершении TLS на обратном прокси список обязателен, иначе `Secure` Cookie и определение IP клиента будут работать некорректно.

Рекомендации для продуктивной среды:

- Задайте `host` равным `127.0.0.1` или адресу внутренней сети, доступ к которому осуществляется через обратный прокси.
- Включайте в `trusted_proxies` только фактические адреса прокси, не настраивайте `0.0.0.0/0`.
- Если прокси и LACTSSL находятся на разных хостах, используйте CIDR внутренней сети.

## 4. `data_dir` и бэкенд базы данных

`data_dir` используется для плагинов, журналов и резервных копий обновлений. По умолчанию база данных — SQLite, файл расположен в `<data_dir>/lactssl.db`; также можно явно использовать PostgreSQL 18:

```yaml
database:
  driver: "postgres"
  dsn: "postgres://user:password@127.0.0.1:5432/lactssl?sslmode=verify-full"
```

- При `driver=postgres` параметр `path` игнорируется, а `dsn` обязателен; его также можно переопределить переменной окружения `LACTSSL_DATABASE_DSN`, чтобы не записывать пароль в файл конфигурации.
- По умолчанию `allow_multi_instance: false`, приложение удерживает advisory lock PostgreSQL; второй экземпляр, подключающийся к той же базе данных, не сможет запуститься.
- SQLite по-прежнему использует одно соединение и подходит для небольшого развёртывания на одном узле; PostgreSQL выбирайте, когда требуются внешнее резервное копирование и централизованная эксплуатация.
- Для переключения бэкенда не нужно вручную изменять базу данных: после входа выполните переключение на карточке «Миграция базы данных» в `/upgrade`, подробнее см. в [upgrade.md](upgrade.md#7-переключение-базы-данных-онлайн-sqlite--postgresql).

Каталог данных используется для хранения базы данных, плагинов, журналов и резервных копий обновлений. Каталог создаётся с правами `0700`. Если `database.path` пуст, используется `<data_dir>/lactssl.db`.

- Не размещайте каталог данных на общем пути с правом записи или в общедоступном каталоге.
- Не размещайте базу данных на общем хранилище с множественной записью, таком как NFS/SMB; SQLite допускает только одну запись, и семантика блокировок нестабильна.
- Область резервного копирования — `config.yaml` + весь `data/`.

## 5. `log`

Журнал процесса нижнего уровня и журнал операций имеют разное назначение: журнал операций фиксирует, «кто, когда и что сделал», и отображается на вкладке «Журнал → Журнал операций»; журнал процесса служит для диагностики во время работы, может асинхронно записываться в базу данных и отображаться на вкладке «Журнал → Системный журнал», а также выводиться в stdout/файл.

- `level`: минимальный уровень вывода, поддерживаются `debug`, `info`, `warn`, `error`. `debug` добавляет расположение в исходном коде и подходит для временной диагностики.
- `format`: `text` подходит для прямого чтения и журналов Docker; `json` подходит для систем сбора журналов.
- `file`: путь к файлу журнала. Если пусто, вывод идёт только в stdout; относительный путь вычисляется от текущего рабочего каталога процесса сервиса. Если каталог не существует, он создаётся автоматически (`0700`), права на файл — `0600`.
- `also_stdout`: выводить ли также в stdout при записи в файл. При развёртывании в Docker рекомендуется оставить `true`.
- `max_size_mb`: максимальный размер одного файла; после достижения лимита выполняется ротация с меткой времени, поддерживается `1–1024`.
- `max_backups`: число сохраняемых исторических файлов, `0` — без ограничения; при превышении удаляется самый старый файл.
- `max_age_days`: срок хранения исторических файлов в днях, `0` — без ограничения.
- `compress`: сжимать ли ротированные исторические файлы в `.gz`.
- `access_log`: записывать ли журнал доступа HTTP. Журнал содержит только метод, шаблон маршрута, код состояния, длительность, IP клиента и т. п. и не записывает параметры запроса, тело запроса и заголовки аутентификации; защищённая точка входа в пути единообразно заменяется на `:entry`. Каждый ответ содержит `X-Request-ID`.
- `system.enabled`: записывать ли журнал в базу данных для просмотра на вкладке «Журнал → Системный журнал».
- `system.level`: минимальный уровень для записи в базу данных. Не может быть ниже `log.level`, иначе журналы низкого уровня не будут создаваться.
- `system.access`: записывать ли журнал доступа HTTP также в базу данных. По умолчанию `false`, чтобы не писать в SQLite при каждом запросе.
- `system.retention_days`: срок хранения в днях, диапазон `1–365`.
- `system.max_rows`: максимальное число строк, диапазон `100–1000000`; при превышении удаляются самые старые записи.
- `archive.enabled`: записывать ли журналы в архив перед удалением/очисткой журналов базы данных. По умолчанию включено; сбой архивирования блокирует удаление и не приводит к молчаливой потере журналов.
- `archive.dir`: корневой каталог архивов; пусто — `<data_dir>/archives/logs`. Каталог создаётся с правами `0700`, права на файлы — `0600`.
- `archive.compress`: сжимать ли gzip; при отключении файлы сохраняются как `.ndjson`.
- `archive.retention_days`: срок хранения архивных файлов в днях, диапазон `0–3650`; по умолчанию `0` означает бессрочное хранение.
- `archive.max_total_mb`: верхний предел объёма каталога архивов (MB), `0` — без ограничения. Политика при превышении определяется `quota_policy`.
- `archive.quota_policy`: `fail` (по умолчанию — прекратить архивирование и заблокировать удаление) или `prune_oldest` (удалить самые старые архивы). `prune_oldest` уничтожает материалы аудита и должен настраиваться явно.

Архивные файлы состоят из `*.ndjson.gz` (или `.ndjson`) и `*.manifest.json`; манифест содержит число строк, диапазон ID, временной диапазон, причину срабатывания, оператора, SHA-256 и размер файла. Каталог архивов не входит в стандартную ZIP-резервную копию и требует отдельного резервного копирования.

Запись выполняется через ограниченную асинхронную очередь и не блокирует бизнес-запросы при занятости базы данных; при заполнении очереди новые журналы отбрасываются. Системный журнал может содержать IP клиентов, домены и подробности ошибок; обращайтесь с ним как с эксплуатационными данными.

Рекомендации для продуктивной среды: размещайте файлы журналов на отдельном диске или смонтированном томе; подключайте `format: json` к платформе журналирования; используйте `access_log: true` для удобства аудита; оставляйте `system.access` равным `false`, если не требуется краткосрочная диагностика.

## 6. `security`

- `entry`: сегмент пути защищённой точки входа страницы управления; при ручной настройке требуется 8–32 символа: буквы, цифры, подчёркивание или дефис. Если пусто, при первом запуске случайно генерируется комбинация из 20 букв в обоих регистрах и цифр, которая сохраняется в базе данных.
- `public_url`: внешний адрес, например `https://ssl.example.com` (без пути). Ссылка в письме для сброса пароля формируется на основе этого адреса, что предотвращает внедрение заголовка Host; если он не настроен, вывод из Host разрешён только для запросов с локального loopback-адреса и Host `localhost`/loopback IP.
- `session_persistence`: сохранение сеансов, по умолчанию `true`. При `true` сервис при запуске больше не очищает таблицу `sessions`, а JWT подписывается фиксированным `jwt_secret`, поэтому после перезапуска фонового процесса браузер может продолжить использовать прежний сеанс входа; при `false` каждый запуск принудительно делает все старые входы недействительными.
- `jwt_secret`: ключ подписи токена входа. Если пусто, автоматически генерируется 32-байтовое случайное значение и записывается обратно в файл конфигурации; при ручной настройке требуется не менее 32 символов, иначе запуск отклоняется.
- `salt`: соль шифрования чувствительных полей базы данных (учётные данные DNS/развёртывания, ключи уведомлений, закрытые ключи частного CA и сертификатов и т. п.). Если пусто, генерируется автоматически и записывается обратно; при ручной настройке требуется не менее 32 символов, иначе запуск отклоняется.
- `rate_limit.max_keys`: максимальное число ключей, сохраняемых в ограничителе скорости в памяти, по умолчанию `10000`. Каждый IP клиента, учётная запись или операция занимает один ключ; при превышении вытесняются давно не использовавшиеся.
- `rate_limit.rules`: переопределение порогов ограничения скорости по имени правила; каждый элемент содержит `max` (число попыток, разрешённых в окне) и `window_seconds` (длительность окна в секундах). Для ненастроенных правил используются встроенные значения по умолчанию; при отсутствии `window_seconds` используется окно по умолчанию; `max: 0` отключает правило. Неизвестное имя правила приводит к сбою запуска, что помогает обнаружить опечатки.

Распространённые правила и значения по умолчанию:

| Правило | Значение по умолчанию | Описание |
| --- | --- | --- |
| `login_ip` / `login_account` / `login_totp` | 10 за 5 минут, 20 за 15 минут, 5 за 10 минут | Вход по IP, сбои учётной записи и проверка TOTP |
| `forgot_ip` / `forgot_account` | 5 за 10 минут, 3 в час | Забытый пароль |
| `passkey_login_begin` / `passkey_login_fail` | 20 за 5 минут, 10 за 5 минут | Вход по ключу доступа |
| `reauth` | 10 за 10 минут | Сбой повторной аутентификации для чувствительных операций |
| `api_ip` / `api_anonymous` / `entry` | 600 в минуту, 120 в минуту, 60 в минуту | Общий объём `/api`, анонимные запросы и зондирование точки входа |
| `csr_create` | 120 в час | Отправка CSR клиентом ACME |
| `acme_request` / `acme_account` / `acme_pki` | 1200 в минуту, 30 в час, 600 в минуту | Протокольный вход ACME, создание учётной записи, CRL/OCSP |
| `acme_order` | 300 в час | Лимит заказов, если он не задан отдельно для конечной точки ACME |

> Изменения порогов ограничения скорости вступают в силу после перезапуска сервиса. «Число заказов в час» самой конечной точки ACME настраивается в интерфейсе управления и имеет приоритет над `acme_order`.

> **Обязательно создавайте резервную копию `config.yaml`.** После потери `salt` зашифрованные учётные данные в базе данных невозможно расшифровать; потеря или замена `jwt_secret` сделает существующие сеансы входа недействительными. По умолчанию сохранение сеансов включено, поэтому перезапуск не очищает серверные сеансы. Установка `security.session_persistence: false` возвращает строгий режим: при каждом запуске сеансы очищаются и подключ подписи JWT ротируется.

Рекомендации по безопасности:

- Поддерживайте `entry` случайной длинной строкой, не используйте предсказуемые значения, такие как `admin`, `ssl`, `panel`.
- `public_url` должен быть фиксированным HTTPS-адресом, нельзя полагаться на заголовок Host запроса.
- Выбирайте `session_persistence` в соответствии с политикой сеансов предприятия; по умолчанию он включён, поэтому перезапуск процесса не требует повторного входа, но необходимо принять более длительный жизненный цикл сеанса.
- `jwt_secret` и `salt` генерируйте и храните в менеджере паролей или системе управления конфигурацией, не добавляйте их в систему контроля версий.
- Замена `salt` сделает существующие зашифрованные учётные данные непригодными, поэтому необходим план миграции; прямое изменение значения запрещено.

## 7. `acme`

- `enabled`: включать ли внутренний сервер ACME, по умолчанию включён. Пока не создана ни одна конечная точка, сертификаты наружу не выпускаются; если нужно полностью закрыть протокольный вход, задайте `false`.
- `addr`: отдельный адрес прослушивания, например `:14000`. Если пусто, протокол ACME подключается к основному порту по префиксу `/acme`.
- `base_url`: базовый адрес ACME, к которому фактически обращаются клиенты; используется для формирования directory, URL ресурсов учётных записей и адресов CRL/OCSP в сертификатах. При публичном развёртывании обязательно настройте фиксированный адрес и не полагайтесь на заголовок Host запроса; если он не настроен, используется `security.public_url`, а если оба пусты, адрес выводится из заголовка Host запроса и выводится предупреждение при запуске.
- `tls.cert` / `tls.key`: используются, когда отдельное прослушивание ACME напрямую предоставляет TLS; при завершении TLS на обратном прокси оставьте пустыми.
- `mtls.enabled` / `mtls.client_ca`: включаются, когда требуется сертификат клиента, и указывают сертификат CA клиентов. При включении mTLS необходимо одновременно настроить TLS-сертификат и закрытый ключ ACME.

Рекомендации по безопасности:

- При публичном развёртывании используйте отдельный порт и ограничьте источники.
- Для каждой конечной точки необходимо настроить белый список доменов; в продуктивной среде включите EAB.
- `base_url` должен быть фиксированным публичным адресом, чтобы избежать внедрения заголовка Host.
- Если сервер ACME не нужен, установите `enabled: false`, чтобы уменьшить поверхность атаки.

## 8. `plugins`, `deploy_plugins`, `notify_plugins`

Три типа плагинов используют `<data_dir>/plugins/dns`, `<data_dir>/plugins/deploy` и `<data_dir>/plugins/notify` соответственно; подкаталоги не смешиваются.

### 8.1 Плагины DNS

```yaml
plugins:
  enabled: true
  dir: ""                 # пусто — <data_dir>/plugins/dns
  memory_limit_mb: 128
  timeout_seconds: 60
  max_output_kb: 64
  repo:
    enabled: true
    url: "https://github.com/AXmishell/LACTSSL-Plugins/releases/download/plugin-index/index.json"
    channel: stable
    auto_update: false
    public_key: "t7Q4vd0B1zh3mRf0t6Q6qlBViL7cKhoipgpGWx5WSss="
    # Явный прокси для получения индекса и загрузки плагинов; пусто — HTTP_PROXY/HTTPS_PROXY/ALL_PROXY
    proxy: "socks5://127.0.0.1:1080"
    timeout_seconds: 30
    max_download_mb: 256
    check_interval_hours: 24
```

### 8.2 Плагины развёртывания

Плагины развёртывания получают закрытые ключи сертификатов и по умолчанию отключены:

```yaml
deploy_plugins:
  enabled: false
  dir: ""
  memory_limit_mb: 128
  timeout_seconds: 300
  max_output_kb: 64
```

### 8.3 Плагины уведомлений

Основная программа содержит только встроенные уведомления по электронной почте; плагины уведомлений по умолчанию включены:

```yaml
notify_plugins:
  enabled: true
  dir: ""
  memory_limit_mb: 128
  timeout_seconds: 30
  max_output_kb: 64
```

Права на каталог плагинов — `0700`, на helper — `0755`, владелец — пользователь, от имени которого работает сервис. В продуктивной среде рекомендуется настроить `public_key` и отключить `auto_update`. Подробное управление см. в разделе [Управление плагинами](plugins.md).

## 9. `upgrade`

`upgrade` управляет автоматической миграцией при запуске и поведением оптимизации на странице `/upgrade`:

```yaml
upgrade:
  auto: true              # автоматически выполнять миграцию унаследованных данных при запуске
  auto_optimize: true     # при запуске дополнять индексы, обновлять статистику, сворачивать WAL; без VACUUM
  vacuum: true            # разрешить VACUUM при ручной оптимизации в /upgrade
  program:
    enabled: true
    repo: "AXmishell/LACTSSL"
    channel: stable       # stable или beta
    check_interval_hours: 6
    max_download_mb: 128
    public_key: ""
    token: ""
```

- Обновление программы скачивает пакет выпуска для соответствующей платформы из GitHub Release, проверяет SHA-256 из `checksums.txt`, атомарно заменяет текущий бинарник и сохраняет резервную копию старой версии в `<data_dir>/upgrade-backups/program/`.
- При файловой системе только для чтения, на платформах без пакетов выпуска или в сборках `dev` обновление отображается как недоступное.
- Обновление внутри контейнера не изменяет образ; после пересоздания контейнер вернётся к версии образа; в продуктивной среде рекомендуется обновляться через тег образа.
- После настройки `public_key` принудительно проверяется `checksums.txt.sig`; `token` используется для повышения лимита частоты GitHub API.

## 11. Ключевые моменты обратного прокси

### 11.1 Граница доверия

- Только TCP-адреса из `server.trusted_proxies` считаются доверенными прокси. Пустой список означает недоверие ко всем заголовкам пересылки и подходит для прямого подключения.
- `X-Forwarded-For`, `X-Real-IP`, `Forwarded`, `CF-Connecting-IP` до установления доверия к прокси являются подделываемыми заявлениями клиента. Автоопределение в настройках даёт только подсказки и никогда не добавляет адреса автоматически.
- Не указывайте `0.0.0.0/0`, `::/0` или слишком широкие внутренние диапазоны: любой хост внутри доверенного диапазона сможет подделывать IP клиента.

### 11.2 Режим перезаписи (рекомендуется)

Ближайший к LACTSSL прокси заменяет заголовки пересылки реальным адресом клиента:

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
```

В этом режиме в `trusted_proxies` достаточно указать ближайший прокси, и одного шага разрешения хватает для получения IP клиента. В многоуровневой схеме пограничный прокси должен сначала восстановить реального клиента, а ближайший узел — перезаписать заголовки; промежуточный прокси не должен записывать в XFF адрес вышестоящего прокси.

### 11.3 Режим добавления

Nginx `$proxy_add_x_forwarded_for` сохраняет XFF, присланный клиентом, и добавляет адрес текущего соединения. LACTSSL идёт по цепочке справа налево, пропуская доверенные элементы:

- Один прокси: достаточно доверять только адресу Nginx.
- Несколько прокси: в `trusted_proxies` должны быть все прокси, которые могут появиться в XFF. Если доверять только ближайшему узлу, результат остановится на IP вышестоящего прокси.
- Никогда не добавляйте самый левый адрес клиента в список доверенных.

Например, при `client → CDN → Nginx → LACTSSL` режим добавления даёт `client, IP edge-узла CDN`. Если доверять только Nginx, будет получен IP edge-узла CDN; нужно также доверять официальным диапазонам CDN или переключить Nginx на перезапись XFF.

### 11.4 CDN и облачные балансировщики

- Доверяйте `CF-Connecting-IP` только если TCP-адрес принадлежит официальным диапазонам Cloudflare. Доверие только по наличию заголовка позволяет прямым клиентам подделывать его.
- Рекомендуется включить `real_ip` на своём Nginx с официальными диапазонами и перезаписывать XFF значением `$remote_addr`; LACTSSL доверяет только этому Nginx.
- IP edge-узлов CDN меняются; не добавляйте их по одному. Используйте официальные диапазоны или поставьте за CDN собственный прокси.
- L4/TCP балансировщик не передаёт HTTP-заголовки, поэтому виден только его адрес. Нужен PROXY protocol или HTTP-прокси за балансировщиком.

### 11.5 Docker и Kubernetes

- В контейнере peer часто является шлюзом моста или адресом Service, а не реальным клиентом.
- Предпочитайте точный IP контейнера/узла прокси. Если IP динамический, используйте отдельную сеть и доверяйте только адресу прокси или минимальному CIDR.
- Не доверяйте `172.16.0.0/12` только потому, что это приватная сеть: другие контейнеры в той же сети могут подделывать заголовки.
- Проверьте, очищает ли Ingress Controller XFF; не предполагайте одинаковое поведение у всех Ingress.

### 11.6 Применение и проверка

1. Добавьте адреса прокси в `trusted_proxies` и настройте `security.public_url`.
2. Если TLS завершается на прокси, передавайте `X-Forwarded-Proto: https`.
3. Для восстановления резервных копий и загрузки плагинов нужен больший лимит тела (например, Nginx `client_max_body_size 256m`); тайм-аут чтения прокси должен покрывать восстановление, загрузку плагинов и развёртывание (например, 600 секунд).
4. После сохранения перезапустите сервис и проверьте в «Настройки → Файл конфигурации → Автоопределение» значения `peer_ip`, `applied_trusted_proxies`, `effective_client_ip`, `client_ip_source`. До перезапуска `configured_trusted_proxies` и `applied_trusted_proxies` могут различаться.
5. Тест подделки: отправьте `X-Forwarded-For: 203.0.113.9` с недоверенного адреса; сервер должен по-прежнему использовать TCP-peer. В журнале доступа есть `ip_source`, `ip_skipped`, `ip_warnings`.

### 11.7 Расширенная идентификация прокси

Порядок разрешения: проверка доверенного прокси → необязательный заголовок Cloudflare → `X-Forwarded-For` → `X-Real-IP` → RFC 7239 `Forwarded` → TCP-peer. Ни один режим не принимает заголовки пересылки от недоверенного источника.

- **RFC 7239 `Forwarded`**: автоматически разбирается, если предыдущие заголовки недоступны. Поддерживаются `for=203.0.113.9`, `for=203.0.113.9:4711`, `for="[2001:db8::1]:4711"`; значения `unknown` и `_hidden` отклоняются.
- **Режим Cloudflare**:
  ```yaml
  server:
    client_ip_mode: cloudflare
    trusted_proxies:
      - "173.245.48.0/20"
      - "103.21.244.0/22"
      # ... другие официальные диапазоны Cloudflare
  ```
  `CF-Connecting-IP` принимается только если peer входит в `trusted_proxies`. Не используйте этот режим с локальным Nginx, который лишь перезаписывает заголовки; ограничьте доступ к источнику только Cloudflare.
- **PROXY protocol**:
  ```yaml
  server:
    proxy_protocol: true
  ```
  Принимаются заголовки v1/v2 только от peer из `trusted_proxies`; PROXY-заголовок от недоверенного источника закрывает соединение. Обычный HTTP без PROXY-заголовка продолжает работать. L4-балансировщик должен быть настроен на его отправку.
- **Идентификация прокси по mTLS**:
  ```yaml
  server:
    tls:
      cert: "/etc/lactssl/server.crt"
      key: "/etc/lactssl/server.key"
      proxy_client_ca: "/etc/lactssl/proxy-ca.pem"
  ```
  Основной listener работает по HTTPS. Соединение с клиентским сертификатом, подписанным `proxy_client_ca`, считается доверенным прокси независимо от IP. Браузеры без клиентского сертификата продолжают работать. Режим предназначен только для прокси, подключающихся к LACTSSL напрямую по TLS; если TLS завершается на прокси, используйте доверие по IP/CIDR или PROXY protocol. Используйте отдельный CA для прокси, а не клиентский CA браузеров.

Полный пример см. в разделе [Установка и запуск](install.md).

## 12. Проверка конфигурации и обработка сбоев

Распространённые причины сбоя запуска:

| Ошибка | Причина | Обработка |
| --- | --- | --- |
| `jwt_secret` слишком короткий | При ручной настройке указано меньше 32 символов | Укажите не менее 32 символов или оставьте пустым для автоматической генерации |
| `salt` слишком короткий | При ручной настройке указано меньше 32 символов | Укажите не менее 32 символов или оставьте пустым для автоматической генерации |
| Сбой прослушивания | Порт занят или недостаточно прав | Проверьте порт и пользователя, от имени которого работает сервис |
| Неполная конфигурация mTLS | mTLS включён, но отсутствует TLS-сертификат/закрытый ключ | Настройте одновременно `acme.tls.cert/key` |
| Сбой проверки конфигурации | Недопустимый пакет восстановления или ручное редактирование | Исправьте по подсказке в журнале; пакет восстановления проверяется перед применением |
| Изменения не вступают в силу | Конфигурация требует перезапуска | Перезапустите сервис; исключение — настройки защищённой точки входа/страницы плагинов |

Восстановление и миграцию конфигурации выполняет инструмент обновления, подробнее см. в разделе [Обновление и изменения](upgrade.md).
