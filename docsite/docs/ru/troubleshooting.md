# Мониторинг и устранение неполадок

Ниже — частые сбои, пути диагностики и аварийные действия. Сначала сохраните текущее состояние, затем ищите причину в порядке «зависимости → аутентификация → приложение → данные», избегая немедленной перезагрузки и очистки журналов.

## Первичная диагностика

### Определение масштаба влияния

- Сбой затрагивает один сертификат, одну задачу или все задачи?
- Недоступна административная точка входа или сбоит только выпуск/развёртывание?
- Затронуты одна или все цели развёртывания, уведомления, мониторинг, клиенты ACME?
- Проблема появилась после обновления/изменения конфигурации или возникла внезапно?

### Сбор базовой информации

```bash
# Версия и процесс
curl -fsS -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/status

# Журналы Docker
docker compose logs --since=30m lactssl

# Журналы systemd
sudo journalctl -u lactssl --since "30 min ago"

# Порты
ss -lntp | grep -E '8080|14000'
```

Также запишите время возникновения и часовой пояс, попадание в окно изменений, ID задач/сертификатов/записей развёртывания, заголовок `X-Request-ID` и исходный текст ошибки после маскирования.

### Проверка зависимостей

| Зависимость | Способ проверки |
| --- | --- |
| Обратный прокси | Журналы прокси, порт бэкенда, заголовки пересылки |
| DNS API | Права учётных данных, квоты, домен/зона, записи TXT |
| Публичный CA | Страница состояния, ограничения частоты, CAA, EAB |
| Цель развёртывания / SMTP/IM | Сеть, аутентификация, путь, права, команда перезагрузки; связность и конфигурация канала |
| Хост | Диск, память, права файлов, синхронизация времени |

## Доступ и вход

### Корневой путь возвращает 404

**Симптом**: `https://ssl.example.com/` возвращает 404.

**Причина**: запрос не прошёл через защищённую точку входа — случайный путь; голый корень всегда возвращает 404.

**Решение**:

1. Посмотрите точку входа в журнале запуска или значение `security.entry` в таблице `settings`.
2. Либо задайте `security.entry` в `config.yaml` и перезапустите сервис.

### Забыта защищённая точка входа

- Журнал запуска (при инициализации выводится полная точка входа) или значение `security.entry` в таблице `settings`.
- Измените `security.entry` в `config.yaml` перед запуском; после перезапуска значение будет переопределено.

После изменения точки входа старые ссылки сразу перестают работать; запишите новую и уведомьте заинтересованные стороны.

### Сразу после входа сеанс завершается/становится недействительным

**Возможные причины**:

- Сервис перезапущен при явно отключённом `security.session_persistence`, изменён пароль или используется другой `jwt_secret`.
- Обратный прокси не передаёт `X-Forwarded-Proto` (некорректные `Secure` Cookie) или браузер/прокси закешировал старые Cookie.

**Решение**:

1. Уточните, не был ли сервис только что перезапущен и не менялся ли пароль.
2. Проверьте заголовки прокси и `trusted_proxies`, очистите Cookie и войдите заново; если задано `security.session_persistence: false`, верните `true`.

### Аномалии Cookie и неточное ограничение скорости

**Симптом**: циклы входа, сбой CSRF, все запросы используют одну квоту IP.

**Причина**: не настроен доверенный прокси, прокси не передаёт заголовки пересылки, или в многоуровневой схеме доверен только ближайший узел.

**Решение**:

```yaml
server:
  trusted_proxies: ["127.0.0.1"]
security:
  public_url: "https://ssl.example.com"
```

Убедитесь, что прокси задаёт:

```nginx
proxy_set_header X-Real-IP $remote_addr;
# Рекомендуемый режим перезаписи: достаточно доверять этому прокси
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
```

В режиме добавления (`$proxy_add_x_forwarded_for`) в цепочке CDN → Nginx → LACTSSL перечислите в `trusted_proxies` все прокси, которые могут появиться в XFF, иначе IP клиента остановится на вышестоящем.

В «Настройки → Файл конфигурации → Автоопределение» проверьте `peer_ip`, `applied_trusted_proxies`, `effective_client_ip` / `client_ip_source`, `trusted_skipped`, `header_warnings` (в журнале доступа — `ip_source`, `ip_skipped`, `ip_warnings`). После сохранения нужен перезапуск; до него `configured_trusted_proxies` и `applied_trusted_proxies` могут различаться.

### 429 Слишком много запросов

- Повторите попытку позже с задержкой согласно `Retry-After`.
- Проверьте, не используется ли общий IP прокси; после настройки доверенных прокси квота считается по реальному IP клиента.
- Для входа, TOTP, сброса пароля, копий, экспорта ключей и ACME действуют отдельные ограничения; не повышайте пороги, чтобы скрыть подбор паролей.

### Ключи доступа недоступны

- Доступ должен осуществляться через HTTPS-домен или localhost; IP-адрес не может быть источником WebAuthn.
- Проверьте поддержку WebAuthn и биометрии/PIN в системе.
- Ключ доступа не заменяет пароль; при утере устройства используйте пароль + TOTP или другой путь восстановления.

## Сбой выпуска сертификата

### Сбой проверки DNS-01

| Возможная причина | Проверка |
| --- | --- |
| Учётные данные не имеют прав | Есть ли у ключа права на чтение и запись целевой зоны |
| Домен/зона не совпадает | Находится ли домен в зоне, видимой текущей учётной записи |
| Медленное распространение TXT | Подождите TTL; проверьте авторитетный DNS |
| Многоуровневый домен/CNAME, wildcard | Путь разрешения `_acme-challenge`; для wildcard необходим DNS-01 |
| Ограничения провайдера, прокси/шлюз | Квоты и частота, изменения API, доступность адреса API и доверие к сертификату |

Обработка:

1. Посмотрите конкретную ошибку провайдера в журнале задачи.
2. С помощью `dig`/`nslookup` проверьте TXT для `_acme-challenge.<domain>`; с теми же учётными данными вручную создайте/удалите TXT в консоли провайдера.
3. Проверьте, разрешает ли CAA использование этого CA, и после исправления повторно запустите задачу.

### Ограничения частоты CA/ошибки EAB

- Публичные CA, такие как Let's Encrypt, ограничивают частоту для учётных записей, доменов и неудачных проверок; смотрите страницу состояния и текст ошибки.
- ZeroSSL, Google Trust Services, LiteSSL, ZoTrus, Actalis и SSL.com требуют EAB; убедитесь, что KID/HMAC верны и не истекли (для ZoTrus KID — зарегистрированная почта).
- ZoTrus формирует запись dns-01 из `tokenPath` сервера (обычно `_<tokenPath>.<domain>`), а не из `_acme-challenge`; после запуска добавьте записи из журнала или панели «DNS-проверка» и нажмите «Продолжить проверку». Wildcard, пулы CA и Target Flow Beta пока не поддерживаются.
- Каталог вышестоящего ACME должен использовать HTTPS (исключение — loopback); для критичных доменов подготовьте резервный CA.

### Сертификат выпущен, но браузер не доверяет ему

- Проверьте, развёрнута ли полная цепочка (fullchain) и правильная ли пара сертификат/ключ; для частного CA установите корневой CA в хранилище доверия клиента.
- Проверьте SNI, домен и SAN сертификата, а также системное время.

### Сбой выпуска в частном CA

- Убедитесь, что CA не истёк, имеет назначение выпуска и длину пути, допускающую подчинённый CA, а срок сертификата не превышает срок CA.
- У импортируемого CA сертификат должен соответствовать ключу и иметь базовые ограничения; перед удалением CA сначала удалите подчинённые.

## Сбой развёртывания

### SSH/SFTP

| Симптом | Причина | Обработка |
| --- | --- | --- |
| Несовпадение отпечатка хоста | Сервер сменил ключ или конфигурация неверна | Сверьте отпечаток, очистите старый и запишите заново |
| Первое подключение отклонено | Отпечаток не указан и TOFU не включён | Укажите `SHA256:...` или включите доверие при первом подключении |
| Сбой аутентификации | Неверны пользователь/пароль/ключ | Проверьте учётные данные и SSH на цели |
| Нет прав на путь | У пользователя развёртывания нет прав на запись | Настройте права каталога или другого пользователя |
| Сбой команды перезагрузки | Нет команды/прав или неверное имя службы | Выполните вручную на целевом хосте |

### Локальный каталог

- Пользователь сервиса не имеет прав на запись, путь не существует или мешают SELinux/AppArmor.
- Команда перезагрузки завершилась сбоем, но файлы обновлены; проверьте, загружает ли служба новые файлы.

### Панель/CDN/Webhook

- Учётные данные истекли, недостаточно прав или версия API не совпадает.
- Параметры развёртывания (сайт, домен, имя сертификата) не соответствуют целевой системе.
- В цели включён белый список IP, а исходящий адрес LACTSSL не разрешён; публичные цели Webhook требуют HTTPS (loopback/частная сеть допускают HTTP).

### Сертификат обновлён, но приложение использует старый

- В узле развёртывания не настроена команда перезагрузки или она не вступила в силу; в целевой системе есть кеш (CDN, WAF, балансировщик), развёртывание выполнено в неверный путь/сайт или обновлён только один экземпляр.
- Сверьте серийный номер/отпечаток сертификата с целевой системой.

## Уведомления и мониторинг

### Уведомление не доставлено

- Включён ли канал и узел уведомлений в задаче, соответствует ли момент срабатывания.
- Не истекли ли Token/Webhook и доступна ли цель.
- SMTP использует неявный TLS; если сервер не поддерживает STARTTLS, отправка отклоняется. Проверьте журнал операций/системный журнал (значения маскируются).

### Ложные срабатывания мониторинга сайтов

- Мониторинг проверяет имя хоста и системную цепочку доверия; самоподписанные сертификаты, неполная цепочка и несовпадение имени помечаются как аномалия.
- Проверьте порт, SNI, хранилище доверия CA и время; разные узлы за балансировщиком могут возвращать разные сертификаты.
- Проверьте частоту и тайм-аут мониторинга, чтобы не получать частые оповещения по нестабильным целям.

### Напоминания об истечении не приходят

- Включено ли автопродление задачи и разумен ли `RenewDays`.
- Работает ли планировщик (записи в журнале), доступны ли каналы, не очищены ли сертификаты и ссылки в задачах.

## Проблемы с плагинами

| Симптом | Причина | Обработка |
| --- | --- | --- |
| Список целей пуст | Категория/элемент не включены | Включите категорию и нужные элементы на странице «Плагины» |
| Сбой установки helper или элемент не появился | Подпись, SHA-256, платформа, `min_host`; элемент не включён | Посмотрите ошибку, сверьте ключ и версию, включите элементы |
| Плагин отклонён при загрузке | Каталог доступен на запись группе/другим, символическая ссылка, изменение дайджеста | Исправьте права или переустановите |
| Сбой миграции старого плагина | Занят старый helper/конфликт файлов | Действуйте по подсказке миграции |
| Плагин развёртывания недоступен | `deploy_plugins.enabled: false` (явно отключено) | Установите true и перезапустите |

Каталоги плагинов:

```text
data/plugins/dns
data/plugins/deploy
data/plugins/notify
```

Требования к правам: каталог `0700`, helper `0755`, владелец — пользователь сервиса.

### После импорта цепочки доверия плагин всё равно сообщает о сбое проверки TLS

Определите причину по сообщению:

- **Сертификат истёк или ещё не вступил в силу**: продлите или обновите сертификат; импорт CA не продлевает срок.
- **Сертификат не соответствует адресу**: используйте домен из SAN; при доступе по IP сертификат должен содержать IP SAN.
- **Сертификат не является доверенным**: импортируйте открытый ключ CA (корневого или промежуточного), а не сертификат сайта; один PEM может содержать несколько CA, перезапуск не требуется.
- В остальных случаях проверьте через `openssl s_client -connect host:port -servername host -showcerts`, полна ли цепочка.

Подпроцесс плагина читает `<data_dir>/trusted-ca-bundle.pem` через `SSL_CERT_FILE`; цепочка объединяет системные корневые, импортированные и частные CA. Импортируйте только контролируемые внутренние CA.

## Резервное копирование и восстановление

### Сбой скачивания резервной копии

- Требуется повторно ввести текущий пароль; при включённом TOTP — динамический код, пароль копии содержит не менее 12 символов.
- Проверьте ограничения размера тела запроса/ответа на прокси и свободное место.
- Посмотрите журнал операций и системный журнал.

### После восстановления учётные данные не расшифровываются

- `config.yaml` в копии не соответствует базе, отличается `salt`, или восстановлена только база без конфигурации.
- Восстановитесь из полной ZIP-копии; не заменяйте базу отдельно.

### После восстановления не удаётся войти

- Используйте административную учётную запись из резервной копии.
- Перезапуск мог очистить сеансы, защищённая точка входа могла измениться — посмотрите журнал запуска; разный `jwt_secret` делает старые токены недействительными.
- Пакет восстановления находится в `data/restore-pending/`; проверьте, применён ли он.

### После восстановления сервис не поднялся автоматически

- Docker: проверьте `restart: unless-stopped`; systemd: убедитесь, что служба запущена.
- При прямом запуске бинарника требуется ручной перезапуск.
- Проверьте ошибки проверки конфигурации в журнале запуска.

## База данных, диск и память

### База данных растёт

- Растут сертификаты, журналы задач, журнал операций, системный журнал и заказы ACME.
- Используйте очистку сертификатов, диагностику ACME и очистку системного журнала; в период низкой нагрузки выполните в `/upgrade` «Только оптимизация базы данных и конфигурации» (при необходимости с VACUUM), проверьте WAL — оптимизация выполняет `wal_checkpoint(TRUNCATE)`.

### Недостаточно диска

- Проверьте `data/`, журналы, `upgrade-backups/` и файлы копий.
- Очистите старые снимки обновления и бинарники по политике хранения.
- Убедитесь, что копии не пишутся в тот же каталог данных; VACUUM требует временного места.

### Высокое потребление памяти/OOM

- Базовая память процесса в простое — несколько десятков MB; плагин — одноразовый подпроцесс с лимитом `memory_limit_mb`.
- Установка/обновление плагинов даёт кратковременный пик, при параллельных задачах запускается несколько helper.
- Проверьте лимит памяти контейнера и оставьте запас на пики; при нормальной работе плагинов снизьте параллелизм или лимит helper.

### Блокировка базы данных/сбой записи

- Убедитесь, что каталог данных подключён только к одному экземпляру, и не размещайте SQLite на общем хранилище с множественной записью.
- Проверьте заполнение диска, права и файловую систему только для чтения; во время копирования/восстановления избегайте множества параллельных задач.

## Обновление и миграция

### Сбой миграции при запуске

- Посмотрите неудавшийся шаг в журнале, проверьте диск, права и целостность базы.
- После исправления перезапустите сервис: шаги идемпотентны, номер версии при сбое не продвигается; не удаляйте вручную `upgrade.schema_version`.

### После обновления страница недоступна

- Проверьте обратный прокси и кеш статических ресурсов; выполните принудительное обновление или очистите кеш CDN.
- Проверьте соответствие версии бинарника/образа, журнал запуска и консоль браузера.

### Самообновление программы отклонено

- Причины: файловая система только для чтения, сборка `dev`, платформа без пакетов выпуска, отсутствие контрольной суммы/подписи.
- Обновление внутри контейнера не изменяет образ; обновляйтесь через тег образа и проверьте ограничения GitHub API и исходящий прокси.

## Устранение неполадок сервера ACME

| Ошибка клиента | Возможная причина | Обработка |
| --- | --- | --- |
| `badNonce` | Перезапуск сервиса или истечение nonce | Клиент повторяет автоматически; проверьте, не используется ли несколько экземпляров |
| `unauthorized` | Ошибка учётной записи/JWS, нет EAB | Проверьте EAB, ключ и конечную точку |
| `rejectedIdentifier` | Домен отсутствует в белом списке | Проверьте белый список конечной точки |
| `caa` | CAA не разрешает этот CA | Измените CAA или смените CA |
| `orderNotReady` | Challenge не завершён | Завершите авторизацию и выполните finalize |
| `rateLimited` | Ограничение частоты конечной точки | Повторите позже согласно `Retry-After` |
| Сбой HTTP-01 | Цель недоступна/частная сеть отклонена | Проверьте белый список CIDR, порт, маршрутизацию |
| Сбой mTLS | Сертификат клиента не доверен | Проверьте `mtls.client_ca` и цепочку клиента |
| Неверный URL ресурса | `base_url` не настроен | Настройте фиксированный `acme.base_url` |

Диагностика: «Диагностика ACME» показывает учётные записи, заказы, авторизации, challenge и сертификаты; проверьте `acme.base_url`, белый список, EAB и тип challenge, не полагайтесь на вывод URL из заголовка Host, убедитесь в доступности CRL/OCSP.

## Аварийные действия

### Подозрение на утечку ключа API

1. На странице «Ключи API» отключите или удалите ключ, создайте новый и обновите вызывающую сторону.
2. Проверьте в журнале операций аномальные вызовы, развёртывания и скачивания ключей.
3. При затрагивании целей ротируйте их учётные данные; запишите инцидент и проведите разбор.

### Подозрение на компрометацию административной учётной записи

1. Смените пароль — это удалит все сеансы, ключи API и ключи доступа.
2. Проверьте почту восстановления, журнал операций, системный журнал и журналы прокси; ротируйте учётные данные DNS/развёртывания/уведомлений.
3. При подозрении на утечку `salt` пересоздайте экземпляр и введите учётные данные заново; оцените перевыпуск сертификатов.

### Сертификат развёрнут/перезаписан ошибочно

1. Приостановите связанные задачи, чтобы избежать дальнейшей перезаписи.
2. Восстановите предыдущую версию из копии целевой системы или истории сертификатов.
3. Проверьте параметры узла развёртывания и команду перезагрузки.
4. Разверните правильный сертификат, сверьте отпечаток, запишите первопричину и добавьте проверку перед развёртыванием.

### Злоупотребление конечной точкой ACME

1. Отключите конечную точку или `acme.enabled`.
2. Проверьте учётные записи, заказы и исходные IP.
3. Включите EAB, mTLS или сетевой ACL.
4. Очистите аномальные учётные записи и заказы; проверьте, не выпущены ли лишние сертификаты.

## Сбор информации для обращения

При обращении предоставьте версию, время сборки, архитектуру и способ развёртывания; ОС, версию контейнера/оркестратора и тип прокси; шаги воспроизведения, ожидаемый и фактический результат; фрагменты журналов с маскированием (время, `X-Request-ID`, код ошибки); ID задач/сертификатов/записей развёртывания; сведения о недавних обновлениях, изменениях, замене плагинов или ротации; уже предпринятые действия.

Не предоставляйте пароль администратора, seed TOTP и ключи API в открытом виде, закрытые ключи сертификатов/CA и пароли копий, немаскированные учётные данные DNS/развёртывания/уведомлений.
