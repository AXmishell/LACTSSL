# Обновление и изменения

Обновление — одно из самых рискованных повседневных изменений: нужно обеспечить откат миграции базы данных и избежать простоя при массовом истечении сертификатов. Ниже — оценка, миграция, обновление программы, откат и чек-лист окна изменений.

## Принципы изменений

- **Сначала резервная копия, затем обновление**: `config.yaml` + весь `data/` либо зашифрованная копия через интерфейс.
- **Сначала предварительная среда, затем продуктивная**: проверьте выпуск, развёртывание, уведомления и API; в продуктивной среде не используйте `latest` и сохраняйте снимок миграции, старый бинарник или тег образа.
- **Вне пиковой нагрузки**: не пересекайтесь с массовым истечением сертификатов, развёртыванием или выпуском релизов приложения; после обновления наблюдайте цикл планирования и выполнение задачи.

## Что делает обновление

`internal/upgrade` автоматически мигрирует унаследованные данные при первом запуске новой версии; после входа можно открыть `/upgrade` для предварительной проверки, ручной миграции и оптимизации базы.

### Порядок автоматической миграции

1. Считывает и проверяет `config.yaml`.
2. Открывает базу (SQLite или PostgreSQL) и выполняет базовое создание таблиц.
3. Создаёт инструмент обновления и считывает `upgrade.schema_version`.
4. При устаревшей версии создаёт резервную копию базы и конфигурации, затем выполняет шаги миграции.
5. Записывает новый номер версии, выполняет недорогую оптимизацию и продолжает инициализацию учётных записей, планировщика и HTTP-сервиса.

- Автоматическая миграция управляется `upgrade.auto` и по умолчанию включена; шаги идемпотентны, при сбое номер версии не продвигается, а шаг повторяется при следующем запуске. Резервная копия находится в `data/upgrade-backups/<время UTC>/`, по умолчанию сохраняются последние 5.

### Содержание миграции

| Проблема | Поведение старой версии | Обработка инструментом обновления |
| --- | --- | --- |
| Нет версии формата | Структура выводится по `ensureColumn` и разрозненным ключам | Записывается `upgrade.schema_version`, шаги выполняются по версиям |
| Чувствительные поля открытым текстом | Ключи TOTP и закрытые ключи пишутся напрямую | Шифрование AES-256-GCM; готовый шифротекст пропускается |
| Файлы ключей старых версий | Ключ в `data/jwt.secret` и `config.yaml` | После подтверждения ключа в конфигурации файл переносится в резервные копии и удаляется |
| Глобальные EAB | `acme.eab_kid` / `acme.eab_hmac` только для CA по умолчанию | Переносятся в настройки CA по умолчанию, старые ключи удаляются |
| Параметры развёртывания в учётных данных | Путь, сайт и команда перезагрузки хранятся в учётных данных | Выносятся в узел развёртывания; в учётных данных остаётся аутентификация |
| Дублирующиеся цели развёртывания | Старые ID, например `qiniu_cdn`, `baota_site` | Объединяются в канонические ID, выбор сайта/CDN переносится в узел |
| Старые настройки и остатки плагинов | Отдельные ключи Gotify / Server酱, старые helper, нет белого списка | Ключи преобразуются в универсальный канал, белые списки DNS/развёртывания/уведомлений инициализируются |
| Разрастание базы и WAL | Свободные страницы и растущий `-wal` | `VACUUM`, `ANALYZE`, `wal_checkpoint(TRUNCATE)` |
| Нет индексов горячих путей | Полное сканирование таблиц при фильтрации и очистке | Индексы добавляются автоматически, повторный запуск безопасен |
| Разделение журналов | `system_logs` и `logs` | Системные журналы копируются в `logs(category=runtime)`, старая таблица сохраняется для отката |
| Устаревшая конфигурация | Нет `plugins.repo`, `notify_plugins`, `log.system`, `upgrade` | Недостающие поля дополняются, комментарии сохраняются |

## Проверка перед обновлением

- [ ] Прочитайте описание изменений и миграции, уточните текущую версию, версию формата и предстоящие шаги.
- [ ] Создайте резервную копию `config.yaml` и `data/`, проверьте её читаемость и запас диска (VACUUM требует временного пространства).
- [ ] Проверьте выпуск, развёртывание, уведомления и API в среде предварительного развёртывания.
- [ ] Убедитесь в доступности бинарника или тега образа старой версии, уведомьте заинтересованные стороны, выберите окно низкой нагрузки и приостановите пакетные задачи.

## Способы обновления

### Docker (рекомендуется)

```bash
# Зафиксируйте целевую версию: сначала измените тег image в docker-compose.yml на 1.2.3
docker compose pull
docker compose up -d
docker compose logs -f lactssl
```

- Используйте явный тег версии для удобства отката.
- Не используйте самообновление внутри контейнера: после пересоздания контейнер вернётся к версии образа. В официальном Compose корневая файловая система только для чтения, поэтому страница сообщит о неподдерживаемом самообновлении — это ожидаемо.

### Бинарник

```bash
sudo systemctl stop lactssl
sudo cp lactssl /opt/lactssl/lactssl
sudo chown lactssl:lactssl /opt/lactssl/lactssl
sudo chmod 0755 /opt/lactssl/lactssl
sudo systemctl start lactssl
sudo journalctl -u lactssl -f
```

- Права доступа сохраняются, а расширенные атрибуты вроде `setcap` — нет; при привилегированных портах или capability настройте их заново.
- Самообновление с `exec` работает в Linux/macOS/FreeBSD, в Windows нужен повторный запуск через менеджер служб; для `dev`-сборок и пакетов без `checksums.txt` или SHA-256 оно отклоняется — замените вручную и проверьте самостоятельно.

### Самообновление программы (опционально)

В верхней части `/upgrade` доступно «Обновление программы»:

- **Проверить обновления**: запрашивает Release согласно `upgrade.program.channel`; `stable` принимает только стабильные версии, `beta` включает предварительные.
- **Установить обновление**: скачивает `lactssl_<version>_<os>_<arch>.tar.xz` (при отсутствии — `.tar.gz`, в Windows — `.zip`), проверяет SHA-256 по `checksums.txt`, распаковывает и заменяет исполняемый файл.
- **Подпись выпуска**: официальные сборки встраивают открытый ключ и принудительно проверяют `checksums.txt.sig`; при ошибке или отсутствии подписи установка отклоняется.
- **Резервная копия и перезапуск**: старый бинарник копируется в `<data_dir>/upgrade-backups/program/` (по умолчанию 3 копии); после установки страница предлагает перезапуск, при `security.session_persistence: false` он очищает сеансы.

Ограничения:

- При файловой системе только для чтения, на платформах без пакетов выпуска и в сборках `dev` обновление недоступно.
- Самостоятельные сборки без `upgrade.program.public_key` отклоняют онлайн-обновление; неподписанный пакет разрешается только `upgrade.program.allow_unsigned: true` в контролируемой среде.
- Без токена GitHub API действует анонимное ограничение; токен задаётся в `upgrade.program.token`, прокси — через переменные системного прокси.

## Проверка после обновления

1. Проверьте в журнале запуска сообщение «Обновление формата данных завершено».
2. Откройте `/upgrade` и убедитесь, что все шаги «Завершено» или «Пропущено».
3. Проверьте версию, время сборки, архитектуру, вход администратора, TOTP/ключи доступа.
4. Проверьте сертификаты, задачи, учётные данные развёртывания, каналы уведомлений, плагины и права ключей API.
5. Вручную запустите тестовую задачу и наблюдайте цикл планирования (30 секунд) и автопродление.

## Откат

### Откат данных

Инструмент обновления создаёт снимок перед изменением структуры:

```text
data/upgrade-backups/20260101-120000/
├── lactssl.db
└── config.yaml
```

1. Остановите сервис.
2. Замените базу файлом `lactssl.db` из резервной копии и удалите `lactssl.db-wal`, `lactssl.db-shm`.
3. При необходимости замените конфигурацию файлом `config.yaml` из резервной копии.
4. Запустите программу старой версии.

- Старая версия может не читать формат новой: при откате между крупными версиями откатывайте бинарник и данные одновременно; не удаляйте вручную `upgrade.schema_version`, иначе шаги миграции выполнятся повторно.
- При сбое автоматической миграции сервис не запустится и покажет шаг; после устранения прав, диска или данных достаточно перезапустить его.

### Откат программы

```text
data/upgrade-backups/program/
├── 20260101-120000-lactssl-1.2.2
└── 20260102-090000-lactssl-1.2.3
```

1. Остановите сервис.
2. Замените бинарник файлом из резервной копии и восстановите права на выполнение (`chmod 0755`).
3. При необходимости откатите данные по предыдущему разделу, запустите сервис и проверьте номер версии и состояние миграции.

## Переключение базы данных онлайн (SQLite ↔ PostgreSQL)

Страница `/upgrade` переключает бэкенд внутри процесса, без ручного SQL и замены файлов базы.

### Предварительные условия

- Для PostgreSQL рекомендуется версия 18; приложение проверяет версию сервера.
- Целевая база по умолчанию должна быть пустой; для непустой установите флажок «Очистить текущую схему» — удаляются только таблицы текущей схемы. Второй экземпляр не может использовать ту же базу PostgreSQL (`database.allow_multi_instance: false`).
- Перед переключением принудительно создаётся резервная копия: для SQLite — `VACUUM INTO`, для PostgreSQL/MySQL — нативное логическое копирование на Go, файлы в `data/db-convert/backups/<время>/`. Сервис должен управляться systemd, политикой Docker или аналогичным менеджером.

### Порядок выполнения

1. В `/upgrade` выберите бэкенд. Для PostgreSQL укажите хост, порт, пользователя, пароль, базу и режим SSL либо полный DSN; для SQLite — путь к файлу внутри `data_dir`.
2. Нажмите «Проверить подключение» и «Предварительная проверка», чтобы увидеть версию, состояние пустой базы, таблицы и число строк.
3. Введите пароль/TOTP и арифметическое подтверждение (API по-прежнему использует слово `CONVERT`). Включается режим обслуживания, приложение создаёт копию, замораживает запись, копирует таблицы, проверяет число строк и хеши, выборочно расшифровывает чувствительные поля.
4. После проверки атомарно перезаписывается `config.yaml`, записывается `data/db-convert/state.json` и выполняется перезапуск. Новый процесс открывает базу и проводит самопроверку; при сбое восстанавливается старая конфигурация, после успеха старый файл SQLite удаляется (включая `-wal`/`-shm`/`-journal`), а копия перед переключением сохраняется.

Время заморозки зависит от объёма данных: секунды для небольшой базы, минуты при большом числе журналов и сертификатов; страница опрашивает ход выполнения.

### Откат одним нажатием

После переключения `/upgrade` показывает «Откат одним нажатием» (кроме однотипной миграции). Это обратное переключение **самых свежих данных текущей базы** на прежний бэкенд с перезаписью конфигурации и перезапуском, чтобы не потерять записи после переключения. Откат создаёт копию, замораживает запись и проверяет данные; нужны арифметическое подтверждение и пароль/TOTP (API использует `ROLLBACK`). Копия конфигурации сохраняется в `config.yaml.before-db-convert-<время>`.

### CLI

При остановленном сервисе ту же логику можно выполнить через CLI:

```bash
./lactssl-dbconvert   -config config.yaml   -source-driver sqlite -source data/lactssl.db   -target-driver postgres -target "postgres://user:pass@host:5432/lactssl?sslmode=verify-full"   -switch -yes
```

`-switch` перезаписывает `config.yaml`, но не запускает сервис. Непустая целевая база по умолчанию отклоняется; очистку подтверждает `-force`.

### Ограничения

- Переключение без простоя с двойной записью/CDC не предоставляется: запись приостанавливается на время копирования; при совместном использовании PostgreSQL несколькими экземплярами v1 сразу отклоняет переключение.
- Переменная `LACTSSL_DATABASE_DSN` делает перезапись конфигурации недействительной — удалите её и перезапустите сервис; также убедитесь, что нет массовых задач развёртывания/выпуска.

### Однотипная миграция (SQLite → SQLite / PostgreSQL → PostgreSQL)

Однотипная миграция по умолчанию запрещена. Для переноса в другой файл или экземпляр PostgreSQL установите флажок «Однотипная миграция» (`allow_same_driver: true` в API, `-allow-same-driver` в CLI).

- Цель должна быть пустой, а флажок «Очистить схему» при однотипной миграции недоступен; цель не может совпадать с текущей базой (SQLite сравнивает реальные файлы, PostgreSQL — время запуска экземпляра и имя базы).
- После PostgreSQL → PostgreSQL исходная база не удаляется, после SQLite → SQLite старый файл удаляется, копия сохраняется.
- «Откат одним нажатием» не поддерживается — восстанавливайтесь вручную из копии; `-force` с однотипной миграцией не используется.

## Ручная миграция и оптимизация базы данных

После входа откройте `/upgrade` (боковое меню «Система → Обновление версии»):

- **Предварительная проверка**: версия программы и формата, шаги миграции, целостность базы, свободные страницы, изменения конфигурации и риски; данные не изменяются.
- **Выполнить миграцию и оптимизацию**: повторяет шаги миграции и оптимизирует конфигурацию и базу; **только оптимизация** работает без повторной миграции.
- **Освободить дисковое пространство**: выполняет `VACUUM`, который монопольно захватывает базу; используйте в период низкой нагрузки.

Результаты записываются в системный журнал и `upgrade.last_run`.

### Содержание оптимизации базы данных

- `PRAGMA quick_check(1)` проверяет целостность; `PRAGMA user_version` хранит версию структуры, поэтому актуальная схема пропускает создание таблиц и `ensureColumn`.
- Добавляются индексы горячих путей (статус и срок сертификата, состояние и следующее выполнение задачи, проверки мониторинга, уровень и время журнала, заказы/challenge ACME, записи развёртывания); `PRAGMA optimize` и `ANALYZE` обновляют статистику, `wal_checkpoint(TRUNCATE)` усекает WAL.
- `VACUUM` освобождает страницы удалённых данных и уменьшает файл, не удаляя данные приложения, но перезаписывая базу; инструмент создаёт снимок, а при нехватке диска возвращает предупреждение без влияния на работу.

### Содержание оптимизации файла конфигурации

- Дополняются стандартные разделы и значения по умолчанию текущей версии.
- Нормализуются пробелы в `server.addr`, `acme.addr`, удаляются завершающие слэши в `security.public_url`, `acme.base_url`, `log.level`, `log.format`, `log.system.level`, `plugins.repo.channel` приводятся к нижнему регистру, `server.trusted_proxies` дедуплицируется.
- Проверяются риски: ACME без фиксированного адреса, репозиторий плагинов без открытого ключа, доступ плагинов развёртывания к ключам, слишком короткие ключи; при сбое проверки исходный файл не перезаписывается, а редактирование YAML сохраняет комментарии и порядок полей.

## Параметры конфигурации

```yaml
upgrade:
  auto: true              # автоматически выполнять миграцию унаследованных данных при запуске
  auto_optimize: true     # выполнять недорогую оптимизацию при запуске; без VACUUM
  vacuum: true            # разрешить VACUUM при ручной оптимизации в /upgrade
  program:
    enabled: true
    repo: "AXmishell/LACTSSL"
    channel: stable
    check_interval_hours: 6
    max_download_mb: 128
    public_key: ""
    # официальные сборки встраивают открытый ключ; самостоятельные сборки без него отклоняют онлайн-обновление, неподписанные пакеты разрешены только в контролируемой среде
    allow_unsigned: false
    token: ""
```

После отключения `upgrade.auto` журнал запуска сообщит о данных, ожидающих миграции, но сервис продолжит запуск. В этом случае как можно скорее выполните миграцию вручную в `/upgrade`, иначе новый код может читать старый формат; исторические системные журналы не отображаются на вкладке «Журнал → Системный журнал» до завершения объединения журналов.

## API

Инструмент обновления использует существующий сеанс входа; интерфейсы расположены в `/api`:

| Интерфейс | Метод | Права | Описание |
| --- | --- | --- | --- |
| `/upgrade` | GET | `upgrade:read` | Состояние предварительной проверки |
| `/upgrade/run` | POST | `upgrade:write` | Миграция, оптимизация конфигурации и базы |
| `/upgrade/optimize` | POST | `upgrade:write` | Только оптимизация конфигурации и базы |
| `/upgrade/database` | GET | `upgrade:read` | Текущий бэкенд и ход переключения |
| `/upgrade/database/test` | POST | `upgrade:read` | Проверка подключения и пустой базы |
| `/upgrade/database/preflight` | POST | `upgrade:read` | Предварительная проверка переключения |
| `/upgrade/database/convert` | POST | `upgrade:write` | Запуск переключения (нужна повторная аутентификация) |
| `/upgrade/database/convert` | GET | `upgrade:read` | Ход переключения |
| `/upgrade/database/rollback` | POST | `upgrade:write` | Обратное переключение на прежний бэкенд (незавершённое переключение отменяется) |
| `/upgrade/program` | GET | `upgrade:read` | Состояние обновления программы |
| `/upgrade/program/check` | POST | `upgrade:write` | Немедленный запрос GitHub Release |
| `/upgrade/program/apply` | POST | `upgrade:write` | Скачивание и установка версии; `/upgrade/program/restart` перезапускает сервис |

Тело запроса может содержать `vacuum`, `analyze`, `config`, `optimize`; для записи достаточно сеанса или ключа API с нужными правами.

- [ ] Резервная копия создана, пароль восстановления проверен.
- [ ] Подтверждено дисковое пространство (копия + временное для VACUUM).
- [ ] Подготовлен бинарник или тег образа старой версии.
- [ ] Пакетные задачи и триггеры приостановлены, обновление и проверка завершены; затем задачи возобновлены, записаны заявка, версия, время и результат.
