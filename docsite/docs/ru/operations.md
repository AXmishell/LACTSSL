# Руководство по эксплуатации

Этот документ предназначен для дежурных и эксплуатационных команд, отвечающих за повседневную работу LACTSSL, и охватывает резервное копирование и восстановление, мониторинг и оповещения, поддержание ёмкости, изменения и обновления, а также реагирование на сбои. Цель — сделать сервис передаваемым, проверяемым при аудите и восстанавливаемым после сбоя.

## 1. Цели обслуживания и ответственность

LACTSSL не предоставляет SLA. Предприятие должно определить внутри себя:

| Пункт | Рекомендуемое определение |
| --- | --- |
| Уровень обслуживания | Выпуск и развёртывание сертификатов как критически важная вспомогательная система либо классификация по влиянию на бизнес |
| Доступное время | Соответствует доступности зависимых DNS, CA, обратного прокси и целей развёртывания |
| RPO | Резервное копирование не реже раза в день; для критичных сред можно сократить до часового уровня |
| RTO | По результатам учений «подготовка хоста + восстановление + проверка запуска» |
| Окно изменений | Вне периодов массового истечения сертификатов и пиковой нагрузки |
| Реакция на оповещения | Реакция на сбой задачи или аномалию сертификата в течение 15–30 минут (по регламенту предприятия) |

Не считайте «живость процесса» LACTSSL доступностью бизнеса. Реальная доступность бизнеса также зависит от DNS API, CA, целей развёртывания и цепочек уведомлений.

## 2. Резервное копирование и восстановление

### 2.1 Область резервного копирования

Необходимо одновременно создавать резервные копии:

1. `config.yaml` (или файла, указанного в `-config`)
2. всего каталога `data/`

`data/` содержит как минимум `lactssl.db`; во время работы также могут присутствовать `lactssl.db-wal` и `lactssl.db-shm`. База данных, плагины, журналы, архивы журналов и резервные копии обновлений находятся в `data/`.

Примечание: ZIP, создаваемый кнопкой «Скачать резервную копию» в интерфейсе, **не включает** архивы журналов `data/archives/logs/`. Архивные файлы столь же чувствительны, как и база данных, поэтому их нужно отдельно копировать или скачивать на офлайн-носитель; при резервном копировании всего `data/` командой они включаются.

Резервное копирование только базы данных приведёт к потере `salt`, и зашифрованные учётные данные станут нерасшифровываемыми; резервное копирование только конфигурации приведёт к потере бизнес-данных. Оба компонента должны дополнять друг друга.

### 2.2 Зашифрованная резервная копия через интерфейс (рекомендуется)

«Системные настройки → Резервное копирование и восстановление» предоставляет онлайн-операции:

- **Скачать резервную копию**: создаёт ZIP, содержащий снимок базы данных (для SQLite — файловый снимок, для PostgreSQL — нативный формат Go ZIP + COPY, для MySQL — нативный SQL), текущий `config.yaml` и информацию о версии `manifest.json`. Резервное копирование и восстановление PostgreSQL/MySQL выполняются напрямую на Go и не зависят от клиентов `pg_dump`/`pg_restore`/`mysqldump`/`mysql`.
- Перед скачиванием нужно повторно ввести пароль текущей учётной записи; при включённом TOTP также требуется динамический код проверки.
- Пароль шифрования резервной копии независим от пароля учётной записи и должен содержать не менее 12 символов.
- Содержимое резервной копии шифруется с помощью PBKDF2-HMAC-SHA256 (600 000 итераций) + AES-256-GCM; при восстановлении необходимо ввести тот же пароль.
- При утере пароля восстановить эту резервную копию будет невозможно.

Рекомендации:

- Храните файлы резервных копий на отдельном носителе или в объектном хранилище, не оставляйте их в `data/`.
- Храните пароль резервной копии в корпоративном менеджере паролей отдельно от файлов резервных копий.
- Записывайте время создания резервной копии, размер, контрольную сумму и место хранения.
- Храните резервные копии не менее 7–30 дней; для критичных сред продлевайте срок согласно требованиям соответствия.

### 2.3 Резервное копирование командой

Если нужна резервная копия на уровне файлов, сначала остановите сервис, затем копируйте, чтобы SQLite находился в согласованном состоянии:

```bash
# Docker
docker compose stop

# или остановите службу systemd
sudo systemctl stop lactssl

tar czf lactssl-backup-$(date +%F).tar.gz config.yaml data
chmod 600 lactssl-backup-*.tar.gz
```

Если остановка невозможна, отдайте предпочтение зашифрованной резервной копии через интерфейс; прямое копирование работающего SQLite может дать несогласованный снимок.

### 2.4 Восстановление

#### Восстановление через интерфейс

1. Загрузите ZIP-архив резервной копии или отдельный файл `.db`.
2. Введите текущий пароль для подтверждения; для зашифрованной резервной копии также введите пароль расшифровки.
3. Сервис запишет восстановленные данные в `data/restore-pending/` и автоматически перезапустится.
4. При развёртывании в Docker контейнер поднимается автоматически благодаря `restart: unless-stopped`; при прямом запуске бинарника перезапуск нужно выполнить самостоятельно.
5. Войдите с административной учётной записью из резервной копии.

#### Ручное восстановление

1. Остановите сервис.
2. Верните `config.yaml` и `data/` из резервной копии на исходное место.
3. Проверьте права: файл конфигурации `0600`, каталог данных `0700`, владелец — пользователь, от имени которого работает сервис.
4. Запустите сервис.
5. Проверьте защищённую точку входа, вход администратора, сертификаты, задачи и плагины.

#### Примечания по восстановлению

- После восстановления входите с административной учётной записью из резервной копии.
- По умолчанию сохранение сеансов включено, поэтому перезапуск сохраняет сеансы. При `security.session_persistence: false` каждый запуск очищает сеансы и ротирует подключ подписи JWT.
- Если в резервной копии `config.yaml` использует другой `jwt_secret`, старые токены не пройдут проверку.
- Если используется другой `salt`, зашифрованные учётные данные в базе данных можно расшифровать только с соответствующей конфигурацией; поэтому рекомендуется всегда восстанавливаться из полной ZIP-резервной копии.
- Если защищённая точка входа в резервной копии отличается от текущей, посмотрите новую точку входа в журнале запуска.
- Если восстановить только базу данных и потерять `salt` из `config.yaml`, зашифрованные учётные данные DNS, развёртывания и уведомлений станут нерасшифровываемыми, и их придётся ввести заново.

### 2.5 Учения по восстановлению

Не реже одного раза в квартал:

- [ ] Восстановите последнюю резервную копию в изолированной среде.
- [ ] Проверьте вход администратора, TOTP/ключи доступа и почту восстановления.
- [ ] Проверьте список сертификатов, задачи, учётные данные развёртывания и каналы уведомлений.
- [ ] Запустите тестовую задачу и разверните её на цель, не относящуюся к продуктивной среде.
- [ ] Запишите фактический RTO, проблемы и направления улучшений.
- [ ] Убедитесь, что пароль резервной копии по-прежнему хранится у уполномоченного лица.

## 3. Мониторинг и оповещения

### 3.1 Сигналы мониторинга

| Сигнал | Способ сбора | Рекомендуемый порог/действие |
| --- | --- | --- |
| Живость процесса | Проверка TCP-порта | Раз в 30–60 секунд; оповещение после 3 последовательных сбоев |
| Работоспособность аутентификации | `GET /api/status` + ключ API с `system:read` | Раз в 1–5 минут; оповещение при ответе не 200 или высокой задержке |
| Сбой задачи | Журнал операций или уведомление | Оповещать при любом сбое, различая DNS/CA/развёртывание/уведомления |
| Приближение срока действия сертификата | Панель мониторинга, мониторинг сайтов | Напоминания по уровням 30/14/7 дней |
| Сбой развёртывания | Записи развёртывания/уведомления | Немедленное оповещение; проверьте целевую систему и команду перезагрузки |
| Диск | Мониторинг хоста/платформы | Предупреждение при использовании > 80 %, оповещение при > 90 % |
| Резервное копирование | Задача резервного копирования/проверка файлов | Оповещение при сбое или превышении интервала без резервной копии |
| HTTP 5xx | Журнал обратного прокси | Порог задаётся относительно базовой линии |
| Аномальный вход | Журнал операций/системный журнал | Оповещение при многократных сбоях и подозрительных исходных IP |

### 3.2 Маршрутизация оповещений

- Сбои задач, аномалии сертификатов и сбои развёртывания направляются в канал эксплуатационного дежурства.
- Инциденты безопасности (аномальный вход, зондирование точки входа, сбой проверки плагина) направляются в канал безопасности.
- Сбои резервного копирования и нехватка дискового пространства направляются в канал платформы.
- Не отправляйте тестовые уведомления в продуктивную группу дежурства; используйте отдельный канал.

Доступность каналов уведомлений определяется внешними сервисами; рекомендуется настроить как минимум два независимых канала (например, электронная почта + корпоративный мессенджер), чтобы избежать единой точки отказа.

### 3.3 Чего не следует мониторить

- Не используйте голый `/` или `/login` для анонимной проверки работоспособности: без прохождения защищённой точки входа будет возвращаться 404, и это ожидаемое поведение.
- Не записывайте пароль администратора или долгоживущий ключ API с полными правами в систему мониторинга.
- Не помещайте закрытые ключи сертификатов или пароли резервных копий в содержимое оповещений.

## 4. Повседневное обслуживание

### 4.1 Ежедневно

- Проверяйте сбои задач, сбои развёртывания и аномалии мониторинга сайтов.
- Убедитесь, что на панели сроков действия сертификатов нет новых элементов высокого риска.
- Проверяйте, создаются ли резервные копии по расписанию.

### 4.2 Еженедельно

- Проверяйте, корректно ли планируются задачи автоматического продления.
- Просматривайте ошибки, ограничения скорости и аномальные входы в системном журнале.
- Сверяйте добавленные и отключённые ключи API и учётные данные.

### 4.3 Ежемесячно

- Проверяйте диск, размер базы данных, WAL и хранение журналов.
- Проверяйте версии плагинов и бюллетени безопасности.
- Выборочно проверяйте журнал операций и записи об изменениях.
- Проверяйте каналы уведомлений.

### 4.4 Ежеквартально

- Проведите учения по восстановлению из резервной копии.
- Пересмотрите административную учётную запись, почту восстановления, TOTP/ключи доступа.
- Пересмотрите права и сроки действия ключей API.
- Оцените окно обновления и план отката.

## 5. Ёмкость и очистка

### 5.1 Ёмкость, за которой нужно следить

| Пункт | Источник роста | Обработка |
| --- | --- | --- |
| SQLite | Сертификаты, журналы задач, журнал операций, системный журнал, заказы ACME | Очистка исторических данных, оптимизация базы данных, архивирование журналов |
| Архивы журналов | NDJSON.gz и манифест в `data/archives/logs/` | Периодически переносите во внешнее хранилище; при необходимости удаляйте в «Журнал → Архивы» |
| WAL | Длительная работа, частые записи | `wal_checkpoint(TRUNCATE)` выполняется инструментом обновления/оптимизации |
| Плагины | Установка и обновление накапливают старые файлы | Удаляйте неиспользуемые плагины, удаляйте старые helper |
| Резервные копии обновлений | Снимки миграции, старые бинарники | Очищайте согласно политике хранения |
| Хранилище резервных копий | Ежедневные и еженедельные резервные копии | Настройте хранение и копии в другом месте |

### 5.2 Точки очистки

- **Управление сертификатами → Очистка одним нажатием**: фильтрация по статусу, давности истечения/отзыва, времени выпуска, домену, центру сертификации и источнику; можно сохранить последний сертификат каждой задачи. После очистки ссылки на сертификаты в связанных задачах будут очищены.
- **Диагностика ACME → Очистка**: очистка недействительных заказов и учётных записей по конечной точке, статусу и времени неиспользования; очистка учётной записи удаляет исторические заказы, но не влияет на уже выпущенные сертификаты.
- **Журнал → Журнал операций/системный журнал → Очистить**: при включённом архивировании данные сначала записываются в `data/archives/logs/`, затем удаляются из базы данных; при сбое архивирования удаление будет отклонено. Действие очистки записывается в журнал операций.
- **Журнал → Архивы**: просмотр, скачивание или удаление архивных файлов. По умолчанию архивы хранятся бессрочно; если настроены `archive.retention_days` или `archive.max_total_mb`, задача обслуживания очищает их согласно политике.
- **Обновление/оптимизация**: выполняйте оптимизацию базы данных в периоды низкой нагрузки; `VACUUM` на короткое время монопольно захватывает базу данных и перезаписывает файл, поэтому необходимо зарезервировать дисковое пространство.

### 5.3 Обслуживание базы данных

- Каждые 6 часов сервис выполняет обслуживающую очистку; на странице журналов можно убедиться, работает ли планировщик.
- При первом запуске новой версии автоматически выполняется миграция исторических данных, а в `data/upgrade-backups/` создаётся снимок перед миграцией.
- Если нужно освободить дисковое пространство, в период низкой нагрузки откройте `/upgrade` и выполните «Только оптимизация базы данных и конфигурации» с включённым VACUUM.
- Перед выполнением убедитесь в наличии работоспособной резервной копии и достаточного дискового пространства; сбой `VACUUM` возвращается как предупреждение и не влияет на дальнейшую работу сервиса.

## 6. Версии и выпуски

### 6.1 Идентификация версии

- Номер версии имеет единственный источник — git tag; репозиторий не поддерживает файл `VERSION`.
- При локальной сборке версия выводится из `git describe --tags --always --dirty` с удалением префикса `v`.
- Сборочный скрипт внедряет версию через `-ldflags -X 'lactssl/internal/api.Version=...'`.
- Версию сборки, время сборки и архитектуру можно посмотреть в «Настройки → О программе».
- При `go run` или отладочной сборке отображается `dev`.

### 6.2 Каналы выпуска

- Теги стабильной версии включают `latest`, `<version>`, `<major>.<minor>`, `<major>`.
- Предварительные версии публикуют только полный тег версии и не перезаписывают `latest`.
- В продуктивной среде закрепляйте конкретную версию и не используйте `latest` для длительной работы, поскольку его нельзя отследить.

### 6.3 Артефакты выпуска

В рамках Release собираются бинарники для Linux/macOS/Windows, `checksums.txt` и образы `linux/amd64`, `linux/arm64`. Архив содержит бинарник, `README.md`, `LICENSE` и `config.yaml.example`.

Подробности процесса выпуска, подписи и локальной сборки см. в разделе [Разработка расширений: исходный код и сборка](development.md).

## 7. Обновление и изменения

Перед обновлением:

1. Прочитайте описание изменений и миграции целевой версии.
2. Создайте резервную копию `config.yaml` и `data/`.
3. Проверьте ключевые цепочки в среде предварительного развёртывания (выпуск, развёртывание, уведомления, API).
4. Убедитесь в наличии версии для отката и шагов отката.
5. Выберите период низкой нагрузки и уведомите заинтересованные стороны.

Docker:

```bash
docker compose pull
docker compose up -d
```

Бинарник:

```bash
sudo systemctl stop lactssl
sudo cp lactssl /opt/lactssl/lactssl
sudo chown lactssl:lactssl /opt/lactssl/lactssl
sudo systemctl start lactssl
```

После обновления:

- Проверьте в журнале сообщение «Обновление формата данных завершено».
- Войдите в `/upgrade` и убедитесь в состоянии шагов.
- Проверьте сертификаты, задачи, развёртывание, уведомления и API.
- Наблюдайте за одним циклом планирования (не менее 30 секунд) и одним выполнением задачи.

Полное описание миграции, отката и обновления программы см. в разделе [Обновление и изменения](upgrade.md).

## 8. Реагирование на сбои

### 8.1 Уровни

| Уровень | Пример | Цель |
| --- | --- | --- |
| P1 | Недоступна административная точка входа; невозможно массово продлить сертификаты; утечка закрытого ключа | Немедленная реакция, запуск аварийного режима |
| P2 | Сбой отдельной задачи; аномалия цели развёртывания; недоступен канал уведомлений | Реакция в течение 30 минут |
| P3 | Ложное срабатывание отдельного мониторинга; аномалия журнала; проблема некритичного плагина | Обработка в рабочее время |

### 8.2 Общие шаги

1. **Определите масштаб влияния**: какие сертификаты, задачи, цели развёртывания и бизнес-системы затронуты.
2. **Сохраните картину**: не очищайте журналы; запишите время, идентификатор запроса и текст ошибки.
3. **Проверьте зависимости**: DNS API, CA, сеть, обратный прокси, целевые системы, SMTP/IM.
4. **Изолируйте изменения**: приостановите связанные задачи, чтобы избежать повторных сбоев или перезаписи сертификатов.
5. **Восстановите сервис**: исправьте зависимость или откатите изменение; при необходимости восстановитесь из резервной копии.
6. **Проверьте**: повторно запустите задачу, проверьте сертификаты, развёртывание и уведомления.
7. **Проведите разбор**: запишите первопричину, хронологию, направления улучшений и ответственных.

Конкретные симптомы и команды см. в разделе [Мониторинг и устранение неполадок](troubleshooting.md).
