# Руководство по эксплуатации

Документ предназначен для разработчиков, развёртывающих и сопровождающих LACTSSL: резервное копирование и восстановление, мониторинг, ёмкость, изменения и реагирование на сбои. Цель — сделать сервис передаваемым, проверяемым при аудите и восстанавливаемым после сбоя.

## Цели обслуживания

Перед развёртыванием определите:

| Пункт | Рекомендуемое определение |
| --- | --- |
| Доступное время | Соответствует DNS, CA, прокси и целям развёртывания |
| RPO | Резервное копирование не реже раза в день; для критичных сред — до часового уровня |
| RTO | По результатам учений «подготовка хоста + восстановление + проверка запуска» |
| Окно изменений | Вне массового истечения сертификатов и пиковой нагрузки |
| Реакция на оповещения | 15–30 минут на сбой задачи или аномалию сертификата |

«Живость процесса» не равна доступности сервиса: она также зависит от DNS API, CA, целей развёртывания и цепочек уведомлений.

## Резервное копирование и восстановление

### Область резервного копирования

Копируйте одновременно `config.yaml` (или файл из `-config`) и весь каталог `data/`.

`data/` содержит как минимум `lactssl.db`, а во время работы также `lactssl.db-wal` и `lactssl.db-shm`; в нём находятся плагины, журналы, архивы журналов и резервные копии обновлений.

ZIP из кнопки «Скачать резервную копию» **не включает** архивы `data/archives/logs/`; они так же чувствительны, как база, поэтому копируйте их отдельно на офлайн-носитель (при копировании всего `data/` командой они включаются). Копия только базы приведёт к потере `salt` и нерасшифровываемым учётным данным, копия только конфигурации — к потере данных приложения.

### Зашифрованная резервная копия через интерфейс (рекомендуется)

«Системные настройки → Резервное копирование и восстановление» предоставляет онлайн-операции:

- **Скачать резервную копию**: ZIP со снимком базы (SQLite — файловый снимок, PostgreSQL — нативный Go ZIP + COPY, MySQL — нативный SQL), текущим `config.yaml` и `manifest.json`. PostgreSQL/MySQL обрабатываются на Go без `pg_dump`/`pg_restore`/`mysqldump`/`mysql`.
- Перед скачиванием повторно введите пароль учётной записи; при включённом TOTP также нужен динамический код. Пароль шифрования независим от пароля учётной записи, содержит не менее 12 символов, а содержимое шифруется PBKDF2-HMAC-SHA256 (600 000 итераций) + AES-256-GCM. При утере пароля копия невосстановима.

Рекомендации:

- Храните копии на отдельном носителе или в объектном хранилище, не в `data/`, а пароль — в менеджере паролей отдельно от файлов; записывайте время, размер, контрольную сумму и место хранения, храните копии 7–30 дней (для критичных сред — дольше).

### Резервное копирование командой

Для копии на уровне файлов сначала остановите сервис, чтобы SQLite был согласован:

```bash
# Docker
docker compose stop

# или остановите службу systemd
sudo systemctl stop lactssl

tar czf lactssl-backup-$(date +%F).tar.gz config.yaml data
chmod 600 lactssl-backup-*.tar.gz
```

Если остановка невозможна, используйте зашифрованную копию через интерфейс: прямое копирование работающего SQLite может дать несогласованный снимок.

### Восстановление

#### Восстановление через интерфейс

1. Загрузите ZIP-архив или отдельный файл `.db` и введите текущий пароль, а для зашифрованной копии — пароль расшифровки.
3. Сервис запишет данные в `data/restore-pending/` и перезапустится; в Docker контейнер поднимется благодаря `restart: unless-stopped`, при прямом запуске бинарника перезапустите вручную.
4. Войдите с административной учётной записью из резервной копии.

#### Ручное восстановление

1. Остановите сервис.
2. Верните `config.yaml` и `data/` на исходное место.
3. Проверьте права (конфигурация `0600`, каталог данных `0700`, владелец — пользователь сервиса), запустите сервис и проверьте защищённую точку входа, вход администратора, сертификаты, задачи и плагины.

#### Примечания по восстановлению

- Входите с административной учётной записью из резервной копии.
- По умолчанию сохранение сеансов включено, и перезапуск сохраняет вход; при `security.session_persistence: false` каждый запуск очищает сеансы и ротирует ключ подписи JWT, а другой `jwt_secret` делает старые токены недействительными. Другой `salt` делает зашифрованные учётные данные нерасшифровываемыми, поэтому восстанавливайтесь из полной ZIP-копии; при восстановлении только базы без `salt` учётные данные DNS, развёртывания и уведомлений придётся ввести заново.
- Если защищённая точка входа отличается от текущей, посмотрите новую в журнале запуска.

### Учения по восстановлению

Не реже раза в квартал:

- [ ] Восстановите последнюю копию в изолированной среде и проверьте вход администратора, TOTP/ключи доступа и почту восстановления.
- [ ] Проверьте сертификаты, задачи, учётные данные развёртывания и каналы уведомлений.
- [ ] Запустите тестовую задачу и разверните её на непродуктивную цель; запишите фактический RTO, проблемы и убедитесь, что пароль копии хранится у уполномоченного лица.

## Мониторинг и оповещения

### Сигналы мониторинга

| Сигнал | Способ сбора | Рекомендуемый порог/действие |
| --- | --- | --- |
| Живость процесса | Проверка TCP-порта | Раз в 30–60 секунд; оповещение после 3 сбоев подряд |
| Работоспособность аутентификации | `GET /api/status` + ключ с `system:read` | Раз в 1–5 минут; оповещение при ответе не 200 или высокой задержке |
| Сбой задачи | Журнал операций или уведомление | При любом сбое, с различением DNS/CA/развёртывания/уведомлений |
| Срок действия сертификата | Панель мониторинга, мониторинг сайтов | Напоминания 30/14/7 дней |
| Сбой развёртывания | Записи развёртывания/уведомления | Немедленно; проверьте цель и команду перезагрузки |
| Диск | Мониторинг хоста/платформы | Предупреждение > 80 %, оповещение > 90 % |
| Резервное копирование | Задача копирования/проверка файлов | При сбое или превышении интервала без копии |
| Аномальный вход | Журнал операций/системный журнал, HTTP 5xx прокси | При многократных сбоях, 5xx выше базовой линии и подозрительных IP |

### Маршрутизация оповещений

- Сбои задач, аномалии сертификатов и развёртывания — в канал эксплуатационного дежурства; инциденты безопасности (аномальный вход, зондирование точки входа, сбой проверки плагина) — в канал безопасности.
- Сбои копирования и нехватка диска — в канал платформы; тестовые уведомления не отправляйте в продуктивную группу.
- Настройте минимум два независимых канала (например, почта + IM), чтобы избежать единой точки отказа.

### Чего не следует мониторить

- Не проверяйте анонимно голый `/` или `/login`: без защищённой точки входа вернётся 404, это ожидаемо.
- Не записывайте в систему мониторинга пароль администратора или долгоживущий ключ API с полными правами и не помещайте закрытые ключи и пароли копий в оповещения.

## Повседневное обслуживание

### Ежедневно

- Проверяйте сбои задач, развёртывания и мониторинга сайтов, новые риски на панели сроков действия и создание резервных копий по расписанию.

### Еженедельно

- Проверяйте планирование автопродления, ошибки, ограничения скорости и аномальные входы, а также изменения ключей API и учётных данных.

### Ежемесячно

- Проверяйте диск, размер базы, WAL, хранение журналов, версии плагинов, бюллетени безопасности, выборочно журнал операций и каналы уведомлений.

### Ежеквартально

- Проведите учения по восстановлению и пересмотрите административную учётную запись, почту восстановления, TOTP/ключи доступа, права и сроки ключей API, окно обновления и план отката.

## Ёмкость и очистка

### Ёмкость, за которой нужно следить

| Пункт | Источник роста | Обработка |
| --- | --- | --- |
| SQLite | Сертификаты, журналы, заказы ACME | Очистка истории, оптимизация, архивирование |
| Архивы журналов | NDJSON.gz и манифест в `data/archives/logs/` | Переносите во внешнее хранилище, удаляйте в «Журнал → Архивы» |
| WAL | Длительная работа, частые записи | `wal_checkpoint(TRUNCATE)` в инструменте оптимизации |
| Плагины | Накопление старых helper | Удаляйте неиспользуемые плагины и helper |
| Резервные копии обновлений и хранилище копий | Снимки миграции, старые бинарники, ежедневные копии | Очищайте по политике, храните копии в другом месте |

### Точки очистки

- **Управление сертификатами → Очистка одним нажатием**: фильтры по статусу, истечению/отзыву, времени выпуска, домену, CA и источнику; последний сертификат каждой задачи можно сохранить, ссылки в задачах после очистки очищаются.
- **Диагностика ACME → Очистка**: недействительные заказы и учётные записи по конечной точке, статусу и времени неиспользования; выпущенные сертификаты не затрагиваются.
- **Журнал → Журнал операций/системный журнал → Очистить**: при включённом архивировании данные сначала пишутся в `data/archives/logs/`, а при сбое архивирования удаление отклоняется; действие фиксируется в журнале операций.
- **Журнал → Архивы**: просмотр, скачивание и удаление; по умолчанию архивы хранятся бессрочно, политику задают `archive.retention_days` и `archive.max_total_mb`.

### Обслуживание базы данных

- Каждые 6 часов сервис выполняет обслуживающую очистку; работу планировщика видно на странице журналов, а снимок перед миграцией новой версии создаётся в `data/upgrade-backups/`.
- Для освобождения диска в период низкой нагрузки откройте `/upgrade` и выполните «Только оптимизация базы данных и конфигурации» с VACUUM; убедитесь в рабочей резервной копии и запасе диска, сбой `VACUUM` вернётся предупреждением и не повлияет на работу.

## Версии и выпуски

### Идентификация версии

- Единственный источник версии — git tag (файл `VERSION` не поддерживается); при локальной сборке версия берётся из `git describe --tags --always --dirty` без префикса `v` и внедряется через `-ldflags -X 'lactssl/internal/api.Version=...'`.
- Версия, время сборки и архитектуру показывает «Настройки → О программе»; при `go run` или отладочной сборке отображается `dev`.

### Каналы выпуска

- Стабильные теги включают `latest`, `<version>`, `<major>.<minor>`, `<major>`; предварительные версии публикуют только полный тег и не перезаписывают `latest`, а в продуктивной среде закрепляйте конкретную версию — `latest` нельзя отследить.

### Артефакты выпуска

Release содержит бинарники для Linux/macOS/Windows, `checksums.txt` и образы `linux/amd64`, `linux/arm64`; архив включает бинарник, `README.md`, `LICENSE` и `config.yaml.example`. Подробности — в разделе [Разработка расширений](development.md).

## Обновление и изменения

Перед обновлением:

1. Прочитайте описание изменений и миграции целевой версии и создайте резервную копию `config.yaml` и `data/`.
2. Проверьте выпуск, развёртывание, уведомления и API в среде предварительного развёртывания; убедитесь в наличии версии и шагов отката, выберите период низкой нагрузки.

Docker:

```bash
docker compose pull
docker compose up -d
```

Бинарник:

```bash
sudo systemctl stop lactssl
sudo cp lactssl /opt/lactssl/lactssl
sudo chown lactssl:lactssl /opt/lactssl/lactssl
sudo systemctl start lactssl
```

После обновления проверьте сообщение «Обновление формата данных завершено», состояние шагов в `/upgrade`, сертификаты, задачи, развёртывание, уведомления и API, затем наблюдайте один цикл планирования (не менее 30 секунд) и одно выполнение задачи. Полное описание миграции и отката — в разделе [Обновление и изменения](upgrade.md).

## Реагирование на сбои

### Уровни

| Уровень | Пример | Цель |
| --- | --- | --- |
| P1 | Недоступна административная точка входа; невозможно массово продлить сертификаты; утечка ключа | Немедленная реакция, аварийный режим |
| P2 | Сбой отдельной задачи; аномалия цели развёртывания; недоступен канал уведомлений | Реакция в течение 30 минут |
| P3 | Ложное срабатывание мониторинга; аномалия журнала; некритичный плагин | Обработка в рабочее время |

### Общие шаги

1. **Определите масштаб**: какие сертификаты, задачи, цели и целевые системы затронуты.
2. **Сохраните картину**: не очищайте журналы; запишите время, идентификатор запроса и текст ошибки, проверьте зависимости (DNS API, CA, сеть, прокси, цели, SMTP/IM).
3. **Изолируйте изменения**: приостановите связанные задачи, чтобы избежать повторных сбоев и перезаписи сертификатов.
4. **Восстановите и проверьте**: исправьте зависимость или откатите изменение, при необходимости восстановитесь из копии и повторно запустите задачу.
5. **Проведите разбор**: запишите первопричину, хронологию, улучшения и ответственных.

Симптомы и команды — в разделе [Мониторинг и устранение неполадок](troubleshooting.md).
