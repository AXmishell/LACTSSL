# 運維手冊

本文面向部署和維護 LACTSSL 的開發者，覆蓋備份恢復、監控告警、容量維護、變更升級和故障回應。

## 服務目標

部署前應明確：

| 專案 | 建議定義 |
| --- | --- |
| 可用時間 | 與依賴的 DNS、CA、反向代理和部署目標一致 |
| RPO | 至少每日一次備份；關鍵環境可縮短到小時級 |
| RTO | 以“準備主機 + 恢復 + 啟動驗證”演練結果為準 |
| 變更視窗 | 避開證書集中到期和發布高峰 |
| 告警回應 | 任務失敗/證書異常 15–30 分鐘內回應（按部署約定） |

不要把“程序存活”當成服務可用；真正的可用性還取決於 DNS API、CA、部署目標和通知鏈路。

## 備份與恢復

### 備份範圍

必須同時備份：

1. `config.yaml`（或 `-config` 指定的路徑）
2. 整個 `data/` 目錄

`data/` 包含資料庫（`lactssl.db` 及執行時的 `-wal`/`-shm`）、外掛、日誌歸檔和升級備份。介面「下載備份」生成的 ZIP **不包含** `data/archives/logs/`，需單獨複製到離線介質。只備份資料庫會丟失 `salt`，導致加密憑據無法解密；只備份配置會丟失應用資料，兩者必須配套。

### 介面加密備份（推薦）

「系統設定 → 備份與恢復」提供線上操作：

- **下載備份**：生成 ZIP，包含資料庫快照（SQLite 檔案快照、PostgreSQL 為 Go 原生 ZIP + COPY、MySQL 為原生 SQL）、當前 `config.yaml` 和 `manifest.json` 版本資訊，不依賴外部資料庫客戶端。
- 下載前需要重新輸入當前帳戶密碼；啟用 TOTP 時還需動態驗證碼。
- 備份加密密碼與帳戶密碼相互獨立，至少 12 位；內容使用 PBKDF2-HMAC-SHA256（600,000 次迭代）+ AES-256-GCM 加密，恢復時必須輸入同一密碼，遺失將無法恢復。
- 備份存到獨立介質或物件儲存，不要留在 `data/` 下；密碼存入密碼管理器，與備份檔案分離保管。
- 記錄備份時間、大小、校驗值和保管位置，至少保留 7–30 天，關鍵環境按需延長。

### 命令備份

需要檔案級備份時，先停止服務再複製，確保 SQLite 處於一致狀態：

```bash
# Docker
docker compose stop

# 或停止 systemd 服務
sudo systemctl stop lactssl

tar czf lactssl-backup-$(date +%F).tar.gz config.yaml data
chmod 600 lactssl-backup-*.tar.gz
```

無法停機時優先使用介面加密備份；直接複製執行中的 SQLite 可能得到不一致快照。

### 恢復

#### 介面恢復

1. 上傳 ZIP 備份包或單獨的 `.db` 檔案。
2. 輸入當前密碼確認；加密備份還需輸入備份解密密碼。
3. 服務會把恢復內容寫入 `data/restore-pending/` 並自動重啟（Docker 由 `restart: unless-stopped` 拉起，直接執行二進位制時需自行重啟），完成後使用備份中的管理員帳戶登入。

#### 手工恢復

1. 停止服務。
2. 將備份中的 `config.yaml` 與 `data/` 放回原位置。
3. 確認權限：配置檔案 `0600`，資料目錄 `0700`，屬主為服務執行使用者。
4. 啟動服務。
5. 檢查門禁入口、管理員登入、證書、任務和外掛。

#### 恢復注意事項

- 恢復後請使用備份中的管理員帳戶登入；門禁入口若變化，檢視啟動日誌。預設開啟會話保持，重啟不會清空會話；`security.session_persistence: false` 時每次啟動清空會話並輪換 JWT 子金鑰。
- 備份中的 `jwt_secret` 不同會使舊令牌失效；`salt` 不同則加密憑據只能在配套配置下解密，因此建議始終用完整 ZIP 恢復。

### 恢復演練

每季度至少一次：

- [ ] 在隔離環境恢復最近備份，驗證管理員登入、TOTP/通行金鑰和恢復郵箱。
- [ ] 驗證證書、任務、部署憑據和通知渠道，執行一條測試任務，記錄實際 RTO、問題和改進項，確認備份密碼仍由授權人持有。

## 監控與告警

### 監控訊號

| 訊號 | 採集方式 | 建議閾值/動作 |
| --- | --- | --- |
| 程序存活 | TCP 埠探測 | 30–60 秒一次，連續 3 次失敗告警 |
| 認證健康 | `GET /api/status` + `system:read` API 金鑰 | 1–5 分鐘一次，非 200 或高延遲告警 |
| 任務失敗 | 操作日誌或通知 | 失敗即告警，區分 DNS/CA/部署/通知 |
| 證書臨期 | 儀表盤、站點監控 | 30/14/7 天分級提醒 |
| 部署失敗 | 部署記錄/通知 | 立即告警，檢查目標系統和過載命令 |
| 磁碟 | 主機/平臺監控 | 使用率 > 80% 預警，> 90% 告警 |
| 備份 | 備份任務/檔案檢查 | 失敗或超過週期未備份告警 |
| HTTP 5xx | 反向代理日誌 | 按基線設定閾值 |
| 登入異常 | 操作日誌/系統日誌 | 多次失敗、異常來源 IP 告警 |

### 告警路由

- 任務失敗、證書異常、部署失敗進入運維告警渠道；備份失敗、磁碟不足進入平臺渠道。
- 安全事件（異常登入、入口探測、外掛校驗失敗）進入安全渠道，測試通知使用獨立頻道；建議至少配置兩個獨立通知渠道（如郵件 + IM），避免單點。

### 不要做的監控

- 不要用裸 `/` 或 `/login` 做匿名健康檢查：未透過門禁會返回 404，這是預期行為。
- 不要把管理員密碼、長期全權限 API 金鑰、證書私鑰或備份密碼寫進監控系統或告警內容。

## 日常維護

### 每日

- 檢視任務/部署失敗和站點監控異常，確認證書到期看板沒有新增高風險項，並檢查備份是否按計劃生成。

### 每週

- 檢查自動續期任務排程，檢視系統日誌中的錯誤、限流和異常登入，核對新增/停用的 API 金鑰和憑據。

### 每月

- 檢查磁碟、資料庫大小、WAL 和日誌保留，抽查操作日誌與變更記錄，檢查外掛版本和安全公告，驗證通知渠道。

### 每季度

- 完成備份恢復演練，複核管理員帳戶、恢復郵箱、TOTP/通行金鑰、API 金鑰權限和過期時間，並評估升級視窗和回滾方案。

## 容量與清理

### 需要關注的容量

| 專案 | 增長來源 | 處理 |
| --- | --- | --- |
| SQLite | 證書、任務日誌、操作日誌、系統日誌、ACME 訂單 | 清理歷史資料、最佳化資料庫、歸檔日誌 |
| 日誌歸檔 | `data/archives/logs/` 下的 NDJSON.gz 與 manifest | 定期轉存到外部儲存；必要時在「日誌 → 歸檔」刪除 |
| WAL | 長期執行、寫入頻繁 | `wal_checkpoint(TRUNCATE)` 由升級/最佳化工具執行 |
| 外掛 | 安裝/更新累積舊檔案 | 解除安裝不用外掛，刪除舊 helper |
| 升級備份 / 備份儲存 | 遷移快照、舊二進位制、每日/每週備份 | 按保留策略清理，設定異地副本 |

### 清理入口

- **證書管理 → 一鍵清理**：按狀態、過期/撤銷時長、簽發時間、網域、頒發機構、來源篩選；可保留每個任務最新證書，清理後相關任務的證書引用會被清空。**ACME 診斷 → 清理** 按端點、狀態和未使用時長清理失效訂單與帳戶；清理帳戶會刪除歷史訂單，但不影響已簽發證書。
- **日誌 → 操作日誌/系統日誌 → 清空**：啟用歸檔時先寫入 `data/archives/logs/`，再從資料庫刪除；歸檔失敗會拒絕刪除，清空動作會寫入操作日誌。歸檔預設永久保留，配置 `archive.retention_days` 或 `archive.max_total_mb` 後由維護任務清理。
- **升級/最佳化**：在低峰期執行資料庫最佳化；`VACUUM` 會短暫獨佔資料庫並重寫檔案，需預留磁碟空間。

### 資料庫維護

- 服務每 6 小時執行一次維護清理；新版本首次啟動會自動執行歷史遷移，並在 `data/upgrade-backups/` 生成遷移前快照。
- 需要回收磁碟空間時，在低峰期訪問 `/upgrade`，執行「僅最佳化資料庫與配置」並開啟 VACUUM；執行前確保有可用備份和足夠磁碟空間，`VACUUM` 失敗會作為警告返回。

## 版本與釋出

### 版本識別

- 版本號以 git tag 為唯一來源，倉庫不維護 `VERSION` 檔案；本地構建由 `git describe --tags --always --dirty` 推導並去掉 `v` 字首，透過 `-ldflags -X 'lactssl/internal/api.Version=...'` 注入。
- 可在「設定 → 關於」檢視構建版本、構建時間與架構；`go run` 或開發構建顯示 `dev`。

### 釋出通道

- 穩定版標籤包括 `latest`、`<version>`、`<major>.<minor>`、`<major>`；預釋出版本只推送完整版本標籤，不覆蓋 `latest`。生產固定到明確版本，不使用不可追溯的 `latest` 長期執行。

### 釋出產物

Release 會構建 Linux/macOS/Windows 二進位制、`checksums.txt` 和 `linux/amd64`、`linux/arm64` 映象。歸檔包含二進位制、`README.md`、`LICENSE` 和 `config.yaml.example`；釋出流程、簽名和本地構建細節見[擴充套件開發：原始碼與構建](development.md)。

## 升級與變更

升級前閱讀目標版本的變更與遷移說明，備份 `config.yaml` 與 `data/`，在預發環境驗證簽發、部署、通知和 API，確認回滾方案並選擇低峰期。

Docker：

```bash
docker compose pull
docker compose up -d
```

二進位制：

```bash
sudo systemctl stop lactssl
sudo cp lactssl /opt/lactssl/lactssl
sudo chown lactssl:lactssl /opt/lactssl/lactssl
sudo systemctl start lactssl
```

升級後檢視日誌中的“資料格式升級完成”，登入 `/upgrade` 確認步驟狀態，驗證證書、任務、部署、通知和 API，並觀察一個排程週期和一次任務執行。

完整遷移、回滾和程式升級說明見[升級與變更](upgrade.md)。

## 故障回應

### 分級

| 級別 | 示例 | 目標 |
| --- | --- | --- |
| P1 | 管理入口不可用；大量證書無法續期；私鑰洩露 | 立即回應，啟動應急 |
| P2 | 單個任務失敗；部署目標異常；通知渠道不可用 | 30 分鐘內回應 |
| P3 | 單個監控誤報；日誌異常；非關鍵外掛問題 | 工作時間內處理 |

### 通用步驟

1. **確認影響範圍**：哪些證書、任務、部署目標和目標系統受影響。
2. **保留現場**：不要清空日誌；記錄時間、請求 ID、錯誤資訊。
3. **檢查依賴**：DNS API、CA、網路、反向代理、目標系統、SMTP/IM。
4. **隔離變更**：暫停相關任務，避免重複失敗或覆蓋證書；修復依賴或回滾變更，必要時從備份恢復。
5. **驗證與覆盤**：重新執行任務並檢查證書、部署和通知，記錄根因、時間線、改進項和責任人。

具體症狀和命令見[監控與排障](troubleshooting.md)。
