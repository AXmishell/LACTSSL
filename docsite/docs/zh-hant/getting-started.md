# 快速上手與上線

本文面向第一次引入 LACTSSL 的團隊和個人使用者，目標是用最短路徑回答三個問題：**能不能滿足場景、需要哪些外部依賴、如何安全地上生產**。個人站點和小團隊可以直接跳到下面的快速路徑，不需要走完整的企業評估流程。

## 快速路徑：個人 / 小團隊

適用場景：個人部落格與站點、家庭實驗室、小團隊內部服務。你需要的只是**一臺能跑 Docker 的 Linux 主機（VPS、NAS 或小主機）、一個網域和 DNS API 憑據、一個部署目標**。

四步跑通，通常 30 分鐘內完成：

1. 按[安裝與啟動](install.md)用 Docker 啟動例項，透過啟動日誌中的門禁入口完成初始化。
2. 進入「外掛」頁重新整理索引，安裝一個 DNS 外掛；需要面板/CDN 等部署目標就再裝部署外掛，需要提醒就裝通知外掛。
3. 建立 DNS 帳戶 → 在「證書申請」建立任務，選擇公共 CA 和網域 → 新增「部署證書」節點（本地目錄、SSH 或面板）→ 可選新增通知節點。
4. 手動執行一次，確認證書檔案已更新且服務已過載；之後觀察一次自動續期或手動觸發續期驗證。

個人場景的最小安全基線：

- 用 HTTPS 網域訪問管理頁，並啟用 TOTP 或通行金鑰。
- 備份密碼與 `config.yaml` 分開保管；丟失 `salt` 後資料庫中的加密憑據無法解密。
- DNS API 使用專用子帳號，只授權需要的網域。

> 企業引入仍需按下面的 1–7 節完成適用性確認、試點和生產上線檢查表。

## 1. 先確認適用性

適合引入 LACTSSL 的典型條件：

- 有多個網域或內部服務需要統一管理 TLS 證書。
- 希望把簽發、部署、到期監控和通知放進一個可審計的控制台。
- 接受自託管單例項，能夠提供一臺 Linux 主機、一個資料目錄和一份備份策略。
- 有 DNS 服務商 API 憑據，或需要自建私有 CA / ACME 服務。
- 自動化場景可以透過 API 金鑰接入，而不是要求多使用者 RBAC 或企業 SSO。

不適合直接作為唯一平臺的情況：

- 要求多租戶隔離、組織架構、審批流或多使用者角色。
- 要求雙活叢集、跨機房自動故障切換或 HSM/KMS 託管私鑰。
- 要求產品自帶等保/ISO 認證證書，而不是由企業自身完成合規測評。

這些邊界不影響 LACTSSL 作為證書自動化元件使用，但需要在方案設計階段明確責任分工。

## 2. 評估前的準備清單

| 專案 | 需要確認的內容 | 責任角色 |
| --- | --- | --- |
| 主機 | Linux amd64/arm64；Docker Compose v2 或可執行靜態二進位制；磁碟與備份空間 | 平臺/運維 |
| 網域與 DNS | 試點網域、DNS 服務商、可建立 TXT 記錄的 API 憑據 | 網路/運維 |
| 入站訪問 | 管理網域、反向代理、TLS 證書、來源 IP 白名單 | 網路/安全 |
| 出站訪問 | DNS API、SMTP、Webhook、部署目標、監控目標的可達性 | 網路/安全 |
| 私鑰與憑據 | DNS/部署/通知憑據的保管人、輪換週期、最小權限帳號 | 安全 |
| 變更與備份 | 變更視窗、備份位置、恢復責任人、RPO/RTO 目標 | 運維 |
| 整合 | 需要接入的 CI/CD、CMDB、告警平臺和 API 權限 | 整合開發 |

建議在試點階段使用**獨立網域、獨立 DNS 子帳號、獨立通知頻道**，不要直接複用生產管理員憑據。

## 3. 30 分鐘試點

### 3.1 啟動例項

Docker 方式最適合評估：

```bash
git clone https://github.com/AXmishell/LACTSSL.git
cd LACTSSL
mkdir -p config data
cp config.yaml.example config/config.yaml && chmod 600 config/config.yaml
docker compose up -d
docker compose logs -f lactssl
```

倉庫預設沿用 1Panel 的 `1panel-network` 外部網路；不使用 1Panel 時刪除 `docker-compose.yml` 中服務下的 `networks` 和末尾的 `networks` 段，或先執行 `docker network create 1panel-network`。GHCR 映象從首個正式 Release 起可用，未釋出時可按[安裝與啟動](install.md)在本地構建。試點階段可以用 `http://127.0.0.1:8080` 訪問；涉及通行金鑰（WebAuthn）時必須使用 HTTPS 網域或 localhost。

### 3.2 完成初始化

啟動日誌會列印兩類一次性資訊：

1. **門禁入口**：形如 `http://127.0.0.1:8080/K7mQ2pX9vR4tY8nL6cWz/`。
2. **初始化令牌**：未初始化時列印，用於建立管理員、恢復備份等初始化操作。

透過門禁入口開啟頁面，按提示建立管理員帳戶。初始化完成後令牌立即失效；忘記入口時可在 `config.yaml` 中設定 `security.entry` 並重啟覆蓋。

### 3.3 安裝最小外掛集

主程式不內建 DNS、部署和通知外掛。進入「外掛」頁：

1. 確認外掛倉庫地址，點選「重新整理索引」。
2. 開啟「外掛市場」，至少安裝一個 DNS 外掛（如常用 DNS 包）、一個通知外掛。
3. 如需 SSH 以外的部署目標，再安裝部署外掛。
4. 在對應列表中啟用需要的服務商、部署目標或通知渠道。

離線環境可以把 `plugins.repo.url` 指向內部 `https://` 映象或 `file://` 索引，詳見[外掛治理](plugins.md)。

### 3.4 跑通一條完整鏈路

推薦用私有 CA 做第一條鏈路，不依賴公網 DNS：

1. 在「私有CA」生成一個根 CA（ECDSA P-256，有效期按試點需要）。
2. 在「證書申請」建立任務，簽發機構選擇該私有 CA，填寫測試網域。
3. 在任務流程中新增「部署證書」節點，選擇「本地目錄」，填寫證書/私鑰路徑和可選過載命令。
4. 新增「通知」節點，選擇已啟用的渠道，觸發時機選「始終」。
5. 手動執行任務，檢查證書、部署記錄和通知是否成功。

再補一條公網鏈路：建立 DNS 帳戶 → 選擇公共 CA → 用測試網域走 DNS-01 → 部署到目標 → 觀察自動續期時間。兩條鏈路都跑通後，再進入試點。

### 3.5 驗證關鍵運維動作

| 動作 | 驗證方式 | 透過標準 |
| --- | --- | --- |
| 備份 | 設定 → 備份與恢復 → 下載加密備份 | 能生成 ZIP，密碼可解密 |
| 恢復 | 在隔離例項匯入備份 | 帳戶、證書、任務和設定完整 |
| 日誌 | 操作日誌與系統日誌篩選/匯出 | 能看到初始化、任務和部署記錄 |
| API | 建立只讀金鑰呼叫 `/api/certificates` | 返回 200，越權介面返回 403 |
| 通知 | 傳送測試通知 | 目標頻道收到訊息 |
| 監控 | 新增一個外部站點 | 能讀取證書並顯示狀態 |

## 4. 試點範圍建議

試點不要追求“全量接入”，應覆蓋最能暴露問題的鏈路：

- 1–2 個真實業務網域，包含一個萬用字元或多網域證書。
- 1 個真實部署目標（SSH、面板、CDN 或 Webhook 中選一個）。
- 1 個內部服務場景（私有 CA 或 ACME 端點）。
- 1 個告警接收渠道，明確值班人和升級路徑。
- 1 個自動化呼叫方（CI/CD 或巡檢腳本），驗證 API 金鑰權限。

試點週期建議 1–2 周，至少觀察一次自動續期或手動續期，確認部署過載命令不會影響業務。

## 5. 生產上線檢查表

### 5.1 網路與訪問

- [ ] 管理入口只透過 HTTPS 反向代理暴露，代理後埠不直接對公網開放。
- [ ] 已配置 `server.trusted_proxies` 和 `security.public_url`。
- [ ] 門禁入口為隨機長字串，未使用 `admin`、`ssl` 等可猜測路徑。
- [ ] 管理入口配置來源 IP 白名單、VPN 或零信任訪問策略。
- [ ] 如啟用 ACME 服務端，使用獨立埠並限制來源；EAB 預設開啟。

### 5.2 身份與金鑰

- [ ] 管理員使用強密碼，並啟用 TOTP 或通行金鑰。
- [ ] 恢復郵箱由安全團隊控制，郵箱本身啟用多因素認證。
- [ ] 為每個自動化系統建立獨立 API 金鑰，按最小權限授權並設定過期時間。
- [ ] DNS、部署、通知憑據使用專用帳號，不使用個人帳號或全域性管理員金鑰。
- [ ] `config.yaml` 權限 `0600`，`data/` 權限 `0700`，屬主為服務執行使用者。

### 5.3 資料與恢復

- [ ] 已定義 RPO/RTO，並配置至少每日一次加密備份。
- [ ] 備份存放在獨立介質，訪問受控，恢復密碼單獨保管。
- [ ] 至少完成一次恢復演練，確認 `salt` 與資料庫配套。
- [ ] 已確認日誌保留期、匯出範圍和儲存容量。

### 5.4 執行與變更

- [ ] 明確服務責任人、告警接收人和變更視窗。
- [ ] 配置程序存活探測和證書到期/任務失敗告警。
- [ ] 固定映象或二進位制版本，不使用不可追溯的 `latest` 長期執行。
- [ ] 已閱讀[升級與變更](upgrade.md)，確認遷移與回滾步驟。
- [ ] 已完成[安全基線](security.md)中的高優先順序項。

## 6. 責任分工建議

| 職責 | 建議歸屬 | 說明 |
| --- | --- | --- |
| 主機、網路、反向代理 | 平臺/運維 | 保障可用性、入站出站策略和 TLS 終止 |
| LACTSSL 管理員帳戶 | 平臺/運維負責人 | 單帳戶，必須由崗位而非個人長期佔有 |
| DNS/部署/通知憑據 | 安全或對應系統負責人 | 專用帳號、定期輪換、最小權限 |
| API 金鑰 | 整合開發負責人 | 按系統發放，登記用途、權限和過期時間 |
| 備份與恢復演練 | 運維 | 備份密碼與恢復流程分離保管 |
| 合規證據 | 安全/審計 | 使用操作日誌、系統日誌和變更記錄 |

## 7. 常見試點失敗原因

- **把門禁入口當成安全邊界**：入口只是額外一層防護，不能替代 HTTPS、強密碼和網路訪問控制。
- **用個人 DNS 帳號做 API 憑據**：人員離職或開啟二次驗證後，自動續期會失敗。
- **部署過載命令未驗證**：證書檔案更新了，但 Nginx/面板沒有過載，業務仍使用舊證書。
- **只備份資料庫，不備份 `config.yaml`**：丟失 `salt` 後，資料庫中的加密憑據無法解密。
- **所有自動化共用一個全權限 API 金鑰**：一旦洩露，攻擊者可簽發、部署和匯出私鑰。
- **在容器內使用自升級**：重建容器後會回到映象版本；生產應透過映象標籤升級。
