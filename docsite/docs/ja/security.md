# セキュリティベースライン

本書は LACTSSL をデプロイ・統合する開発者向けに、セキュリティモデル、実装済みの制御、導入前のチェックリストを説明します。

## セキュリティモデルと信頼境界

LACTSSL は「セルフホストの単一インスタンス」として設計されています。

```text
[非信頼] インターネット/外部ネットワークのユーザー
    │ HTTPS（リバースプロキシで終端）
[境界] リバースプロキシ / WAF / ネットワーク ACL
    │ HTTP（ループバックまたは内部ネットワーク）
[信頼] LACTSSL プロセス
    ├─ 管理者セッション: 完全な制御と同等
    ├─ API キー: 権限スコープにより制限
    ├─ プライベート CA 秘密鍵: 暗号化してローカルデータベースに保存
    └─ プラグインのサブプロセス: サービスアカウントで実行され、信頼済みコードと見なす
[外部] DNS API / CA / SMTP / デプロイ先 / 通知チャネル
```

- **管理者セッションは完全な制御と同等**で、ローカルのデプロイコマンド実行、秘密鍵のエクスポート、バックアップからの復元を含みます。
- **API キーはマシン ID** で、自動化の権限を下げるためのものであり、マルチユーザー RBAC ではありません。
- **プラグインは信頼済みコード**です。デプロイプラグインは秘密鍵に触れるため、サプライチェーンのセキュリティはデプロイ担当が担保します。
- **データベースと `config.yaml` は同等に機密**です。`salt` を失うと暗号化認証情報が使えず、漏えいすると復号される可能性があります。

## アイデンティティとアクセス制御

### 管理者アカウント

- 単一の管理者アカウントで、マルチユーザーや RBAC は提供しません。
- パスワードは bcrypt で保存され 8 文字以上、本番では 16 文字以上のランダムなパスワードを推奨します。
- TOTP とパスキー（WebAuthn/Passkey）に対応します。TOTP の有効化とパスキー登録にはその場での再認証（現在のパスワード、TOTP 有効時は動的コードも）が必須で、盗まれたセッションを攻撃者の認証器へ紐付けることを防ぎます。
- 再認証に成功すると同じブラウザセッションで 5 分間、機密操作を連続実行できます。パスワード、メール、TOTP、パスキーの変更は引き続き都度確認が必要です。SMTP/通知ターゲットの変更やテスト送信はログインセッションまたは対応する API 権限のみを要求します。
- パスキーは HTTPS ドメインまたは localhost で使用します（IP アドレスは WebAuthn のオリジンとして不可）。パスキーログイン後に TOTP を再度要求することはありません。
- パスワード変更はトークンバージョンを上げ、すべてのセッション、API キー、パスキーを削除します。メールによるリセットも同様に TOTP を無効化し、パスキーと API キーを削除するため、復旧メール自体の安全性を確保してください。

### API キー

- キーは 86 文字の Base64URL ランダム文字列（64 バイトのエントロピー）で、固定プレフィックスはなく、サーバーには SHA-256 ダイジェストのみを保存します。
- 権限は「リソース:アクション」で区分します。`*` はすべてのシステム API 能力を表し、機密権限（`certificates:key`、`private_cas:key`、`deploy:execute`、`deploy:command`、`plugins:write`、`settings:write`、`api_keys:write`、`monitors:internal` など）は個別に列挙されます。バックアップのダウンロード/復元、入口変更、データベース切り替えはブラウザセッションのみです。
- API キーで他のキーを管理する場合、自身が持たない権限は付与できず、自身より高い権限のキーを変更/ローテーション/削除することもできません。
- アカウントセキュリティ関連の操作（パスワード変更、パスキー、セッション管理）はブラウザセッションのみに許可されます。自動化ごとに独立したキーを作成し、有効期限と最小権限を設定して定期ローテーションしてください。

## ネットワークと TLS

### インバウンド

- 管理コンソールは HTTPS のリバースプロキシ経由でアクセスし、バックエンドポートはループバックまたは内部ネットワークのみでリッスンします。
- プロキシ層で送信元 IP のホワイトリスト、VPN、ゼロトラスト、または WAF を設定します。
- プロキシは `X-Forwarded-For` を上書きまたは正しく追記し、`X-Forwarded-Proto` を転送します。LACTSSL は `server.trusted_proxies` の正確な IP または最小 CIDR のみを信頼し、追記チェーンでは全プロキシを登録します。未設定の場合、全リクエストがプロキシ IP と見なされ、レート制限と `Secure` Cookie の判定が誤ります。
- プロキシ層で HSTS、TLS 1.2+ を設定して弱い暗号スイートを無効化し、リクエストボディサイズを制限します（バックアップ復元とプラグインアップロードには大きな上限が必要です）。

### アウトバウンド

サーバーは DNS プロバイダー API、パブリック ACME CA と汎用アップストリーム、SMTP/Gotify/Telegram/DingTalk/WeCom/Webhook などの通知、SSH/SFTP・FTP/FTPS・CDN・パネルなどのデプロイ先、サイト監視対象へ外向きリクエストを発行します。

- 本番ではドメインまたはセグメント単位の egress ホワイトリストを設定し、必要な対象のみを許可します。
- プロキシはシステムの環境変数で設定し（Go HTTP クライアントの挙動）、アプリケーション内設定に依存しないでください。
- カスタムのデプロイ/通知 Webhook は送信元を審査し、秘密鍵やトークンを信頼できないアドレスへ送らないようにします。内部 HTTPS には「システム設定 → TLS 信頼チェーン」で内部 CA をインポートし、TLS 検証を無効にしないでください（インポート CA とプライベート CA は `SSL_CERT_FILE` に統合され、プラグインとデプロイコマンドが使用します）。

### SSRF 対策

- リテラルおよび解決後のアドレスについて、クラウドメタデータ、リンクローカル、予約済み、ドキュメント用、NAT64 などのセグメントを拒否します（例: `169.254.169.254`、`100.100.100.200`、`fd00:ec2::254`、`0.0.0.0/8`、`240.0.0.0/4`）。
- ループバックとプライベートネットワークは引き続き許可され、Gotify、自前パネル、内部 Webhook に利用できます。不要ならネットワーク層で制限してください。
- サイト監視は既定でパブリック対象のみを許可します。プライベート/ループバックの監視には `monitors:internal` が必要で、ダイヤル段階で解決後の IP を再検証して DNS リバインディングを防ぎます。
- デプロイ Webhook は秘密鍵を伴うため、パブリック対象には `https://` を強制し、ループバック、プライベートネットワーク、`.local`、`.internal` には HTTP を許可します。
- サードパーティへのリクエストが失敗した場合、ログ書き込み前に URL のパスとクエリをマスキングし、Telegram bot token、Gotify token、Server酱 の SendKey などがログやバックアップへ入らないようにします。

## セキュアエントリ、セッション、CSRF

### セキュアエントリ

管理ページはルートパスに直接公開されず、ランダムに生成されたエントリを経由します。

```text
https://your-domain/<entry>/
```

- エントリは既定で 20 文字の英数字をランダム生成して DB に保存し、通過していないページは素の `/` を含め一律 `404` を返します。探索には頻度制限があります。API は素の `/api` に固定され、ログインセッションまたは API キーで保護されます（旧版の `/<entry>/api` は互換エイリアス）。
- 正しいエントリへアクセスすると、有効期間 24 時間の署名付き `HttpOnly` セキュアエントリ Cookie が書き込まれ、サーバー側でも有効期限を検証します。
- 「設定 → セキュアエントリ」で変更でき、変更は即座に反映されます。手動エントリは 8〜32 文字が要件です。忘れた場合は `config.yaml` の `security.entry` を変更して再起動するか、`settings` テーブルで確認します。
- 未初期化の場合、起動ログにワンタイム初期化トークンも出力されます。管理者作成、初期化設定の変更、初期化の再起動、バックアップ復元には `X-LACTSSL-SETUP-TOKEN` の付与が必要で、トークンは初期化成功と同時に無効になり、再起動後に再生成されます。

> エントリは追加の防御層であり、HTTPS、強力なパスワード、ネットワークアクセス制御の代わりにはなりません。

### セッション

- セッションは `HttpOnly` Cookie に保存され、フロントエンドから読み取れません。Cookie は `SameSite=Lax` を使用し、書き込み操作は二重送信 CSRF と Origin 検証で保護されます。セッショントークンはコンパクトな JWT で、セッション ID は 24 バイト（192 ビット）の乱数、CSRF トークンは 32 文字です。
- 初回アクセスまたはログイン時に、1 年有効の `HttpOnly` デバイス識別 Cookie（`lactssl_device`、32 文字の 16 進数）を発行します。HTTPS デプロイではセッション、CSRF、エントリの Cookie に自動で `__Host-` プレフィックスが付き、共有親ドメイン下の兄弟サブドメインによる上書きを防ぎます。
- 既定ではセッション保持が有効で、再起動後も固定の `jwt_secret` で署名してログインを継続します。`security.session_persistence: false` にすると起動のたびにクリアし、起動時のランダム値を署名サブキーに混ぜて古いログインを無効化します。
- パスワード変更はトークンバージョンを上げ、すべてのセッション、API キー、パスキーを削除します。

### CSRF とクロスサイト対策

- 状態を変更するすべてのリクエスト（POST/PUT/DELETE など）は `X-LACTSSL-CSRF` ヘッダーを伴い、`lactssl_csrf` Cookie と一致する必要があります。旧セッションの初回リクエストでは Cookie を再発行し、ヘッダーのみのダウングレード検証は受け入れません。
- ログイン、初期化、パスワード忘れ/リセットなどの未認証インターフェースでは、追加で `Origin`/`Sec-Fetch-Site` を検証します。`Authorization: Bearer <token>` を明示的に使う API 呼び出しは CSRF 検証の対象外です。
- ページレスポンスはリクエストごとにランダムな CSP nonce を使用し、`script-src` は任意のインラインスクリプトを許可しません。スタイルはコンポーネントライブラリの要件のためインラインを許可します。

## パスワードリセットと外部アドレス

パスワードリセットメールのリンクは固定アドレスに基づいて生成します。

```yaml
security:
  public_url: "https://ssl.example.com"
```

- `public_url` が未設定の場合、ローカルループバックからで Host が `localhost`/ループバック IP のリクエストに限り現在の Host からリンクを推測できます。それ以外の「パスワードを忘れた場合」は拒否されます。
- クライアントが偽造できる `X-Forwarded-Host` は信頼しません。リバースプロキシ構成では必ず `public_url` を設定し、攻撃者が Host を偽造してリセットリンク（token とセキュアエントリを含む）を自身のドメインへ誘導することを防いでください。

## 認証情報とデータの保護

### 暗号化

- DNS/デプロイ認証情報、SMTP パスワード、通知 Token、TOTP キー、プライベート CA と証明書の秘密鍵は、AES-256-GCM で暗号化してから DB へ書き込みます。旧バージョンの平文データは起動時に自動移行されます。
- 暗号化キーは `config.yaml` の `security.salt` から導出します。JWT は `security.jwt_secret` と起動時のランダム値から HKDF で派生した独立サブキーで署名し、DB の AES-GCM キーとは分離しています。
- `security.jwt_secret` と `security.salt` を手動設定する場合は 32 文字以上が必要で、短すぎると起動を拒否します。API が設定を返す際はキー系フィールドをマスキングし、編集時に空欄なら元の値を保持します。

### ファイルとバックアップ

- `config.yaml` は `0600`、`data/` は `0700` を維持し、所有者はサービス実行ユーザーとします。DB、WAL、プラグイン、ログ、アップグレードバックアップはすべて `data/` 配下です。
- バックアップのダウンロードには 12 文字以上の暗号化パスワードが必要で、PBKDF2-HMAC-SHA256（600,000 回反復）+ AES-256-GCM で暗号化されます。パッケージには DB、設定、バージョン情報が含まれるため機密ファイルとして管理し、暗号化されていないコピーを配布しないでください。
- 復元パッケージは設定を完全に検証してから適用し（キー長、セキュアエントリ、リッスンアドレス、TLS/mTLS の組み合わせなど）、不正な設定は拒否されます。初期化成功後、未適用の復元パッケージはクリアされ、初期化前の内容が新しいアカウントを上書きすることを防ぎます。

### 認証情報のローテーション

- DNS/デプロイ/通知の認証情報には専用アカウントを使用し、定期的にローテーションします。
- SSH は既定でホストフィンガープリント入力を要求し、「初回接続時にホストキーを自動信頼」を有効にした場合のみ TOFU を採用します。FTP は既定で明示的 TLS を使用し、`none` を選んだ場合のみ平文になります。
- API キーはシステムごとに個別発行し、有効期限を設定して、漏えい時には即座にローテーションします。

## 監査とログ

| ログ | 内容 | 保持/エクスポート |
| --- | --- | --- |
| 操作ログ | タスク、証明書、デプロイ、通知、監視、設定変更 | 由来/レベル/時刻で絞り込み可能。直近 90 日を CSV/JSON でエクスポート。削除前にアーカイブへ書き込み |
| システムログ | 起動、HTTP、スケジューリング、プラグイン、ACME | 既定で 7 日/20,000 行。調整とクリアが可能。削除前にアーカイブへ書き込み |
| ログアーカイブ | 操作ログ/システムログの生 NDJSON と manifest | `data/archives/logs/`、既定で永久保持。「ログ → アーカイブ」でダウンロードまたは削除 |
| プロセスログ | stdout または `log.file` | サイズ/日数でローテーション。JSON 出力も可能 |
| リバースプロキシログ | アクセス、送信元 IP、ステータスコード | 外部のログ基盤で管理 |

- 操作ログ、システムログ、アーカイブを定期的に SIEM やログ基盤へエクスポートし、管理者によるクリア、アーカイブ削除、データ破損による監査欠落を防いでください。
- 両ログは `logs` テーブルを共有しますが `category` で分離され、システムログをクリアしても操作ログは残ります。各レスポンスの `X-Request-ID` はアクセスログ、panic、エラーの関連付けに使えます。
- アクセスログにはクエリパラメータ、リクエストボディ、認証ヘッダーを記録せず、セキュアエントリはパス内で `:entry` に置き換えます。ログとアーカイブにはクライアント IP、ドメイン、エラー詳細、操作者情報が含まれる場合があるため、公開共有を避けてください（アーカイブは `0600`、ディレクトリは `0700`）。
- アーカイブは改ざん不能な監査ではありません。データディレクトリの権限を持つ管理者は削除・変更できます。改ざん防止が必要な場合は外部の WORM ストレージや SIEM へ同期し、秘密鍵のエクスポート、バックアップ復元、CA 生成、プラグイン導入、セキュアエントリ変更は変更記録と関連付けることを推奨します。

## プラグインとサプライチェーンのセキュリティ

- 公式リリースは `checksums.txt` と Ed25519 署名で検証し、アセットは 64 桁の 16 進数 SHA-256 を提供してダウンロード後に強制検証します。アップロード helper は manifest の `sha256` とインストール記録で検証します。
- 公式ビルドは `upgrade.program.public_key` を埋め込み、既定でリリース署名を検証します。自前ビルドで未設定の場合はオンラインアップグレードを拒否し、管理された環境のみ `upgrade.program.allow_unsigned` を明示的に有効にできます。
- インストール時に `plugin.json`、manifest の ID とバージョンを検証し、失敗時はロールバックします。ファイルダイジェストは検出時、登録時、DNS/デプロイ/通知の呼び出しごとに再確認し、置き換えられたファイルは読み込み・実行しません。
- プラグインディレクトリは `0700`、helper は `0755` で、グループやその他の書き込みを許可せず、シンボリックリンクは拒否します。デプロイ機能は秘密鍵を受け取るため既定で有効です。信頼できる提供元のみを有効にし、不要なターゲットは無効にしてください。
- 本体は helper のタイムアウト、常駐メモリ、出力サイズを制限し、エラーメッセージ内の認証情報と秘密鍵をマスキングします。本番では内部ミラー（HTTPS または `file://`）を使い、バージョンを固定して自動更新を無効化します。プラグインの提供元、バージョン、ダイジェスト、レビュー担当、ロールバック版を記録し、ステージングで検証してから適用してください。

## ACME サーバーのセキュリティ

- 内蔵 ACME サーバーは既定で有効ですが、エンドポイントを作成して有効化するまで外部へ証明書を発行しません。有効化後は独立したプロトコルエントリを提供し、管理側のセキュアエントリ、セッション Cookie、CSRF は使用しません。不要なら `acme.enabled` を `false` にできます。
- パブリックなデプロイでは独立ポートを使い、ファイアウォールまたはプロキシ層でアクセスを制限します。各エンドポイントにはドメイン許可リストが必須で、空のまま有効化すると拒否されます。
- EAB はオン/オフ可能で、既定では有効化を推奨します。無効にするとそのポートへアクセスできる誰もがアカウントを作成できるため、ドメイン許可リスト、mTLS、ネットワーク ACL を併用してください。mTLS はトランスポート層の保護であり、ACME の JWS アカウント認証の代わりにはなりません。
- `acme.base_url` は固定のパブリックアドレスに設定し、Host ヘッダーインジェクションでリソース URL が誤った場所を指すことを避けます。未設定の場合は Host から推測するため、パブリックデプロイでは依存しないでください。
- HTTP-01 検証は既定でループバック、プライベートネットワーク、リンクローカル、CGNAT/予約済みセグメント（例: `100.64.0.0/10`、`192.0.0.0/24`）を拒否します。内部ネットワークではエンドポイント単位の CIDR ホワイトリストで明示的に許可してください。
- ACME のリソースはランダムな公開 ID を使用し、DB の自動増分 ID は使いません。カスタム ACME アップストリームのディレクトリアドレスは HTTPS が必須で、ローカルループバックのみ HTTP を許可します。
- 単一インスタンスではメモリ内 nonce を使用し、再起動後はクライアントが `badNonce` を受けて自動再試行します。CRL/OCSP は `/pki/{ca}/...` にあり、通常はパブリックに到達可能である必要があります。CA ごとに構成されるため、ACME 登録エンドポイントを無効にしても利用可能に保ってください。
- CRL/OCSP は IP 単位でレート制限され、CRL は同じ失効集合の結果をキャッシュして変化時のみ CRL Number を増やします。レート制限は `server.trusted_proxies` 内のプロキシを読み、実際のクライアント IP でカウントします。失効確認は能動的に確認するクライアントにのみ有効で、既存証明書は再発行しないと CRL/OCSP アドレスが付与されません。失効状態は独立した `revocations` テーブルに保存され、証明書行を削除・クリーンアップしても失効記録は残ります。
- リーフ発行前に CA の `ExtKeyUsage`（`serverAuth` または `any` を含む）と NameConstraints を検証し、タスク発行と ACME finalize で同じ検証を共有します。

## デプロイとコンテナの強化

- 専用ユーザーでサービスを実行し、`config.yaml` は `0600`、データディレクトリは `0700` を維持してください。Docker はエントリポイントでボリューム権限を修正してから非 root の `lactssl` ユーザーで実行し、Compose は既定で全ケイパビリティを破棄して必要に応じて `CHOWN`/`SETUID` を追加、読み取り専用ルート、`/tmp` の tmpfs、`pids_limit`、`init` を有効にします。
- `data/` と `config.yaml` はバージョン管理へコミットせず、公開ディレクトリへ置かないでください。
- サービスは既定で通常リクエストのボディを 2 MiB に制限し（バックアップ復元とプラグインアップロードを除く）、読み書きタイムアウトを設定します。プロキシ層でもサイズとタイムアウトを設定してください。
- 本番ではイメージ/バイナリのバージョンを固定し、定期的に脆弱性をスキャンしてセキュリティアドバイザリに注意してください。80/443 はリバースプロキシで転送し、バイナリへ追加のケイパビリティを与えないでください。

## 既知の制限

- マルチユーザーと RBAC は提供せず、管理者セッションは単一障害点です。SSO、LDAP、OIDC、SAML、SCIM も提供しません。
- HSM/KMS は提供しません。秘密鍵はローカル DB に暗号化して保存されます。
- デュアルアクティブクラスタは提供しません。SQLite は単一書き込みで、複数インスタンスがデータディレクトリを共有することはできません。
- 改ざん不能な監査は提供しません。管理者はログをクリアし、ローカルアーカイブを削除できます。改ざん防止が必要な場合は外部アーカイブと WORM/保持ロックを使用してください。
- Prometheus メトリクスエンドポイントは提供せず、監視はログ、認証 API、外部監視に依存します。デプロイ先の自動ロールバックも提供しないため、ターゲット側で旧バージョンを保持するかアトミックなリリースを使用してください。

## 導入時のセキュリティチェックリスト

### アイデンティティ

- [ ] 管理者は強力なパスワードを使用し、TOTP またはパスキーを有効にしている。
- [ ] 復旧用メールアドレスが管理下にあり、MFA が有効になっている。
- [ ] 不明なセッションをクリア済み。
- [ ] API キーはシステムごとに独立し、最小権限で、有効期限を設定している。

### ネットワーク

- [ ] 管理エントリは HTTPS のみで、バックエンドポートはインターネットへ直接公開していない。
- [ ] `trusted_proxies` と `public_url` を設定済み。
- [ ] プロキシが `X-Forwarded-For`/`X-Forwarded-Proto` を転送している。
- [ ] 送信元の制限、WAF、またはゼロトラストポリシーを設定済み。
- [ ] アウトバウンドは対象ごとのホワイトリストで、必要に応じてプロキシを経由している。

### データ

- [ ] `config.yaml` 0600、`data/` 0700、所有者が正しい。
- [ ] 暗号化バックアップを生成し、別拠点へ保存済み。
- [ ] バックアップパスワードとバックアップファイルを分離して保管している。
- [ ] リストア演習を 1 回完了済み。
- [ ] ログの保持とエクスポートが監査要件を満たしている。

### プラグインと ACME

- [ ] 信頼できるリポジトリ/内部ミラーのみを使用し、署名公開鍵を設定している。
- [ ] 本番では自動更新を無効にしている。
- [ ] デプロイプラグインは必要に応じて有効化し、提供元を審査済み。
- [ ] ACME エンドポイントにドメインホワイトリストを設定し、本番では EAB を有効にしている。
- [ ] ACME エントリの送信元を制限し、必要に応じて mTLS を有効にしている。

## セキュリティインシデント対応

1. **範囲の確認**: アカウント、API キー、DNS/デプロイ認証情報、プラグイン、ホストのいずれか。
2. **隔離**: セッション/API キーを取り消し、プラグインを無効化し、ACME エンドポイントを停止し、必要に応じてネットワーク層で切断します。
3. **証拠保全**: 操作ログ、システムログ、リバースプロキシログをエクスポートし、`X-Request-ID` を記録します。先にログをクリアしないでください。
4. **ローテーション**: パスワードを変更するとすべてのセッションと API キーが削除されます。DNS/デプロイ/通知の認証情報をローテーションし、`salt` の漏えいが疑われる場合はキー漏えいの手順に従います。
5. **復旧**: 信頼できるバックアップから復元し、設定とデータの一貫性を検証し、影響を受けた可能性のある証明書を再発行します。
6. **振り返り**: Runbook、権限一覧、監視ルールを更新します。

具体的なトラブルシューティングは[監視とトラブルシューティング](troubleshooting.md)、バックアップと復元は[運用マニュアル](operations.md)を参照してください。
