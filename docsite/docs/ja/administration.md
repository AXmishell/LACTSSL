# 管理ワークスペース

本文は LACTSSL をデプロイ・運用する開発者向けに、アカウント、権限、キー、監査、日常運用の方法を説明します。製品は**単一管理者 + API キーによる権限分離**モデルです。

## 運用モデル

### 3 種類のアイデンティティ

| アイデンティティ | 機能 | 対象 |
| --- | --- | --- |
| 管理者アカウント | ブラウザログイン後にすべての操作を実行可能。秘密鍵のエクスポート、バックアップの復元、設定変更を含む | プラットフォーム責任者 |
| API キー | `リソース:アクション` で認可。自動化と読み取り専用連携に適する | CI/CD、巡回、CMDB、デプロイスクリプト |
| ACME クライアントアカウント | 特定の ACME エンドポイントのみにアクセス。EAB/ドメイン許可リストで制限 | certbot、lego、acme.sh など |

管理者アカウントは単一障害点であり、固定の責任者が保持します。API キーは人手による確認の代替にはならず、アカウントセキュリティ系のインターフェース（パスワード変更、パスキー、セッション管理など）にもアクセスできません。

### 推奨される職責分離

| 職責 | 推奨される所属 | 管理者アカウントを使用するか |
| --- | --- | --- |
| 日常の証明書発行とデプロイ | プラットフォーム/運用 | はい、または制限付き API キーを使用 |
| DNS/デプロイ資格情報の保管 | 該当システムの責任者 | いいえ、資格情報は管理者が登録し、必要に応じてローテーション |
| 自動化連携 | 連携開発 | いいえ、独立した API キーを使用 |
| セキュリティ監査 | セキュリティ/監査 | いいえ、`logs:read` / `system_logs:read` の読み取り専用キーを使用 |
| バックアップ復元 | 運用責任者 | はい、復元はサービスを再起動する |
| プラグインとアップグレード | プラットフォーム責任者 | はい、高権限の変更に該当 |

## 初期化と引き継ぎ

### 初期化

1. 起動ログのセキュアエントリから入り、ワンタイム初期化トークンで管理者を作成します。
2. 直ちに TOTP またはパスキーを有効化し、復旧メールアドレスを設定して検証します。
3. `security.public_url`、信頼するプロキシ、ログを設定します。
4. 最初の暗号化バックアップを作成し、復旧パスワードが使用できることを確認します。
5. 必要なプラグインのカテゴリと項目を有効化します。

### 担当者の引き継ぎ

- 管理者パスワード、TOTP シード、パスキーデバイス、復旧メールアドレスの管理権を移管します。
- API キー一覧を照合し、用途、権限、有効期限、責任者を確認します。
- DNS/デプロイ/通知資格情報、バックアップ場所、復旧パスワード、直近の復旧訓練記録を引き継ぎます。
- 未完了のタスク、監視項目、アラートルーティングを説明します。チャットツールで平文のパスワード、API キー、バックアップパスワードを送らず、パスワードマネージャーまたは密封引き継ぎプロセスを使用してください。

## アカウントセキュリティ

### ログイン方式

- パスワードは bcrypt で保存され 8 文字以上、本番では 16 文字以上のランダムなパスワードを推奨します。TOTP 有効化後はパスワードログインでも動的コードが必要で、同じコードは有効ウィンドウ内で再利用できません。
- パスキー（WebAuthn/Passkey）は追加のログイン方式で、パスワードの代替にはなりません。HTTPS ドメインまたは localhost で使用します。
- パスワード変更はトークンバージョンを上げ、すべてのセッション、API キー、パスキーを削除してログインを即座に無効化します。メールによるリセットも TOTP を無効化し、パスキーと API キーを削除します。

### セッション

- セッション保持は既定で有効で、再起動後もログインを維持します。`security.session_persistence: false` にすると再起動のたびにクリアされます。保持はセッション寿命も延ばすため、デプロイ方針に合わせて判断してください。「設定 → セッション」で定期的に不明なデバイスを確認して取り消します。ログイン済みセッションは管理者権限と同等のため、共有ブラウザや信頼できないデバイスで維持しないでください。

### 復旧パス

1. **メールリセット**：パスワードを忘れたがメールを管理できる場合に適用し、TOTP、パスキー、API キーをクリアします。
2. **バックアップ復元**：アカウント、データベース、設定が破損した場合に適用します。バックアップの復号パスワードと初期化トークン（未初期化インスタンス）が必要です。

独立した復旧パスを 2 つ用意し、手順を Runbook に書いて定期的に訓練してください。復旧パスワードとバックアップファイルは同じ場所に置かないでください。

## API キーガバナンス

API キーはマシン ID に適しており、人には適しません。「1 システム 1 キー」で管理します。

### ロールから権限へのマッピング

| 利用者 | 推奨権限 | 説明 |
| --- | --- | --- |
| 読み取り専用巡回/CMDB | `system:read`、`dashboard:read`、`certificates:read`、`tasks:read`、`monitors:read`、`deployments:read` | `*:write` は一切付与しない |
| 証明書一覧の同期 | `certificates:read`、`tasks:read` | 秘密鍵権限は付与しない |
| CI/CD による更新トリガー | `tasks:read`、`tasks:run`。デプロイノードを含む場合は `deploy:execute` も追加 | タスク範囲で制御 |
| 証明書のダウンロードと配布 | `certificates:read`、`certificates:key`、`deploy:execute` | 高機密。送信元と有効期限を必ず制限 |
| ログ監査 | `logs:read`、`system_logs:read` | 読み取り専用キー、短い有効期限を設定 |
| 監視アラート | `system:read`、`monitors:read` | `/api/status` と監視の読み取りに使用 |
| プラットフォーム自動化 | 実際の必要に応じて組み合わせ、`*` は避ける | `*` はすべてのシステム機能と同等 |

### ライフサイクル

1. 用途、責任者、権限、有効期限を登録します。
2. 作成後直ちにパスワードマネージャーまたはキー管理システムへ保存し、コードリポジトリへ平文で残しません。
3. 呼び出し元に設定して最小権限を検証し、期限前にローテーションします（旧トークンは即座に無効）。
4. システム廃止または担当者変更時に直ちに無効化/削除します。

### 保護要件

- キーをログ、スクリーンショット、チケット、公開リポジトリに置かず、HTTPS でのみ送信し、送信元 IP 制限をネットワーク層またはゲートウェイ層で実装します。
- `api_keys:read` 権限のキーを定期的に確認して権限の拡散を防ぎ、漏洩が疑われる場合は直ちにローテーションまたは削除して操作ログを確認します。

> API キーはパスワード変更、パスキーのバインド、他のセッションのログアウトはできません。これらの操作はブラウザのログインセッションのみ許可されます。

## 証明書と CA のガバナンス

### パブリック CA

- ACME アカウントには専用メールアドレスを使用し、個人メールを紐づけません。
- CA ごとに EAB 資格情報を管理してアクセス範囲を制限し、レート制限とドメイン検証要件に備えて重要なドメインには予備 CA を用意します。汎用 ACME アップストリームは HTTPS を使用します（ローカルループバックを除く）。

### プライベート CA

- ルート CA の秘密鍵は中間 CA の署名にのみ使用し、エンドエンティティ証明書を直接署名しないでください。中間 CA にはパス長、Key Usage、Name Constraints、有効期間を設定します。
- ルート CA の秘密鍵はエクスポート後オフラインで保管します。DB 内の秘密鍵は `security.salt` で保護されますが HSM ではありません。
- CA を削除する前に下位 CA と依存証明書がないことを確認し、既存証明書は CRL/OCSP 拡張を自動取得しないため再発行が必要です。

### ACME サーバー

- 各エンドポイントは 1 つのプライベート CA にバインドし、ドメイン許可リストを設定します。本番では EAB を有効化します（無効にすると、アクセスできる誰もがアカウントを作成できます）。
- パブリックネットワークのエンドポイントは専用ポート、送信元制限、可能なら mTLS を使用します。
- 無効なオーダーと長期間未使用のアカウントを定期的にクリーンアップします。アカウントのクリーンアップは履歴オーダーを削除しますが、発行済み証明書には影響しません。

## プラグインとサプライチェーン

- 内蔵の公式実装を使用し、アップロード helper は信頼できるソースに限定します。リリースの署名公開鍵を設定して検証を強制します。
- 本番では変更ウィンドウに従って手動でアップグレードし、ロールバック用にバージョン、インストール時刻、変更記録を保持します。
- デプロイ機能は秘密鍵に触れるため既定で有効です。信頼できる提供元のみ有効化し、不要なターゲットは無効化して、プラグインディレクトリは `0700`、ヘルパーは `0755`、所有者はサービス実行ユーザーにします（詳細は[プラグインガバナンス](plugins.md)）。

## 監査と証跡

| ログ | 内容 | 用途 |
| --- | --- | --- |
| 操作ログ | タスク、証明書、デプロイ、通知、監視、設定変更 | 操作監査、変更追跡 |
| システムログ | 起動、HTTP、スケジューリング、プラグイン、ACME などのプロセスログ | 運用トラブルシューティング、セキュリティインシデント分析 |
| プロセスログ | stdout または `log.file` | ログプラットフォームでの収集、panic 分析 |

- 操作ログは少なくとも 90 日保持し（エクスポート範囲の上限）、より長い保持は外部のログ基盤へ定期エクスポートします。システムログは既定で 7 日または 20,000 行を保持し、`log.system.retention_days` と `max_rows` で調整します。
- リバースプロキシのアクセスログは独立して保存し、送信元 IP、ステータスコード、`X-Request-ID` を記録します。CSV エクスポートでは数式インジェクションに注意し、資格情報を含むログを外部へ送らないでください。重要な変更には変更票またはチケットを関連付けます。

## 日常運用チェックリスト

### 毎日

- [ ] タスク失敗、デプロイ失敗、証明書異常、サイト監視の期限間近を確認する。
- [ ] 外部スケジューラを使用する場合、バックアップの成功を確認する。

### 毎週

- [ ] 期限間近の証明書と自動更新状態、システムログのエラー/レート制限/異常ログインを確認する。
- [ ] 追加/無効化した API キーと資格情報を照合する。

### 毎月

- [ ] ディスク、データベースサイズ、WAL、ログ保持、通知チャネルの到達性を確認する。
- [ ] プラグインバージョンとセキュリティアドバイザリを確認し、操作ログと変更記録の一致を抜き打ち確認する。

### 四半期ごと

- [ ] バックアップ復旧訓練を 1 回完了し、管理者アカウント、復旧メール、TOTP/パスキーを確認する。
- [ ] API キーの権限と有効期限、アップグレードウィンドウとロールバック計画を再評価する。

## 変更管理

| 操作 | リスク | 推奨される統制 |
| --- | --- | --- |
| セキュアエントリの変更 | 管理エントリがロックされる可能性 | 新しいエントリを記録し、`config.yaml` による上書き方法を保持 |
| `security.salt` の変更 | 既存の暗号化資格情報を復号できない | 無断変更を禁止。移行を伴う必要がある |
| プライベート CA の削除 | 下位 CA と依存証明書に影響 | 先に依存関係を確認し、バックアップをエクスポート |
| バックアップの復元 | 現在のデータを上書きして再起動 | 二人確認、低負荷時間帯を選択 |
| デプロイカテゴリ/helper の有効化 | 証明書の秘密鍵を読み取れる | ソースレビュー、署名検証、最小権限 |
| プログラムのアップグレード | データ移行は不可逆 | バックアップ、ステージング検証、ロールバック計画 |
| 証明書/ログの一括クリーンアップ | データは復旧不可 | 先にプレビュー、エクスポート、二人確認 |
