# 監視とトラブルシューティング

本書では、企業の導入時および運用時に最も多く発生する障害、診断の手順、応急処置を示します。トラブルシューティングではまず現場を保全し、「依存関係 → 認証 → 業務 → データ」の順で切り分けてください。安易な再起動やログのクリアは避けます。

## 1. 初動調査

### 1.1 影響範囲の確認

- 単一の証明書、単一のタスク、それともすべてのタスクが失敗しているのか。
- 管理エントリが利用できないのか、それとも発行/デプロイのみが失敗しているのか。
- 単一のデプロイ先か、それともすべての対象か。
- アップグレード/設定変更の後に発生したのか、稼働中に突然発生したのか。
- 通知、監視、ACME クライアントにも同時に影響しているか。

### 1.2 基本情報の収集

```bash
# バージョンとプロセス
curl -fsS -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/status

# Docker ログ
docker compose logs --since=30m lactssl

# systemd ログ
sudo journalctl -u lactssl --since "30 min ago"

# ポート
ss -lntp | grep -E '8080|14000'
```

併せて次を記録します。

- 発生日時、タイムゾーン、変更ウィンドウ内かどうか。
- 関連するタスク/証明書/デプロイ記録の ID。
- レスポンスヘッダー `X-Request-ID`。
- エラーメッセージの原文（マスキング後）。

### 1.3 依存関係の確認

| 依存関係 | 確認方法 |
| --- | --- |
| リバースプロキシ | プロキシログ、バックエンドポート、転送ヘッダー |
| DNS API | 認証情報の権限、クォータ、ドメイン/Zone、TXT レコード |
| パブリック CA | ステータスページ、レート制限、CAA、EAB |
| デプロイ先 | ネットワーク、認証、パス、権限、リロードコマンド |
| SMTP/IM | 接続性、認証、チャネル設定 |
| ホスト | ディスク、メモリ、ファイル権限、時刻同期 |

## 2. アクセスとログイン

### 2.1 ルートパスが 404 を返す

**症状**: `https://ssl.example.com/` へのアクセスが 404 を返す。

**原因**: セキュアエントリを通過していません。エントリはランダムなパスであり、素のルートパスは一律で 404 を返します。

**対処**:

1. 起動ログでセキュアエントリを確認します。
2. またはデータベースの `settings` テーブルで `security.entry` を照会します。
3. または `config.yaml` の `security.entry` を設定し、再起動して上書きします。

### 2.2 セキュアエントリを忘れた

- 起動ログ（初期化時に完全なエントリが出力されます）。
- データベースの `settings` テーブルの `security.entry`。
- 起動前に `config.yaml` の `security.entry` を変更し、再起動後に上書き。

エントリを変更すると古いリンクは即座に無効になります。新しいエントリを記録し、関係者へ通知してください。

### 2.3 ログイン直後に切断される/セッションが失効する

**考えられる原因**:

- サービスが再起動され、`security.session_persistence` が明示的に無効になっている。
- パスワードを変更し、すべてのセッションが削除された。
- 異なる `jwt_secret` で起動した。
- リバースプロキシが `X-Forwarded-Proto` を転送しておらず、`Secure` Cookie が異常になった。
- ブラウザ/プロキシが古い Cookie をキャッシュしている。

**対処**:

1. 直前に再起動またはパスワード変更を行ったか確認します。
2. プロキシヘッダーと `trusted_proxies` を確認します。
3. ブラウザの Cookie を削除し、セキュアエントリから再度アクセスします。
4. セッション保持は既定で有効です。`security.session_persistence: false` にしていた場合は `true` に戻すと再起動後もセッションを保持できます。

### 2.4 Cookie の異常、レート制限が不正確

**症状**: ログインループ、CSRF 失敗、すべてのリクエストが同じ IP のクォータを共有する。

**原因**: 信頼できるプロキシが未設定、プロキシが転送ヘッダーを渡していない、または多段プロキシで直近ホップだけを信頼している。

**対処**:

```yaml
server:
  trusted_proxies: ["127.0.0.1"]
security:
  public_url: "https://ssl.example.com"
```

プロキシで次が設定されていることを確認します。

```nginx
proxy_set_header X-Real-IP $remote_addr;
# 推奨の上書きモード: このプロキシだけを信頼すれば十分
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
```

追記モード `$proxy_add_x_forwarded_for` を使う場合、CDN → Nginx → LACTSSL のような多段構成では、XFF に現れ得るすべてのプロキシを `trusted_proxies` に含める必要があります。含めないとクライアント IP は上流プロキシで止まります。

「設定 → 設定ファイル → 自動検出」で次を確認します:

- `peer_ip`: TCP 対向アドレス;
- `applied_trusted_proxies`: 現在有効な信頼リスト;
- `effective_client_ip` / `client_ip_source`: 最終結果と取得元;
- `trusted_skipped`: 右から左へスキップした信頼済みプロキシ数;
- `header_warnings`: XFF の不正・長すぎる値などの解析問題。

アクセスログの `ip_source`、`ip_skipped`、`ip_warnings` も調査に使えます。保存後は再起動が必要で、再起動前は `configured_trusted_proxies` と `applied_trusted_proxies` が異なる場合があります。

### 2.5 429 リクエストが多すぎる

- レスポンスの `Retry-After` に従ってバックオフします。
- プロキシ IP を共有していないか確認します。信頼できるプロキシを設定すると、実際のクライアント IP でカウントされます。
- ログイン、TOTP、パスワードリセット、バックアップのダウンロード、秘密鍵のエクスポート、ACME プロトコルなどにはそれぞれ独立したレート制限があります。
- レート制限のしきい値を上げて、ブルートフォースやスクリプトの暴走を覆い隠さないでください。

### 2.6 パスキーが利用できない

- HTTPS のドメインまたは localhost 経由でアクセスする必要があります。IP アドレスは WebAuthn のオリジンとして使用できません。
- ブラウザが WebAuthn に対応しているか、システムで生体認証/PIN が有効か確認します。
- パスキーはパスワードの代わりにはなりません。デバイスを紛失した場合は、パスワード + TOTP またはその他の復旧経路を使用します。

## 3. 証明書の発行失敗

### 3.1 DNS-01 検証の失敗

| 考えられる原因 | 確認項目 |
| --- | --- |
| 認証情報に権限がない | API Key に対象 Zone の読み書き権限があるか |
| ドメイン/Zone の不一致 | ドメインが現在のアカウントで参照可能な Zone 内にあるか |
| TXT の伝播が遅い | TTL を待つ。権威 DNS が TXT を返すか確認 |
| 多段ドメイン/CNAME | `_acme-challenge` の解決経路を確認 |
| ワイルドカード | ワイルドカードは DNS-01 が必須 |
| プロバイダーの制限 | クォータ、頻度制限、API の変更 |
| プロキシ/ゲートウェイ | カスタム API アドレスに到達できるか、証明書が信頼されているか |

対処:

1. タスクログで DNS プロバイダーの具体的なエラーを確認します。
2. `dig`/`nslookup` で `_acme-challenge.<domain>` の TXT を確認します。
3. 同じ認証情報を使い、プロバイダーのコンソールで手動で TXT を作成/削除し、権限を確認します。
4. CA の CAA レコードがその CA を許可しているか確認します。
5. 修正後にタスクを再実行します。

### 3.2 CA のレート制限/EAB エラー

- Let's Encrypt などのパブリック CA には、アカウント、ドメイン、検証失敗などに対するレート制限があります。CA のステータスページとエラーの詳細を確認してください。
- ZeroSSL、Google Trust Services、LiteSSL、ZoTrus、Actalis、SSL.com は EAB が必要です。EAB の KID/HMAC が正しく、有効期限内であることを確認してください（ZoTrus の KID は登録メールアドレスです）。
- ZoTrus の dns-01 レコード名はサーバーが返す `tokenPath` に基づきます（通常 `_<tokenPath>.<domain>`）。標準の `_acme-challenge` ではありません。ZoTrus を使用するタスクは実行後に「DNS 検証待ち」になり、タスクログまたは「DNS 検証」パネルに表示されるレコードを追加して「検証を続行」をクリックしてください。ZoTrus はワイルドカード、CA プール、ターゲットフロー Beta には未対応です。
- 汎用 ACME アップストリームのディレクトリは HTTPS である必要があります。ローカルループバックは除きます。
- 重要なドメインには予備の CA を用意し、単一の CA のレート制限ですべてが失敗するのを避けてください。

### 3.3 証明書の発行は成功したがブラウザが信頼しない

- パブリック CA の証明書は信頼されるはずです。完全なチェーン（fullchain）をデプロイしているか確認してください。
- プライベート CA の証明書は、ルート CA をクライアントの信頼ストアへインストールする必要があります。
- 誤った証明書/秘密鍵の組み合わせをデプロイしていないか確認してください。
- SNI、ドメイン、証明書の SAN が一致しているか確認してください。
- システム時刻が正確か確認してください。

### 3.4 プライベート CA の発行失敗

- CA が失効しておらず、発行用途を持ち、パス長が下位 CA を許可していることを確認してください。
- 証明書の有効期間が CA の有効期限を超えていないことを確認してください。
- インポートした CA は証明書と秘密鍵が一致し、CA の基本制約を備えている必要があります。
- CA を削除する前に、下位 CA を削除してください。

## 4. デプロイの失敗

### 4.1 SSH/SFTP

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| ホストフィンガープリントの不一致 | サーバーのキー変更または設定ミス | フィンガープリントを照合し、古いフィンガープリントをクリアして再記録 |
| 初回接続が拒否される | フィンガープリント未入力かつ TOFU が無効 | `SHA256:...` を入力するか、初回信頼を明示的に有効化 |
| 認証失敗 | ユーザー名/パスワード/秘密鍵の誤り | 認証情報と対象の SSH 設定を確認 |
| パスの権限がない | デプロイユーザーに書き込み権限がない | ディレクトリの権限を調整するか、権限のあるユーザーを使用 |
| リロードコマンドの失敗 | コマンドが存在しない/権限不足/サービス名の誤り | 対象ホストで手動実行して検証 |

### 4.2 ローカルディレクトリ

- 実行ユーザーに対象ディレクトリの書き込み権限がありません。
- パスが存在しません。事前にディレクトリを作成する必要があります。
- SELinux/AppArmor による制限。
- リロードコマンドは失敗したが、証明書ファイルは更新済み。サービスが実際に新しいファイルを読み込んだか確認してください。

### 4.3 パネル/CDN/Webhook

- 認証情報の期限切れ、権限不足、API バージョンの不一致。
- デプロイパラメータ（サイト、ドメイン、証明書名）が対象システムと一致しない。
- 対象システムで IP ホワイトリストが有効になっており、LACTSSL の出口が許可されていない。
- Webhook のパブリックな対象は HTTPS が必須です。ループバック/プライベートネットワークでは HTTP を許可します。
- デプロイプラグインが未インストール、未有効化、またはファイル検証に失敗している。

### 4.4 証明書は更新されたが業務側が古い証明書のまま

- デプロイノードにリロードコマンドが未設定、またはコマンドが反映されていない。
- 対象システムにキャッシュがある（CDN、WAF、ロードバランサー）。
- 誤ったパス/サイトへデプロイしている。
- 複数インスタンスへのデプロイで 1 台しか更新していない。
- 証明書のシリアル番号/フィンガープリントが対象システムと一致しているか確認してください。

## 5. 通知と監視

### 5.1 通知が届かない

- チャネルがプラグインページで有効になっているか、通知ページで有効になっているか。
- Token/Webhook が期限切れでないか、対象に到達できるか。
- SMTP が暗黙的 TLS を使用しているか。サーバーが STARTTLS に対応していない場合は送信が拒否されます。
- タスクの通知ノードが有効か、トリガーのタイミングが一致しているか。
- 操作ログ/システムログで送信エラーを確認してください。機密値はマスキングされます。

### 5.2 サイト監視の誤検知

- 監視はホスト名とシステムの信頼チェーンを検証します。自己署名、不完全なチェーン、ホスト名の不一致はすべて異常として記録されます。
- 対象のポート、SNI、システムの CA 信頼ストア、時刻を確認してください。
- ロードバランサー背後のノードによって返される証明書が異なる場合があります。監視対象が安定していることを確認してください。
- 監視の頻度とタイムアウトが妥当か確認してください。不安定な対象への頻繁なアラートは避けます。

### 5.3 期限リマインドが届かない

- タスクの自動更新が有効か、`RenewDays` が妥当か。
- スケジューラが動作しているか（ログでスケジュール記録を確認）。
- 通知チャネルが利用可能か。
- 証明書がクリーンアップ済みでないか、タスクの参照がクリアされていないか。

## 6. プラグインの問題

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| プラグインマーケットの一覧が空 | インデックス未更新/リポジトリに到達不可 | リポジトリのアドレス、ネットワーク、TLS を確認 |
| インストール失敗 | 署名、SHA-256、プラットフォーム、`min_host` の不一致 | エラーの詳細を確認し、公開鍵とバージョンを照合 |
| インストール後にプロバイダーが表示されない | ファイル/項目が無効 | helper ファイルと具体的な項目を有効化 |
| プラグインの読み込みが拒否される | グループ/その他ユーザーが書き込み可能、シンボリックリンク、ダイジェストの変化 | 権限を修正するか再インストール |
| 旧プラグインの移行失敗 | 旧 helper の使用中/ファイルの競合 | 移行の案内に従う。失敗時はロールバック |
| デプロイプラグインが利用できない | `deploy_plugins.enabled: false` | 明示的に有効化して再起動 |
| 通知チャネルが欠落 | helper が未インストール/無効 | 通知プラグインをインストールして有効化 |

プラグインディレクトリ:

```text
data/plugins/dns
data/plugins/deploy
data/plugins/notify
```

権限要件: ディレクトリは `0700`、helper は `0755`、所有者はサービス実行ユーザーです。

### 6.1 信頼チェーンをインポートしてもプラグインが TLS 検証失敗を表示する

まず具体的なメッセージに応じて原因を判断します。

- **証明書が期限切れまたは未発効**: 対象の証明書を更新してください。CA をインポートしても証明書の有効期間は延長されません。
- **証明書とアクセス先アドレスが一致しない**: 証明書の SAN に含まれるドメインでアクセスしてください。IP でアクセスする場合、証明書に対応する IP SAN が含まれている必要があります。
- **証明書が信頼されていない**: その証明書を発行した CA の公開鍵（ルート CA または中間 CA）をインポートしていることを確認してください。サイトのリーフ証明書ではありません。1 回の PEM インポートに複数の CA を含められます。インポート後の再起動は不要です。
- その他の場合: `openssl s_client -connect host:port -servername host -showcerts` で、対象が実際に返す証明書チェーンが完全か確認してください。

プラグインのサブプロセスは `SSL_CERT_FILE` 経由で `<data_dir>/trusted-ca-bundle.pem` を読み取ります。信頼チェーンはシステムのルート証明書、インポートした CA、プライベート CA を統合します。実際に管理下にある内部 CA のみをインポートしてください。

## 7. バックアップとリストア

### 7.1 バックアップのダウンロードに失敗する

- 現在のパスワードの再入力が必要です。TOTP を有効にしている場合は動的コードも必要です。
- バックアップパスワードは 12 文字以上です。
- リバースプロキシのリクエストボディ/レスポンスボディの制限。
- ディスク容量の不足。
- 操作ログとシステムログを確認してください。

### 7.2 リストア後に認証情報を復号できない

- バックアップ内の `config.yaml` とデータベースが対応しておらず、`salt` が異なる。
- データベースのみをリストアし、設定を失った。
- 解決策: 完全な ZIP バックアップでリストアしてください。データベースだけを個別に置き換えないでください。

### 7.3 リストア後にログインできない

- バックアップ内の管理者アカウントを使用してください。
- 既定ではセッション保持が有効なため、再起動後の再ログインは不要です。`security.session_persistence: false` にすると再起動でセッションがクリアされます。
- セキュアエントリが変わっている可能性があります。起動ログを確認してください。
- `jwt_secret` が異なると古いトークンは無効になります。
- リストアパッケージは `data/restore-pending/` にあります。適用済みか確認してください。

### 7.4 リストア後にサービスが自動起動しない

- Docker: `restart: unless-stopped` を確認してください。
- systemd: サービスが起動しているか確認してください。
- バイナリを直接実行: 手動で再起動する必要があります。
- 起動ログの設定検証エラーを確認してください。

## 8. データベース、ディスク、メモリ

### 8.1 データベースが大きくなる

- 証明書、タスクログ、操作ログ、システムログ、ACME オーダーはすべて増加します。
- 証明書の一括クリーンアップ、ACME 診断のクリーンアップ、システムログのクリアを使用してください。
- ピークを避けた時間帯に `/upgrade` の「データベースと設定のみを最適化」を実行し、必要に応じて VACUUM を有効にします。
- WAL のサイズを確認してください。最適化ツールは `wal_checkpoint(TRUNCATE)` を実行します。

### 8.2 ディスク不足

- `data/`、ログ、`upgrade-backups/`、バックアップファイルを確認してください。
- 古いアップグレードスナップショットと旧バイナリのバックアップを削除します（保持ポリシーに従う）。
- バックアップが同じデータディレクトリへ書き戻されていないことを確認してください。
- VACUUM には一時領域が必要で、ディスク不足時は失敗します。

### 8.3 メモリが高い/OOM になる

- メインプロセスのアイドル時のベースラインは数十 MB です。プラグインは一時的なサブプロセスで、`memory_limit_mb` によって制限されます。
- プラグインのインストール/更新の展開時には瞬間的なピークがあり、大きな DNS パッケージではより顕著です。
- 複数のタスクが同時実行されると、複数の helper が同時に起動します。
- コンテナのメモリ上限が低すぎないか確認し、ピーク用の余裕を確保してください。
- 並列度を下げるか helper のメモリ制限を下げますが、プラグインが正常に動作することを確認してください。

### 8.4 データベースのロック/書き込み失敗

- データディレクトリをマウントしているインスタンスが 1 つだけであることを確認してください。
- SQLite をマルチライトの共有ストレージに置かないでください。
- ディスクの満杯、権限、ファイルシステムの読み取り専用を確認してください。
- バックアップ/リストア中は大量の並列タスクを避けてください。

## 9. アップグレードと移行

### 9.1 起動時の移行失敗

- ログで失敗したステップを確認します。
- ディスク、権限、データベースの整合性を確認します。
- 修正後はそのまま再起動して再試行します。移行ステップは冪等で、失敗したバージョン番号は進みません。
- `upgrade.schema_version` を手動で削除しないでください。

### 9.2 アップグレード後にページが利用できない

- リバースプロキシ/静的リソースのキャッシュを確認します。
- 強制リロードまたは CDN キャッシュのクリアを行います。
- バイナリ/イメージのバージョンが一致しているか確認します。
- 起動ログとブラウザのコンソールを確認します。

### 9.3 プログラムの自己アップグレードが拒否される

- 読み取り専用ファイルシステム、`dev` ビルド、リリースパッケージのないプラットフォーム、チェックサム/署名の欠落はすべて拒否されます。
- コンテナ内のアップグレードはイメージを変更しません。イメージタグでアップグレードしてください。
- GitHub API のレート制限と外向きプロキシを確認してください。

## 10. ACME サーバーのトラブルシューティング

| クライアントのエラー | 考えられる原因 | 対処 |
| --- | --- | --- |
| `badNonce` | サービス再起動または nonce の期限切れ | クライアントは自動再試行。複数インスタンスでの共有を確認 |
| `unauthorized` | アカウント/JWS の誤り、EAB の欠落 | EAB、アカウントキー、エンドポイントを確認 |
| `rejectedIdentifier` | ドメインがホワイトリストにない | エンドポイントのドメインホワイトリストを確認 |
| `caa` | CAA がその CA を許可していない | CAA を調整するか CA を変更 |
| `orderNotReady` | チャレンジが未完了 | 認証を完了してから finalize |
| `rateLimited` | エンドポイントのレート制限に達した | `Retry-After` に従ってバックオフ |
| HTTP-01 の失敗 | 対象に到達不可/プライベートネットワークが拒否 | CIDR ホワイトリスト、ポート、ルーティングを確認 |
| mTLS の失敗 | クライアント証明書が信頼されていない | `mtls.client_ca` とクライアント証明書チェーンを確認 |
| リソース URL の誤り | `base_url` が未設定 | 固定の `acme.base_url` を設定 |

診断:

- 「ACME 診断」でアカウント、オーダー、認可、チャレンジ、証明書を確認します。
- `acme.base_url`、エンドポイントのホワイトリスト、EAB、チャレンジタイプを確認します。
- パブリックなデプロイでは、リクエストの Host から URL を推測することに依存しないでください。
- CRL/OCSP のエンドポイントは CA ごとに構成されます。クライアントからアクセスできることを確認してください。

## 11. インシデント対応

### 11.1 API キーの漏えいが疑われる

1. 「API キー」ページで該当キーを無効化または削除します。
2. 新しいキーを作成し、呼び出し元を更新します。
3. 操作ログで異常な呼び出し、デプロイ、秘密鍵のダウンロードを確認します。
4. デプロイ先に関わる場合は、対応する認証情報をローテーションします。
5. インシデントを記録し、振り返りを行います。

### 11.2 管理者アカウントの漏えいが疑われる

1. 直ちにパスワードを変更します。これによりすべてのセッション、API キー、パスキーが削除されます。
2. 復旧用メールアドレスが改ざんされていないか確認します。
3. 操作ログ、システムログ、リバースプロキシログを確認します。
4. DNS/デプロイ/通知の認証情報をローテーションします。
5. `salt` の漏えいが疑われる場合は、キー漏えいの手順に従い、必要に応じてインスタンスを再構築して認証情報を再登録します。
6. 影響を受けた証明書の再発行が必要か評価します。

### 11.3 証明書が誤ってデプロイ/上書きされた

1. 関連タスクを一時停止し、上書きの継続を防ぎます。
2. 対象システムのバックアップまたは証明書履歴から前のバージョンを復元します。
3. タスクのデプロイノードのパラメータとリロードコマンドを確認します。
4. 正しい証明書を再デプロイし、シリアル番号/フィンガープリントを検証します。
5. 根本原因を記録し、デプロイ前の検証を追加します。

### 11.4 ACME エンドポイントの悪用

1. エンドポイントを無効化するか、`acme.enabled` を無効にします。
2. アカウント、オーダー、送信元 IP を確認します。
3. EAB、mTLS、またはネットワーク ACL を有効にします。
4. 異常なアカウントとオーダーをクリーンアップします。
5. 想定外の証明書が発行されていないか評価します。

## 12. アップグレード情報の収集

ベンダーやコミュニティに問い合わせる際は、次を提供してください。

- LACTSSL のバージョン、ビルド日時、アーキテクチャ、デプロイ方法。
- OS、コンテナ/オーケストレーションのバージョン、リバースプロキシの種類。
- 再現手順、期待する結果、実際の結果。
- 関連するログの抜粋（マスキング済み）: 時刻、`X-Request-ID`、エラーコード。
- タスク/証明書/デプロイ記録の ID。
- 最近アップグレード、設定変更、プラグインの変更、認証情報のローテーションを行ったか。
- 試した対処とその結果。

提供しないでください。

- 管理者パスワード、TOTP シード、API キーの平文。
- 証明書の秘密鍵、CA の秘密鍵、バックアップパスワード。
- マスキングされていない DNS/デプロイ/通知の認証情報。
