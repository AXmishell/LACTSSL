# 製品機能

本文は機能領域ごとに LACTSSL ができること、主要パラメータ、制限を説明します。操作手順は[クイックスタート](getting-started.md)、[管理ワークスペース](administration.md)、[API 連携](api.md)、[セキュリティベースライン](security.md)を参照してください。

| 機能領域 | 主な内容 | 主な利用者 |

## 証明書の申請と更新

### 検証方式

- パブリック CA への申請は **DNS-01** のみを使用し、単一ドメイン、複数ドメイン、ワイルドカードに対応します。
- 「DNS アカウント」でプロバイダーの API 資格情報を設定すると、タスク実行時に TXT レコードを自動で作成/削除します。
- プライベート CA は ACME 検証を経ずに直接署名します。内蔵 ACME サーバーは HTTP-01、DNS-01、TLS-ALPN-01 を社内クライアントに提供します。

### 内蔵認証局

| CA | 説明 |
| --- | --- |
| Let's Encrypt | デフォルトのパブリック CA、EAB 不要 |
| ZeroSSL | EAB が必要 |
| Google Trust Services | EAB が必要 |
| LiteSSL | EAB が必要 |
| ZoTrus | EAB が必要（KID は登録メールアドレス）。手動 DNS 検証を使用し、ワイルドカードには未対応 |
| Actalis | EAB が必要 |
| SSL.com | EAB が必要（鍵種別に応じて ECDSA/RSA エンドポイントを自動選択） |

「パブリック認証局」では**汎用 ACME アップストリーム**も追加できます。ディレクトリアドレス、ACME v1/v2、任意の EAB を設定するとタスクとデフォルト CA の選択リストに表示されます。カスタムディレクトリアドレスは HTTPS が必須で、ローカルループバックのみ HTTP を許可します。ACME v1 は DNS-01 のみ対応し、EAB はサポートしません。

### キーと更新

- 秘密鍵の種類：`ecdsa`（デフォルト）、`ecdsa384`、`rsa2048`、`rsa4096`。
- 自動更新はデフォルトで期限前 30 日にトリガーされ、タスクごとに調整できます。スケジューラは 30 秒ごとに期限タスクを確認します。
- 申請ノードで「証明書の秘密鍵をサーバーに保存しない」を選択できます。秘密鍵は発行とデプロイ中のみメモリ上に保持され、DB に保存されずダウンロードもできません。自動更新時は再発行して再デプロイし、標準フローでは有効なデプロイモジュールが 1 つ以上必要です。
- 証明書管理ページは検索、状態、ソース（タスク発行、ACME サーバー、CSR）で絞り込めます。証明書チェーンのダウンロードには `certificates:read`、秘密鍵の表示/ダウンロードには `certificates:key` が必要です。
- ワンクリッククリーンアップは状態、期間、発行時刻、ドメイン、発行機関、ソース、「各タスクの最新証明書を保持」で絞り込めます。実行後、関連タスクの証明書参照はクリアされます。

### デフォルト設定

「パブリック認証局」で ACME アカウントのメールアドレス、デフォルト CA、秘密鍵種別、更新日数、各 CA の EAB 資格情報を設定できます。

### ターゲットフロー Beta

ターゲットフロー Beta は「証明書をパネルの Web サイトに追従させる」シナリオ向けです。デプロイプラグインの `plan` でターゲット内のサイトとドメインを読み取り、ポリシーに従ってグループ化し、証明書を申請して各サイトへデプロイします。

- タスクページと新規作成/編集ダイアログで「すべて / 通常フロー / ターゲットフロー Beta」を切り替えます。サイト一覧はターゲットから取得し、手入力に依存しません。
- 割り当てポリシーは、スマート推奨、1 サイト 1 証明書、メインドメインごとに統合、全サイトを 1 枚に統合、ターゲットソースごとに 1 枚、カスタムグループに対応します。
- サイトの選択、ドメインの包含/除外、追加ドメインの付加に対応します。自動更新時はサイトを再読み取りし、`すべてのサイト` では新規サイトを含め、`選択したサイトのみ` では保存済みのサイトキーを保持します。
- 1 つの Beta タスクに複数の証明書を関連付けられ、`certificates.task_id` がすべてを保持します。クリーンアップで「各タスクの最新証明書を保持」を有効にすると、Beta タスクの証明書は誤削除されません。

### クライアント CSR 申請

- API はクライアント CSR を受け取り、サーバーがパブリック CA への DNS-01 検証を代行して発行します。秘密鍵は生成も保存もせず、常にクライアントが保持します。
- 申請は非同期で、状態照会、キャンセル、再試行、申請単位の証明書チェーンダウンロードが可能です。
- ACME v2 パブリック CA と DNS-01 のみに対応し、ワイルドカードは DNS-01 が必要です。
- `certificates:request` 権限が必要で、`csr.allowed_domains` で申請可能なドメインを制限できます。

## DNS プロバイダー

公式 DNS 実装は内蔵され、約 235 の項目（lego v5 と互換 ID を含む）をカバーし、既定ではすべて無効です。「プラグイン」ページで必要なサービスプロバイダーを有効にしてください。資格情報は DB 書き込み前に暗号化され、`manual` プロバイダーは TXT レコードの手動追加が必要で自動フローに含まれません。一部のプロバイダーはカスタム API アップストリームアドレスに対応し、プロキシや互換ゲートウェイに利用できます。完全な一覧、資格情報、排障は[DNS プラグイン](dns-plugins.md)を参照してください。

## タスク編成

タスクはノードで構成され、デフォルトフローは「申請 → デプロイ（複数可）→ 通知」です。

| ノード | 主要パラメータ |
| --- | --- |
| 申請 | ドメイン、DNS アカウント、CA、秘密鍵種別、自動更新、事前日数 |
| デプロイ | ターゲット資格情報、証明書/秘密鍵パス、サイト/ドメイン/証明書名、リロードコマンド |
| 通知 | チャネル、トリガータイミング（常に / 成功時のみ / 失敗時のみ） |

- ノードは有効/無効の切り替えと並べ替えができ、複数のデプロイノードで同じ証明書を複数ターゲットへ配信できます。
- フローがない旧タスクは既存フィールドから同等のフローを推測します。アップグレード時は旧資格情報のデプロイパス、サイト、ドメインをデプロイノードへ移行します。
- 一覧は全選択と複数選択に対応し、一括実行、一時停止、自動更新の開始が可能です。一括実行は実行中タスクをスキップし、有効化/停止はスケジュール状態のみを変えて開始済みの発行を中断しません。
- 実行前には有効期間内で更新ウィンドウ外の同一ドメイン証明書を再利用し、デプロイのみ再実行します。再発行は「強制再発行」または API の `?force=1` を使用します。CA のレート制限時は「レート制限待ち」となり、CA が示す復旧時刻に再試行します。

## 証明書のデプロイ

「ターゲット資格情報」は認証と接続情報のみを保存し、証明書パス、リロードコマンド、デプロイドメイン、サイトはタスクのデプロイノードで入力します。同じ資格情報を複数のタスクで再利用できます。

### 内蔵ターゲット

| ターゲット | 資格情報 | デプロイパラメータ |
| --- | --- | --- |
| ローカルディレクトリ | なし | 証明書/秘密鍵パス、任意のリロードコマンド |
| SSH / SFTP | ホスト、ポート、ユーザー名、パスワードまたは秘密鍵、ホストフィンガープリント | リモートの証明書/秘密鍵パス、任意のリモートリロードコマンド |

SSH はデフォルトでターゲットのフィンガープリント（`SHA256:...`）入力を必須とします。「初回接続時にホスト鍵を自動信頼」を有効にした場合のみ TOFU で記録し、以降の不一致は接続を拒否します。

### プラグインターゲット

FTP/FTPS、Webhook、阿里云 CDN、七牛云、宝塔パネル、1Panel、雷池 WAF などは公式デプロイ実装として内蔵され、「プラグイン」ページでカテゴリと対象を有効にすると使用できます。デプロイ実装は証明書と秘密鍵を受け取るため信頼されたコードと同等で、既定では有効です。不要なターゲットは無効にしてください。詳細は[デプロイプラグイン](deploy-plugins.md)を参照してください。

### 内部 CA 信頼チェーン

「システム設定 → TLS 信頼チェーン」で内部 CA の公開鍵（PEM、ルートと下位 CA を含められる）をインポートできます。

- デプロイ実装が内部 HTTPS へアクセスする際、システムルートとインポート CA で TLS 検証を完了し、検証をスキップする必要がありません。
- 証明書監視はこれらの CA が署名したサイト証明書を信頼します。本プログラムのプライベート CA も自動的に追加されます。
- デプロイ、リロードコマンド、プラグインの子プロセスはマージされた `SSL_CERT_FILE` を読み、`CURL_CA_BUNDLE` と `REQUESTS_CA_BUNDLE` にも対応します。信頼チェーンは `trusted-ca-bundle.pem` に保存され、設定ページからダウンロードできます。

管理下にある内部 CA のみをインポートしてください。誤った CA は TLS 検証を弱め、CA を削除するとその CA が署名した証明書は信頼されなくなります。この機能は「証明書が信頼されない」問題のみを解決し、期限切れ、未発効、ドメイン不一致には更新またはアドレス変更が必要です。

### デプロイ記録

- デプロイごとに記録が生成され、証明書の詳細とログで結果を確認できます。
- 手動デプロイはタスクのデプロイノードパラメータを優先再利用し、ターゲットごとに今回のパラメータを個別入力することもできます。
- ローカル/SSH のリロードコマンドは、API キーが明示的に `deploy:execute` を持つ場合のみ実行できます。
- 失敗時にターゲット上の旧証明書へ自動ロールバックしません。ターゲット側で前バージョンを保持するか、アトミックなリリース機構を使用してください。

## サイト証明書監視

外部サイトを追加すると、サービスは定期的に TLS 接続で証明書を読み取ります。

- ターゲットは `example.com`、`example.com:8443`、完全な URL に対応し、デフォルトポートは `443` です。
- デフォルトで 24 時間ごとに確認し、監視項目ごとに調整できます。ホスト名、発行者、有効期限、状態を検証します。
- 残り 30 日以内は「期限間近」、期限切れ、接続失敗、チェーンが信頼されない/不完全、ホスト名不一致は異常とマークされ、状態変化時に通知されます。
- 監視はシステムの信頼チェーンを検証し、自己署名証明書による中間者攻撃を防ぎます。管理者がインポートした内部 CA とプライベート CA も含まれます。

## 通知

### 内蔵チャネル

- **メール（SMTP）**：サーバー、ポート、ユーザー名、パスワード、送信者、SSL 対応。
- デフォルトで暗黙的 TLS を使用します（`smtp.ssl=true`）。無効にした場合、STARTTLS 非対応サーバーへの送信を拒否し、リセットトークンなどの平文送信を防ぎます。

### プラグインチャネル

Gotify、ServerChan、ntfy、GoCQHTTP、PushDeer、Bark、Telegram、钉钉、企业微信、飞书、PushPlus、WxPusher、Synology Chat、汎用カスタム Webhook など、20 以上のチャネルを公式実装として内蔵しています。

- メール以外のチャネルは「プラグイン」ページで有効化し、テストメッセージを送信できます。
- タスクの通知ノードでは特定チャネルまたは有効化済みの全チャネルを選択でき、トリガーは常に、成功時のみ、失敗時のみに対応します。詳細は[通知プラグイン](notify-plugins.md)を参照してください。

## プライベート CA

「プライベート CA」で内部認証局を管理します。

### 生成

- 秘密鍵種別：ECDSA P-256 / P-384、RSA 2048 / 4096。有効期間は必要に応じて設定します。
- ルート CA を生成でき、「中間/発行 CA」を選択して既存の CA から下位 CA を署名することもできます。
- サブジェクト（ST、L、OU、Email、カスタムシリアル）、拡張（パス長、Key Usage、Extended Key Usage、SAN、Name Constraints）、インフラ（上位 CA、CRL 配布ポイント、OCSP アドレス、CA 発行者アドレス、ポリシー OID と CPS アドレス）を設定できます。
- SKI、AKI、CA 基本制約は自動生成され、上位 CA を選ぶと有効期間とパス長はその許容範囲に収束します。

### インポート

PEM 形式の CA 証明書と秘密鍵を貼り付け、CA 基本制約、署名用途、証明書と秘密鍵の一致を検証します。中間 CA では上位 CA を選択でき、署名を検証して階層関係を構築します。

### ダウンロードと削除

CA 証明書、秘密鍵、完全なチェーン（中間 + 上位）をダウンロードできます。一覧 API は内容を返さず、秘密鍵のダウンロードには `private_cas:key` が必要です。削除すると CA レコードと秘密鍵が削除され、下位 CA がある場合は先に削除する必要があります。

### 制限

- 秘密鍵は DB 書き込み前に暗号化されますが、HSM/KMS による管理ではありません。
- ルート CA と中間/発行 CA の両方を発行機関として使用でき、完全なチェーンは証明書とともに保存・デプロイされます。
- 証明書のデフォルト有効期間は 365 日で、CA の有効期限を超えません。
- CRL/OCSP アドレスは新規証明書に書き込まれますが、失効リストとオンライン状態サービスは外部 PKI が提供する必要があります。既存証明書は CDP/AIA 拡張を自動取得しないため再発行が必要です。

## ACME サーバー

内蔵 ACME v2 サーバーはデフォルトで有効で、プライベート CA を certbot、lego、acme.sh などに公開できます。エンドポイントを作成して有効化しない限り証明書は発行されません。

### エンドポイント

- 各エンドポイントは 1 つのプライベート CA にバインドされ、ランダムな URL slug（例 `/acme/internal/directory`）を使用します。
- EAB スイッチ、ドメイン許可リスト、HTTP-01 / DNS-01 / TLS-ALPN-01 の機能スイッチに対応します。
- 独立したリッスンポート、直接 TLS、任意の mTLS に対応し、証明書の有効期間、オーダーのレート制限、HTTP-01 の社内 CIDR 許可リストを設定できます。

### プロトコル機能

- アカウントは公開鍵のみを保存し、クライアント秘密鍵は保存しません。アカウントキーのローテーション（`keyChange`）に対応します。
- ARI（RFC 9773）に対応し、デフォルトで期限前約 1/3 ライフサイクル（最大 30 日）に更新ウィンドウを示します。失効/期限切れは過去のウィンドウを返して即時更新を促します。`replaces` は旧証明書の帰属、識別子の重複、重複置換を検証します。
- DNS と IP 識別子に対応します。IP は HTTP-01 / TLS-ALPN-01 のみで、IP セグメント許可リストが必要です。
- 新規証明書には CRL Distribution Point と OCSP AIA が書き込まれ、`/pki/{ca}/crl` と `/pki/{ca}/ocsp` で失効状態を確認できます。プライベート CA は `cRLSign` 用途が必要で、有効化時に検証されます。

### 診断とクリーンアップ

「ACME 診断」でアカウント、オーダー、認可、チャレンジ、証明書の状態を確認できます。エンドポイント、状態、時間で無効なオーダーと長期間未使用のアカウントをクリーンアップでき、アカウントの削除は履歴オーダーを消しますが発行済み証明書には影響しません。CRL/OCSP は CA ごとに編成され、ACME 登録エンドポイントを停止した後も到達可能に保つ必要があります。

## ダッシュボードとログ

### ダッシュボード

UI は簡体字中国語と英語に対応し、設定で切り替えられます。ホームには証明書の総数、期限間近/期限切れ、タスクと監視の状態、デプロイ成功率、期限分布、発行トレンドを表示します。

### ログ：操作ログ

- 「その他 → ログ」の上部タブに表示し、タスク実行、証明書発行、デプロイ、通知、監視、設定変更を記録します。
- ソース、レベル、キーワード、時間範囲で絞り込め、キーワードは保存された原文とパラメータ値に一致します（現在の言語のテンプレート文言には一致しません）。
- CSV/JSON でエクスポートでき、CSV は UTF-8 BOM 付きで Excel/WPS で開けます。範囲は直近 90 日に限られ、時刻はブラウザのタイムゾーン、指定がなければサーバーの `TZ` に従います。
- クリアには独立した `logs:write` が必要で、二段階確認を行います。アーカイブが有効な場合は `data/archives/logs/` へ書き込んでから削除し、クリア自体も監査ログを 1 件残します。

### ログ：システムログ

- 操作ログと同じページのタブに表示し、プロセスログから絞り込んで非同期で DB へ書き込みます。
- レベル、コンポーネント、キーワード、時間範囲で絞り込め、CSV/JSON エクスポートとクリアに対応します。アーカイブ有効時は先にアーカイブへ書き込み、クリアは操作ログに記録されます。
- デフォルトで `info` 以上を記録し、7 日または 20,000 行を保持します。HTTP アクセスログは既定で DB へ書き込まず、`log.system` で調整できます。

### ログ：アーカイブ

- 3 番目のタブに表示し、手動クリア、90 日の操作ログクリーンアップ、システムログの保持クリーンアップは削除前に自動でアーカイブを生成します。
- アーカイブは `*.ndjson.gz` と `*.manifest.json` で構成され、元のフィールド、行数、ID/時間範囲、トリガー理由、実行者、SHA-256、サイズを保存します。
- カテゴリ、理由、キーワード、時間範囲で絞り込み、ダウンロードまたは削除できます。既定では永久保持で、`log.archive.retention_days`、`max_total_mb`、`quota_policy` を設定できます。
- アーカイブ失敗時は削除がブロックされ、手動クリアはエラー、自動クリーンアップは次回再試行を待ちます。アーカイブは既定の ZIP バックアップに含まれず、別途転送が必要です。改ざん不能な監査ではなく、データディレクトリの権限を持つ管理者は削除・変更できます。

## 機能の境界

| 境界 | 説明 |
| --- | --- |
| パブリック証明書の検証 | DNS-01 のみ。パブリック CA への HTTP-01 申請は非対応 |
| マルチユーザー | 単一管理者アカウント、マルチユーザー/RBAC なし |
| アイデンティティフェデレーション | LDAP/OIDC/SAML/SCIM なし |
| 高可用性 | 組み込みクラスタ/Active-Active なし。SQLite 単一書き込み |
| 秘密鍵管理 | ローカル暗号化保存、HSM/KMS なし |
| 監視出力 | Prometheus メトリクスエンドポイントなし。ログと認証 API を提供 |
| デプロイのロールバック | ターゲットの旧証明書へ自動ロールバックしない。ターゲット側でバージョン保持が必要 |
