# デプロイアーキテクチャ

本文は LACTSSL をデプロイ・運用する開発者向けに、デプロイ単位、ネットワーク境界、容量見積もり、可用性設計を説明します。**デフォルトは単一インスタンス、SQLite 単一書き込み**です。現行バージョンでは PostgreSQL 18 も選択でき、`/upgrade` で 2 つのバックエンド間を変換できます。複数インスタンスによる PostgreSQL 共有はデフォルトで拒否され、HA は内蔵機能の範囲外です。

## デプロイ単位

LACTSSL は自己完結型の Go バイナリです：

- フロントエンドはバイナリに埋め込まれ、独立した Web サーバーや Node ランタイムは不要です。データはローカル SQLite に保存され、外部データベース、キャッシュ、メッセージキューに依存しません。
- 公式の DNS、デプロイ、通知実装はホストに組み込まれ、アップロードしたサードパーティ helper はワンショットの子プロセスとして実行されます。実行時の永続入力は `config.yaml` と `data/` の 2 種類のみです。

```text
/opt/lactssl/
├── lactssl                   # バイナリ
├── config.yaml               # 設定とキー、0600
└── data/                     # 0700
    ├── lactssl.db            # SQLite メイン DB
    ├── lactssl.db-wal        # WAL（実行時）
    ├── lactssl.db-shm        # 共有メモリ（実行時）
    ├── plugins/              # アップロード helper（dns / deploy / notify）
    ├── plugin-icons/         # プラグインアイコンのキャッシュ
    ├── upgrade-backups/      # 移行とプログラムアップグレードのバックアップ
    └── restore-pending/      # 適用待ちの復元パッケージ
```

## 参考トポロジー

### 単一ホスト + リバースプロキシ（推奨の起点）

```text
インターネット / 外部ネットワーク
        │ HTTPS 443
┌───────▼────────┐
│ Nginx / Caddy  │  TLS 終端、送信元制限、アクセスログ
│ / WAF / LB     │
└───────┬────────┘
        │ HTTP 127.0.0.1:8080
┌───────▼─────────────────────────────┐
│ LACTSSL                             │
│  ├─ 管理コンソール / API            │
│  ├─ スケジューラ（30 秒間隔）       │
│  ├─ プライベート CA / ACME（任意）  │
│  └─ SQLite + ローカルプラグイン     │
└───┬──────────┬──────────┬───────────┘
    │          │          │
 DNS API    デプロイ先   通知/メール
```

適用：大多数の単一環境デプロイ、数十〜数千枚の証明書。

- メインプログラムは管理ポートの TLS を提供しないため、リバースプロキシで終端します。プロキシと LACTSSL は同一ホストまたは同一セグメントに置き、バックエンドはループバックまたは社内ネットワークのみをリッスンします。
- プロキシは `X-Forwarded-For` を上書きまたは正しく追記し、`X-Forwarded-Proto` を渡します。`server.trusted_proxies` には正確な IP または最小 CIDR を登録し、追記チェーンでは全プロキシを登録します。`security.public_url` は固定の外部アドレスにします。

### DMZ プロキシ + 社内アプリケーション

```text
ユーザー ──HTTPS──► DMZ リバースプロキシ ──社内 HTTP──► LACTSSL（アプリ網）
                                              │
                                              ├─► DNS API / パブリック CA（アウトバウンド 443）
                                              ├─► SSH / パネル / CDN（ターゲット別）
                                              └─► SMTP / Webhook（チャネル別）
```

適用：セキュリティ要件が高く、管理面を内部セグメントに直接公開しない場合。

- ファイアウォールではプロキシから管理ポートへの通信のみを許可します。
- アウトバウンドはターゲット別に許可リスト化し、ドメイン制限ができない場合も宛先ポートとセグメントを制限します。DMZ で ACME を別途公開する場合は専用ポートを使い、管理ポートを再利用しません。

### 社内 PKI / ACME サービス

```text
社内サービス / certbot / lego / acme.sh
        │ ACME v2（HTTPS または mTLS）
┌───────▼────────────────────────┐
│ LACTSSL ACME エンドポイント    │  専用ポート :14000
│ プライベート CA をバインド     │ ドメイン許可リスト / EAB / チャレンジ種別
└───────┬────────────────────────┘
        │
   プライベート CA 階層
```

適用：社内サービス、デバイス、テスト環境の証明書。

- エンドポイントを作成して有効化しない限り証明書は発行されず、各エンドポイントにドメイン許可リストの設定が必須です。パブリックネットワークから到達可能な場合は EAB を有効にし、ネットワーク層で送信元を制限します。高い要件では mTLS を使用し、`acme.base_url` はクライアントが実際にアクセスする固定アドレスにします。
- CRL/OCSP は CA ごとに編成され、ACME 登録エンドポイントを停止した後も到達可能に保つ必要があります。

### コンテナプラットフォーム

```text
Ingress / Service
        │
┌───────▼────────┐
│ Pod: lactssl   │
│  /app/config    │── PVC または設定ボリューム
│  /app/data      │── PVC
└────────────────┘
```

- コンテナ内は常に `/app/config/config.yaml` と `/app/data` を使用し、エントリスクリプトは所有者を修正してから `lactssl` ユーザーで実行します。Compose は読み取り専用ルートと capabilities の削除を既定で行います。**単一レプリカ**とし、複数の Pod が同じ SQLite ボリュームへ同時に書き込まないでください。
- コンテナ内の自己アップグレードは再作成でイメージのバージョンへ戻るため、本番はイメージタグで更新します。`restart: unless-stopped` などで復元後の自動起動を確保します。

## ポートとネットワークフロー

| 方向 | ポート/プロトコル | 用途 | 推奨 |
| --- | --- | --- | --- |
| インバウンド | 443/TCP | 管理コンソールと API（リバースプロキシ経由） | 管理された送信元のみに公開 |
| インバウンド | 8080/TCP | LACTSSL メインリスン（デフォルト） | ループバック/社内ネットワークのみをリッスン |
| インバウンド | カスタム/TCP | ACME 専用リスン（任意） | 専用ポート、送信元を制限 |
| アウトバウンド | 443/TCP | DNS API、パブリック ACME CA、通知、Webhook、パネル、CDN | ドメイン/セグメント別の許可リスト |
| アウトバウンド | 22/TCP またはカスタム | SSH/SFTP デプロイ | 対象ホストのみ許可 |
| アウトバウンド | 21/990/TCP | FTP/FTPS デプロイ（プラグイン） | FTPS を優先し、ターゲットを制限 |
| アウトバウンド | 25/465/587/TCP | SMTP 通知 | SMTP サービスを使用 |
| アウトバウンド | カスタム | 自前の Gotify、社内 Webhook、監視対象 | 必要に応じて許可、SSRF 境界に注意 |

- サーバーはアウトバウンド先に SSRF 検証を行い、クラウドメタデータ、リンクローカル、予約ネットワークを拒否します。ループバックとプライベートネットワークは社内連携のため許可されます。デプロイ Webhook は秘密鍵を伴うため、パブリックネットワークのターゲットには HTTPS を強制し、ループバック、プライベートネットワーク、`.local`、`.internal` は HTTP を許可します。TLS 終端時は `X-Forwarded-Proto` を正しく渡さないと、Cookie の `Secure` 判定とレート制限の識別が誤ります。

## 容量計画

以下は**参考の起点**であり、容量の保証ではありません。実際の容量は証明書数、タスク頻度、ログ量、プラグイン種別、バックアップ戦略に依存するため、本番前に実負荷でテストしてください。

| 規模 | 証明書/タスク量 | 推奨構成 | 説明 |
| --- | --- | --- | --- |
| パイロット/小規模 | 証明書 100 枚未満、タスク少数 | 2 vCPU / 1 GB / 10 GB | 大型ヘルパーの同時インストールを避ける |
| 中規模 | 100〜1,000 枚、日常的な更新 | 2〜4 vCPU / 2 GB / 20 GB | ログローテーションと定期クリーンアップを有効化 |
| やや大規模 | 1,000〜5,000 枚、頻繁なデプロイ | 4〜8 vCPU / 4 GB / 50 GB+ | SQLite の書き込み増幅、バックアップ、プラグインのピークに注意 |

- アイドル時のメインプロセスは数十 MB です。プラグインは呼び出しごとの子プロセスで、単一ヘルパーは `memory_limit_mb`（デフォルト 128 MB）で制限されます。同時実行時は複数ヘルパーが起動し、インストール/更新時の展開でも一時的なメモリピークが生じるため、コンテナのメモリをアイドル時の使用量ちょうどに抑えないでください。
- データベースの増加は証明書、タスクログ、操作ログ、システムログ、ACME オーダーによるものです。操作ログとシステムログは `logs` テーブルを共有し `category` で区別され、保持とクリアはカテゴリごとに分離されています。証明書、ログ、ACME 診断データにはクリーンアップ入口があり、システムログは `retention_days` と `max_rows` で制御します。
- `data/upgrade-backups/` は直近 5 件の移行スナップショット、プログラムアップグレードは 3 件の旧バイナリを既定で保持します。バックアップは同じデータディレクトリへ書き戻さず、容量は DB サイズの数倍を見込んでください。

## 可用性と災害復旧

### 現行バージョンの可用性境界

- **クラスタ/Active-Active は非対応**。SQLite は単一書き込みのため、複数インスタンスが同じデータディレクトリを同時にマウントするとロック競合やデータ破損を招きます。
- **自動フェイルオーバーは提供しません**。プロキシは生存を検知できますが、同じデータを書き込む別インスタンスへ自動で切り替えるべきではありません。
- **単一管理者アカウント**は単一障害点です。失った場合はバックアップまたはパスワードリセットで復旧し、職責を職位に紐づけて引き継ぎます。

### 単一アクティブ + 迅速復旧（推奨）

```text
プライマリインスタンス ──定期暗号化バックアップ──► 独立バックアップストレージ
   │
   └─ 障害 ──► 新ホスト/新コンテナ ──バックアップ復元──► トラフィック切替
```

| 指標 | 推奨 |
| --- | --- |
| RPO | 許容できる停止時間に応じて少なくとも 1 日 1 回。重要な環境では時間単位まで短縮 |
| RTO | 「ホスト準備 + バックアップ復元 + 起動検証」で見積もり、訓練後に Runbook へ記載 |
| バックアップ保持 | 少なくとも 7〜30 日。必要に応じて延長 |
| 訓練頻度 | 四半期ごとに少なくとも 1 回の完全復旧訓練 |

復旧手順は[運用マニュアル](operations.md)を参照してください。

### コンテナとホスト層の高可用性

オーケストレーションは**プロセス**の再起動を保証できますが、データの単一書き込み問題は解決できません。

- レプリカ数は 1 に固定し、永続ボリュームで Pod 再作成後のデータ消失を防ぎます。ヘルスチェックには TCP ポートまたは認証付き `/api/status` を使用し、セキュアエントリ Cookie が必要なページを未認証監視に使わないでください。ノード障害時は単一レプリカが再スケジュールされ、データボリュームを再マウントできる必要があります。

### マルチ環境の分離

本番、ステージング、テストは独立したインスタンスを使用します。

- `config.yaml`、`security.salt`、データディレクトリを環境ごとに分け、独立した DNS サブアカウント、デプロイ資格情報、通知チャネルを使ってテストが本番へ影響しないようにします。本番データベースをテストへコピーした後は同じ資格情報を使い続けず、先にローテーションします。

## 監視と可観測性

Prometheus メトリクスエンドポイントは提供しませんが、以下のシグナルで監視を構築できます：

| シグナル | 方法 | 推奨 |
| --- | --- | --- |
| プロセス生存 | TCP ポート監視 | 30〜60 秒に 1 回 |
| 詳細ヘルス | `GET /api/status`、`system:read` を持つ API キーを使用 | 1〜5 分に 1 回、200 と応答時間を確認 |
| タスク失敗 | 操作ログの絞り込みまたは通知チャネル | タスク失敗/デプロイ失敗を即時アラート |
| 証明書期限間近 | ダッシュボード、サイト監視、タスク更新状態 | 期限前 30/14/7 日に段階的に通知 |
| ログ異常 | システムログのキーワード、リバースプロキシの 5xx | 外部のログ基盤に接続 |
| ディスク/バックアップ | ホストまたはプラットフォーム監視 | ディスク < 20% とバックアップ失敗でアラート |

`/api/status` は認証が必要で、匿名のヘルスチェックには使えません。匿名監視ではポートへの接続可否のみ判断できます。

## TLS と証明書の境界

- 管理コンソールの TLS はリバースプロキシが提供し、メインポートには直接 TLS を設定しません。プロキシは内部 CA またはパブリック CA の証明書を使い、HSTS、TLS 1.2+ を設定して弱い暗号スイートを無効化します。
- ACME の専用リスンは直接 TLS を提供でき（`acme.tls.cert/key`）、プロキシで終端することもできます。mTLS には ACME の TLS 証明書と秘密鍵の同時設定が必要です。
- 管理する証明書の秘密鍵はデータベースに保存され、`security.salt` から派生したキーで暗号化されます。HSM/KMS は提供せず、バックアップには暗号化資格情報とキー素材が含まれるため機密ファイルとして管理してください。

## アーキテクチャ決定チェックリスト

| 決定 | 選択肢 | 推奨 |
| --- | --- | --- |
| デプロイ方式 | Docker / バイナリ / オーケストレーションプラットフォーム | コンテナ基盤があればイメージ、なければバイナリ + systemd |
| TLS 終端 | リバースプロキシ / ACME 専用リスン | 管理面は統一的にリバースプロキシ経由 |
| データストレージ | ローカルディスク / 永続ボリューム / ネットワークディスク | 単一書き込みマウントのみ使用。ネットワークディスクは SQLite のロックを検証 |
| 可用性 | 単一アクティブ + バックアップ / プラットフォーム再起動 | Active-Active は使用せず、RTO/RPO を明確化 |
| アウトバウンド戦略 | 全許可 / ドメイン許可リスト / プロキシ | 本番はターゲット別許可リスト、必要に応じてプロキシ |
| プラグインソース | 内蔵の公式実装 / サードパーティ helper のアップロード | 本番は内蔵実装と検証済み helper のみ有効化 |
| アップグレード方式 | イメージタグ / バイナリ置換 | コンテナはイメージ、バイナリはリリースパッケージでロールバックを保持 |
