# 通知プラグイン

通知プラグインは、証明書の発行、デプロイ、監視、システムイベントを企業 IM、メール、Webhook へプッシュします。企業利用では**アラートルーティング、チャンネルの可用性、キーのローテーション、ノイズ制御**に重点を置きます。

## 1. 組み込みチャンネルとプラグインチャンネル

| 種別 | チャンネル | 組み込み | 説明 |
| --- | --- | --- | --- |
| 組み込み | メール（SMTP） | はい | SSL をサポート。デフォルトは暗黙的 TLS |
| プラグイン | Gotify、ServerChan、ntfy | いいえ | セルフホスト/サードパーティのプッシュ |
| プラグイン | Telegram、Bark、PushDeer | いいえ | モバイルプッシュ |
| プラグイン | DingTalk、WeCom ロボット/アプリ/スマートロボット、Feishu | いいえ | 企業 IM |
| プラグイン | GoCQHTTP、iGot、PushPlus、WePlus、WxPusher、WxPusher SPT、OpenILink、WPush、Synology Chat、PushMe、ChronoCat | いいえ | その他のチャンネル |
| プラグイン | 汎用カスタム Webhook | いいえ | 内部アラートプラットフォームとの連携 |

helper が未インストールまたは未有効化の場合、通知ページにはメールのみが表示されます。過去のチャンネル設定は失われず、helper をインストール後に引き続き使用できます。

## 2. 設定

```yaml
notify_plugins:
  enabled: true           # デフォルトで有効
  dir: ""                 # 空の場合は <data_dir>/plugins/notify
  memory_limit_mb: 128    # 単一 helper の常駐メモリ上限
  timeout_seconds: 30     # 1 回の send のタイムアウト
  max_output_kb: 64       # helper 出力の上限
```

3 種類のプラグインは `<data_dir>/plugins` 配下の独立したサブディレクトリを使用します:

- DNS: `<data_dir>/plugins/dns`
- デプロイ: `<data_dir>/plugins/deploy`
- 通知: `<data_dir>/plugins/notify`

設定変更後はサービスを再起動すると反映されます。起動時に自動スキャンします。新しい helper をインストールした後は、「プラグイン」ページで「プラグインを再スキャン」をクリックするか、次を呼び出します:

```bash
curl -X POST -H "Authorization: Bearer $LACTSSL_TOKEN" \
  https://ssl.example.com/api/plugins/rescan
```

## 3. インストールと有効化

1. 「プラグイン」ページを開き、リポジトリ URL を確認して「インデックスを更新」をクリックします。
2. 「プラグインマーケット」で必要な通知チャンネルをインストールします。
3. まずプラグインファイルを有効化し、次にチャンネル一覧で具体的なチャンネルを有効化します。新しくダウンロードしたファイルとエントリはデフォルトで無効です。
4. 「通知」ページでチャンネル認証情報を設定し、テストメッセージを送信します。

有効状態は settings テーブルの `plugins.notify.enabled_channels` に保存され、再起動と再スキャン後も保持されます。有効化されたチャンネルのみが「通知」ページとタスクの通知ノードに表示されます。

メールはプラグインではなく、常に利用可能で無効化できません。

## 4. 企業アラート設計

### 4.1 ルーティング

| イベント | 推奨送信先 | 説明 |
| --- | --- | --- |
| 証明書の発行失敗 | 運用当番 | 直ちに対応が必要。更新に影響する可能性 |
| デプロイ失敗 | 運用 + ターゲットシステム責任者 | ターゲットシステムとリロードコマンドを確認 |
| 証明書の期限接近 | 運用 + ビジネス責任者 | 30/14/7 日の段階分け |
| サイト監視の異常 | 運用 | ネットワーク、チェーン、ホスト名の問題を区別 |
| バックアップ失敗 | プラットフォーム | 証明書アラートとは分離 |
| セキュリティインシデント | セキュリティ | 異常ログイン、プラグイン検証失敗など |
| テストメッセージ | 専用テストチャンネル | 本番の当番グループへ送らない |

### 4.2 ノイズ削減

- 環境ごとに異なる通知チャンネルと投稿先を使用してください。
- タスク通知ノードは「常に/成功時のみ/失敗時のみ」で選択し、成功メッセージが失敗を埋もれさせないようにしてください。
- 同種のイベントには集約またはサイレントウィンドウを設定してください（外部 IM/アラートプラットフォームで実装）。
- 監視項目はビジネス上の重要度で段階分けし、不安定なターゲットへの頻繁なアラートを避けてください。
- 無効になったチャンネルと重複設定を定期的にクリーンアップしてください。

### 4.3 可用性

- 少なくとも 2 つの独立したチャンネル（例: メール + 企業 IM）を設定し、単一障害点を避けてください。
- 定期的にテストメッセージを送信し、Token/Webhook が期限切れでないことを確認してください。
- チャンネルプロバイダーのレート制限とコンテンツ審査に注意してください。
- 通知失敗はログに記録されます。通知失敗自体も監視対象にすることを推奨します。

## 5. チャンネル認証情報のガバナンス

- 専用のボット/アプリを使用し、個人アカウントの Token を使用しないでください。
- メッセージ送信に必要な権限のみを付与し、組織管理、連絡先読み取りなどの権限は付与しないでください。
- 環境/チームごとに異なるボットを使用してください。
- Token の責任者、作成日時、ローテーション周期を記録してください。
- 認証情報はデータベースへ書き込む前に暗号化され、API レスポンスではマスクされます。
- Token、Webhook URL をタスク名、備考、ログに書き込まないでください。
- 漏洩時は直ちにチャンネル側で失効させ、LACTSSL の設定を更新してください。

## 6. メール（SMTP）

- デフォルトでは暗黙的 TLS を使用します（`smtp.ssl=true`）。
- 暗黙的 TLS を無効にした場合、SMTP サーバーが STARTTLS をサポートしていなければ、サービスは送信を拒否し、パスワードリセットトークンなどの機密メールが平文で送信されるのを防ぎます。
- 企業のメールゲートウェイ、専用送信アカウント、SPF/DKIM/DMARC の使用を推奨します。
- 復旧用メールアドレスと通知送信アカウントは分離し、相互に影響しないようにしてください。
- テストメールと本番通知では異なる受信者を使用してください。

## 7. Helper プロトコル v1（連携開発）

helper は実行ファイルで、2 つのサブコマンドをサポートします:

```bash
notify-helper manifest   # JSON マニフェストを出力
notify-helper send       # stdin からリクエストを読み取り、通知を送信
```

`manifest` 出力例:

```json
{
  "protocol": "v1",
  "name": "example notify helper",
  "version": "1.0.0",
  "sha256": "省略可能な helper ファイルのチェックサム",
  "channels": [
    {
      "id": "example-push",
      "name": "Example Push",
      "description": "通知を Example サービスへプッシュします",
      "fields": [
        {"key": "url", "label": "サービスアドレス", "type": "text", "required": true},
        {"key": "token", "label": "Token", "type": "password", "secret": true, "required": true}
      ]
    }
  ]
}
```

フィールドの説明:

- `secret: true` または `type: "password"` のフィールドは API レスポンス時にマスクされ、チャンネル設定とともに暗号化して保存されます。
- フィールドタイプは `text`、`password`、`textarea`、`number`、`select`、`switch` をサポートします。
- チャンネル `id` は小文字、数字、アンダースコア、ハイフンのみを含められます。組み込みメール（`mail`）と重複するプラグインは無視されます。
- `label_key` は任意で、公式フロントエンドは i18n key によるローカライズを優先します。サードパーティプラグインは `label` を直接提供できます。

`send` の stdin:

```json
{
  "action": "send",
  "protocol": "v1",
  "channel": "example-push",
  "config": {"url": "https://push.example.com", "token": "..."},
  "title": "証明書の発行に成功: example.com",
  "body": "タスク：example.com\n状態：成功"
}
```

規約:

- 終了コード `0` は成功、非 `0` は失敗を表します。stderr は通知ログに入ります（機密値はマスクされます）。
- stdout は空、または 1 行の JSON `{"ok": true, "message": "..."}` を出力できます。`ok` が `false` の場合は失敗として扱います。
- 不正な JSON はエラーとみなされます。デバッグログは stderr に書き込んでください。
- helper は `LACTSSL_PLUGIN_MEMORY_LIMIT`（バイト）からメモリ予算を取得します。
- メインプログラムは helper の `VmRSS` を定期的に確認し、`memory_limit_mb` を超えるとプロセスグループ全体を終了してエラーを記録します。
- メインプログラムは最小限の環境変数セットのみを渡し、サーバー側のキーを漏洩しません。
- プラグインファイルは実行可能で、グループまたは他のユーザーに書き込みを許可してはなりません。`manifest.sha256` が空でない場合は検証します。
- メインプログラムはスキャン時のファイルダイジェストを記録し、各送信前に再検証します。helper を置き換えた後は再スキャンが必要です。

## 8. セキュリティ推奨事項

- 信頼できる helper のみを有効化してください。通知プラグインはチャンネルキーを読み取れるため、信頼されたコードと同等です。
- プラグインディレクトリは `0700`、helper は `0755`、所有者はサービスの実行ユーザーにします。
- 本番ではマニフェストに `sha256` を記入し、アップグレード後にダイジェストを更新してください。
- 適切な `memory_limit_mb` と `timeout_seconds` を設定し、異常なプラグインが通知送信を遅延させないようにしてください。
- 通知内容にはドメイン、エラー詳細、内部アドレスが含まれる場合があります。公開チャンネルへ送信しないでください。
- Webhook ターゲットは HTTPS と署名検証を使用し、偽造/リプレイを防いでください。

## 9. トラブルシューティング

| 現象 | 原因 | 対処 |
| --- | --- | --- |
| 通知ページにメールのみ表示 | 通知プラグインが未インストール/未有効化 | notify プラグインをインストールして有効化 |
| チャンネルがタスクノードにない | チャンネルが未有効化 | プラグインページと通知ページで有効化 |
| テストメッセージの失敗 | Token/URL/ネットワーク | チャンネル設定とアウトバウンドポリシーを確認 |
| メール送信の失敗 | SMTP TLS/認証/送信者 | 暗黙的 TLS、STARTTLS、SPF/DKIM を確認 |
| 通知の遅延 | チャンネルのレート制限/ネットワーク | チャンネル状態とログを確認 |
| 通知内容に機密情報が含まれる | テンプレート/ログのマスク不足 | 内容を調整し、認証情報と秘密キーの送信を避ける |

その他のトラブルシューティングは[監視とトラブルシューティング](troubleshooting.md)を参照してください。
