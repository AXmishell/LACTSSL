# アップグレードと変更

バージョンアップグレードは、証明書基盤における日常変更の中でも特にリスクが高い作業です。データベース移行をロールバック可能に保つことと、証明書の一斉失効時に停止を持ち込まないことの両方が必要です。本書では、アップグレード前の評価、移行の仕組み、プログラムのアップグレード、ロールバック、変更ウィンドウのチェックリストを説明します。

## 1. 変更の原則

- **まずバックアップ、次にアップグレード**: `config.yaml` + `data/` 全体、または画面からの暗号化バックアップを使用します。
- **まずステージング、次に本番**: 少なくとも発行、デプロイ、通知、API の 4 経路を検証します。
- **バージョンを固定**: 本番では追跡不能な `latest` で長期運用しません。
- **ロールバックポイントを確保**: データベース移行スナップショット、旧バイナリ/旧イメージタグ。
- **ピークを避ける**: 証明書の一斉失効、一括デプロイ、業務リリースのウィンドウと重ねないでください。
- **可観測性**: アップグレード後は少なくとも 1 回のスケジューリング周期と 1 回のタスク実行を観察します。

## 2. アップグレードで行われること

LACTSSL は長期の開発の中で、歴史的なデータ形式と互換分岐を蓄積してきました。`internal/upgrade` は新バージョンの初回起動時に履歴移行を自動実行します。また、ログイン後に `/upgrade` へアクセスして、事前チェック、手動移行、データベース最適化を実行できます。

### 2.1 自動移行の順序

1. `config.yaml` を読み込み、検証します。
2. 設定されたデータベース（既定は SQLite、PostgreSQL も可）を開き、基本テーブルを作成します。
3. アップグレードツールを生成し、`upgrade.schema_version` を読み取ります。
4. バージョンが古い場合は、データベースと設定をバックアップしてから、移行ステップを順番に実行します。
5. 新しいバージョン番号を書き込み、低コストなデータベース最適化を実行します。
6. 続いてアカウント、スケジューラ、HTTP サービスの初期化を行います。

- 自動移行は `upgrade.auto` で制御され、既定で有効です。
- 移行ステップはすべて冪等です。失敗時にはバージョン番号を進めず、次回起動時に失敗したステップを再試行します。
- 移行前のバックアップは `data/upgrade-backups/<UTC 時刻>/` に置かれ、既定で直近 5 件を保持します。

### 2.2 移行の内容

| 問題 | 旧バージョンの挙動 | アップグレードツールの処理 |
| --- | --- | --- |
| データベースに形式バージョンがない | `ensureColumn` と散在する移行キーからしか構造を推測できない | `upgrade.schema_version` を書き込み、バージョン順に冪等なステップを実行 |
| 機密フィールドが平文 | 旧版の TOTP キー、証明書秘密鍵がそのまま保存 | AES-256-GCM で暗号化し、すでに暗号文のレコードは自動的にスキップ |
| 旧版のキーファイル | `data/jwt.secret` と `config.yaml` にキーが二重に存在 | 設定にキーが保存されたことを確認してからアップグレードバックアップディレクトリへ移動し、整理 |
| グローバル EAB 認証情報 | `acme.eab_kid` / `acme.eab_hmac` は既定 CA にのみ適用 | 既定 CA の個別設定へ移行し、旧キーを整理 |
| デプロイパラメータが認証情報に混在 | パス、サイト、リロードコマンドが対象の認証情報に保存 | タスクフローのデプロイノードへ分離し、認証情報は認証情報のみを保持 |
| 重複したデプロイ先 | `qiniu_cdn`、`baota_site` などの旧 ID が分散 | 正規 ID に統合し、サイト/パネル、CDN/Kodo の選択をノードへ書き込み |
| 旧通知設定 | Gotify / Server酱が独立した設定キーを使用 | 汎用的な通知チャネル設定へ変換し、旧キーを整理 |
| プラグイン移行の残骸 | 旧フルセット helper、無効化リスト、欠落した有効化ホワイトリスト | DNS/デプロイ/通知のホワイトリストを初期化し、組み込み項目の既定の有効状態を維持 |
| 旧検証モード | `password_passkey` などの履歴値 | `passkey` に正規化し、無効な値はフォールバック |
| データベースの肥大化 | 証明書、ログ、ACME オーダーを削除した後に空きページが残る | `VACUUM` で領域を回収し、`ANALYZE` で統計を更新 |
| WAL の肥大化 | 長期稼働後に `-wal` ファイルが増え続ける | `wal_checkpoint(TRUNCATE)` で折り畳み、切り詰め |
| ホットパスインデックスの欠落 | 証明書の絞り込み、スケジューリング、ログ削除が全表走査 | インデックスを自動追加。繰り返し実行しても安全 |
| ログテーブルの分離 | システムログは `system_logs`、操作ログは `logs` に保存 | システムログを `logs(category=runtime)` へコピーし、旧テーブルはロールバック用に保持 |
| 設定構造の陳腐化 | `plugins.repo`、`notify_plugins`、`log.system`、`upgrade` などの新しいセクションが欠落 | 現行バージョンに合わせて不足フィールドを補完し、コメントを保持して等価な記法を正規化 |

## 3. アップグレード前のチェック

- [ ] 対象バージョンの変更点と移行手順を読む。
- [ ] 現在のバージョン、データ形式のバージョン、未適用の移行ステップを確認する。
- [ ] `config.yaml` と `data/` をバックアップし、バックアップが読めることを検証する。
- [ ] ディスク容量が十分であることを確認する（`VACUUM` には一時領域が必要）。
- [ ] ステージング環境で発行、デプロイ、通知、API を検証する。
- [ ] 旧バージョンのバイナリ/イメージタグが利用可能であることを確認する。
- [ ] 関係者へ通知し、ピークを避けたウィンドウを選ぶ。
- [ ] 一括タスクを一時停止し、アップグレード中の同時書き込みを避ける。

## 4. アップグレード方法

### 4.1 Docker（推奨）

```bash
# 対象バージョンを固定: 先に docker-compose.yml の image タグを 1.2.3 に変更
docker compose pull
docker compose up -d
docker compose logs -f lactssl
```

- 明確なバージョンタグを使用すると、ロールバックが容易です。
- コンテナ内で自己アップグレードを行わないでください。コンテナを再作成するとイメージのバージョンに戻ります。
- 公式 Compose は既定でルートファイルシステムを読み取り専用にするため、プログラムディレクトリは書き込み不可となり、画面には自己アップグレード非対応の旨が表示されます。これは想定どおりの動作です。

### 4.2 バイナリ

```bash
sudo systemctl stop lactssl
sudo cp lactssl /opt/lactssl/lactssl
sudo chown lactssl:lactssl /opt/lactssl/lactssl
sudo chmod 0755 /opt/lactssl/lactssl
sudo systemctl start lactssl
sudo journalctl -u lactssl -f
```

注意:

- アップグレードでは元のファイルパーミッションビットは保持されますが、`setcap` などの拡張属性は保持されません。特権ポートやファイルケイパビリティを使用するデプロイでは、アップグレード後に再設定が必要です。
- 新しいバイナリを直接 `exec` する自己アップグレードは Linux/macOS/FreeBSD で利用できます。Windows ではサービスマネージャーによる再起動が必要です。
- `dev`/ソースビルド、および `checksums.txt` もアセットの SHA-256 もないリリースパッケージは自己アップグレードを拒否します。手動で置き換え、ご自身で検証する必要があります。

### 4.3 プログラムの自己アップグレード（任意）

`/upgrade` ページの上部に「プログラムのアップグレード」があります。

- **アップデートを確認**: `upgrade.program.channel` に従って Release を照会します。`stable` は正式版のみを受け入れ、`beta` はプレリリースを含みます。
- **アップデートをインストール**: `lactssl_<version>_<os>_<arch>.tar.xz`（存在しない場合は `.tar.gz` にフォールバック。Windows は `.zip`）をダウンロードし、`checksums.txt` を使って SHA-256 を強制検証してから、`lactssl` を展開して現在の実行ファイルを置き換えます。
- **リリース署名**: 公式ビルドはリリース公開鍵を自動的に埋め込み、既定で `checksums.txt.sig` の検証を必須にします。署名の欠落や不一致は即座に拒否されます。自前ビルドで `upgrade.program.public_key` が未設定の場合、オンラインアップグレードは既定で拒否されます。未署名パッケージをインストールするには、管理された環境で `upgrade.program.allow_unsigned: true` を明示的に設定する必要があります。
- **バックアップとロールバック**: 置き換え前に旧バイナリを `<data_dir>/upgrade-backups/program/` へコピーし、既定で直近 3 件を保持します。
- **再起動で反映**: インストール完了後、ページに再起動の案内が表示されます。既定ではセッション保持が有効なため、元のセッションを引き続き使用できます。`security.session_persistence: false` にすると再起動時にセッションがクリアされます。

制限:

- 読み取り専用ファイルシステム、リリースパッケージのないプラットフォーム、`dev` ビルドはアップグレード不可と表示されます。
- コンテナ内のアップグレードはイメージを変更しないため、再作成するとイメージのバージョンに戻ります。
- GitHub API のトークンが未設定の場合、匿名のレート制限を受けます。`upgrade.program.token` で設定できます。
- 外向きプロキシが必要な場合は、システムのプロキシ環境変数で設定します（Go HTTP クライアントの挙動）。

## 5. アップグレード後の検証

1. 起動ログの「データ形式のアップグレード完了」を確認します。
2. ログイン後に `/upgrade` を開き、すべてのステップが「完了」または「スキップ」であることを確認します。
3. バージョン、ビルド日時、アーキテクチャを確認します。
4. 管理者ログイン、TOTP/パスキーを検証します。
5. 証明書一覧、タスク、デプロイ認証情報、通知チャネル、プラグインを確認します。
6. テストタスクを 1 件手動で実行し、発行、デプロイ、通知を確認します。
7. API キーの権限と呼び出しを確認します。
8. 少なくとも 1 回のスケジューリング周期（30 秒）と 1 回の自動更新を観察します。

## 6. ロールバック

### 6.1 データのロールバック

アップグレードツールは構造変更の前にスナップショットを生成します。

```text
data/upgrade-backups/20260101-120000/
├── lactssl.db
└── config.yaml
```

手順:

1. サービスを停止します。
2. バックアップ内の `lactssl.db` で現在のデータベースを上書きし、`lactssl.db-wal`、`lactssl.db-shm` を削除します。
3. 設定も併せてロールバックする場合は、バックアップ内の `config.yaml` で現在の設定を上書きします。
4. 旧バージョンのプログラムを起動します。

注意:

- 旧バージョンのプログラムは、新バージョンが書き込んだデータ形式を読めない場合があります。メジャーバージョンをまたぐロールバックでは、バイナリとバックアップデータを同時にロールバックしてください。
- `upgrade.schema_version` を手動で削除しないでください。移行ステップが再実行されます。
- 自動移行に失敗した場合、サービスは起動を拒否し、失敗したステップを出力します。権限、ディスク、データの問題を修正した後、そのまま再起動すれば再試行されます。

### 6.2 プログラムのロールバック

プログラムアップグレードのバックアップは次にあります。

```text
data/upgrade-backups/program/
├── 20260101-120000-lactssl-1.2.2
└── 20260102-090000-lactssl-1.2.3
```

手順:

1. サービスを停止します。
2. バックアップファイルで現在のバイナリを上書きし、実行権限を復元します（`chmod 0755`）。
3. データもロールバックする場合は、前節の手順に従います。
4. サービスを起動し、バージョン番号とデータ形式の移行状態を確認します。

## 7. データベースのオンライン切り替え（SQLite ↔ PostgreSQL）

`/upgrade` ページではデータベースバックエンドの切り替えを提供します。切り替えはサービスプロセス内で完結し、SQL を手動で実行したりデータベースファイルを置き換えたりする必要はありません。

### 7.1 前提

- 対象の PostgreSQL は 18 を推奨します。アプリケーションはサーバーのバージョンを検査します。
- 対象の PostgreSQL は既定で空のデータベースである必要があります。空でない場合はページで「現在の schema をクリア」をチェックする必要があります。この操作は現在の schema 内のテーブルのみを削除します。
- 既定では 2 つ目のインスタンスが同じ PostgreSQL データベースを共有することは許可されません（`database.allow_multi_instance: false`）。切り替え前にも検査されます。
- 切り替え前には元のデータベースのバックアップが強制されます。SQLite は `VACUUM INTO`、PostgreSQL/MySQL は Go ネイティブの論理バックアップを使用し、バックアップは `data/db-convert/backups/<時刻>/` に置かれます。
- サービスは systemd、Docker の restart policy、または同様のプロセス管理下で動作している必要があります。そうでない場合、切り替え後に手動で起動する必要があります。

### 7.2 実行フロー

1. `/upgrade` で対象のバックエンドを選択します。PostgreSQL ではホスト、ポート、ユーザー名、パスワード、データベース名、SSL モードを入力できます。また「ネイティブ DSN」に切り替えて完全な DSN を直接貼り付けることもできます。SQLite ではファイルパスを入力します（`data_dir` 内である必要があります）。
2. 「接続テスト」と「事前チェック」をクリックし、対象のバージョン、空データベースの状態、テーブルと行数を確認します。
3. アカウントパスワード/TOTP を入力し、ページ上の計算による確認を完了してから切り替えを開始します（画面では `CONVERT` の手動入力は求められなくなりましたが、API では引き続きこの確認語を使用します）。
4. 切り替え中はメンテナンスモードに入り、通常の API は一時停止します。アプリケーションはまずバックアップを行い、その後書き込みを凍結し、テーブルごとにコピーし、行数とテーブルごとのハッシュを検証し、機密フィールドの復号をサンプリングします。
5. 検証に通過すると `config.yaml` をアトミックに書き換え、`data/db-convert/state.json` を書き込み、自動的に再起動します。
6. 新しいプロセスが対象のデータベースを開き、起動時のセルフチェックを実行します。失敗した場合は自動的に旧設定へ戻り、元のデータベースに戻ります。セルフチェックに通過すると、旧 SQLite データベースファイル（`-wal`/`-shm`/`-journal` を含む）は自動的に削除されます。切り替え前のバックアップは引き続き保持されます。

書き込み凍結の時間はデータ量に依存します。一般的な小規模データベースでは秒単位、ログや証明書が多い場合は分単位です。コピーと検証の間も、ページは進捗をポーリングできます。

### 7.3 ワンクリックロールバック

切り替え完了後、`/upgrade` に「ワンクリックロールバック」が表示されます（同種移行を除く）。ロールバックは単に旧設定へ戻すのではなく、**現在のデータベースの最新データ**を切り替え前のバックエンドへ逆方向に切り替え、その後設定を切り替えて再起動するもので、切り替え後の書き込みを失わないようにします。

ロールバックでも現在のデータベースのバックアップが強制され、書き込みが凍結され、検証が行われます。ページ上の計算による確認を完了し、アカウントパスワード/TOTP を入力する必要があります（API では引き続き `ROLLBACK` を確認語として使用します）。切り替え前の設定バックアップは `config.yaml.before-db-convert-<時刻>` に保持されます。切り替えのセルフチェックに通過すると旧 SQLite ファイルは自動的に削除されますが、`data/db-convert/backups/<時刻>/` 内の切り替え前バックアップは引き続き保持されます。ロールバックは現在の PostgreSQL データに基づいて SQLite データベースを再生成します。

### 7.4 CLI

サービス停止中でも CLI で同じコアロジックを実行できます。

```bash
./lactssl-dbconvert   -config config.yaml   -source-driver sqlite -source data/lactssl.db   -target-driver postgres -target "postgres://user:pass@host:5432/lactssl?sslmode=verify-full"   -switch -yes
```

`-switch` は `config.yaml` を書き換えますが、サービスは自動起動しません。対象のデータベースが空でない場合は既定で拒否されます。クリアを確認する場合は `-force` を追加します。

### 7.5 制限

- デュアルライト/CDC によるゼロダウンタイム切り替えは提供しません。書き込みはコピーと切り替えの段階で一時停止します。
- 複数インスタンスが PostgreSQL を共有している場合、安全に切り替えられないため、v1 では直接拒否します。
- 環境変数 `LACTSSL_DATABASE_DSN` が存在する場合、設定ファイルの書き換えは反映されません。切り替え前に必ずこの変数を削除して再起動してください。
- 切り替え前に、実行中の一括デプロイ/発行タスクがないことを確認する必要があります。

### 7.6 同種移行（SQLite → SQLite / PostgreSQL → PostgreSQL）

同種移行は既定では許可されません。データベースを別のファイルや PostgreSQL インスタンスへ移す必要がある場合は、ページで「同種移行」をチェックして確認する必要があります。API リクエストボディでは `allow_same_driver: true`、CLI では `-allow-same-driver` を使用します。同種移行には追加の制限があります。

- 対象は空のデータベース/空のファイルである必要があります。同種移行では「schema をクリア」をチェックできません。元のデータベースの誤削除を避けるためです。
- 対象は現在のデータベース自体にできません。SQLite では実際のファイル（シンボリックリンク、ハードリンクを含む）を比較します。PostgreSQL ではインスタンスの起動時刻とデータベース名を比較し、同じインスタンスの同じデータベース（異なる schema を含む）はすべて拒否されます。
- PostgreSQL → PostgreSQL の切り替えが成功しても元のデータベースは削除されず、管理者の確認後に手動で削除する必要があります。
- SQLite → SQLite の切り替えはセルフチェックに通過すると旧 SQLite ファイルを削除します。切り替え前のバックアップは `data/db-convert/backups/` に引き続き保持されます。
- 同種移行はページ上の「ワンクリックロールバック」に対応していません。切り替え前のバックアップを使って手動で復元してください。PostgreSQL の元データベースは保持され、SQLite の旧ファイルはバックアップから復元できます。
- 同種移行と `-force` は同時に使用できません。

## 8. 手動移行とデータベース最適化

ログイン後に `/upgrade`（サイドバー「システム → バージョンアップグレード」）へアクセスします。

- **事前チェック**: プログラムのバージョン、データ形式のバージョン、移行ステップの状態、データベースの整合性、空きページ、設定の変更、リスクの注意事項を表示します。データは変更しません。
- **移行を実行して最適化**: 移行ステップを再度実行し、続いて設定ファイルとデータベースを最適化します。
- **データベースと設定のみを最適化**: 移行を繰り返さず、日常メンテナンスに適しています。
- **ディスク容量を回収**: 有効にすると `VACUUM` を実行し、データベースを一時的に排他します。ピークを避けた時間帯の使用を推奨します。

実行結果はシステムログと `upgrade.last_run` 設定に書き込まれます。

### 7.1 データベース最適化の内容

- `PRAGMA quick_check(1)`: 簡易的な整合性チェック。
- 基本テーブル構造は `PRAGMA user_version` でバージョンを記録し、構造が最新の場合はテーブル作成と `ensureColumn` の走査をスキップします。
- ホットパスインデックスを補完: 証明書の状態と有効期限、タスクの有効状態と次回実行、監視チェック、ログのレベルと時刻、ACME オーダー/チャレンジ、デプロイ記録。
- `PRAGMA optimize`: クエリパターンに応じて統計を更新。
- `ANALYZE`: テーブルとインデックスを完全に分析（手動最適化）。
- `PRAGMA wal_checkpoint(TRUNCATE)`: WAL を折り畳み、切り詰め。
- `VACUUM`: 削除データによって生じた空きページを回収し、ファイルサイズを削減。

`VACUUM` は業務データを削除しませんが、データベースファイルを書き換えます。実行前にツールはデータベースのスナップショットを作成します。ディスク容量が不足すると失敗する場合があり、失敗は警告として返され、サービスの稼働継続には影響しません。

### 7.2 設定ファイル最適化の内容

- 現行バージョンの標準的な設定セクションと既定値をすべて補完します。
- `server.addr`、`acme.addr` などの空白を正規化します。
- `security.public_url`、`acme.base_url` の末尾スラッシュを除去します。
- `log.level`、`log.format`、`log.system.level`、`plugins.repo.channel` を小文字に変換します。
- `server.trusted_proxies` の重複と空白を除去します。
- ACME の固定アドレス未設定、プラグインリポジトリの署名公開鍵未設定、デプロイプラグインの秘密鍵への接触、キーの短さなどのリスクを検査します。
- 書き込み前に起動時の読み込みロジックに従って完全に検証し、検証に失敗した場合は元のファイルを上書きしません。
- YAML ノード編集を使用し、コメントとフィールドの順序を保持します。

## 9. 設定項目

```yaml
upgrade:
  auto: true              # 起動時に履歴移行を自動実行
  auto_optimize: true     # 起動時に低コストな最適化を実行。VACUUM は実行しない
  vacuum: true            # /upgrade での手動最適化時に VACUUM の実行を許可
  program:
    enabled: true
    repo: "AXmishell/LACTSSL"
    channel: stable
    check_interval_hours: 6
    max_download_mb: 128
    public_key: ""
    # 公式ビルドは公開鍵を自動的に埋め込みます。自前ビルドで未設定の場合、オンラインアップグレードは既定で拒否。管理された環境のみ未署名パッケージを明示的に許可可能
    allow_unsigned: false
    token: ""
```

`upgrade.auto` を無効にすると、起動ログに未移行データの存在が表示されますが、サービスは起動を継続します。この場合は速やかに `/upgrade` へログインして手動で実行し、新しいコードが旧形式のデータを読み取ることを避けてください。履歴のシステムログは、ログ統合ステップが完了するまで「ログ → システムログ」タブに表示されません。

## 10. API

アップグレードツールは既存のログインセッションを使用し、インターフェースは `/api` に固定されています。

| インターフェース | メソッド | 権限 | 説明 |
| --- | --- | --- | --- |
| `/upgrade` | GET | `upgrade:read` | 事前チェックの状態 |
| `/upgrade/run` | POST | `upgrade:write` | 移行、設定最適化、データベース最適化 |
| `/upgrade/optimize` | POST | `upgrade:write` | 設定とデータベースのみを最適化 |
| `/upgrade/database` | GET | `upgrade:read` | 現在のバックエンドと切り替えの進捗 |
| `/upgrade/database/test` | POST | `upgrade:read` | 対象の接続と空データベースの状態をテスト |
| `/upgrade/database/preflight` | POST | `upgrade:read` | 切り替えの事前チェック |
| `/upgrade/database/convert` | POST | `upgrade:write` | 切り替えを開始（再認証が必要） |
| `/upgrade/database/convert` | GET | `upgrade:read` | 切り替えの進捗を照会 |
| `/upgrade/database/convert/cancel` | POST | `upgrade:write` | 未完了の切り替えをキャンセル |
| `/upgrade/database/rollback` | POST | `upgrade:write` | 旧バックエンドへワンクリックで逆切り替え |
| `/upgrade/program` | GET | `upgrade:read` | プログラムアップグレードの状態 |
| `/upgrade/program/check` | POST | `upgrade:write` | GitHub Release を即時照会 |
| `/upgrade/program/apply` | POST | `upgrade:write` | 指定バージョンをダウンロードしてインストール |
| `/upgrade/program/restart` | POST | `upgrade:write` | インストール完了後にサービスを再起動 |

リクエストボディには `vacuum`、`analyze`、`config`、`optimize` などのブールフィールドを含められます。書き込みインターフェースは、ログインセッションまたは該当する権限を持つ API キーのみで利用できます。
