# 運用マニュアル

本書は LACTSSL をデプロイ・運用する開発者向けに、バックアップとリストア、監視とアラート、容量管理、変更とアップグレード、障害対応を扱います。目的は、サービスを引き継げること、監査できること、障害後に復旧できることです。

## サービス目標

デプロイ前に次を明確にしてください。

| 項目 | 推奨する定義 |
| --- | --- |
| 稼働時間 | 依存する DNS、CA、リバースプロキシ、デプロイ先と整合させる |
| RPO / RTO | 少なくとも 1 日 1 回のバックアップ。「ホスト準備 + リストア + 起動検証」の演習結果を基準とする |
| 変更ウィンドウ | 証明書の一斉失効やリリースピークを避ける |
| アラート対応 | タスク失敗・証明書異常は 15〜30 分以内に対応（デプロイ方針による） |

プロセスの生存をサービス可用性と見なさないでください。実際の可用性は DNS API、CA、デプロイ先、通知経路にも依存します。

## バックアップとリストア

### バックアップ範囲

必ず `config.yaml`（または `-config` で指定したパス）と `data/` ディレクトリ全体を同時にバックアップします。

`data/` には `lactssl.db`、実行中の `lactssl.db-wal`/`-shm`、プラグイン、ログ、ログアーカイブ、アップグレードバックアップが含まれます。画面の「バックアップをダウンロード」で生成される ZIP には `data/archives/logs/` のログアーカイブが**含まれません**。アーカイブはデータベースと同等に機密性が高いため、別途コピーするかオフラインメディアへ保存してください。データベースのみでは `salt` が失われて暗号化された認証情報を復号できず、設定のみではアプリケーションデータが失われるため、両者は必ずセットで扱ってください。

### 画面からの暗号化バックアップ（推奨）

「システム設定 → バックアップと復元」でオンライン操作を提供します。

- **バックアップをダウンロード**: ZIP にデータベーススナップショット（SQLite はファイルスナップショット、PostgreSQL は Go ネイティブの ZIP + COPY 形式、MySQL はネイティブ SQL 形式）、現在の `config.yaml`、`manifest.json` を含めます。PostgreSQL/MySQL は `pg_dump`/`pg_restore`/`mysqldump`/`mysql` クライアントに依存しません。
- ダウンロード前にアカウントパスワードの再入力が必要で、TOTP 有効時は動的コードも求められます。バックアップ暗号化パスワードはアカウントパスワードと独立した 12 文字以上です。
- 内容は PBKDF2-HMAC-SHA256（600,000 回反復）+ AES-256-GCM で暗号化され、リストアには同じパスワードが必須です。紛失すると復元できません。
- **推奨**: バックアップは独立したメディアやオブジェクトストレージに保存し、`data/` 配下に置かないでください。パスワードはパスワードマネージャーでファイルと分離して管理します。
- 日時、サイズ、チェックサム、保管場所を記録し、少なくとも 7〜30 日保持してください。重要環境では必要に応じて延長します。

### コマンドによるバックアップ

ファイルレベルのバックアップが必要な場合は、SQLite を一貫した状態に保つため、先にサービスを停止してからコピーします。停止できない場合は画面からの暗号化バックアップを優先してください。稼働中の SQLite を直接コピーすると、一貫性のないスナップショットになる可能性があります。

```bash
# Docker
docker compose stop

# または systemd サービスを停止
sudo systemctl stop lactssl

tar czf lactssl-backup-$(date +%F).tar.gz config.yaml data
chmod 600 lactssl-backup-*.tar.gz
```

### リストア

#### 画面からのリストア

1. ZIP バックアップまたは単体の `.db` ファイルをアップロードし、現在のパスワード（暗号化バックアップの場合は復号パスワードも）を入力します。
2. サービスはリストア内容を `data/restore-pending/` に書き込み、自動的に再起動します。Docker では `restart: unless-stopped` により自動起動するため、バイナリを直接実行している場合のみ手動で再起動してください。
3. バックアップ内の管理者アカウントでログインします。

#### 手動リストア

1. サービスを停止し、バックアップ内の `config.yaml` と `data/` を元の場所に戻します。
2. 権限を確認します。設定ファイルは `0600`、データディレクトリは `0700`、所有者はサービス実行ユーザーです。
3. サービスを起動し、セキュアエントリ、管理者ログイン、証明書、タスク、プラグインを確認します。

#### リストア時の注意

- リストア後は、バックアップ内の管理者アカウントでログインしてください。既定ではセッション保持が有効なため再起動してもセッションは保持され、`security.session_persistence: false` にすると起動のたびにクリアされ JWT サブキーがローテーションされます。
- 異なる `jwt_secret` では以前のトークンが検証を通過せず、異なる `salt` では暗号化された認証情報を復号できません。常に完全な ZIP バックアップでリストアすることを推奨します。セキュアエントリが異なる場合は起動ログで確認してください。
- データベースのみをリストアして `salt` を失った場合、DNS/デプロイ/通知の認証情報は復号できず、再入力が必要になります。

### リストア演習

四半期に少なくとも 1 回:

- [ ] 隔離環境で最新バックアップをリストアし、管理者ログイン、TOTP/パスキー、復旧用メールアドレス、証明書一覧、タスク、デプロイ認証情報、通知チャネルを検証する。
- [ ] テストタスクを 1 件実行し、非本番のターゲットへデプロイする。
- [ ] 実測した RTO、問題点、改善項目を記録し、バックアップパスワードが引き続き権限を持つ担当者に保管されていることを確認する。

## 監視とアラート

### 監視シグナル

| シグナル | 取得方法 | 推奨しきい値/アクション |
| --- | --- | --- |
| プロセス生存 / 認証ヘルス | TCP ポート監視、`GET /api/status` + `system:read` API キー | 30〜60 秒ごとの監視で 3 回連続失敗、または 1〜5 分ごとの確認で 200 以外・高レイテンシ時にアラート |
| タスク失敗 | 操作ログまたは通知 | 失敗時に即アラート、DNS/CA/デプロイ/通知を区別 |
| 証明書の期限接近 | ダッシュボード、サイト監視 | 30/14/7 日の段階的リマインド |
| デプロイ失敗 | デプロイ記録/通知 | 即アラート、ターゲットシステムとリロードコマンドを確認 |
| ディスク / バックアップ | ホスト監視、バックアップタスク | 使用率 > 80% で予告、> 90% またはバックアップ失敗・周期超過でアラート |
| HTTP 5xx / ログイン異常 | リバースプロキシログ、操作ログ | ベースラインに応じたしきい値、複数失敗や異常な送信元 IP でアラート |

### アラートのルーティング

- タスク失敗、証明書異常、デプロイ失敗は運用アラートのチャネルへ送ります。
- セキュリティインシデント（異常ログイン、エントリの探索、プラグイン検証失敗）はセキュリティチャネルへ、バックアップ失敗とディスク不足はプラットフォームチャネルへ送ります。
- テスト通知は本番のアラートグループへ送らず、専用のチャネルを使用してください。

通知チャネルの可用性は外部サービスに依存します。単一障害点を避けるため、少なくとも 2 つの独立したチャネル（例: メール + IM）を設定してください。

### 行うべきでない監視

- 素の `/` や `/login` を匿名ヘルスチェックに使わないでください。セキュアエントリを通過しない場合は 404 を返しますが、これは想定どおりの動作です。
- 管理者パスワードや長期間有効な全権限 API キーを監視システムへ書き込まず、証明書の秘密鍵やバックアップパスワードをアラート内容に含めないでください。

## 日常メンテナンス

### 毎日

- タスク失敗、デプロイ失敗、サイト監視の異常、バックアップの生成状況を確認し、証明書の期限ダッシュボードに新たな高リスク項目がないことを確認します。

### 毎週

- 自動更新タスクのスケジュールと、システムログのエラー、レート制限、異常ログインを確認し、API キーと認証情報の追加/無効化を突き合わせます。

### 毎月

- ディスク、データベースサイズ、WAL、ログ保持を確認し、プラグインのバージョンとセキュリティアドバイザリ、操作ログと変更記録の抜き取り、通知チャネルの検証を行います。

### 四半期ごと

- バックアップとリストアの演習を完了し、管理者アカウント、復旧用メールアドレス、TOTP/パスキー、API キーの権限と有効期限、アップグレードウィンドウとロールバック計画を見直します。

## 容量とクリーンアップ

### 注視すべき容量

| 項目 | 増加要因 | 対応 |
| --- | --- | --- |
| SQLite | 証明書、タスクログ、操作ログ、システムログ、ACME オーダー | 履歴データの削除、データベースの最適化、ログのアーカイブ |
| ログアーカイブ | `data/archives/logs/` 配下の NDJSON.gz と manifest | 定期的に外部ストレージへ退避。必要に応じて「ログ → アーカイブ」で削除 |
| WAL | 長期稼働、書き込み頻度の高さ | `wal_checkpoint(TRUNCATE)` をアップグレード/最適化ツールが実行 |
| プラグイン | インストール/更新による旧ファイルの累積 | 不要なプラグインをアンインストールし、古い helper を削除 |
| アップグレードバックアップ / バックアップストレージ | 移行スナップショット、旧バイナリ、日次/週次バックアップ | 保持ポリシーに従って削除し、保持期間と別拠点のコピーを設定 |

### クリーンアップの入口

- **証明書管理 → 一括クリーンアップ / ACME 診断 → クリーンアップ**: 証明書は状態、失効/取り消しからの経過時間、発行日時、ドメイン、発行機関、由来で絞り込み、各タスクの最新証明書を保持できます。ACME はエンドポイント、状態、未使用期間で無効なオーダーとアカウントを削除します。アカウント削除は過去のオーダーも削除しますが、発行済み証明書には影響しません。
- **ログ → 操作ログ/システムログ → クリア、ログ → アーカイブ**: クリア時はアーカイブが有効なら先に `data/archives/logs/` へ書き込み、失敗した場合は削除を拒否します。アーカイブは表示、ダウンロード、削除ができ、既定では永久保持です。`archive.retention_days` または `archive.max_total_mb` が設定されている場合はメンテナンスタスクがポリシーに従って削除します。
- **アップグレード/最適化**: ピークを避けた時間帯にデータベース最適化を実行します。`VACUUM` はデータベースを一時的に排他しファイルを書き換えるため、ディスク空き容量を確保してください。

### データベースメンテナンス

- サービスは 6 時間ごとにメンテナンスクリーンアップを実行します。ログページでスケジューラが動作しているか確認できます。新バージョンの初回起動時には履歴移行が自動実行され、`data/upgrade-backups/` に移行前スナップショットが生成されます。
- ディスク容量を回収する場合は、ピークを避けた時間帯に `/upgrade` へアクセスし、「データベースと設定のみを最適化」で VACUUM を有効にします。実行前にバックアップと十分なディスク容量を確保してください。`VACUUM` の失敗は警告として返され、サービスの稼働継続には影響しません。

## バージョンとリリース

### バージョンの識別

- バージョン番号は git tag を唯一の情報源とし、リポジトリでは `VERSION` ファイルを管理しません。ローカルビルドでは `git describe --tags --always --dirty` から導出し、`v` プレフィックスを除去します。ビルドスクリプトは `-ldflags -X 'lactssl/internal/api.Version=...'` でバージョンを注入し、「設定 → バージョン情報」でビルドバージョン、ビルド日時、アーキテクチャを確認できます。`go run` や開発ビルドでは `dev` と表示されます。

### リリースチャネル

- 安定版のタグには `latest`、`<version>`、`<major>.<minor>`、`<major>` が含まれます。プレリリース版は完全なバージョンタグのみをプッシュし、`latest` を上書きしません。
- 本番では明確なバージョンに固定し、追跡不能な `latest` で長期運用しないでください。

### リリース成果物

Release では Linux/macOS/Windows のバイナリ、`checksums.txt`、`linux/amd64`・`linux/arm64` のイメージをビルドします。アーカイブにはバイナリ、`README.md`、`LICENSE`、`config.yaml.example` が含まれます。

リリース手順、署名、ローカルビルドの詳細は[拡張開発: ソースとビルド](development.md)を参照してください。

## アップグレードと変更

アップグレード前に、対象バージョンの変更点と移行手順を読み、`config.yaml` と `data/` をバックアップします。ロールバックするバージョンと手順を確認し、ステージング環境で主要経路（発行、デプロイ、通知、API）を検証して、ピークを避けた時間帯を選び関係者へ通知してください。

Docker:

```bash
docker compose pull
docker compose up -d
```

バイナリ:

```bash
sudo systemctl stop lactssl
sudo cp lactssl /opt/lactssl/lactssl
sudo chown lactssl:lactssl /opt/lactssl/lactssl
sudo systemctl start lactssl
```

アップグレード後:

- ログの「データ形式のアップグレード完了」を確認し、`/upgrade` にログインして各ステップの状態と、証明書、タスク、デプロイ、通知、API を検証します。
- 1 回のスケジューリング周期（少なくとも 30 秒）と 1 回のタスク実行を観察します。

移行、ロールバック、プログラムのアップグレードの詳細は[アップグレードと変更](upgrade.md)を参照してください。

## 障害対応

### 重大度

| レベル | 例 | 目標 |
| --- | --- | --- |
| P1 | 管理エントリが利用不可、多数の証明書が更新不可、秘密鍵の漏えい | 即時対応、インシデント対応の開始 |
| P2 | 単一タスクの失敗、デプロイ先の異常、通知チャネルの停止 | 30 分以内に対応 |
| P3 | 単一監視の誤検知、ログの異常、重要でないプラグインの問題 | 営業時間内に対応 |

### 共通手順

1. **影響範囲の確認**: どの証明書、タスク、デプロイ先、対象システムが影響を受けるか。
2. **現場の保全**: ログをクリアしないでください。時刻、リクエスト ID、エラーメッセージを記録します。
3. **依存関係の確認と変更の隔離**: DNS API、CA、ネットワーク、リバースプロキシ、ターゲットシステム、SMTP/IM を確認し、関連タスクを一時停止して繰り返しの失敗や証明書の上書きを防ぎます。
4. **サービスの復旧**: 依存関係を修正するか変更をロールバックします。必要に応じてバックアップからリストアします。
5. **検証と振り返り**: タスクを再実行して証明書、デプロイ、通知を確認し、根本原因、タイムライン、改善項目、担当者を記録します。

具体的な症状とコマンドは[監視とトラブルシューティング](troubleshooting.md)を参照してください。
